# M5: Windows — те же возможности, что на macOS

## Цель и согласование

На Windows 11 (x64 и ARM64) Workflow Kit должен делать то же, что на macOS: создавать и вести
сессии Claude и ChatGPT/Codex, ревью плана, оркестрацию, автопилот, публикацию. Сейчас на
Windows работают только установщик, служба и панель; провайдеры отключены (вопросы Q1, Q2 вехи M1).

Решение пользователя (09.11.2026): «я же изначально требовал … мультиоперационную систему»;
«очень-очень внимательно проверь теоретические решения. Чтобы они были оправданы и повторяли
возможности, которые уже реализованы для Mac OS. … приступай к реализации, спецификации и плана».
Первая проверка — ВМ Windows 11 ARM в UTM (инструкция — [M5-windows-vm.md](M5-windows-vm.md)),
затем — пользователь Windows x64.

Основание — инвентаризация кода macOS (всё, что делается с внешними программами) и исследование
Claude Code, Codex и ConPTY на Windows (09.11, исходники openai/codex 0.167, документация
code.claude.com и CHANGELOG Claude Code 2.1.319, tarball-ы node-pty). Уверенность: **В** —
подтверждено исходниками или официальной документацией, **С** — issues или вывод из кода,
**П** — проверить на ВМ (задача T008).

## 1. Принципы

- macOS не меняется: `expect`, сокет демона, POSIX-хуки остаются как есть. Новый код — ветки
  `win32` за теми же контрактами; общие функции меняются только там, где Windows иначе не работает.
- Каждая возможность из таблицы раздела 9 либо работает на Windows, либо отказывает с понятной
  причиной; «недоступно (Q1/Q2)» исчезает.
- Linux не трогаем (там остаётся `expect`).

## 2. Псевдотерминал: node-pty в составе приложения

- Claude Code — TUI: ему нужен настоящий терминал; через pipe он не работает (CHANGELOG 2.1.287, **В**).
  На Windows терминал даёт ConPTY. Сам Claude Code держит фоновые сессии в headless ConPTY (**С**).
- Берём `node-pty` 1.1.0 от Microsoft (стабильная, MIT, активное сопровождение). В tarball есть
  готовые сборки `win32-x64` и `win32-arm64` (настоящие AArch64 PE), модуль на N-API — подходит
  к Node 24 без компилятора (**В**). Ветку 1.2 не берём: регрессия #955 (процесс завершается до
  первой записи).
- Новый модуль `pty-host` (часть `provider-runtime`, кластер `provider-contract`):
  - `vendor/node-pty-1.1.0/` — `lib/*.js` и `prebuilds/win32-x64`, `prebuilds/win32-arm64`
    только для ConPTY (`conpty.node`, `conpty_console_list.node`, `conpty/conpty.dll`,
    `conpty/OpenConsole.exe`); без `.pdb`, без winpty (x64 winpty-agent падает на ARM64, #52756
    Claude Code). `PROVENANCE` (источник, версия, SHA-256 каждого файла), `LICENSE`.
  - загрузка через `createRequire` по `process.arch`; нет сборки для архитектуры — понятный
    отказ «pty недоступен: нет сборки для <arch>».
  - обёртка: `useConpty: true`, `useConptyDll: true` (свой conpty.dll — обход потери клавиш
    встроенным conhost, #99659 Claude Code); обработчики ошибок сокетов (#976, #942, #960);
    `kill()` строго один раз (#983), затем `taskkill /PID <pid> /T /F`; запись текста Buffer'ом;
    вывод читается непрерывно.
- Установщик копирует модуль как остальной код; npm и сеть при установке не нужны.

## 3. Процессы сессий (process-supervisor) на Windows

| macOS | Windows |
| --- | --- |
| `spawn(detached)` — своя группа (`setsid`) | `spawn(detached, windowsHide)` — процесс переживает службу |
| `ps -o pgid,lstart,args` | один вызов PowerShell `Get-CimInstance Win32_Process` на пачку pid: `CreationDate` → `startToken`, `CommandLine`; без `wmic` (удалён в 24H2) |
| boot id `sysctl kern.boottime` | `Win32_OperatingSystem.LastBootUpTime` → `win32:<время>` |
| `SIGTERM` группе → ожидание → `SIGKILL` | `taskkill /PID <pid> /T` → ожидание → повторная сверка → `taskkill /PID <pid> /T /F`; дерево процессов вместо группы |
| `check` по `ps` | по CIM; `unverifiable` больше не возвращается |

- Все `spawn` и `runCommand` на Windows — с `windowsHide: true`. Файлы `.cmd` без оболочки Node 24
  не запускает (EINVAL, CVE-2024-27980, **В**) — запускаем только `.exe`.
- Остальное (записи, `reconcile`, перезапуск после перезагрузки) работает на тех же записях.

## 4. Claude на Windows

### 4.1. Программа и запуск сессии

- `claude.exe`: `config.programs.claude`, PATH, `%USERPROFILE%\.local\bin\claude.exe` (нативный
  установщик, **В**); npm-установка ставит тот же нативный exe (**В**). Минимальная версия — как
  на macOS; Remote Control на Windows официально поддерживается, ошибка `--sdk-url` исправлена в 2.1.69 (**В**).
- `expect` на Windows не нужен. Вместо `session.exp` и `environment.exp` — один Node-хост
  `pty/win-host.ts` с режимом `session` или `environment` (логика — `pty/host.ts`, шаблоны экрана —
  `pty/screen.ts`) и с **тем же контрактом**: те же аргументы,
  те же строки-маркеры в журнале (`CLAUDE_PID`, `SESSION_URL`, `FIRST_MESSAGE_SENT`,
  `NO_SESSION_URL`, `SESSION_NOT_TRUSTED`, `SESSION_EXITED`, `DIALOG <вид>`, `RENAMED`, `WOKEN`,
  `SESSION_ENDED`, `ENV_*`), те же файлы управления `<debug>.rename` и `<debug>.message`, те же
  тайм-ауты и размер 160×40 (120×40 у окружения). Поэтому `followSession`, переименование,
  пробуждение и возобновление в `sessions.ts` не меняются.
- Хост запускает `claude.exe --remote-control <имя> --debug-file <файл>` (и `--resume <id>`) в
  ConPTY, ищет на экране `claude.ai/code/session_…`, диалоги — по тем же шаблонам
  (`dialogs.tcl` переносится в общий модуль шаблонов), при диалоге собирает экран до 5 с и
  останавливает Claude без нажатия клавиш (`taskkill /T`).
- Ввод: текст одной записью, пауза, затем отдельно `\r` — как на macOS. Длинные тексты в терминал
  не набираются (уже так для ревьюера, M4 13.9); первое приветствие мастера короткое.
- Риск **П**: задержка старта Claude под ConPTY (ответ на DA1, issue #36328 закрыт 03.2026) —
  измерить; тайм-аут ожидания ссылки 90 с сохраняется.

### 4.2. Доверие к папке (`~/.claude.json`)

- Файл `%USERPROFILE%\.claude.json` (**В**). Ключ проекта — путь с **прямыми слэшами** и буквой
  диска как пришла (`C:/Users/…`), регистр не нормализуется; дубли `C:/` и `c:/` ломают файл (#106692, **С**).
- Правило записи: если в `projects` уже есть ключ, равный пути без учёта регистра и вида
  слэшей, — правим его; иначе пишем `realpath` с `/` и буквой диска в верхнем регистре. Чтение —
  без учёта регистра и слэшей. Какой ключ пишет сам Claude — **П**.
- Атомарная замена на Windows может получить `EPERM/EBUSY`, если файл открыт Claude: до 5
  повторов с паузой 100–500 мс; копия до записи и проверка после — как на macOS. Права файлов
  (`chmod`) на Windows не выставляются.

### 4.3. Остальное

- Остановка, возобновление после перезагрузки, окружение папки, `claude purge`, транскрипты и
  журнал хуков — те же пути через раздел 3 (транскрипты читаются по абсолютному пути из хука,
  имя каталога `projects` вычислять не нужно).
- `/rename` из CLI может не доходить до мобильного приложения (#104749, и на macOS), поэтому имя
  задаётся сразу в `--remote-control <имя>` — как сейчас.

## 5. Codex на Windows

- **Программа:** только `codex.exe`: `config.programs.codex`, PATH (сначала `.exe`),
  `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe` (standalone-установщик и winget),
  `%USERPROFILE%\.codex\packages\standalone\current\bin\codex.exe`, а для npm — exe платформенного
  пакета `@openai/codex-win32-<arch>` рядом с шимом `codex.cmd` (**В**). ARM64-сборки есть (**В**).
- **Демон и remote control:** команды те же (`codex remote-control start --json`, `stop`),
  демон поддерживает Windows с 0.154 (**В**). Ограничения: служба должна работать в сессии
  пользователя **без повышения прав** и не в job-объекте без breakaway (**В**) — автозапуск через
  `HKCU\…\Run` это выполняет; установщик предупреждает, если запущен с правами администратора.
- **Транспорт:** на Windows демон слушает AF_UNIX-сокет `%USERPROFILE%\.codex\app-server-control\app-server-control.sock`,
  а `node:net` на Windows к AF_UNIX не подключается (только `\\.\pipe\…`, **В**). Поэтому на
  Windows подключение идёт через официальный `codex app-server proxy` (ретранслятор stdio ↔ сокет
  демона, **В**): дочерний процесс со скрытым окном, наш WebSocket-клиент работает поверх его
  stdin/stdout (`ws.ts` принимает любой Duplex; на macOS — по-прежнему сокет).
- **PID демона:** на Windows `processStartTime` в `daemon.pid` — FILETIME (100 нс с 1601 г.,
  **С**): секунды = FILETIME/1e7 − 11644473600; так считается «вход новее демона».
- **Доверие и ключи `config.toml`:** Codex пишет ключ проекта путём в нижнем регистре и ищет без
  учёта регистра (**В**). В `keyPath` внутри кавычек `\` экранирует следующий символ: `\` → `\\`,
  `"` → `\"` (**В**) — `tomlKey` кодирует так вместо отказа. Чтение доверия — без учёта регистра.
- **Хуки:** в `.codex/hooks.json` у обработчика Kit добавляется поле `commandWindows` (Codex на
  Windows выполняет его через PowerShell `-NoProfile -Command`, **В**; `command` остаётся POSIX
  для macOS). Хеш одобрения считается от `commandWindows`, ключ одобрения берётся из ответа
  `hooks/list` (**В**). Шаблон Kit для сравнения на Windows — `commandWindows`.
- **Остальное:** `codex app-server` по stdio — с `windowsHide`, завершение `stdin.end()` →
  `kill()`; журнал `logs_<N>.sqlite` и каталог `sqlite\codex.db` — те же пути (**П**); показывает
  ли приложение ChatGPT/Codex на Windows треды демона и конфликт 409 — как на macOS (**С**, **П**).
  Видимые окна консоли демона (#46949) исправлены в 0.158–0.160 (**С**) — минимальная версия
  Codex на Windows 0.160.

## 6. Хуки Kit и запускатель `wfk`

- Сейчас команда хука — POSIX `sh` (`[ -x "$HOME/.local/bin/wfk" ] && …; exit 0`), а на Windows
  запускатель — `%LOCALAPPDATA%\Workflow Kit\wfk.cmd`, и Kit узнаёт свой хук по `/.local/bin/wfk`.
- **Claude на Windows:** exec-форма хука (Claude Code 2.1.139+, **В**) без оболочки — не зависит от
  Git Bash и PowerShell, stdin с данными хука доходит напрямую:
  `{ "type": "command", "command": "<node.exe>", "args": ["<…/bin/wfk.mjs>", "hook", "stop", "--client", "claude"], "timeout": 600 }`
  с абсолютными путями через `/` (обратные слэши в командах хуков теряются, #108050). Пути —
  `node.exe` службы и стабильный запускатель `%LOCALAPPDATA%\Workflow Kit\wfk.mjs` (его пишут
  `wfk install` и `wfk link`; он запускает текущую копию, а копии лежат в `app/<версия>`, и
  прямой путь менялся бы при каждом обновлении). При смене `node` проверка структуры показывает
  «устарело», обновление переписывает хук.
- **Codex на Windows:** `commandWindows` — PowerShell-строка в одинарных кавычках, вызывающая тот
  же `node.exe … wfk.mjs hook … --client codex` и завершающаяся `exit 0`. Вход хука передаётся
  явно: `[Console]::In.ReadToEnd() | & node …` с кодировками UTF-8 (PowerShell сам не передаёт
  свой stdin дочерней программе); работу на Windows подтверждает живая проверка (**П**).
- **Узнавание своего хука:** по `hook <событие> ` и точке входа `wfk.mjs` или `/.local/bin/wfk`.
- **Проект на двух ОС:** хук Claude в `.claude/settings.json` у Windows и macOS разный (у Claude
  нет поля для другой ОС, **В**): при открытии проекта на другой ОС проверка структуры показывает
  «устарело». Ограничение записывается в документацию.
- **Команды агента** (`wfk session title|plan`, `wfk project publish`): `wfk.cmd` в PATH работает
  из PowerShell и cmd; для Git Bash (инструмент Bash Claude) установщик кладёт рядом `wfk` —
  sh-скрипт с той же командой.

## 7. Ссылки, служба, прочее

- **Открытие чатов (`POST /api/open-link`):** на Windows `claude://…` — через
  `rundll32 url.dll,FileProtocolHandler`; `codex://threads/<id>` — через запуск приложения из
  пакета AppX `OpenAI.Codex` с адресом (тот же приём, что у самого Codex TUI, потому что
  ассоциация протокола на Windows ненадёжна, #25822, **В**), запасной путь — `rundll32`.
  Открывает ли Claude Desktop на Windows `claude://claude.ai/code/session_…` — **П**, запасной путь —
  `https://claude.ai/code/session_…` в браузере.
- **Остановка службы:** на Windows сигналов нет, `kill` — жёсткое завершение. Добавить
  `POST /api/system/shutdown` (только loopback, с Origin) — штатная остановка; установщик
  останавливает службу через него и только потом завершает процесс.
- **Права администратора:** `wfk install` на Windows предупреждает, если запущен с повышением
  (демон Codex откажется работать).
- **`wfk link`** (запускатель для разработки) на Windows пишет те же три файла, что установщик
  (`wfk.cmd`, sh-скрипт `wfk`, `wfk.mjs`), в `%LOCALAPPDATA%\Workflow Kit`, указывая на клон.

## 8. Границы

- Windows 10 — без гарантий (Claude Code и Codex считают его best-effort). Windows Server, WSL —
  не входят.
- Подпись кода и MSI-установщик — не входят: установка та же (`node bin/wfk.mjs install` из клона
  или ZIP).
- macOS и Linux не должны измениться — их тесты проходят без правок поведения.
