# M41: автоприёмка без тупиков

## Цель и согласование

17.11.2026 полный автопилот scope `speech-integration` выполнил все задачи, но не принял
результат: запуск перешёл в «Остановлен: нужно ваше действие» с
`AUTOPILOT_EVIDENCE_REQUIRED: Criterion 3: check installed-service has no passed record on the
history of HEAD`, и «Продолжить» ничего не исправляло. Пользователь остановил автопилот,
принял и закрыл план кнопками.

Причины:
1. Проверку `installed-service` (стадия `delivery`) Kit не запускает нигде: `runStage`
   вызывается только для `prepare`, `commit` и `push`. Задача поставки T005 назначала её
   (`tasks[].checks`), но запись не появилась, а `scope:propose` принял критерий с ней.
2. После зелёного CI выпуска пользователь нажал «Обновить Kit»: коммит `186d73a` (runtime Kit,
   не `.md`) сделал CI-доказательство непригодным (`exactSha`: после проверенного SHA должна
   меняться только документация).
3. Любой отказ доказательств превращает запуск в остановку с ошибкой, хотя путь «приёмку
   выполняет пользователь, затем запуск сам закрывает и публикует» уже есть для ручных
   критериев.

Решение пользователя (17.11.2026): «Автопилот должен автоматически сам заканчиваться сниматься
при выполнении полного плана или не влиять на приёмку чтобы не возникало этой ошибки предложи
лучший вариант» — на предложение из четырёх пунктов (ручная приёмка вместо остановки, запись
проверок поставки, отложенное «Обновить Kit», ранняя проверка): «Окей согласен подготовь
новый (спецификацию todo Plan)».

Прежняя заготовка M41 о механике Kit стала [M42](M42-kit-mechanics.md).

## 1. Принципы

- Автоматическая приёмка — ускорение, а не барьер. Если Kit не может доказать результат,
  запуск не останавливается с ошибкой, а ждёт приёмки пользователя; после неё он сам
  закрывает план и публикует, как разрешил «Полный автопилот».
- Kit не ослабляет доказательства: принимает автоматически только по записанным проверкам,
  закоммиченным файлам и зелёному CI точного SHA (M39, M40).
- План, который заведомо не может быть принят автоматически, Kit отклоняет при предложении.
- Ручная приёмка кнопкой при живом разрешении уже работает (`acceptScope` разрешение не
  проверяет); закрытие и публикация запуском после неё — путь ручного критерия M39.
- Проекты на Kit до 2.4.5 работают как раньше; новые поля статуса необязательны.

## 2. Решение

### 2.1. Kit 2.4.5 (`kit-core`, бандл приложения)

**Проверки поставки записываются.** Хук `pre-commit` (`kit-hooks.ts`) для кандидата задачи
вида `delivery`, чьи `checks` называют проверки стадии `delivery`, после проверок `commit`
запускает ровно их (`runStage` с `only`, стадия `delivery`) и кладёт отчёт в те же
доказательства коммита (`verification/<sha>.json`), которые читает `readEvidence`.
Обязательные проверки `delivery`, не назначенные задачей, не запускаются (задача CI не
вызывает `doctor --installed`). Провал — `CHECK_FAILED`, коммит откатывается и повторяется,
как у проверок `commit`.

**Где появляется запись.** Успешную запись (`passed`) в доказательствах коммита задачи дают
стадии `commit` (хук), `prepare` (`storePrepareEvidence` после коммита задачи) и после этой
правки `delivery`; отчёт `push` в доказательства коммитов не попадает. `skipped` — не запись:
раннер пропускает проверку, если ни один файл кандидата не подходит под её `appliesTo`.

**Правило «задача может записать проверку»** (`canRecord(check, task)`), общее для отказа и
статуса. Выбор считается тем же кодом, что у раннера (`selectChecks` из `workflow-quality`, без
своей копии правил):
- задача сервисная (DOCS, QUALITY) — только то, что раннер выбирает для сервисного коммита:
  builtin из `DOCUMENTATION_BUILTINS` (`kit:file-lines` туда не входит);
- стадия `commit` или `prepare`: проверка обязательная или назначена задаче (`tasks[].checks`);
- стадия `delivery`: задача вида `delivery` и проверка назначена ей;
- стадия `push` — никогда;
- и `appliesTo` проверки совместим с `files` задачи: у проверки нет `appliesTo`; или у задачи
  нет `files`; или путь задачи подходит под glob; или путь задачи — каталог, в котором лежит
  литеральное начало glob (часть до первого `*`, `?`, `[`, `{`), или наоборот.

**Невыполнимые критерии отклоняются.** `ensureAutomationInput(context, automation, tasks)`
(`kit-automation.ts`; вызовы в `kit-scope-create.ts` для `scope:create` и `scope:propose`)
после `CHECK_UNKNOWN` требует для каждой проверки `automation.acceptance[].checks` задачу входа,
которая может её записать. Иначе — отказ `AUTOMATION_CHECK_UNRECORDED` с `details { field,
check, stage, reason }` (`reason`: `stage-push`, `delivery-unassigned`, `not-assigned`,
`applies-to`) и следующим шагом «Назовите проверки стадий commit или prepare, назначьте
проверку delivery задаче поставки (tasks[].checks), согласуйте appliesTo с files задачи».
Описание правил `scope:propose` в `schema` дополняется этим кодом.

**До настройки профиля.** Пока профиль не `CONFIGURED`, стадия и `appliesTo` будущей проверки
неизвестны: `scope:propose` допускает id, как сейчас (`plannedCheckRule`), и отказ не
вычисляется. После `quality:apply` достижимость видна в `autopilot:status`
(`checksUnreachable`), служба предупреждает запуск (2.2), а в конце действует приёмка
пользователя вместо остановки. `quality:apply` не отказывает из-за `automation`: профиль
нужен, чтобы работа шла.

**Статус называет недостижимые проверки.** `autopilot:status` в каждой записи `acceptance`
даёт `checksPending` (нет записи `passed` на истории HEAD, любой стадии — как `passedAt`) и
`checksUnreachable` (из `checksPending` те, для которых нет задачи scope не в статусе `DONE`,
удовлетворяющей `canRecord`). Типы `plan-view` (`kit-types.ts`) получают оба поля как
необязательные.

Версия Kit 2.4.5: `installer-payload.ts`, `bundle-meta.ts`, `vendor/workflow-kit-2.4.5.mjs.gz`
(`npm run build:kit`), `PROVENANCE`.

### 2.2. Служба: приёмка пользователя вместо остановки (`autopilot`)

- `RunRecord.manualAcceptance: { head, reason, since } | null` (`run-journal.ts`).
- `accept()` (`run-complete.ts`) не вызывает `block` для: нехватки закоммиченных файлов
  доказательств (`evidenceMissing`), отказа Kit `AUTOPILOT_EVIDENCE_REQUIRED` (кроме случая,
  когда служба сама ставит CI для HEAD) и `AUTOPILOT_MANUAL_REQUIRED`. Вместо этого запуск
  остаётся в фазе `accepting` с `manualAcceptance` и `nextAction` «Автоприёмка не смогла
  доказать результат: <причина>. Проверьте результат и нажмите «Принять план» — запуск сам
  закроет план и опубликует.»; журнал службы — `autopiloting: <run> awaits the user's
  acceptance: <причина>`.
- Пока HEAD равен `manualAcceptance.head`, Kit повторно не вызывается. Новый HEAD (агент
  закоммитил доказательства) — снова автоматическая попытка.
- Пользователь принял (кнопка или сообщение, M40) — `delivery: ACCEPTED`, запуск закрывает
  план (`close --autopilot-run`) и публикует проверенный SHA. Закрыл руками — запуск
  завершается (`settleRunEnd`, M40).
- Остальные отказы (ревизия, транзакция, разрешение, `close`, публикация) остаются
  остановкой с «Продолжить».
- Ранняя проверка: в фазах `executing` и `delivering` служба читает `checksUnreachable`; если
  список не пуст, запуск один раз записывает `notice` («Автоприёмка не сможет доказать: <id>
  (критерий N) — в конце понадобится ваша приёмка») и продолжает работу. Kit без поля —
  предупреждения нет.

### 2.3. «Обновить Kit» откладывается, пока план открыт (`kit-update`)

`POST /api/projects/:id/kit/update` отказывает, пока у проекта есть незавершённая работа плана:
- открыт scope (`kit.status`: scope не `NONE`) — 409 `scope-open` («Обновление Kit — после
  закрытия плана «<scope>»: коммит Kit посреди плана меняет процесс и делает CI-доказательство
  приёмки непригодным»);
- scope закрыт, но запуск автопилота проекта не в конечной фазе (`completed`, `finished`,
  `stopped`) — 409 `run-active` («Обновление Kit — после публикации запуска <run>: новый коммит
  остановил бы публикацию проверенного SHA (`head-changed`)»).

Опции `registerKitUpdateRoutes` получают `deferral(projectId) → { code, scopeId, runId } |
null` и `mutex` (тот же `KeyedMutex`, что у завершения запуска, ключ `project:<id>`); `cli/app.ts`
передаёт их из журнала запусков и Kit. Проверка выполняется при запросе (быстрый отказ 409) и
заново в начале фонового обновления под блокировкой `project:<id>` — до первой записи. Под
той же блокировкой идут подготовка структуры (`prepareStructure` → `structure.install`),
`kit.install` и восстановление сохранённых текстов при отказе; блокировка снимается после них.
Если при свежей проверке запрет появился, обновление не пишет ни одного файла и не меняет HEAD,
а `error` раздела — `{ code: 'scope-open' | 'run-active', … }`. Шаг завершения запуска и
обновление не пересекаются. Раздел состояния `kit` получает
`deferred: { code, scopeId, runId } | null`.

### 2.4. Панель

- `run-model.js`: фаза `accepting` с `manualAcceptance` — «Ждёт вашей приёмки», тон
  `waiting`, подробность — причина, следующий шаг — «Принять план» на карточке плана; кнопки
  «Пауза» и «Остановить автопилот» остаются. `notice` запуска — строка-предупреждение без
  смены фазы.
- `kit-card.js`: при `deferred` кнопка «Обновить Kit» выключена с подписью «После закрытия
  плана «<scope>»» (`scope-open`) или «После публикации запуска» (`run-active`).

нет.

## 4. Проверка

- Kit (`*.test.mjs`): запись назначенной проверки `delivery` в доказательствах коммита
  задачи поставки, обязательная неназначенная не запускается, провал откатывает коммит;
  `AUTOMATION_CHECK_UNRECORDED` для `push`, `delivery` без задачи и проверки с `appliesTo
  src/**`, назначенной поставке с `files` только `docs/**`; допуск обязательной и назначенной
  `commit`, `prepare` и builtin; приёмка `accept --autopilot-run` по сохранённому отчёту
  `prepare`; новый проект: предложение с будущей проверкой до QUALITY принято, после
  `quality:apply` со стадией `delivery` без назначения — `checksUnreachable`;
  `checksPending`/`checksUnreachable`, в том числе: записи `kit:file-lines` нет, из задач
  осталась только DOCS — проверка в `checksUnreachable`.
- `kit-update`: между проверкой при запросе и входом в блокировку появляется активный запуск —
  обновление не меняет ни файлы структуры, ни HEAD.
- Служба: `manualAcceptance` вместо `blocked` для трёх отказов, без повторного вызова Kit при
  том же HEAD, повтор при новом HEAD, закрытие и публикация после ручной приёмки; `notice`;
  409 `scope-open`; модели панели.
- Сквозные сценарии с настоящим bundle 2.4.5 (`autopilot/test`, стенд `m40-world.ts`):
  1. задача поставки с назначенной проверкой `delivery` (фиктивная команда `node`), критерий
     с ней — полный автопилот принимает, закрывает и публикует сам;
  2. критерий с проверкой без записи — `scope:propose` отклоняет `AUTOMATION_CHECK_UNRECORDED`;
  3. файла доказательств нет ни в HEAD, ни на диске, дерево чистое — запуск ждёт приёмки (ни
     разу не `blocked`, Kit при том же HEAD не вызывается), «Принять план» — запуск закрывает
     план, CI запускается для SHA закрытия, и публикуется именно этот SHA;
  3a. файл доказательств лежит незакоммиченным — тоже ожидание приёмки; после «Принять план»
     закрытие запуском получает `DIRTY_TREE`, запуск останавливается с подсказкой о
     незакоммиченных файлах, файл сохранён;
  4. «Обновить Kit» при открытом плане — 409 `scope-open`; scope закрыт, запуск ждёт CI
     финального SHA — 409 `run-active`, HEAD и Kit проекта не изменились; после публикации —
     202.
- CI: macOS ARM64, Linux x64, Windows x64 и ARM64. Живые проверки: macOS — пользователь
  (панель: «Ждёт вашей приёмки», выключенная «Обновить Kit»); Windows — проверяющий; Linux — CI.
- Проект Workflow_Kit остаётся на Kit 2.4.4 до закрытия M41: его хуки ещё не записывают
  проверки поставки, поэтому `installed-service` в критериях `automation` этого scope не
  называется; выпуск проверяет её командой `doctor --installed` и записью в evidence.

## 5. Границы

- Не входит: механика M42 (CI силами Kit, `repair`, тексты); ослабление правила `exactSha`
  для коммитов Kit; автоматическая приёмка по ручным критериям.
