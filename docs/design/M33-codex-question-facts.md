# M33: вопросы Codex — факты и проба T002

Дополнение к [спецификации M33](../planning/M33-agent-questions.md). Уровни доказательства:
**[код]** — прочитано в коде Kit; **[схема]** — типы протокола, сгенерированные локально
`codex app-server generate-ts --experimental` (codex-cli 0.169.0, 15.11.2026), поведение
сервера не испытано; **[проверено]** — наблюдалось вживую. Разделы 4 и 5 заполняет T002.

## 1. Схема протокола

- **[схема]** Запрос сервера `item/tool/requestUserInput`, параметры
  `{ threadId, turnId, itemId, questions, isBlocking, autoResolutionMs }`; помечен
  EXPERIMENTAL.
- **[схема]** Вопрос: `{ id, header, question, isOther, isSecret, options }`, `options` —
  массив `{ label, description }` или `null`.
- **[схема]** Ответ: `{ answers: { [id вопроса]: { answers: string[] } } }`.
- **[схема]** Уведомление `serverRequest/resolved { threadId, requestId }`.
- **[схема]** Статус треда: `active` с `activeFlags` из `waitingOnApproval`,
  `waitingOnUserInput`.
- **[схема]** Среди видов элемента истории (`ThreadItem`) вопроса пользователю нет: опросом
  `thread/items/list` его не прочитать.
- **[схема]** Другие запросы сервера: одобрения команд, правок и разрешений,
  `mcpServer/elicitation/request`, `item/tool/call` и служебные.

## 2. Проверено по коду Kit (0.13.7)

- **[код]** `createRpcSession` отвечает на любой запрос сервера ошибкой `-32601` «Workflow
  Kit does not handle server requests» и копит все уведомления в памяти соединения
  (`provider-codex/src/rpc.ts`).
- **[код]** Соединения короткие: каждая операция открывает своё (`withDaemon`, `readDaemon`).
  После служебного хода, прямого хода и смены параметров Kit делает `thread/unsubscribe`.
- **[код]** Лента не загружает тред и не подписывается: `thread/read`, `thread/turns/list`,
  `thread/items/list`; опрос раз в 3 с, пока карточка диалога видна.
- **[код]** Соединение с `experimentalApi` уже есть (`initializeSession`).
- **[код]** Windows ходит к демону через процесс `codex app-server proxy`.

## 3. Программа пробы T002

Стенд: демон Kit, одноразовый проект и тестовый тред в нём; пользовательские треды не
читаются и не возобновляются. Два соединения скрипта: A — слушатель, B — начинает ход.
Скрипт использует только публичный RPC, не импортирует код Kit и хранится в evidence в блоке
кода. Переписка в вывод не печатается: только методы, id, размеры и флаги.

| № | Что доказать |
| --- | --- |
| Q1 | Способ вызвать `request_user_input` в тестовом треде (режим плана или иной) и нужные параметры хода |
| Q2 | Соединение A, подписанное `thread/resume { excludeTurns: true }` до хода, получает `item/tool/requestUserInput` хода, начатого соединением B, в том числе после `thread/unsubscribe` соединения B; нужен ли `experimentalApi` |
| Q3 | Подписка A после появления вопроса (быстрый вопрос, панель открыта посреди хода): повторяет ли демон ожидающий запрос новому подписчику; что A видит без повтора |
| Q4 | Ответ A доходит до агента; B получает `serverRequest/resolved`; в ChatGPT карточка вопроса закрывается |
| Q5 | Гонка разных ответов A и B (или ChatGPT): признак, по которому A отличает свой принятый ответ от опоздавшего и от неподтверждённого (ответ сервера на поздний результат, порядок `serverRequest/resolved`, содержимое хода); нет признака — так и записать |
| Q6 | Ответ ошибкой `-32601` и молчание одного подписчика: влияет ли это на вопрос у остальных; то же для одного запроса одобрения команды |
| Q7 | Флаг `waitingOnUserInput` в `thread/read`, пока вопрос ждёт, и его снятие после ответа |
| Q8 | Трафик подписанного соединения за ход: виды уведомлений и байты |
| Q9 | Побочные эффекты подписки: `thread/loaded/list` до и после, состояние после `thread/unsubscribe` |
| Q10 | Прерывание хода при ожидающем вопросе: что получает слушатель |
| Q11 | Обрыв соединения A при ожидающем вопросе и новая подписка: повторяется ли запрос, остаётся ли вопрос у других клиентов |
| Q12 | `thread/unsubscribe` A посреди хода и повторная подписка до и после появления вопроса |

Что видно в приложении ChatGPT (Q4, Q5), подтверждает пользователь в одной совместной
проверке; без неё эти строки остаются «не проверено».

## 5. Выбор варианта (заполняет T002)

Момент подписки (L1 «по флагу» или L2 «с первого опроса активного хода», с ограничениями
раздела 2.4 решения по провайдерам) либо только C0; признак исхода гонки ответов (`accepted`,
`question-stale` или только `unknown`); обращение с чужими запросами сервера на соединении
слушателя; нужен ли `experimentalApi`.

## 6. Бюджет и согласие

Не больше 8 коротких ходов на самой дешёвой доступной модели с низким усилием. Ходы
запускаются только после прямого согласия пользователя с этим бюджетом в начале T002.
