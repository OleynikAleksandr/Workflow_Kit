# M18: диалог сессии в панели

## Цель и согласование

Сейчас панель показывает переписку только при ревью плана (журнал реплик основной сессии и
ревьюера). У обычной сессии виден лишь хвост последнего ответа агента (400 знаков), а написать
агенту из панели нельзя: карточку «Сообщение агенту» убрали в M3, остался только маршрут.

После M18 экран любой сессии показывает её диалог (реплики пользователя и агента) и поле ввода.
Щелчок по карточке сессии по-прежнему открывает и экран сессии в панели, и чат в родном
приложении; работа в родных приложениях не меняется.

Пользователь, 2026-11-12: «Я бы хотел… сделать возможным показывать диалоги любой сессии. То
есть, когда мы клацаем по карточке, у нас открывается и сессия в родном приложении, и диалоговая
сессия с полем ввода пользователя в самом Workflow Kit. Какой именно интерфейс будет этих сессий,
сейчас не столь важно. Я предлагаю тебе это решить самому, важно, чтобы это заработало, а дальше
будем заниматься полировкой… Подготовь план таким образом, чтобы ты его мог реализовывать через
сабагентов с другой моделью. С Opus 5.5 Medium.» Выбор в панели: спецификация и план без ревью.

## 1. Принципы

- Основная функция не меняется: сессии создаются, открываются и ведутся в родных приложениях как
  раньше. Диалог в панели — дополнительный вид той же сессии, своего чата у Kit нет.
- Провайдеры различаются только через контракт (`Provider`): два новых необязательных метода.
  Провайдер без метода работает как сейчас. `agent-channel`, `cli` и панель провайдеров не
  называют.
- Сообщение не теряется: если провайдер не может принять его сразу как реплику пользователя, оно
  идёт прежним путём — в очередь канала и агенту с ближайшим хуком.
- Kit по-прежнему не отвечает на запросы разрешений и диалоги провайдеров. Режим полного доступа,
  ограничение родных приложений и замена Tailscale в M18 не входят (раздел 5).
- Интерфейс — рабочий минимум; полировка позже.

## 2. Решение

### 2.1. Контракт провайдера (`provider-registry`)

Типы — в `src/chat.ts` (подробности — `chat.md` модуля): `ChatMessage { id, role: 'user' |
'assistant', text, at: string | null }` (`id` — собственный id сообщения у провайдера; текст
простой, без вызовов инструментов и рассуждений; `at` — ISO или `null`) и `ChatPage { messages,
truncated }` (новейшие сообщения от старых к новым; `truncated` — старые не вошли).

В `Provider` (`src/contract.ts`):

- `readMessages?(project, sessionId, opts: { limit: number }): Promise<ChatPage>` — последние
  `limit` сообщений сессии, от старых к новым. Ничего не меняет у провайдера: не загружает чат,
  не начинает ход. Сессия без записей — пустая страница. Нечитаемый источник —
  `ProviderError('chat-unavailable', …)` с причиной по-русски.
- `sendDirect?(project, sessionId, text): Promise<boolean>` — передаёт текст агенту как реплику
  пользователя прямо сейчас; `true` — текст принят провайдером, `false` — сейчас нельзя (вызывающий
  кладёт сообщение в очередь). Не бросает на ожидаемых отказах (сессия не под управлением панели,
  идёт ход, нет общего доступа): возвращает `false`.

Константы: `CHAT_PAGE_LIMIT = 100` (сообщений на страницу), `CHAT_TEXT_MAX_CHARS = 20_000`
(длиннее — текст обрезается с конца пометкой `\n… (обрезано, полный текст — в чате провайдера)`;
обрезку делает маршрут, не провайдер; `cutChatText` не разрезает суррогатную пару).

Маршрут — `src/chat-routes.ts` (`registerChatRoutes`, его зовёт `registerProviderRoutes`):

`GET /api/projects/:id/providers/:p/sessions/:sid/messages` →
`{ supported: boolean, messages: ChatMessage[], truncated: boolean }`.

- Проект или провайдер неизвестен — 404 как у соседних маршрутов.
- У провайдера нет `readMessages` — `{ supported: false, messages: [], truncated: false }`.
- `:sid` — `localId` сессии; сессия должна быть в `listSessions(project)` этого провайдера
  (`localId` или `remoteId`), иначе 404 `unknown-session` «Сессия не найдена».
- `ProviderError` провайдера — 502 с его кодом и текстом; панель показывает текст в карточке.
- Тексты длиннее `CHAT_TEXT_MAX_CHARS` обрезаются здесь.

`fake-provider.ts` тестов получает оба метода.

### 2.2. Claude (`provider-claude`)

**Чтение — `src/chat.ts`.** Источник — файл транскрипта сессии (`transcript_path` журнала хука,
как у `BridgeReader`; каталог транскриптов не вычисляется). Транскрипт только растёт и бывает
большим (служебные записи запросов), поэтому чтение инкрементное: состояние на файл (`ino`,
смещение, остаток строки, декодер — как в `transcripts.ts`), в памяти хранятся последние
`CHAT_PAGE_LIMIT` сообщений файла. Смена `ino` или уменьшение размера — чтение заново.

Строка транскрипта становится сообщением, если это JSON-объект и:

- `type: "user"`, не `isMeta`, не `isSidechain`, и в `message.content` есть текст: строка целиком
  или части `type: "text"` (через перевод строки). Запись только из `tool_result` — не сообщение.
  Пропускаются тексты, начинающиеся с `<local-command`, `<command-name>`, `<command-message>`,
  `<task-notification>`, `<system-reminder>`.
- `type: "assistant"`, не `isSidechain`, части `type: "text"` из `message.content` (без
  `thinking` и `tool_use`); пустой текст — не сообщение.

`id` — `uuid` записи, `at` — `timestamp`. Строка длиннее 8 МБ или не JSON пропускается. Сессия без
транскрипта в журнале хука (в том числе сессия панели до первого хука) или без файла — пустая
страница; файл есть, но не читается — `chat-unavailable`. Ответ хука `Stop` («Stop hook feedback: …») Claude
записывает как реплику пользователя — она остаётся в ленте: это то, что получил агент.

**Запись — `sendDirect`.** Только сессия, которую ведёт панель (есть запись с живым процессом;
прерванная поднимается так же, как в `wakeSession`). Иначе `false`.

Управляющий файл `<debug>.message` получает второй вид содержимого:

- `wake\n` — как сейчас: служебная фраза `WAKE_TEXT`.
- `text\n<текст UTF-8>` — текст сообщения. Сценарий печатает его в терминал как вставку
  (bracketed paste): `ESC[200~` + текст + `ESC[201~`, пауза 700 мс, `\r`, строка `MESSAGE_SENT`.

Перед записью текст очищается (`cleanDirectText`): `\r\n` и `\r` → `\n`, управляющие символы
C0, DEL и C1 кроме `\n` и `\t` удаляются (в том числе `ESC`, чтобы текст не мог закрыть
вставку). Пустой после очистки — `false`. Код — `src/direct.ts`; запись атомарная:
`<debug>.message.partial`, затем переименование.

Файл читается раз в секунду и один на сессию, поэтому `sendDirect` идёт по очереди на сессию:
ждёт, пока прежний файл заберут (до 5 с, проверка раз в 200 мс), и только потом пишет. Не
дождался — `false`. После записи ждёт, пока файл заберут (до 5 с): забрали — `true`, нет —
удаляет файл и возвращает `false`. Если сценарий забрал файл ровно в момент тайм-аута, текст уже
вставлен, а сообщение ещё и уходит в очередь — редкий повтор (известное ограничение).

Меняются `pty/session.exp` (macOS, Linux; чтение файла в UTF-8, как у `.rename`) и `pty/host.ts`
(Windows, ConPTY). `WAKE_TEXT` и `wakeSession` остаются: ими пользуются автопилот и ревью;
`wakeSession` пишет `wake\n` только если файла нет (флаг `wx`): ждущий текст сам начнёт ход.
Ведёт ли панель сессию, обе функции проверяют общим `runningPanelRecord` (`src/sessions.ts`).

Ввод во время хода Claude сам ставит в очередь и отдаёт агенту в том же ходе (проба), поэтому
вставка безопасна и тогда, когда служба после перезапуска ещё не знает состояния сессии.

### 2.3. ChatGPT (`provider-codex`)

**Чтение — `src/chat.ts`.** `thread/read { threadId, includeTurns: true }` через `withDaemon`.
Чат при этом не загружается (проба: `notLoaded` до и после), поэтому приложению ChatGPT чтение не
мешает и работает без общего доступа. Из `thread.turns[].items[]` берутся:

- `userMessage` — текст частей `content[]` с полем `text` через перевод строки;
- `agentMessage` — `text`.

`id` — `id` элемента, `at` — `startedAtMs` элемента в ISO (нет поля — `startedAt` хода, иначе
`null`). Остальные элементы (`reasoning`, `commandExecution` и другие) — не сообщения. Элементы
появляются по мере завершения, поэтому лента обновляется целыми сообщениями. Демон не запущен или
не ответил — `chat-unavailable` «Codex не отдал переписку: <причина>».

**Запись — `sendDirect`.** Только в режиме общего демона (`sharedMode.refresh()`), иначе `false`.
Состояние чата — `thread/read { threadId }` без ходов, поле `thread.status.type`:

- `idle` или `notLoaded` — `wakeThread(session, threadId, text)`: ход начинается самим текстом
  (как уже делает служебная фраза; в ChatGPT он виден репликой пользователя) → `true`;
- `active` — `false`. `turn/start` во время хода не встаёт в очередь, а вливается в идущий ход, и
  агент может бросить текущую задачу (проба); сообщение уйдёт в очередь канала и придёт агенту
  ответом хука `Stop`. `turn/steer` в M18 не используется (раздел 5);
- другое или ошибка — `false`, строка в журнале.

`thread-ops.ts` получает `threadStatus(session, threadId) → string | null`.

### 2.4. Kimi (`provider-kimi`)

**Чтение.** `readMessages` — `readKimiChat` в `src/chat.ts`: одна страница
`GET /api/v1/sessions/{id}/messages?page_size=100` (от новых к старым), разворот в порядок от
старых к новым. Сообщения: `role: "user"` с `origin: "user"` (вставки Kimi — нет) и
`role: "assistant"` с непустым текстом. `truncated` — `has_more`. `at` — время сообщения, если
сервер его отдаёт (`created_at`; `parseMessages` получает необязательное поле), иначе `null`.
Сервер недоступен — `chat-unavailable` «Kimi не отдал переписку: <причина>».

**Запись.** `sendDirect` не нужен: канал уже отправляет сообщение панели промптом (`sendMessage`)
без служебной фразы.

### 2.5. Отправка из панели (`agent-channel`, `cli`)

`POST /api/projects/:id/sessions/:sid/message { text }`:

- `MESSAGE_MAX_CHARS` — 20 000 вместо 4000 (задание из панели бывает длинным). Проверки текста и
  принадлежности сессии — прежние; они вынесены из `queueSessionMessage` в
  `checkSessionMessage(channel, projectId, key, text, owned) → string` (чистый текст),
  `queueSessionMessage` зовёт её.
- Новая опция маршрутов `direct?(projectId, key, text) → Promise<boolean>`. После проверок маршрут
  зовёт `direct`; `true` — ответ `{ sent: true }`, сообщение в очередь не кладётся. `false`,
  ошибка или нет опции — прежний путь: `{ queued: <id> }`.

`cli/src/session-wiring.ts` передаёт `direct` — `createDirectMessage` из `src/direct-message.ts`:

- записи канала нет (служба перезапускалась) или её состояние `waiting` → `provider.sendDirect`,
  если он есть у провайдера и проект найден; ошибка — `false` и строка в журнале;
- `working` и `holding` → `false` без вызова: при удержанном `Stop` текст доходит мгновенно ответом
  хука, во время хода — ответом `Stop` в его конце (проверенный путь);
- провайдер с `sendMessage` (Kimi) → `false`: очередь канала отправляет сама.

Прямая реплика запускает обычный ход: `UserPromptSubmit` приходит без сообщений очереди, автопилот
видит ход пользователя (`autopilot.onPrompt(key, false)`) — как при вводе в родном приложении.

### 2.6. Панель: модуль `session-chat` и слот `sessionChat`

Новый модуль `control-panel/web-panel/session-chat` (алиас `#session-chat`), расширение панели, как
`session-view`.

`panel-shell`: третий слот сессии `sessionChat` (`slots.js`, тот же `SessionSlot`); новый
`session-screen.js` (`createSessionScreen`, его зовёт `app.js`) рисует его на экране сессии под
`sessionBody` в отдельном контейнере `.session-chat`, с тем же правилом «перерисовать, только
если изменились данные»; `PANEL_EXTENSIONS` получает
`/session-chat/session-chat.js`, `index.html` — `session-chat/session-chat.css`. `cli/src/app.ts`
монтирует модуль (`sessionChatMount()`), `package.json` — алиас.

Файлы модуля:

- `src/index.ts` — `SESSION_CHAT_PREFIX` (`/session-chat/`), `SESSION_CHAT_ASSETS_DIR`,
  `sessionChatMount()`.
- `src/chat-model.js` — чистая логика без DOM: `messagesUrl(projectId, session)`,
  `sendUrl(projectId, key)`, `mergePage(previous, page)` (по `id`: прежние узлы сохраняются,
  новые добавляются, признак «появились новые»), `sendOutcome(response)` (`sent` → «Отправлено
  агенту», `queued` → «В очереди: агент получит сообщение в конце хода или с вашим следующим
  сообщением в чате»), `canSend(text, busy)`, `roleLabel(role, providerLabel)` («Вы» /
  название провайдера), `timeLabel(at)`.
- `src/session-chat.js` — `install(shell)`: слот `sessionChat`. Карточка «Диалог»:
  - лента сообщений (прокрутка внутри карточки, высота до 60 % окна): подпись (кто, время) и
    текст; текст только через `textContent`, перенос строк сохраняется (`white-space: pre-wrap`);
  - `truncated` — строка «Показаны последние сообщения; полная переписка — в чате провайдера»;
  - `supported: false` — «<Провайдер> не отдаёт переписку; сообщение агенту можно отправить»;
  - ошибка чтения — её текст в карточке, прежние сообщения остаются;
  - поле ввода (`textarea`, 3 строки) и кнопка «Отправить»; Ctrl+Enter и ⌘+Enter отправляют;
    во время отправки кнопка выключена; после успеха поле очищается, под ним — итог из
    `sendOutcome`; отказ — текст ошибки, введённое остаётся.
  - Состояние на сессию (узлы, введённый текст, прокрутка) хранится в `Map` по ключу сессии и
    переживает опрос и уход с экрана. Лента сама прокручивается вниз при новых сообщениях, если
    пользователь был внизу.
  - Опрос: `GET …/messages` при открытии экрана сессии и раз в 3 с, пока экран этой сессии открыт
    и вкладка видима; сразу после успешной отправки — внеочередной. Одновременно не больше одного
    запроса на сессию.
- `src/session-chat.css` — `.sc-card`, `.sc-feed`, `.sc-msg`, `.sc-msg-user`, `.sc-msg-agent`,
  `.sc-meta`, `.sc-input`, `.sc-status`; цвета — переменные темы панели (светлая и тёмная).

`session-view` не меняется, кроме строки `module.md` про карточку сообщения агенту.

### 2.7. Пробы 2026-11-12 (macOS, Claude Code 2.1.322, codex-cli 0.167.2)

## 3. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Лента: Claude | транскрипт по пути из хука | так же | так же (x64 и ARM64) |
| Лента: ChatGPT | `thread/read` через сокет демона | так же | `thread/read` через `codex app-server proxy` (x64 и ARM64) |
| Лента: Kimi | сервер приложения Kimi | так же | так же |
| Прямая отправка: Claude | вставка в терминал, `session.exp` | так же, нужен `expect` | вставка через ConPTY, `pty/host.ts` |
| Прямая отправка: ChatGPT | при общем доступе к чатам | общего доступа нет: всегда очередь | при общем доступе к чатам |
| Прямая отправка: Kimi | промпт через канал (как было) | так же | так же |
| Очередь и хуки | без изменений | без изменений | без изменений |
| Панель | одинаково во всех браузерах панели | так же | так же |

Новых вызовов программ ОС нет: `expect` уже в `allowlist.json`. Код с ветками по ОС получает
платформу параметром; путь транскрипта и управляющих файлов — через `path`.

## 4. Проверка

- Автоматические тесты — в модулях раунда; что проверяет каждый набор, записано в их
  документах: `chat.md` модулей `provider-registry`, `provider-claude`, `provider-codex`,
  `provider-kimi`; `module.md` модулей `agent-channel`, `session-chat`, `panel-shell`;
  `session-chat.md` модуля `cli`. Сверх плана: `host.ts` и `session.exp` проверены на
  многострочной вставке, `wakeSession` — на том, что ждущий файл не перезаписывается.
- `npm run typecheck`, `npm test`, `npm run check:platforms`.
- CI: macOS, Linux, Windows x64 и ARM64 на ветке `ci/m18-session-chat`.
- Живая проверка:
  - macOS — пользователь: для Claude, ChatGPT (общий доступ включён) и Kimi открыть сессию,
    увидеть диалог, отправить многострочное сообщение ждущему агенту (в родном чате оно видно
    репликой пользователя) и работающему агенту (приходит в конце хода), увидеть ответ в ленте.
  - Windows — проверяющий на Windows: то же для Claude и ChatGPT.
  - Linux — только CI.

## 5. Границы

Не входит: режим «только Kit» (полный доступ без подтверждений, ограничение родных приложений),
ответы на запросы разрешений и вопросы агента из панели, `turn/steer` для ChatGPT, посимвольный
вывод ответа, вложения и картинки, поиск и подгрузка старых сообщений, уведомления, доверенная
подсеть вместо Tailscale и авторизация панели, диалог сессий Claude, начатых не панелью (читать
