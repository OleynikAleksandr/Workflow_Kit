# M31: неначатый план виден в любой сессии проекта

## Цель и согласование

Пользователь с одним провайдером обсуждает тему, агент пишет спецификацию и план, план
проходит ревью, агент предлагает его (`scope:propose`). Потом пользователь открывает в том же
проекте совершенно новую сессию (другой провайдер или другая модель — неважно). Сейчас в
левом сайдбаре новой сессии нет ни карточки выбора способа выполнения, ни карточки плана,
хотя план ещё не начат. Так быть не должно: неначатый план принадлежит проекту, а не сессии.

Пользователь, 14.11.2026: «Нужно чтобы работал такой вариант … я начинаю совершенно новую
сессию провайдером или с другой моделью неважно сессия возникает а плана нет хотя я ее
открываю в том же workspace и это неправильно у нас остался неначатый даже план я не нажал
кнопку его начинать и как карточка этого плана отсутствует в левом сайт баре нашего workflow
кита это недопустимо, это нужно исправить». После разбора причин пользователь выбрал в панели
«спецификация и план без ревью».

## 1. Факты (разбор 14.11.2026, версия 0.13.4, Kit 2.2.4)

Kit план не теряет. Предложение лежит в `.harness/workflow/local/scope-proposal.json`, раздел
`workflow` службы держит его на проект, и пакет восстановления новой сессии пишет «the scope
proposal … is waiting for the user's choice on the card». Карточку прячут правила «владельца».

1. Карточка выбора способа. `choiceView` (`session-view/src/session-model.js`) показывает её
   только сессии, которая держит Stop с причиной `waiting-for-mode-choice` (`choiceHolder`).
   После ревью основная сессия держит Stop без срока (`agent-channel/src/detached.ts`, `hold`
   без `timeoutAnswer`), поэтому новая сессия карточку не получает.
2. Карточка плана. `scope:choose --session <id>` записывает `execution.ownerSession`. `planView`
   скрывает карточку у всех, кроме владельца. Служба (`autopilot.ts`, `owner`) без явной сессии
   отвечает «Не найдена сессия-владелец плана · Откройте сессию, в которой агент предложил план».
   Команды Kit, которая меняет владельца, нет.
3. Ревью привязано к сессии. Признак «план уже проверен» — запись ревью по ключу основной
   сессии (`cross-review/src/review.ts`: `reviews.get(context.key)`, сравнение `own.scopeId`),
   решение «с ревью / без ревью» — тоже по сессии (`plan-review/src/toggles.ts`, `decided`).
   Новая сессия, у которой нет своей записи, после своего хода спросит о ревью снова или
   начнёт второе ревью того же плана (когда старая сессия уже не держит Stop, например после
   перезапуска службы). Пока новая сессия работает, `reviewComing` в панели прячет карточку, а
   `choiceBlocked` службы отказывает в выборе («CHOICE_WAITS_TURN»).

Проба на модели панели (синтетическое состояние, старая сессия `claude:old-id`, новая
`codex:new-id`): `choice old: true new: false`, `plan old: true new: false`.

В исходном дизайне Harness было правило «Владелец — `execution.ownerSession`, если это сессия
workspace, иначе последняя активная основная сессия»
([WorkflowKitExecutionModes.md](../architecture/workflow-kit/WorkflowKitExecutionModes.md));
в панели Workflow Kit его нет.

## 2. Принципы

- Неначатый план (предложение без выбора и scope в фазе `ready`) принадлежит проекту. Его
  карточки видны в каждой основной сессии проекта — в той, что стоит в дереве сайдбара
  (ревьюеры в дерево не входят, архивные сессии карточек не показывают).
- Владельцем становится сессия, в которой пользователь нажал кнопку выбора способа или
  «Начать выполнение плана». Kit записывает это в `execution.ownerSession`; источник истины —
  Kit, память службы только кэш.
- Начатый план остаётся у владельца. Другие сессии видят краткую карточку «План выполняет
  сессия «…»» с кнопкой «Открыть сессию»; переноса начатого плана в этой работе нет (раздел 6).
- Предложение проверяет ревью один раз. Новая сессия, которая не писала предложение, не
  спрашивает о ревью и не начинает ревью этого предложения.
- Тексты для агента — английские, тексты панели — русские. Маршруты HTTP не меняются, меняется
  только поведение `choose` и `start`.

## 3. Решение

### 3.1. Kit 2.2.5: команда `scope:owner` (`workflow-kit`, `workflow-plan`)

`scripts/workflow scope:owner --session <id> --note "<why>"` меняет владельца открытого scope.

- Работает под блокировкой проекта, без незавершённой транзакции (`ensureNoTransaction`).
- Отказы: нет активного scope — `NO_SCOPE`; есть задача `IN_PROGRESS` или назначение не
  `INTEGRATED` — `OWNER_BUSY` («The plan has started work; the owner changes only before it.»,
  nextAction «Continue the plan in its owner session.»); пустые `--session` или `--note` —
  `USAGE`.
- Тот же владелец — ответ без изменения плана (`changed: false`).
- Иначе записывает `execution.ownerSession = <id>` и решение в `scope.decisions`:
  `Owner session moved from <old|none> to <id>: <note>`. План сохраняется как при
  `task:block` (ревизия +1, без отдельного коммита; следующий коммит Kit его записывает).
- Ответ JSON: `{ changed, previous, execution }`; `--format text` — одна строка
  `owner: <old|none> → <id>`.
- `workflow-plan` получает чистую функцию `setOwner(plan, session, note, now)` в фасаде;
  проверка `OWNER_BUSY` — там же.
- `KIT_VERSION` = `2.2.5` (`workflow-installer/src/installer-payload.ts`), бандл пересобирается
  `npm run build:kit` (`kit-bundle/vendor`, `src/bundle-meta.ts`, `PROVENANCE`). Команда
  описана в `WorkflowKitCommands.md` (раздел Scope) и в `help`.

### 3.2. Автор предложения (`agent-channel`, `cross-review`)

Автор предложения — сессия, чей ход начался не позже `createdAt` предложения. Ход, который
начался позже, предложение не писал.

- `StopContext` получает `turnStartedAt: string | null` — начало закончившегося хода (то же
  значение, что `SessionActivity.turnStartedAt` до перехода в `waiting`). Неизвестно — `null`.
- `cross-review` (новый файл `src/author.ts`, `review.ts` уже 387 строк):
  `isAuthor(turnStartedAt, proposal.createdAt)` — `true`, если хоть одно значение неизвестно
  (прежнее поведение) или ход начался не позже предложения.
- `decide`: для не автора — не спрашивать о ревью (`askProposal`) и не начинать ревью; ответ
  `null`, дальше решает автопилот. Ревью, уже идущее для этого `scopeId`, не трогается.
- `choiceBlocked(projectId, working)`: кандидатами остаются только работающие сессии-авторы
  (по `turnStartedAt` их текущего хода из канала). Новая сессия, с которой пользователь
  разговаривает, выбор не блокирует.

### 3.3. Служба (`autopilot`)

Новый файл `src/owner.ts` (`autopilot.ts` уже 394 строки) — передача владельца и пробуждение
прежнего.

- `choose(projectId, { session, … })`: после успешного `scope:choose --session <session>`
  служба будит (`channel.wake`) каждую другую сессию проекта, которая держит Stop с причиной
  `waiting-for-mode-choice`. Решатель отпускает её: предложения больше нет, владелец другой.
  Сообщение о выбранном способе получает только `session`.
- `start(projectId, session)`: если `session` задана и не совпадает с
  `execution.ownerSession`, служба сначала вызывает
  `scope:owner --session <id> --note "The user started the plan from this session in the Workflow Kit panel"`,
  обновляет `owners`, будит прежнего владельца (его `waiting-for-plan-start` отпускается) и
  дальше запускает план как сейчас — сообщение старта уходит в `session`. Для `orchestrated`
  проверка `requireOrchestration` идёт для новой сессии.
- Kit проекта старше 2.2.5 (`UNKNOWN_COMMAND`): старт из чужой сессии отказывает с кодом
  `kit-outdated`, 409, «Обновите Kit проекта до 2.2.5, чтобы начать план из этой сессии»,
  nextAction «Нажмите «Обновить Kit» у проекта или начните план в сессии, где выбран способ».
  Старт в сессии-владельце работает как раньше.
- `OWNER_BUSY` от Kit приходит как обычная ошибка Kit (409) с её текстом.
- `decide` не меняется: сессия держит `waiting-for-plan-start`, только если она владелец; не
  владелец отпускается.

### 3.4. Панель (`session-view`)

Логика карточек уходит в новый файл `src/plan-cards.js` (`session-model.js` уже 399 строк);
`session-model.js` реэкспортирует `choiceView` и `planView`, вызовы не меняются.

- `choiceView`: без фильтра `choiceHolder` — карточка видна в любой основной сессии проекта.
  Остаются прежние условия: идущее ревью и сессия-ревьюер, открытый вопрос о плане,
  `reviewComing`.
- `reviewComing`: работающая сессия считается «ревью впереди», только если она автор
  (`turnStartedAt` не позже `createdAt` предложения; неизвестно — автор, как сейчас).
- `planView`: в фазе `ready` карточка с «Начать выполнение плана» видна в любой основной
  сессии. Нажатие уже отправляет `{ session: key }`; владельцем становится эта сессия.
- В других фазах сессия не владелец получает вид `{ foreign: { ownerKey, ownerName } }`:
  карточка с заголовком цели scope, строкой «План выполняет сессия «<имя>»», прогрессом
  «в main N из M» и кнопкой «Открыть сессию» (`ctx.openSession` или `navigate`). Без кнопок
  плана и без задач. Владелец не найден в дереве — строка «План выполняет другая сессия» без
  кнопки.
- `needsAttention` сайдбара не зажигается для чужой карточки.

## 4. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| `scope:owner` в Kit | одинаково | одинаково | одинаково; x64 и ARM64 |
| Автор предложения, пробуждение прежней сессии | одинаково | одинаково | одинаково |
| Карточки в сайдбаре новой сессии | одинаково | одинаково | одинаково |

Поведение везде одинаковое: веток по платформе нет, новых вызовов программ ОС нет. Время
сравнивается как ISO-строки службы, пути не участвуют. Сборка бандла Kit идёт как в M22.

## 5. Проверка

- Kit: тесты `scope:owner` — смена владельца, тот же владелец, `NO_SCOPE`, `OWNER_BUSY`
  (задача `IN_PROGRESS`, открытое назначение), `USAGE`; запись решения; `build:kit --check`.
- Канал и ревью: `turnStartedAt` в `StopContext` (hook и detached); не автор не получает
  вопроса о ревью и второго ревью; автор — как раньше; `choiceBlocked` не блокирует выбор из-за
  работающей новой сессии.
- Служба: выбор в новой сессии будит старую, держащую `waiting-for-mode-choice`; старт из
  новой сессии вызывает `scope:owner`, будит прежнего владельца и шлёт старт новой; старый Kit —
  `kit-outdated`; старт владельца не вызывает `scope:owner`.
- Панель: модельные тесты — карточка выбора и карточка `ready` в новой сессии; чужая карточка
  начатого плана с «Открыть сессию»; `reviewComing` не прячет карточку из-за новой сессии.
- Ветки `win32`/`linux` не появляются; `npm run check:platforms` зелёный.
- CI: macOS, Linux, Windows x64 и ARM64 для коммита поставки (ветка `ci/<scope>`).
- Живая проверка: macOS — пользователь (предложение в сессии Claude, новая сессия Codex или
  другой модели в том же проекте: карточка выбора видна, выбор и «Начать выполнение плана» в
  новой сессии, старая сессия отпущена); Windows — проверяющий на Windows по тому же сценарию;
  Linux — только CI. Сценарий и результаты — `docs/evidence/M31-plan-in-any-session.md`.

## 6. Границы

- Перенос уже начатого плана в другую сессию («Продолжить здесь») — отдельная работа: у
  прежней сессии может идти задача. Здесь чужая сессия только видит план и открывает владельца.
- Карточки в отдельных окнах без сайдбара не появляются.
- Пустые папки `\var\folders\…\wfk-acw-*` в корне репозитория (их создаёт
  `cli/test/auto-compact-context.test.ts`) — отдельный дефект, не в этой работе.
