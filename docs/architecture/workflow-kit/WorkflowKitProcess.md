# Workflow Kit — алгоритм процесса

Статус: спецификация scope `workflow-kit-2026-11-03`. Корневой документ —
`docs/architecture/workflow-kit/WorkflowKit.md`. Здесь описан процесс,
который Kit проверяет механически. Как он устроен в коде — в документах
модулей кластера `core-runtime/clusters/project-workflow`.

## 1. Принципы

- Один Git checkout (worktree) — один текущий план:
  `.harness/plans/todo-plan.md`. Новый чат, клиент или провайдер продолжает
  этот же план. Независимой параллельной работе нужен отдельный worktree.
- В checkout одновременно в работе не больше одной задачи. Исключение —
  scope в режиме `orchestrated`: задачи `work` и `DOCS` выполняют
  исполнители, каждый в своём worktree со своим планом из одной задачи, а
  main принимает их результат интеграционными коммитами. Это описано в
  [WorkflowKitExecutionModes.md](WorkflowKitExecutionModes.md) и
  [WorkflowKitOrchestration.md](WorkflowKitOrchestration.md). Режим
  `sequential` (и scope без блока `execution`) работает по этому
  документу без изменений.
- Каждый статус меняет команда Kit. Ручная правка состояния плана
  обнаруживается как повреждение (`PLAN_PROJECTION`).
- Каждая завершённая задача — ровно один коммит, созданный транзакцией Kit.
  Прямой `git commit` в установленном проекте отклоняется хуком
  (`MANAGED_COMMIT_REQUIRED`).
- Hooks не обходятся (`--no-verify` запрещён правилами для агента).
- История живёт в Git. Kit не создаёт архивных копий планов, отчётов и
  changelog.

## 2. Когда нужен план

- Обсуждение, исследование, написание спецификации и коммиты только
  документации не требуют плана. Документацию можно зафиксировать командой
  `docs:commit` при scope `NONE` или между задачами активного scope.
  Документация — это Markdown (`.md`, `.markdown`) и дерево продукта
  `.harness/product-tree/**`.
- Реализация (изменение функциональных файлов) возможна только в задаче
  активного scope.
- Ясное поручение пользователя реализовать разрешает агенту подготовить
  спецификацию и план без повторного согласования. Само наличие плана не
  разрешает выполнять его вместо текущего поручения пользователя.
- Согласованное содержание scope записывается в план (`scope.approval`), а
  последующие решения пользователя — в `scope.decisions`.

## 3. Создание scope

`scope:create --input <file.json>` при состоянии `NONE`:

1. Если задач больше одной, нужна спецификация: существующий Markdown-документ
   (`spec`), на котором построен план. Если задача одна, `spec` можно не
   указывать.
2. Вход содержит `id`, `objective`, `acceptance`, `approval` и `tasks`.
   Необязательные поля: `spec`, `context` и `decisions`.
3. Kit записывает `baselineCommit = HEAD`, создаёт первый раунд
   (`R1`, вид `implementation`), нормализует задачи и добавляет служебные
   задачи (раздел 5). Затем делает служебный коммит с ролью `scope-plan`:
   в него входят план и, если они изменены, документ спецификации и
   документы из `context`.
4. При ошибке валидации проект не меняется. Форму входа печатает
   `scripts/workflow schema scope:create`. Текст `context` каждой задачи
   (или спецификации) не больше `budget.briefBytes`, иначе
   `CONTEXT_TOO_LARGE`; отсутствующий файл или раздел — `CONTEXT_MISSING`.
5. В проекте Harness (`config.host: "harness"`) `scope:create` отвечает
   `EXECUTION_MODE_REQUIRED`: агент вызывает `scope:propose`, а scope
   создаёт выбор пользователя на карточке режима
   (`WorkflowKitExecutionModes.md`, раздел 4). Проверка входа та же.

## 4. Деление на задачи

- Работа делится по проверяемому результату, смысловым зависимостям,
  контрактам и пересечениям записи. Числовых норм нет: небольшой результат
  может быть одной задачей.
- Конфигурация проекта может задать мягкий лимит числа функциональных файлов
  в задаче (`policy.taskFileSoftLimit`). Превышение выдаёт предупреждение в
  `task:start` и в recovery и не блокирует работу.
- Каждая задача содержит:
  - `title` и `why`;
  - `files` — ориентир, а не запрет;
  - `dependencies` — только на задачи, стоящие раньше;
  - `acceptance` — критерии готовности;
  - `checks` — проверки профиля качества;
  - `context` — документы задачи, по возможности разделами;
  - `commitMessage` — ожидаемое сообщение коммита одной строкой.
- Вид задачи (`kind`):
  - `work` — обычная задача;
  - `quality` — настройка профиля качества;
  - `docs` — завершение раунда;
  - `delivery` — сборка, выпуск или публикация.

## 5. Служебные задачи, которые Kit добавляет сам

- **`QUALITY`.** Ставится перед первой задачей `work` с функциональными
  файлами, если профиль качества проекта ещё в состоянии `DISCOVERY`. Задача
  определяет стек, подключает проверки (`quality:apply`) и коммитит профиль.
  Подробности — в `WorkflowKitQuality.md`.
- **`DOCS-<раунд>`.** Последняя рабочая задача каждого раунда. Она зависит от
  всех задач `work` раунда и предшествует его задачам `delivery`. Задача
  сверяет общие документы проекта с результатом раунда и записывает **сводку
  раунда**: результат, решения, изменённые контракты и ссылки. Без сводки
  коммит DOCS отклоняется (`ROUND_DIGEST_REQUIRED`).

## 6. Цикл задачи

1. `task:start <ID>`:
   - проверяет, что scope `ACTIVE`, задача `TODO`, все зависимости `DONE`,
     а назначенные проверки настроены;
   - запоминает снимок изменений, которые уже были в рабочем дереве до
     начала задачи;
   - переводит задачу в `IN_PROGRESS`.

   Для задачи `delivery` команда требует `--confirmed "<note>"`:
   подтверждение пользователя на сборку или выпуск.

   В scope `orchestrated` в main `task:start` задачи `work` или `DOCS`
   отвечает `ORCHESTRATED_MAIN_READ_ONLY`, а задачи `delivery` —
   `DELIVERY_NOT_READY`, пока предыдущие задачи не `DONE` или есть
   активное назначение.
2. Работа над задачей.
3. `commit --task <ID> [--files <json>] [--digest <file>]` открывает
   транзакцию:
   1. Выбирает файлы задачи: изменённые после старта задачи или явно
      перечисленные. Служебные файлы `.harness/**` и приватные файлы
      (`.env*`, ключи, домашние каталоги провайдеров) не выбираются.
      Остальные изменения остаются в рабочем дереве, и коммит о них
      сообщает (`excludedChanges`).
   2. Выполняет проверки этапа `prepare` (форматтеры и автоисправления) на
      выбранных файлах. Им разрешено менять файлы.
   3. Отмечает задачу `DONE`, записывает план-кандидат, индексирует файлы
      и фиксирует дерево кандидата (`candidateTree`).
   4. Запускает `git commit` с сообщением задачи и служебными trailers
      (`Workflow-Scope`, `Workflow-Task`, `Workflow-Role`,
      `Workflow-Iteration`, `Workflow-Transaction`).
   5. Pre-commit hook запускает проверки этапа `commit`. Им запрещено менять
      кандидат (`CHECK_MODIFIED_CANDIDATE`). Встроенную
      `kit:conflict-markers` (маркеры конфликта Git в добавляемых файлах)
      выполняет каждый коммит, в том числе служебный
      (`WorkflowKitQuality.md`, раздел 4).
   6. Если проверка не прошла, Kit восстанавливает исходные план и index,
      а правки в рабочем дереве сохраняет. Агент исправляет причину и
      повторяет ту же команду. Repair при этом не нужен.
   7. Если коммит прошёл, Kit подтверждает его по trailers, родителю и
      дереву и сохраняет доказательства проверок.
4. После коммита агент кратко сообщает результат. Ход заканчивается после
   **одной** задачи. Следующую задачу запускает пользователь («Continue»)
   или автопилот Core (`WorkflowKitRecovery.md`, раздел 6).
5. Если задачу нельзя завершить в текущем ходе, агент сохраняет работу в
   безопасной точке, кратко называет состояние и заканчивает ход без `DONE`.
   Следующее «Continue» продолжает ту же задачу.
6. Новое сообщение пользователя не отменяет уже принятое поручение. Агент
   учитывает его и продолжает в границах текущей задачи.

## 7. Связь задачи с Git

- Каждая задача в состоянии `DONE` должна соответствовать ровно одному
  коммиту на участке `baselineCommit..HEAD`, пройденном по первым
  родителям. Коммит ищется по trailers `Workflow-Scope`, `Workflow-Task` и
  `Workflow-Iteration`. В scope `orchestrated` коммит задачи `work` или
  `DOCS` — интеграционный (роль `integration`).
- Коммит задачи содержит только файлы этой задачи и сам план.
  Интеграционный коммит сравнивается со своим первым родителем, и путь
  входит в задачу, если он равен записи `files` или вложен в неё по
  сегментам пути.
- Коммит с несколькими родителями допустим только как интеграционный: два
  родителя, `Workflow-Source` равен второму, есть `Workflow-Task` и
  `Workflow-Assignment` (иначе `HISTORY_NOT_LINEAR`).
- Коммиты зависимостей предшествуют коммиту задачи.
- `validate` проверяет эти правила. Нарушение — ошибка
  `PLAN_COMMIT_MISMATCH`, `COMMIT_SCOPE_MISMATCH`, `DEPENDENCY_ORDER` или
  `HISTORY_NOT_LINEAR`.

## 8. Раунды и расширение плана

- План делится на раунды:
  - `R1` — основная реализация;
  - следующие — исправления или продолжение.
- `plan:extend --input <file.json> --expected-revision N`:
  - добавляет задачи в новый раунд (`round: "new"`, вид `fixes` или
    `implementation`) или в текущий открытый раунд;
  - задачи в состоянии `DONE` не меняются;
  - `before` вставляет задачу перед ещё не начатой задачей;
  - зависимости не ссылаются вперёд;
  - задача-исправление ссылается на исходную через `fixes: "<taskId>"`.
- Если `DOCS` открытого раунда уже в работе, а в раунд добавляется новая
  работа, `DOCS` возвращается в `TODO`. Её незакоммиченные документы
  передаются первой добавленной задаче.
- Раунд закрывается коммитом своей `DOCS` вместе со сводкой. Закрытые раунды
  попадают в recovery только как сводки.

## 9. Приёмка и закрытие

Состояния результата (`scope.delivery`):

```text
IN_PROGRESS ──(все задачи DONE)──▶ READY_FOR_ACCEPTANCE
READY_FOR_ACCEPTANCE ──accept──▶ ACCEPTED
READY_FOR_ACCEPTANCE / ACCEPTED ──plan:extend──▶ IN_PROGRESS   (приёмка снимается)
ACCEPTED ──close──▶ scope NONE
```

- `accept --note "<слова пользователя>"` фиксирует приёмку служебным
  коммитом (роль `acceptance`). Scope остаётся открытым.
- Если пользователь нашёл дефекты, план расширяется новым раундом
  исправлений и возвращается в `IN_PROGRESS`. Закрывать план и начинать
  новый для этого не нужно: recovery ограничен по размеру
  (`WorkflowKitRecovery.md`).
- `close --scope <id> --note "<прямая команда пользователя>"` закрывает
  scope. Это возможно только из `ACCEPTED`, при чистом рабочем дереве и по
  отдельной прямой команде пользователя. Приёмка сама по себе такой
  командой не является. Kit записывает пустой план (`NONE`). Прежний план
  остаётся в родителе коммита закрытия, `lastClosed` хранит ссылку на него.
- `carryover --input <file.json>` по отдельному поручению переносит
  незавершённые задачи закрываемого scope в новый scope со ссылкой на
  исходный коммит. Принудительного закрытия незавершённого scope нет.

## 10. Блокировка и восстановление после сбоев

- `task:block --reason "<текст>"` переводит scope в `BLOCKED`. В этом
  состоянии разрешены обсуждение и диагностика, реализация — нет.
  `task:unblock` возвращает scope в `ACTIVE`.
- Если операция оборвалась, журнал транзакции остаётся в
  `.harness/workflow/local/transaction.json`. `status` показывает это.
  `repair` без аргументов выполняет пробный прогон и выдаёт `repairId` с
  одним из действий:
  - `finish-commit` — коммит подтверждён, остаётся завершить журнал;
  - `retry-commit` — повторить транзакцию с сохранением правок;
  - `projection` — перестроить читаемую часть плана из JSON;
  - `defer-docs` — вернуть начатую `DOCS` в `TODO`, если в раунд добавлена
    работа.

  `repair --apply <id>` выполняет действие, `repair --cancel <id>` отменяет
  неподтверждённую подготовку коммита с сохранением правок. Если после
  подготовки изменились индекс или план, а HEAD прежний, `--cancel`
  восстанавливает индекс (`index-before`, иначе дерево HEAD) и исходный
  план из журнала, файлы рабочего дерева не трогает и убирает журнал;
  `--apply` в этом случае отвечает `REPAIR_MANUAL` и называет
  `repair --cancel <id>`. Если HEAD сдвинулся — `REPAIR_MANUAL` с
  `details {beforeHead, head}`: с согласия пользователя вернуть HEAD
  (`git reset --soft <beforeHead>`) и повторить `repair`.
- Подготовка коммита передаёт в `git add` пути из индекса и существующие
  неигнорируемые пути вне индекса. Удаление, уже подготовленное в индексе
  для игнорируемого или отсутствующего на диске пути (например,
  `git rm -r --cached node_modules` вместе с `node_modules/` в
  `.gitignore`), коммитится как есть.
- Пути, которых не будет в дереве коммита (`absentPaths`: вне индекса и
  нет на диске или игнорируются), проверки получают как `removed`: этап
  `prepare` до подготовки индекса, хук `pre-commit` — после. Проверки
  содержимого не читают их копии на диске, а `{files}` их не передаёт
  (`WorkflowKitQuality.md`, раздел 4).

## 11. Документация (гибридная политика)

- **Контракты модулей обновляются вместе с кодом.** Конфигурация профиля
  (`docs.contracts`) связывает пути кода с документами-контрактами. Пример
  для Harness:
  `product-parts/{part}/clusters/{cluster}/modules/{module}/src/**` →
  `.../modules/{module}/module.md`. Встроенная проверка `kit:docs-contracts`
  на этапе `commit` требует, чтобы при изменении кода в коммите был и его
  контракт. Исключение — задача с явным `docsWaiver: "<причина>"`.
- **Общие документы сверяются в `DOCS` раунда:** обзор, дерево продукта,
  README, индексы и архитектурные документы.
- **Временные спецификации** (`docs/planning/**`) после выпуска переносят
  действующее содержание в контракты модулей и удаляются. Незавершённые
  требования сохраняются.
- **Размер одного Markdown-документа** ограничен
  `budget.documentBytes` (по умолчанию 28 000 байт). Ограничение
  проверяется только для Markdown-документов, которые меняются в коммите.
  План и JSON дерева продукта в проверку не входят.

## 12. Выпуск

- Сборка, упаковка, подпись, публикация и push выполняются только в задачах
  `delivery`, явно перечисленных в плане. Задача `delivery` идёт после `DOCS`
  своего раунда, а её старт требует подтверждения пользователя.
- Задача `delivery` требует проверку вида `package` или `installed` с
  описанием проверяемого артефакта (`evidence`).
- `git push` разрешён, только если нет незавершённой транзакции, а у
  последнего раунда с завершённой работой закрыта `DOCS`.
