# M9: исправления старта сессий Kimi Code

## Цель и согласование

Живая проверка 0.6.0 на macOS (2026-11-10, проект F001) показала, что старт сессии Kimi
работает неправильно. Слова пользователя: «Я думаю, что нужно закрыть текущий план приняв
его и откроем новый, для замечаний, касающихся в первую очередь, конечно же, провайдера
Кими.» и «В общем, прям при старте что-то сильно неправильно работает с провайдером Kimi
Code.» Цель — чтобы сессия Kimi, созданная из панели, сразу была видна в приложении Kimi
Code с первым сообщением и ответом, а хуки Kit в ней срабатывали. Выпуск — 0.6.1.

## 1. Что показала диагностика

Данные — файлы `~/.kimi-code` и ответы серверов Kimi (только чтение), опыт — на
отдельном `KIMI_CODE_HOME` в скретч-каталоге.

1. **Два сервера.** Приложение Kimi Code (2.5.1) держит свой сервер внутри процесса
   приложения (запись в `server/instances`, порт 127.0.0.1). Kit запустил второй —
   `kimi web` 2.5.2. Оба принимают токен из `server.token`.
2. **Две рабочие области одной папки.** Kit создал область `wm_64d4…` в 09:02:12 и в ней
   сессию «F001»; первое сообщение доставлено, агент ответил («Здравствуйте! Проект готов
   к работе…»). Через 3,5 с приложение, открытое ссылкой `kimi-code://open?root=…`,
   создало свою область `wm_845c…` для той же папки: о чужой области его интерфейс не
   знал. Проект F001 в приложении — это его область, сессии Kit в нём нет; задание
   пользователя ушло в новую сессию приложения. Ответ П «видит ли приложение ход сервера
   Kit» — **нет**.
3. **Хуки не сработали ни в одной сессии.** Сервер Kit запущен в 09:02:11.99 (шаг
   доверия), хук Kit записан в `config.toml` в 09:02:12.13, приложение запущено в 10:01:33.
   Опыт на стенде: сервер Kimi берёт хуки **только при своём запуске**; после создания
   сессии `GET /api/v1/config` уже показывает новые хуки, но они не выполняются.
   `syncServer` сравнивал файл с `GET /api/v1/config`, решил, что сервер их знает, и не
   перезапустил его. Журнал хуков проекта пуст, панель: «Агент ещё не присылал хуков».
   Ответ П «подхват `config.toml` без перезапуска» — **нет**.
4. **`wfk session plan` без хуков.** Служба ищет сессию с идущим ходом только по каналу;
   без хуков канал о ходе не знает, хотя замок хода `locks/sessions/<id>` был.
5. **Клик по сессии.** Ссылка ведёт на проект (`root`); при двух областях приложение
   открывает не ту, где сессия.

## 2. Решение

### 2.1. Один сервер: сервер приложения, если оно работает

- `provider-kimi/src/server.ts`: сервер приложения — запись `server/instances` с живым
  pid, не процесс Kit (не запись учёта процессов с `SERVER_OWNER`), `host` 127.0.0.1,
  `healthz` отвечает, `meta.backend` = `v2`, версия строки 2.5 (2.5.1 допустима для
  сервера приложения; иная — как сейчас: пометка «не проверялась»). Из нескольких —
  самый поздний `started_at`.
- `current()` / `ensure()`: работает сервер приложения → все запросы (область, доверие,
  сессии, сообщения, список, имя, архив, удаление, ответ) идут на него; свой сервер Kit
  не запускается. Нет его — свой сервер, как сейчас.
- Приложение запустилось, пока работает сервер Kit: `maintain()` переводит работу на
  сервер приложения и останавливает свой, когда у сессий сервера Kit нет живых замков
  ходов; иначе ждёт следующего обслуживания. Приложение закрылось — следующий запрос
  запускает свой сервер.
- Remote Control при сервере приложения: действия `kimi-remote`, `kimi-remote-off` и
  `restart-kimi-server` выключены с причиной «сервер ведёт приложение Kimi Code»;
  `links.mobile` — адрес Remote Control сервера приложения, если он включён (только
  чтение). Kit не меняет Remote Control и вход приложения.
- Статус: `details.server` — `app`, `kit` или `null`; `note` называет, чей сервер.
- Область для новой сессии создаётся через сервер приложения: его интерфейс узнаёт её
  сам, ссылка `kimi-code://open?root=…` открывает её без новой области (П, проверяет
  пользователь). Уже созданные дубли областей Kit не удаляет.

### 2.2. Хуки действительно работают

- Свой сервер: перед запуском Kit читает `config.toml` и запоминает отпечаток блоков
  Kit, с которыми сервер стартует. `syncServer` сравнивает текущие блоки Kit в файле с
  этим отпечатком (не с `GET /api/v1/config`); разные — перезапуск, когда у его сессий
  нет живых замков. `approveHooks` и `remove` перезапускают сразу; `requireReady()`
  (создание сессии, доставка) сначала делает `syncServer`, поэтому первая сессия после
  мастера стартует уже с хуком.
- Сервер приложения Kit не перезапускает. Если блоков Kit не было при запуске
  приложения (`started_at` его записи раньше записи хука Kit; время записи Kit хранит в
  `sessions/kimi-hook.json`, без записи — время изменения `config.toml`), то статус
  провайдера, шаг хука в мастере и сессии проекта получают пометку `APP_RESTART_NOTE`:
  «Перезапустите приложение Kimi Code: хук Kit заработает в его сессиях только после
  перезапуска; до этого автопилот и ревью в них не работают».

### 2.3. `wfk session title|plan` без хуков

`session-titles`: если по каналу идущего хода нет, служба берёт сессии проекта из
списков провайдеров с `state: 'running'` (у Kimi — живой замок хода). Одна такая —
она; иначе прежний ответ 409 `session-ambiguous` с кандидатами. `cli` передаёт этот
список (`runningListed(projectId)`).

## 3. Поведение на ОС

| Что | macOS | Linux | Windows (x64, ARM64) |
| --- | --- | --- | --- |
| Сервер приложения | запись `~/.kimi-code/server/instances`, процесс `Kimi Code.app` | то же, если приложение или чужой `kimi web` запущены | то же в `%USERPROFILE%\.kimi-code` |
| Живой pid записи | `process.kill(pid, 0)` через `holderAlive` | то же | то же |
| Хуки сервера Kit | отпечаток блоков при запуске, перезапуск | то же | то же |
| Пометка о перезапуске приложения | есть | есть, если сервер чужой | есть |
| `wfk session` по замку хода | одинаково | одинаково | одинаково |

Отличий по ОС в решении нет: пути — через `kimiPaths`, платформа — параметром. Новых
вызовов программ одной ОС нет. Вживую — только macOS.

## 4. Проверка

- Тесты `provider-kimi`: подставной «сервер приложения» в `server/instances` —
  сессия, первое сообщение и список идут через него, свой сервер не запускается;
  приложение появилось при сервере Kit — переход после конца хода; приложение
  закрылось — свой сервер; хук записан после запуска сервера Kit — перезапуск по
  отпечатку, а `GET /api/v1/config` с новыми хуками перезапуск не отменяет; пометка
  `APP_RESTART_NOTE`; ветки `win32` и `linux` — с подставленной платформой.
- Тесты `session-titles` и `cli`: ход без хуков находится по списку провайдера.
- Сценарный тест: мастер при работающем приложении — область и сессия на сервере
  приложения, первое сообщение доставлено.
- CI: macOS, Linux, Windows x64 и ARM64.
- Живая проверка (macOS, пользователь): новый проект с Kimi при открытом приложении —
  сессия сразу видна в приложении с первым сообщением и ответом, области не
  дублируются; пометка о перезапуске; после перезапуска приложения — хуки, автопилот,
  `wfk session plan`. Windows — проверяющий на Windows; Linux — только CI.

## 5. Границы

## 7. Уточнения реализации

- Сервер, подхваченный после перезапуска службы, сверяется по времени: `started_at` его
  записи против `changedAt` из `sessions/kimi-hook.json`; отпечаток — только у сервера,
  запущенного этой службой.
- Для блоков Kit, записанных до 0.6.1, время — изменение `config.toml` при первой проверке;
  оно сохраняется, и позднейшие правки файла приложением пометку не вызывают.
- «Сервер приложения» — любая живая чужая запись `server/instances`, отвечающая на
  `healthz` (ответ хранится 5 с), в том числе `kimi web` пользователя. Свой сервер Kit
  останавливает, когда все живые замки ходов принадлежат процессу приложения.
- Описание серверов вынесено в `provider-kimi/server.md`.

## 8. Раунд исправлений R2 (живая проверка 0.6.1)

Слова пользователя: «Клик по сессии в дереве проекта Workflow Kit открывает пустую сессию в
проекте Kimi Code, а не созданную для работы… Поищи, как это исправить» и «Трогаешь и
ложную пометку… можешь уже начинать. Просто не собирай пока новый релиз».

### 8.1. Открытие проекта без пустого чата

- Факт (код приложения Kimi Code 1.3.2, сервер 2.5.1): ссылка `kimi-code://open?root=…`
  всегда открывает проект **с новым чатом** — параметр `new` не учитывается. Параметр
  запуска `--workspace=<папка>` открывает проект без нового чата; уже открытое приложение
  получает его от второй копии (одна копия на машину). Проверено пользователем: команда
  `open -n -a "Kimi Code" --args --workspace=<папка>` открыла нужный проект и сессию. Ссылки
  на конкретную сессию у приложения нет.
- `provider-kimi/src/app-link.ts`: `kimiWorkspaceCommand(check, folder)` → команда или
  `null`. macOS: `open -n -a <путь Kimi Code.app> --args --workspace=<папка>`. Windows: путь
  `Kimi Code.exe` из значения `shell\open\command` ключа обработчика `kimi-code`
  (`reg query … /ve`), запуск без ожидания: PowerShell `Start-Process` с аргументом
  `--workspace="<папка>"`. Linux: `null` (приложения нет).
- `cli/src/open-link.ts`: ссылка проекта Kimi без `new=1` открывается этой командой; нет
  команды или она не удалась — прежняя ссылка.
- `panel-shell`: клик по карточке сессии Kimi на компьютере (не сенсорный экран) идёт через
  `POST /api/open-link`, а не через переход по ссылке; отказ службы — переход по ссылке.

### 8.2. Ложная пометка о перезапуске и потерянный сервер Kit

- Факт: `kimi web` после запуска переименовывает свой процесс (`ps` показывает
  `kimi-code`). Учёт процессов сверяет командную строку, поэтому после перезапуска службы
  `reconcile()` удалял запись сервера Kit, а сам сервер оставался работать «чужим». Он был
  запущен до записи хука, и `appRestart()` (любой чужой сервер старше хука) давал ложную
  пометку, хотя приложение было перезапущено.
- `process-supervisor`: `SpawnSpec.renames` — процесс меняет своё имя; запись хранит
  `renames: true`, и такую запись (и её остановку) узнаёт по времени запуска (`startToken`)
  без сравнения командной строки. `provider-kimi` запускает сервер с `renames: true`.
- `appRestart()` смотрит только на сервер, с которым Kit работает (`server.app()`), а не
  на все чужие записи.
- Серверы, потерянные версиями 0.6.0 и 0.6.1, этим не находятся: их запись уже удалена (на
  машине пользователя такой сервер остановлен вручную).

### 8.3. Поведение на ОС (R2)

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Открытие проекта | `open -n -a <Kimi Code.app> --args --workspace=` | ссылка `xdg-open`, как раньше | `Start-Process <Kimi Code.exe> --workspace="…"` (**П**) |
| Запись процесса, меняющего имя | по `startToken` (`ps`) | то же | то же (CIM `CreationDate`) |
