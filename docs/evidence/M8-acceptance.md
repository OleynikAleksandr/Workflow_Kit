- CI, первый запуск (коммит `4c0e9d2`, ветка `ci/m8-kimi-provider`,
  [запуск 42774649237](https://github.com/OleynikAleksandr/Workflow_Kit/actions/runs/42774649237)):
  macOS ARM64, Linux x64 и Windows x64 — успех; Windows ARM64 — оба сценарных теста Kimi
  прошли, но процесс тестов не завершился до предела 20 минут. Причина: `app.stop()` не
  снимал ежеминутное обслуживание провайдеров, и оно заново запускало подставной сервер
  Kimi уже закрытого теста (проявляется, когда файл сценариев идёт дольше минуты;
  воспроизведено на macOS под нагрузкой). Исправлено в релизном коммите:
  `lifecycle.stop()` в `cli` и отказ закрытой подставной машины запускать серверы.
- CI, релизный коммит `5c2b1f5` в ветке `ci/m8-kimi-provider`,
  [запуск 42779716378](https://github.com/OleynikAleksandr/Workflow_Kit/actions/runs/42779716378) —
  успех на macOS ARM64, Linux x64, Windows x64 и Windows ARM64 (typecheck, тесты,
  `check:platforms`). После коммита 0.6.0 переустановлен из него: `wfk doctor --installed` —
  «всё в порядке».

## Не проверено (**П**)

- Код `40932` (сессию держит другой сервер) на практике и перезагрузка сессии после него.
- Видит ли приложение Kimi Code ход, который ведёт сервер Kit, без перезапуска приложения.
- Приложение Kimi Code 2.5.1 и CLI 2.5.2 на одном каталоге `~/.kimi-code`.
- Подхват изменённого `config.toml` приложением и открытыми `kimi` без их перезапуска.
- `Stop` при выключенных замках сессий (`KIMI_CODE_SESSION_LOCK=false`).
- Реальные ответы Remote Control (в тестах — схема из OpenAPI Kimi) и разбор параметра
  `root` ссылки приложением Kimi Code.
- Kimi Code на Windows и Linux вживую: пути, `kimi.exe`, оболочка хука, обработчик ссылки.
