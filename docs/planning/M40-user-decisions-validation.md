# M40: проверка

Часть [спецификации M40](M40-user-decisions.md); контракт —
[решения пользователя](M40-user-decisions-contract.md).

## 1. По задачам

- **T001.** В режиме `host` каждая команда решения без билета даёт `USER_DECISION_REQUIRED`,
  не меняет план и создаёт запрос с параметрами по таблице контракта; повтор с тем же входом
  возвращает тот же `id`, другой вход помечает прежний `stale`. `status` отдаёт только
  воспроизводимые запросы `pending`; подложенная запись не выдаётся. Операция с билетом
  записывает решение с `decisionId` и источником; билет другого корня, ревизии, `id` или
  дайджеста — отказ; изменённые данные — `DECISION_STALE`; повтор применённого
  `decisionId` — `already: true` без второй записи. `quality:apply --decision` применяет
  сохранённый вход: правка файла после регистрации запроса ничего не меняет, повторный
  `quality:apply` с другим входом заменяет запрос, старый `id` даёт `DECISION_STALE`.
  Операция с `runId` и источником `grant` проверяет живое разрешение scope (отозванное,
  чужое, не покрывающее действие — отказы M39) и записывает источник `grant` с `runId`;
  `task:start` delivery под живым разрешением записывает подтверждение с источником `grant`. `scope:choose` проверяет поколение и дайджест предложения до появления
  scope. `task:start` delivery без флагов стартует задачу, покрытую живым разрешением.
  Режим `agent` и отсутствие ключа ведут себя как Kit 2.3.3 (тесты M39 проходят без
  изменений). Сравнение корня `win32`/`linux` — с внедрённой платформой.
- **T002.** `pre-push` по целевым refs, stdin `\n` и `\r\n`: `HEAD:main`, другая локальная
  ветка в `main`, несколько refs одним push (один запрещённый отклоняет весь push), ветка
  публикации при открытом и закрытом scope; ветка CI: объявленная `automation.ci.task`
  TODO, IN_PROGRESS, DONE; посторонняя delivery IN_PROGRESS при объявленной задаче CI —
  отказ; `automation.ci` без `task` — до и после завершения всех задач; план без
  `automation`; удаление ветки; прочие ветки. Внешний коммит (`--no-verify`) отклоняет
  `task:start`, `commit`, `accept`, `close`; `commits:adopt` с точным списком снимает отказ,
  новый внешний коммит после показа карточки — `DECISION_STALE`.
- **T003.** `TASK_FILES_OUTSIDE` и снятие через `task:update`; задача без `files`;
  preexisting и управляемые файлы. `INPUT_LOCATION` для файла в проекте вне
  `.harness/inputs/`, файл вне проекта проходит; пути `win32` с другим регистром,
  разделителями и коротким именем — с внедрённой платформой и путями, которых нет ни на
  одной ОС.
- **T004.** Сгенерированные раздел Kit и recovery в режиме `host` не содержат
  `--confirmed`, `--autopilot-run`, `accept --note`, `close --note`, `task:unblock` как
  поручений агенту; в режиме `agent` совпадают с Kit 2.3.3 по смыслу.
- **T005.** Источник решения по контракту, раздел 3, на поколении хода канала: сообщение
  текущего хода — решение записано, примечание из сообщения; пользовательский ход → Stop с
  `block` → автоматический ход автопилота → `wfk decision` отклонён; то же после
  напоминания и после доставки замечаний ревью; сообщение панели в очереди во время предыдущего хода —
  отказ, после доставки в новом ходе — принято; повтор того же текста в старом ходе, старый
  ход, служебное сообщение, провайдер без привязки — `decision-source-missing` без записи;
  второе решение по тому же сообщению — отказ. Идемпотентность по разделу 4: двойной запрос
  и двойное нажатие дают одну запись в истории Kit; потерянный ответ (сбой между вызовом
  Kit и записью результата) сверяется по `decisionId`; перезапуск службы с записью `issued`.
  Служба читает `decisions` из `status` и публикует их в состоянии панели. Кнопки приёмки,
  закрытия, выбора режима и подтверждения поставки для `host` идут операциями хоста, для
  Kit 2.3.x — прежними формами; кнопка со старым дайджестом — `DECISION_STALE`.
  Подтверждение поставки стартует задачу до сообщения агенту. Решения запуска автопилота
  (выбор режима, приёмка, закрытие) идут с источником `grant`: не потребляют сообщение,
  проверяют паузу, остановку и отзыв перед билетом, повтор шага после перезапуска не
  создаёт второго решения (квитанция или применённый `decisionId`).
- **T006.** «Стоп», «Stop.», «пауза, посмотрю» останавливают или ставят на паузу при
  получении сообщения; «а когда стоп?» — нет (первое слово другое); сообщение не владельцу
  запуска и сообщение без живого запуска ничего не меняют. Сообщение панели «стоп» при
  занятом агенте (сообщение в очереди, не доставлено) останавливает запуск сразу: после
  конца хода продолжение не отправляется. «Стоп» перед автоматической приёмкой и перед
  публикацией: приёмка, закрытие и push не выполняются. Начатое действие заканчивается с
  записью результата.
- **T007.** Таблица раздела 2.3 спецификации — по строке на тест; `--authorized` с любым
  значением даёт тот же результат, что без флага; сообщение из очереди и старого хода не
  запускает подготовку.
- **T008.** Карточки `unblock`, `approve-install`, `adopt-commits` строятся по запросам из
  состояния панели и по кнопке записывают решение; клавиатура и `aria` как у существующих
  карточек; светлая и тёмная темы. Создание проекта и «Обновить Kit» на Kit ≥ 2.4.0 ставят
  `decisions: host`; раздел панели без `--authorized`.

## 2. Сквозные сценарии (T009)

На одноразовых проектах во временной папке, с настоящим bundle Kit из исходников и настоящей
службой на свободном порту; агент — тестовый (выполняет команды по сценарию отдельным
процессом), провайдеры не нужны; результаты CI задаются сценарием (без GitHub), `origin` —
локальный bare-репозиторий.

1. **Полный проход `host` под автопилотом.** Settings `full`, ревью выключено, проект
   `decisions: host`: сообщение пользователя → `wfk session plan` (запуск без карточки) →
   `scope:propose` → автоматический выбор режима операцией хоста с дайджестом предложения →
   задачи → delivery по живому разрешению без флагов → CI → автоматическая приёмка →
   закрытие → публикация → SHA в `origin` совпал. После каждого этапа проверяется записанное
   состояние: журнал запуска, история Kit с `decisionId` и источником, состояние scope.
   В истории выбор режима, старт delivery, приёмка и закрытие имеют источник `grant` с
   `runId` запуска; источников `button` и `message` нет; исходное сообщение пользователя
   использовано один раз — для регистрации запуска. Отзыв разрешения перед приёмкой
   (отдельный прогон) останавливает проход без приёмки.
2. **Полный проход `host` вручную.** Settings `off`: кнопки выбора режима, подтверждения
   поставки (задачу стартует служба), приёмки и закрытия — операциями хоста; в истории Kit
   источник `button`; публикация после закрытия проходит `pre-push`.
3. **Отказ из терминала агента.** Отдельный процесс вызывает `accept --note "…"` →
   `USER_DECISION_REQUIRED`, в состоянии панели появляется карточка приёмки без сообщения
   агента. `wfk decision accept` после сообщения пользователя → принято, примечание — текст
   сообщения; без сообщения → `decision-source-missing`.
4. **Вопрос о плане.** Сообщение `Workflow Kit:` + `wfk session plan` в новом ходе →
   карточка; Settings `off` → карточка.
5. **Согласование установки.** `quality:apply` с установкой → карточка с точными командами.
   Агент правит файл входа, не вызывая команду → кнопка применяет сохранённый вход,
   показанный на карточке. Агент повторно вызывает `quality:apply` с другим входом → старая
   кнопка даёт `DECISION_STALE`, появляется новая карточка с новыми командами.
6. **Устаревшее решение.** Предложение изменено после показа карточки выбора → старая
   кнопка отклонена; решение по сообщению прошлого хода, по сообщению из очереди и после
   автоматического продолжения (Stop с `block`) отклонено;
   двойное нажатие и потерянный ответ дают одну запись.
7. **Барьеры Git.** `git push origin HEAD:main` при открытом scope → `PUBLISH_SCOPE_OPEN`;
   push ветки CI во время посторонней delivery → `CI_PUSH_NOT_ALLOWED`; `git commit
   --no-verify` → `EXTERNAL_COMMITS`, карточка `adopt-commits` → снято.
8. **«Стоп».** Сообщение панели «стоп» во время хода занятого агента → запуск остановлен
   сразу, продолжение после конца хода не отправлено. «Стоп» после завершения задач, перед
   автоматической приёмкой → приёмки, закрытия и публикации нет.
9. **Регрессия Kit 2.3.3.** Проект с сохранённым bundle 2.3.3 и новой службой: ручные
   формы `accept --note` и `--confirmed` проходят, кнопки панели работают прежними
   маршрутами; сквозной тест M39 (`lifecycle-real`) проходит на новом ядре в режиме `agent`.

Каждый сценарий — отдельный тест; таблица «сценарий → тест → результат» и что не проверено
записываются в `docs/evidence/M40-acceptance.md`.

## 3. Поставка и CI

- T010: `npm run build`, установка 0.16.0, проверка `installed-service` (версия службы,
  ответ `/api/health`, bundle Kit 2.4.3 в установленном приложении).
- T011: push в `ci/M40-user-decisions`, обязательные задания `macOS ARM64`, `Linux x64`,
  `Windows x64`, `Windows ARM64` для точного SHA. Красный CI — `task:defer-delivery` и раунд
  исправлений, как в M39; результат CI записывается вне git.

## 4. Живые проверки

Обязательных ручных проверок нет. После публикации пользователь может проверить на macOS:
полный автопилот на новом проекте без карточки вопроса, карточки решений, «стоп» в чате.
Windows — проверяющий на Windows, Linux — только CI. Эти проверки необязательны и
записываются отдельно.

## 5. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Тесты задач T001–T008 | запуск на этой ОС в CI и локально | запуск в CI | запуск в CI, x64 и ARM64 |
| Ветки путей `win32` и `linux` | тесты с внедрённой платформой и путями, которых нет ни на одной ОС | то же | то же |
| Сквозные сценарии T009 | временная папка, свободный порт, локальный bare-репозиторий | то же | то же; удаление временных папок с повторами (`maxRetries`) |

Проверки одинаковы на всех ОС. Что и где различается в поведении —
[спецификация, раздел 5](M40-user-decisions.md#5-поведение-на-ос).
