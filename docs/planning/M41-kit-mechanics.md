# M41: механику выполняет Kit (заготовка)

Заготовка второго scope, согласованного 17.11.2026 вместе с
[M40](M40-user-decisions.md). Спецификация пишется после M40; здесь — найденное аудитом,
чтобы ничего не потерялось.

## Механика, которую Kit знает сам

- CI: Kit пушит `ci/<scope>`, ждёт обязательные задания, записывает доказательства и при
  красном CI сам откладывает поставку; приёмка требует зелёного CI точного SHA. Ранний CI
  до конца раунда. Сейчас это делает агент через `gh` и `wfk session progress`.
- Автопилот стартует задачу сам (`task:start`) и называет её агенту; первая задача
  последовательного запуска вместо заготовки `<ID>`; после перезапуска службы — конкретный
  шаг, а не «run recover».
- Оркестрация: `assignment:create` создаёт worktree для Codex и Kimi; `assignment:attach`
  выполняет setup и старт единственной задачи; `integration:start` без `--source`
  (Kit знает SHA исполнителя); тексты оркестратора по клиенту, а не «Claude subagent».
- Лишние аргументы: `--expected-revision` для агента, `<ID>` у `task:defer-delivery` и
  `commit --task`, `--scope` у `close`, `--id` у `integration:continue`.
- `repair`: безопасные случаи (`finish-commit`, `projection`, повтор коммита) Kit
  выполняет сам при следующей команде.
- `quality:apply --detected` вместо ручного копирования профиля; `--input -` (stdin);
  текст схемы в каждом отказе проверки входа.
- Recovery: один снимок на событие SessionStart (одинаковый дайджест частей), итоговая
  строка «complete N/N»; пакет recovery для Kimi.
- Ревью: задачи плана ревьюеру выдаёт Kit (`scope:proposal --tasks`), а не пересказ агента.
- Заголовок сессии: служба ставит временный заголовок из первого сообщения пользователя.
- Вопрос о плане: служба не открывает его повторно, если есть предложение, scope или ответ.
- Ожидание проверки после выбора режима без лишнего хода агента; ворота `task:start` до
  отметки хоста «план запущен».

## Противоречия текстов

- Два управляемых раздела `AGENTS.md` по-разному описывают публикацию, автопилот, выбор
  режима и «не спрашивай, продолжать ли».
- `plan:extend --expected-revision <N>` в шаблоне как обязательный, в CLI — необязательный.
- Три разных списка команд исполнителя; шаг `assignment:setup` есть не везде.
- `wfk session run` и `wfk session progress` нет в общей справке `wfk`.
- «Пакет приходит при старте» неверно для Kimi.
- Смешанный язык служебных текстов агенту.
- Найдено в M40 (T009): продолжение delivery под запуском (`decide-orchestration.ts` службы,
  `autopilot-decision.ts` Kit) называет `task:start <ID> --autopilot-run <run>`, хотя живое
  разрешение покрывает задачу и без флага.

## Найдено в M40, вне текстов

- Сообщение, уже использованное для `wfk decision`, ещё может зарегистрировать запуск
  полного автопилота (`wfk session plan`): журнал запусков не читает журнал решений.
- Барьер коммитов в обход Kit верит трейлеру `Workflow-Transaction`; подделанный трейлер он
  не распознаёт.
- Повторное нажатие кнопки приёмки без запроса Kit получает `NOT_READY` вместо `already: true`.

## Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Каждая позиция перечня | должна работать | должна работать | должна работать, x64 и ARM64 |

Это заготовка: точная таблица по позициям появится в спецификации M41. Позиции с
процессами, путями и git (push CI-ветки, worktree, `repair`) получат разбор рисков Windows
до плана.
