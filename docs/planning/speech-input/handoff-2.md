Существенные ограничения:

## 7. Минимальная архитектура

Предлагаются три логические части. Конкретные каталоги согласовать с текущей структурой product-parts/clusters/modules, сохранив публичные фасады.

| Часть | Ответственность |
|---|---|
| speech-input, браузерный модуль | Микрофон, PCM, кнопка, состояние диктовки, доставка текста владельцу поля |
| speech-service, локальный backend | Каталог, загрузки, выбор модели, единственный активный поток, связь с helper |
| speech-helper, нативный исполняемый файл | transcribe.cpp, Metal/CPU, загрузка модели, feed/finalize/reset |

Поток данных:

    Микрофон браузера → PCM → speech-service → speech-helper
    speech-helper → текст потока → speech-service → черновик поля

Нативная библиотека не загружается в процесс Node. Сбой Metal/движка не должен завершать Kit.

Отдельный локальный HTTP-сервер на случайном дополнительном порту не нужен. Использовать сервер Kit и его жизненный цикл. Worker получает только stdio и не открывает собственный сетевой порт.

Для первой версии не строить универсальную платформу плагинов STT. Достаточно одного адаптера runtime с проверкой capabilities и каталога, который способен описывать поддерживаемые движком модели.

### 7.1. Примерные контракты модулей

Это проектные интерфейсы, не существующие API:

- speech-input: attach к владельцу textarea, start, stop, cancel, dispose, состояние blockingSend.
- speech-service: status, listModels, download/cancelDownload, selectModel, removeManagedModel, begin/feed/finalize/cancel, shutdown.
- speech-helper: handshake с protocolVersion, load, begin, feed, finalize, reset/exit.

Владелец поля отвечает за текст, draftRevision, отправку и сохранение черновика. Модуль speech-input не знает внутреннюю логику провайдера, очереди или ответа на вопрос.

## 8. Захват микрофона

### 8.1. Предпочтительный путь для существующей web-panel

Использовать getUserMedia({audio: ...}) и AudioWorklet. Это позволяет получить микрофон именно той машины, где открыт интерфейс, и работать с привычными разрешениями браузера.

Для первого выпуска ограничить проверяемый сценарий локальной панелью на Mac, открытой через localhost/loopback. Удалённый доступ к Kit через Tailscale не объявлять поддержанным сценарием диктовки без отдельной проверки secure context и выбора источника звука.

Порядок начала:

1. Заблокировать повторный start и зафиксировать владельца поля.
2. Проверить выбранную модель, доступность helper и право владения диктовкой.
3. Подготовить модель; показать «Подготовка…».
4. Получить/активировать AudioContext и разрешение микрофона в рамках допустимых browser user-gesture правил.
5. Создать поток движка и обработчик аудио.
6. Только после готовности всех частей включить передачу и состояние «Слушаю».

Фактический порядок getUserMedia/AudioContext/load можно уточнить из-за ограничений Safari. Обязательный инвариант: **не показывать «Слушаю», когда звук ещё не принимается**, и не терять первые слова из-за незагруженной модели.

Разрешение, пришедшее после отмены старта, должно немедленно освобождать полученные tracks.

### 8.2. Формат и обработка

- Получать фактическую sampleRate AudioContext; нельзя считать её равной 16 kHz.
- Приводить к одному каналу.
- Выполнять корректный непрерывный resampling в 16 kHz с сохранением состояния между блоками.
- Передавать float32 little-endian; проверять конечность чисел и допустимый размер.
- Не отправлять WebM/Opus из MediaRecorder в API, ожидающий PCM.
- Не нормализовать/усиливать каждый короткий блок независимо: это меняет речь и шум.
- Не вырезать паузы из нативного stream произвольно: модели может требоваться непрерывная временная шкала.
- VAD не нужен для определения Stop: запись управляется кнопкой.
- Выбирать echoCancellation/noiseSuppression/autoGainControl после проверки качества; не обещать, что любой набор улучшает русскую диктовку.
- AudioWorklet должен передавать данные через bounded queue и не выполнять тяжёлый inference в аудиопотоке.

Размер блока выбрать экспериментально. Отправная точка проверки — пакеты порядка 100–250 ms при независимой настройке model delay. Если runtime эффективнее работает с другими блоками, принять измеренный вариант. Не приравнивать размер транспортного пакета к минимальной задержке модели.

### 8.3. Освобождение ресурсов

На Stop, Cancel, ошибку, закрытие панели и shutdown:

- остановить MediaStreamTrack;
- снять обработчики;
- отключить worklet;
- закрыть или корректно освободить AudioContext;
- закончить или отменить поток движка;
- снять владение активной диктовкой.

Остановка записи должна происходить сразу по нажатию, а не после длительного finalize.

### 8.4. Альтернатива: нативный захват

Handy использует нативный аудиостек, включая handy-recorder. Его можно адаптировать, если фактический desktop shell Kit делает браузерный захват неудобным.

Но это отдельное решение: потребуются macOS microphone usage description, TCC-разрешения для правильно упакованного приложения и понимание, чей микрофон используется. Не реализовывать browser capture и native capture одновременно «на всякий случай».

В первичном spike выбрать один путь и подтвердить его на способе запуска пользователя.

## 9. Транспорт и границы доступа

### 9.1. Browser ↔ Kit

Рекомендуемый путь: один same-origin WebSocket на существующем сервере Kit.

Пример маршрута, подлежащий согласованию:

    /api/speech/stream

Управляющие сообщения — небольшой JSON. Аудиоблоки — binary frames. При необходимости добавить маленькую поддерживаемую WebSocket-зависимость; сначала проверить актуальные зависимости проекта. Не писать собственный неполный RFC 6455 сервер ради отсутствия одной библиотеки.

Каталог, настройки и команды загрузки модели могут оставаться обычным JSON HTTP API. Прогресс загрузки можно получать существующим механизмом обновления UI или редким polling; отдельная шина событий не требуется.

Почему не использовать существующий shell.api для PCM: он буферизует JSON, ожидает конечный JSON-ответ и имеет неподходящий таймаут.

### 9.2. Минимальная семантика протокола

Пример имён, не готовая спецификация библиотеки:

| Направление | Сообщение | Смысл |
|---|---|---|
| UI → service | begin | Запрос активной диктовки с modelId и клиентским dictationId |
| service → UI | ready | Модель и поток готовы принимать звук |
| UI → service | binary audio | PCM с монотонным порядком блоков |
| service → UI | transcript | Снимок committed и tentative, eventSeq |
| UI → service | finish | Последний аудиоблок передан; завершить поток |
| service → UI | final | Итоговый снимок, снять блокировку отправки |
| UI → service | cancel | Немедленно перестать принимать результаты |
| service → UI | error / ended | Код причины, закрытие владения потоком |

Для binary audio зафиксировать небольшой header с номером блока или связать порядок с единственным контекстом соединения. Если используется application header, указать точные endian/offset/version в спецификации. Не смешивать аудио двух dictationId в одном неразмеченном потоке.

Событие transcript должно обозначать **снимок текста текущей диктовки**, а не двусмысленный «кусок для append». UI заменяет свой участок целиком. Это предотвращает повторение слов.

### 9.3. Проверка WebSocket upgrade

Upgrade не проходит обычную обработку JSON POST. Добавить отдельную проверку:

- разрешённый Host и ожидаемый порт;
- Origin строго соответствует панели Kit; отсутствие или null для браузерного соединения не принимать;
- допустимые localAddress/remoteAddress;
- первая конфигурация — только loopback для speech stream;
- допустимый путь;
- версия протокола;
- лимиты размера сообщений, частоты и очереди;
- один владелец активной диктовки.

Обычный GET в нынешнем checkAccess не требует Origin. Поэтому нельзя просто вызвать его как для GET и считать WebSocket защищённым от сторонней страницы.

Не менять политику доступа всего Kit ради этого маршрута. При будущей поддержке удалённой панели расширять speech-политику отдельно. User-Agent не является проверкой безопасности или доказательством платформы клиента.

Передавать события только владельцу соединения. Не включать аудио или промежуточный текст в общий broadcast состояния всем панелям.

### 9.4. Service ↔ helper

В Handy используется фрейминг:

    [u32 json_length LE][JSON UTF-8][u32 pcm_byte_length LE][PCM f32 LE]

Каждому запросу соответствует один ответ. В проверенной версии есть Hello, Load, Run, StreamBegin, Feed, Finalize, StreamReset; ответы Feed могут содержать StreamText с committed/tentative.

Если адаптируется этот код:

- добавить/зафиксировать собственную protocolVersion;
- читать поток инкрементально: один read не равен одному frame;
- сериализовать запросы, не перемешивать ответы;
- использовать малые обоснованные лимиты для live-блоков;
- обрабатывать неполный frame, EOF и остановку процесса;
- stdout резервировать для протокола, stderr — для диагностических сообщений;
- завершать worker при закрытии stdin и при shutdown Kit.

Не наследовать большой общий лимит donor-протокола как допустимый размер каждого browser frame. Допустимый объём live-аудио существенно меньше.

Node запускает helper напрямую через spawn с массивом аргументов, без shell и конкатенации пользовательских путей.
