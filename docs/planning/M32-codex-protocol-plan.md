# M32: проверка протокола до реализации

Часть [спецификации](M32-codex-history-recovery.md).

### 2.1. Проверка совместимости до реализации

T001 оформляет `docs/evidence/M32-codex-protocol.md`: версия CLI и подключённого сервера,
формы params/response, допустимые itemsView и семантика текста в summary, курсоры,
порядок, изменения текущего хода, terminal status, excludeTurns при resume.
Проверяются отдельно paginated и legacy истории, незагруженный тред и активный ход.
Живые проверки чтения выполняются только через публичный RPC без вывода содержимого
пользовательской переписки; подставные протокольные ответы — в тестовом сервере. Живые запросы к существующим
тредам ограничиваются чтением и выводом счётчиков/типов/id, без текстов.
Во временном CODEX_HOME без входа не предполагается генерация agentMessage.
Копирование auth.json и других учётных данных запрещено; реальные истории не читаются
напрямую с диска. При недостатке безопасных данных обязательная живая проба блокирует T001. Сессия пользователя не возобновляется и не прерывается ради пробы.
Результат различает schema-only, fake transport и live; недоступный live не заменяется
утверждением об успешной проверке. Результат нужен для решения о совместимости T002.

Базовый путь: `thread/read` только метаданные; `thread/turns/list` для состояния ходов;
`thread/items/list` для текста. Возможен путь через turns/list с itemsView=summary,
если проба доказала сохранение полного нужного текста и ограниченность служебных данных.
`itemsView=full` для целой истории запрещён. Возможности кэшируются на поколение сервера,
а не навсегда по версии CLI; явный unsupported отличается от сетевого сбоя.

Если старое хранилище не поддерживает items/list, использовать подтверждённый в T001
ограниченный turns/list путь. Если ни один путь не работает, вернуть понятный отказ
совместимости с сохранением уже показанной ленты. Нельзя молча вернуться к includeTurns=true,
читать внутреннюю базу/транскрипты Codex или объявить старые сессии поддержанными.
При отсутствии подходящего пути T001 НЕ коммитится как DONE: исполнитель вызывает
`scripts/workflow task:block --reason "<точная причина>"` и завершает ход. Пользователь
решает дальнейшее действие; task:unblock только после его решения, изменение задач —
через plan:extend, а refine применим к ещё неначатому предложению. Самостоятельного
автоматического перехода к следующей задаче или несуществующего повторного ревью нет.
Подходящий путь: ограниченный ответ, полный текст обычных сообщений до согласованной
обрезки 20 000 символов, рабочие курсоры paginated/legacy, отсутствие загрузки треда;
для большого output — ограниченный gap и видимые реплики по обе стороны в том же ходе (§2.3).


### Программа проб T001

- Проверить backwardsCursor с обратным sortDirection: повтор якоря и его обновления, отсутствие
  пропуска/дублирования при окончании хода; проверить отдельно turns и items.
  Для items/list проверить asc/desc при limit=1 и exclusive anchor внутри одного turnId.
  Проверить чтение изменяемого хвоста от последнего завершённого item без повторного
  скачивания всех завершённых outputs. itemsView во всех запросах задаётся явно.
- thread/loaded/list и runtime status до/после turns/list и items/list: notLoaded
  сохраняется, нет подписки/запуска хода. Статусы и счётчики разрешено выводить без текста.
- summary: сохранение user/agent text, большой успешный и упавший tool output,
  реплики по обе стороны большого output в том же ходе и продолжение новых ходов.
- deferOutput: сравнить схему с/без --experimental и требования experimentalApi;
  проверить ограничения turnId и failed commands, не выдавать наличие поля за поддержку.
- Поколение сервера: наблюдаемые pid + start identity (если есть), realpath цели сокета,
  initialize.userAgent. Отсутствующий pid/userAgent — unknown, не доказательство прежнего
  поколения. Координатор увеличивает локальный epoch только при сетевом сбое, не oversized/нормальном закрытии;
  одинаковая тройка после reconnect не восстанавливает доверие к старому снимку.

### Уровни доказательства и граница изменения плана

Обязательные живые доказательства T001 на доступном macOS-демоне: turns/list и items/list
на существующем треде, включая незагруженный; loaded/list и status до/после неизменны;
большой успешный и упавший output того размера, который Codex реально сохраняет,
с короткими репликами по обе стороны; двусторонний limit=1 и рабочие якоря.
Наблюдаемый размер записать в evidence; отдельный установленный предел хранения — только
если он доказан. Максимум в выбранной выборке не объявлять глобальным пределом Codex.
Поддержка paginated/legacy фиксируется отдельно: для каждой заявленной поддержанной
формы нужен живой ограниченный путь чтения. Schema-only описывает форму, fake проверяет
наш клиент, но не доказывает поведение сервера.

Обход непрочитанного элемента проверить против настоящего сервера с искусственно
пониженным пределом сообщения только в скрипте пробы (например, 1 МиБ). Выбрать предел
по фактическим размерам: соседние короткие сообщения и служебные ответы проходят,
страница limit=1 с целевым output — нет. Если сервер сохраняет меньше 1 МиБ, снизить
предел дальше; зафиксировать его в evidence. После реального отказа клиента по размеру
прочитать тот же ход с противоположной стороны, подтвердить доступность обеих реплик
и границ gap. Не подменять ответ сервера искусственным oversized: проба должна получить
настоящую страницу и отклонить её по заданному лимиту. Настройки сервера и рабочий
лимит транспорта Workflow Kit 16 МиБ не меняются.

Живой элемент >16 МиБ не обязателен: его отсутствие или обрезка Codex не блокируют T001.
Если такой элемент доступен, проверить дополнительно вживую; иначе сценарий >16 МиБ
остаётся обязательным на fake-сервере в T002a/T005. Для обхода oversized основание
блокировки — невозможность пройти вокруг элемента по настоящим якорям и сохранить обе
реплики, а не отсутствие вывода >16 МиБ. Другие обязательные live-факты сохраняются:
их отсутствие не выдаётся за DONE; нехватка фикстуры отличается от несовместимости.

Подготовку фикстуры рекомендуется завершить после ревью, до task:start T001: сначала
проверить наличие подходящей существующей сессии публичным read-only RPC. Если её нет,
заранее предложить пользователю отдельную тестовую сессию: короткий вопрос, большой
успешный и большой упавший вывод, короткий ответ. Требуется фактически сохранённый
вывод, а не заданные 16 МиБ. Подготовка не является условием одобрения этого плана.
Если T001 уже начата без необходимых данных, запросить фикстуру через task:block,
указав нехватку доказательства, а не дефект протокола. Читать фикстуру только через RPC.
Не копировать auth.json, не resume/interrupt пользовательские сессии, не создавать
генерирующий agentMessage ход без отдельного разрешения. Эта программа не требует
живого доказательства на недоступных Windows/Linux в T001: их проверки указаны отдельно.

Динамические обновления active item, terminal-переходы и backwardsCursor проверяются,
если наблюдаемы безопасным чтением, иначе честно pending. Консервативный вариант —
повторное чтение изменяемого хвоста от подтверждённого завершённого anchor с дедупликацией
и ограничениями общего бюджета. Если это не обеспечивает согласованные критерии
(включая отсутствие повторного скачивания завершённых outputs), T001 блокируется.
Последующие задачи используют механизм, подтверждённый T001; backwardsCursor не является
самостоятельным безусловным требованием. T001 может уточнить только факты, evidence
и выбор уже описанного варианта. Новые факты и результаты идут в evidence и этот
M32-codex-protocol-plan.md; в основную спецификацию — только ссылки. Её текущий размер
26 027 байт не позволяет накапливать там протокольные подробности. Разделять документы
внутри started task нельзя; новый перенос при необходимости — до task:start.
Изменять поведение или критерии прошедшего ревью плана
нельзя: противоречие факта любому критерию следующих задач — task:block, решение пользователя.

В docs/evidence/M32-codex-protocol.md хранить полный воспроизводимый скрипт пробы
в fenced code block, команды его извлечения во временный каталог и запуска, версии,
SHA, результаты/счётчики и уровень каждого доказательства. Скрипт использует публичный
RPC, не импортирует Kit runtime; новые исполняемые файлы репозитория в T001 не создаются.
Повтор запуска читает ту же фикстуру без изменения её состояния и без печати переписки.

## Результаты T001

Счётчики, скрипт и уровни доказательства — [M32-codex-protocol.md](../evidence/M32-codex-protocol.md);
codex-cli и сервер 0.169.0, 15.11.2026. Здесь факты и выбор уже описанных вариантов; согласованные
критерии следующих задач не меняются.

### Форма протокола (schema, подтверждена live)

- `thread/turns/list`: threadId, cursor, limit, sortDirection (по умолчанию desc), itemsView
  notLoaded | summary | full (по умолчанию summary, поэтому всегда задаётся явно). Ответ: data
  (Turn: id, status, items, itemsView, startedAt, completedAt), nextCursor, backwardsCursor.
- `thread/items/list`: threadId, turnId (без него — элементы всего треда), limit, sortDirection
  (по умолчанию asc), cursor — opaque-строка или исключающий якорь `{ type: 'item', itemId }`
  только вместе с turnId, deferOutput. Элемент ответа — `{ item, turnId, startedAtMs,
  completedAtMs }`; nextCursor, backwardsCursor.
- `Thread.historyMode`: legacy | paginated (по умолчанию legacy) выбирается при создании треда и
  приходит в `thread/read` без ходов. `thread/resume` принимает excludeTurns.
- backwardsCursor страницы при обратном sortDirection повторяет первый элемент этой страницы и
  продолжает в обратную сторону; так у ходов и у элементов.

### Наблюдения

- paginated: turns/list и items/list работают на notLoaded треде; loaded/list и статус до и после
  те же; порядок стабилен; limit=1 проходит ход целиком в обе стороны; якоря исключающие; чтение
  после якоря отдаёт только более новые элементы.
- legacy: items/list всегда -32601 «thread/items/list is not supported yet»; turns/list, курсоры и
  notLoaded как у paginated; itemsView=full содержит только userMessage и agentMessage, без
  выводов команд. На этом Mac legacy-тредов нет (26 тредов CLI 0.164–0.169 — paginated); legacy
  проверен на треде, созданном 0.169.0 во временном CODEX_HOME.
- Новый paginated тред до сохранения первого хода отвечает тем же -32601 у turns/list
  («list_turns is not supported yet») и items/list, includeTurns — тем же текстом ошибки; это не
  постоянная несовместимость.
- summary: первая userMessage и одна agentMessage хода (обычно финальная) с полным текстом;
  промежуточных реплик и commandExecution нет. Для ленты M18 этого мало.
- Вывод commandExecution хранится не длиннее 65 536 байт (300 000 → 65 536 для exit 0 и exit 3;
  в истории пользователя максимум тот же) — наблюдение 0.169.0, а не объявленный предел.
  Крупнейший элемент — userMessage 591 095 байт с тремя изображениями; страница 50 элементов —
  до 2,69 МБ; история 20,4 МБ. Изображения входят в байты транспорта, но не в текст ленты.
- Обход oversized на настоящем сервере: клиент отказывает по заголовку кадра, чтение с другой
  стороны по исключающим якорям даёт обе реплики; gap — один элемент или диапазон между двумя
  большими выводами (реплика между ними входит в диапазон). Среди упавших выводов пользователя с
  репликами по обе стороны нет крупнейшего в своём ходе, поэтому изоляция показана во временном
  сервере; на демоне у упавшего вывода проверены limit=1 и якоря.
- Активный ход: items/list отдаёт только завершённые элементы; изменения уже выданного элемента
  не наблюдалось. turns/list отстаёт от живого thread/read: новейшим бывает прежний ход; новый
  ход виден interrupted без items, пока thread/read показывает active и inProgress (в каждом из
  7 прогонов); бывает и inProgress при живом completed.
- deferOutput: в обычной схеме пустой объект; `commandExecution` требует experimentalApi (иначе
  -32600) и откладывает только успешные выводы (aggregatedOutput null); получить их можно
  экспериментальным thread/items/read. Наличие поля поддержкой не считается.
- resume с excludeTurns=true возвращает тред без ходов (paginated и legacy), без флага — все ходы.
- Идентичность: initialize отдаёт userAgent (с clientInfo клиента), codexHome, platformFamily,
  platformOs; pid и processIdentity.startSeconds — в daemon.pid; цель сокета — realpath.

### Выбор вариантов для следующих задач

- paginated — базовый путь §2.1: thread/read без ходов, turns/list с явным itemsView=notLoaded,
  items/list по turnId. summary, itemsView=full и deferOutput не используются.
- legacy — «ограниченный turns/list путь» §2.1, путь выбирается по historyMode из thread/read:
  turns/list с явным itemsView=full; страница ходов при отказе по размеру уменьшается до одного.
  Если и один ход больше предела — summary этого хода и gap-диапазон между его репликами; если
  больше и summary — gap хода с причиной `codex-history-item-too-large`. items/list и
  includeTurns=true для legacy не вызываются; другая форма ответа — отказ `codex-history-unsupported`.
- -32601 у paginated треда — ещё не сохранённая история: пустой хвост и повтор на следующем
  опросе, без отметки unsupported в кэше возможностей сервера.
- Хвост активного хода — консервативный вариант §2.2: asc от последнего подтверждённого
  завершённого item-якоря с дедупликацией по id; backwardsCursor не обязателен. Завершённые
  outputs не перечитываются; при terminal хвост дочитывается один раз.
- Снимок Stop (§2.4, interrupt.md): статус хода из turns/list сам по себе не доказывает
  завершения. Доказательство — событие turn/completed или terminal статус цели при thread/read
  не active. Сочетания active с terminal, idle с inProgress и новейший ход не цель — противоречие:
  перепроверка в пределах deadline, иначе unavailable/stale. Это уже согласованное правило о
  неатомарных чтениях, применённое к наблюдённому отставанию.
- Идентичность сервера для epoch и gaps — pid и startSeconds из daemon.pid, realpath цели,
  userAgent при своём clientInfo; отсутствующий признак — unknown.
- Байтовый бюджет и уменьшение страницы нужны и без больших выводов: изображения userMessage.

### Pending
