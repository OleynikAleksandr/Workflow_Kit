# Claude: прерывание текущего ответа (M24)

Часть [module.md](module.md); общий протокол —
[M24-turn-interruption](../../../../../../docs/design/M24-turn-interruption.md).

## Управление

`interrupt.ts` реализует Provider.interruptAvailability и interruptTurn. Capability включена
только при доступном pty. Во время штатного listSessions читаются маленькие локальные снимки
живых управляемых сессий; синхронная availability читает кэш, без RPC/чтения транскрипта.
Снимок старше 3,5 с, внешний/остановленный процесс, старая сессия без протокола, диалог и
неизвестный экран дают отказ с причиной. Поддерживаются локальный и Remote Control id.
Прерывание не возобновляет умерший процесс и не вызывает stopSession/kill.

## Host и файлы

Оба host используют `pty/interrupt-control.ts` и ограниченный TerminalScreen из #pty-host.
На macOS/Linux `session.exp` через `interrupt.tcl` запускает длинноживущий Node
`interrupt-worker.ts` (путь к текущему Node из WFK_PTY_NODE, удаляется из окружения Claude).
Сырой вывод передаётся по pipe в hex, совместимом со штатным Tcl 8.5 macOS. В stdout
помощника только DONE/ESC/FAILED; экран на диск не записывается. Перед Esc expect повторно
осушает доступный pty-вывод: любое изменение отменяет команду. На Windows x64/ARM64 runHost
получает onData ConPTY и проверяет тот же контроллер после чтения файла запроса.

Файлы рядом с debug, UTF-8 JSON с атомарной заменой (на POSIX mode 0600):

- `.interrupt-state`: version=1, epoch, state (working/idle/dialog/unknown), at;
- `.interrupt`: id (UUID), epoch, expires;
- `.interrupt-result`: id, status (interrupted/already-idle/unavailable/stale/timeout), reason?.

Состояние обновляется при штатном цикле host раз в секунду. Epoch содержит случайный id
процесса host и счётчик нового busy после idle/unknown. Несовпавший epoch не получает Esc.
Истёкший запрос тоже не получает клавиши. Helper не отвечает на разрешения: ни startup
диалоги M15, ни предложения функций после запуска, ни неизвестные экраны не обходятся.
Прежний M15-ответ «Not now» до ссылки остаётся прежним, Stop его не использует.

## Подтверждение

Working требует распознанного `esc to interrupt`; idle — отдельного готового промпта.
Диалог проверяется первым. Esc записывается ровно один раз для принятого запроса.
Успех требует новой записи `[Request interrupted by user]` после команды и готового ввода
без busy/диалога. Число видимых маркеров должно превысить число до команды: повторная
отрисовка прежнего маркера не подтверждает остановку. Если старый маркер ушёл с экрана
и доказательство неоднозначно, операция отказывает по тайм-ауту, даже если Claude уже idle.
Такой консервативный отказ предпочтительнее ложного успеха. Неизвестные VT-операции
запрещают классификацию до полного стирания; текст ответа с фразами диалога также может
дать консервативную недоступность. Живой тест актуального TUI остаётся обязательным.

Idle того же ранее наблюдавшегося busy epoch даёт already-idle без клавиши;
пустой/неизвестный epoch не считается подтверждённым простоем. Provider возвращает
stopped:true с proof pty-marker либо provider-state и nativeTurnId исходной цели.
Общий канал T002 затем сам переходит в waiting, независимо от Claude Stop hook.

Ожидание адаптера interruptWaitMs (по умолчанию 8 с), запрос истекает на 500 мс раньше;
нет подтверждения — ProviderError interrupt-timeout (504). Запоздалый ответ другого UUID
не принимается, оставшийся свой запрос удаляется. Исправление передачи этого ProviderError
через HTTP выполнено в T008 (дефект T002): тайм-аут адаптера возвращает 504 с подсказкой,
остальные ошибки остаются 502.
История, Remote Control, черновик панели и очередь сохраняются; назначения Kit не отменяются.

## Проверки и ОС

Алгоритм одинаков для macOS/Linux/Windows. Тесты чистого контроллера и ConPTY-host проверяют
свежий/старый/перерисованный маркер, диалог после availability, unknown, stale epoch,
idle, тайм-аут и отсутствие kill. Настоящий expect с подставным CLI проверяет путь pipe,
следующую реплику и живой процесс для injected darwin/linux; Windows native не запускается
на Mac. macOS — пользователь; Windows x64/ARM64 — проверяющий; Linux — CI, не живая приёмка.

Ошибки новых управляющих файлов в Windows перехватываются host и не вызывают kill;
Unix-помощник сообщает FAILED, ошибка send Esc отменяет запрос. Отсутствие подтверждения
при таком отказе остаётся ошибкой операции, но не завершением процесса Claude.
