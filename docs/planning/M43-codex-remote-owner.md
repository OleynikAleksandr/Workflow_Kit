# M43: удалённое управление ChatGPT всегда у демона Kit

## Цель и согласование

Пользователь 18.11.2026 (скриншот iPad: «Эта задача используется в другом сеансе Codex.
Завершите и закройте этот сеанс, затем попробуйте снова»): «сессия, которую я создаю в
Workflow Kit с ChatGPT, блокируется, не открывается на мобильном ChatGPT, при том, что на
ChatGPT десктоп на Mac прекрасно открывается … нужно эту проблему решить каким-то
административным путем, чтобы при создании сессии новой проверялось, кто держит демон. Если
его держит ChatGPT десктоп, то гасить его принудительно … чтобы всегда сессия принадлежала
Workflow Kit, а не какому-то из ChatGPT, десктоп, мобайл».

Результат: Kit сам замечает, что удалённое управление (доступ телефона и iPad к этому Mac)
держит встроенный сервер приложения ChatGPT, и возвращает его своему демону — при создании
сессии и в минутной самопроверке. Чат Kit открывается на телефоне без ручных шагов.

## 1. Причины (диагностика 18.11.2026, macOS, ChatGPT 26.1106, демон Codex 0.170.0)

1. **Слот удалённого управления один на установку Codex.** Демон Kit (`codex app-server
   --remote-control --listen unix:// --managed-daemon`) и встроенный сервер приложения
   (`/Applications/ChatGPT.app/…/codex … app-server`, stdio) делят `~/.codex` и один
   `installation_id`. Сервер ChatGPT пускает только первый подключившийся; второй получает
   `HTTP 409 Conflict … "Remote app server already online"` и повторяет попытку бесконечно
   (у демона `95747` — 472 попытки за утро, `~/.codex/logs_2.sqlite`).
2. **Слот переходит к приложению в любой разрыв демона.** Приложение запущено 15.11 и держит
   попытки подключения всё время; демон перезапускался 18.11 в 04:40 и 05:02 (05:02 —
   самообновление `codex app-server daemon pid-update-loop` до 0.170.0). Хватает секунд
   разрыва — перезапуск Kit («Перезапустить демон», устаревший вход), обновление Codex, сон
   Mac, потеря сети.
3. **Телефон попадает в того, кто держит слот.** Лог встроенного сервера: клиент
   `codex_chatgpt_ios_remote` в 07:49:36 делает `thread/resume` треда `01a1ed6a…`, созданного
   Kit в демоне в 07:49:30, и получает `thread-store conflict: thread … already has an active
   writer` — у треда один писатель (демон). Это и есть надпись на iPad.
4. **Почему Mac открывает.** Приложение открывает чаты Kit через SSH-подключение `wfk-local`
   (`codex app-server proxy` к сокету демона, M12) — оно пишет в демон, а не в свой сервер.
5. Kit сейчас это только показывает: в режиме общего демона — подсказка «закройте ChatGPT,
   дождитесь "подключён" и откройте снова» (M12 §2.3); без режима — передача управления
   приложению (M7, `handover.ts`) прямо создаёт эту ошибку для чатов Kit.

Проверено пользователем 11.11.2026 (память пробы M12): закрыть ChatGPT → демон
`connected`; после нового запуска приложения управление остаётся у демона.

## 2. Принципы

- Владелец удалённого управления на этом компьютере — демон Kit, в обоих режимах.
  Передача M7 приложению удаляется.
- Kit не трогает настройки и файлы приложения ChatGPT и не убивает его процессы сигналом
  `KILL`: только штатный выход приложения (как ⌘Q) и новый запуск в фоне. Убить один
  встроенный сервер нельзя — приложение поднимает его снова и сразу берёт слот.
- Демон при возврате не останавливается: сессии Kit, ходы и чаты через `wfk-local` идут.
- Определение «держит приложение» прежнее: `DaemonState.remoteOwner === 'app'`
  (`heldByApp` по последнему WARN `remote_control` процесса демона).

## 3. Решение (`provider-codex`)

### 3.1. `src/reclaim.ts` вместо `src/handover.ts`

`createReclaim(rt, deps)` → `{ active, lastResult, request(reason), maintain() }`.

- `maintain()` (бэкенд зовёт раз в минуту) и `request('create-session')` запускают один
  возврат, если: платформа `darwin`; codex установлен; демон `running`, `remoteOwner ===
  'app'`; работает встроенный сервер приложения (`appServerPids`, перенесено из
  `handover.ts`); возврат не идёт; лимит попыток не исчерпан. Параллельный вызов во время
  возврата ничего не делает.
- Шаги (каждый — с таймаутом, `sleep`/`now` подставляются в тестах):
  1. `osascript -e 'tell application id "com.openai.codex" to quit'` (bundle id ChatGPT для
     Mac 26.11; `CHATGPT_BUNDLE_ID`).
  2. Ожидание выхода: нет pid встроенного сервера, опрос `ps` раз в 2 с до `QUIT_WAIT_MS`
     30 с. Не вышло (приложение спросило подтверждение) — результат `app-kept`, приложение
     не трогается.
  3. Толчок демона: `codex remote-control start --json` (как «Подключить к ChatGPT», демон
     не перезапускается).
  4. Ожидание `remoteControl === 'connected'` и `remoteOwner !== 'app'`: `rt.daemon(true)`
     раз в 5 с до `RECLAIM_WAIT_MS` 90 с.
  5. Новый запуск приложения в фоне, если оно работало: `open -g -b com.openai.codex` —
     и после неудачи шага 4, чтобы пользователь не остался без приложения.
- Результат: `reclaimed` | `app-kept` | `not-connected` | `failed: <причина>`; строка в
  журнал службы; `lastResult` с временем.
- Защита от цикла: не больше 3 автоматических попыток за 60 минут; после `app-kept` или
  `not-connected` автоматические попытки до нового pid приложения не идут. Тогда статус
  показывает подсказку и действие «Вернуть управление Kit» (п. 3.3).

### 3.2. Создание сессии и самопроверка (`src/provider.ts`)

- `createSession`: после успешного создания, если `rt.cachedDaemon()?.remoteOwner ===
  'app'`, — `reclaim.request('create-session')` без ожидания; ответ создания не меняется.
  Создание во время возврата разрешено (демон работает).
- `maintain`: `reclaim.maintain()` вместо `handover.maintain()`, затем проверка общего
  доступа, как сейчас.
- `HANDOVER_REASON`, `codex-handover` и выключение создания сессий во время передачи
  удаляются.

### 3.3. Статус и действие

| Состояние | label | note |
| --- | --- | --- |
| возврат идёт | `возвращает управление Kit` | `RECLAIM_REASON`: «Удалённое управление держало приложение ChatGPT: Kit закрывает и снова открывает ChatGPT — около минуты, чаты Kit продолжаются.» |
| держит приложение, автоматических попыток нет | прежний | `APP_OWNER_NOTE`: «Удалённое управление держит приложение ChatGPT — чаты Kit не откроются на телефоне. «Вернуть управление Kit» или закройте ChatGPT и откройте снова.» (заменяет `SHARED_APP_OWNER_REASON`, в обоих режимах) |
| Windows | прежний | «Удалённое управление держит приложение ChatGPT: закройте ChatGPT, дождитесь «подключён» и откройте снова.» |

Действие провайдера `reclaim-remote` «Вернуть управление Kit» (подтверждение: «Закрыть
ChatGPT и открыть снова, чтобы удалённое управление вернулось демону Kit? Незавершённые
ходы в собственных чатах приложения прервутся.»): видно при `remoteOwner === 'app'`,
включено на macOS, на Windows и Linux выключено с причиной из таблицы. Ручной вызов
сбрасывает лимит.

## 4. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Распознавание «держит приложение» | WARN 409 демона в `logs_N.sqlite` (как сейчас) | тот же код; приложения ChatGPT нет — не наступает | тот же код (как сейчас) |
| Автоматический возврат | `osascript` quit, `ps`, `codex remote-control start --json`, `open -g -b` | нет (приложения нет), `maintain` ничего не делает | нет: проверенного способа штатно закрыть и открыть пакетное приложение ChatGPT нет (выход окна Electron может свернуть его в трей); подсказка закрыть вручную (**П** проверяющий на Windows) |
| Действие «Вернуть управление Kit» | включено | скрыто (нет состояния) | выключено с причиной |
| Передача M7 приложению | удалена | не было | удалена |

Пути не меняются; процессы ОС — `osascript`, `open`, `ps` только в ветке `darwin`;
ветки `win32` и `linux` покрыты тестами с подставленной платформой.

## 5. Проверка

- `reclaim.test.ts` на подставном runtime и `runCommand`: darwin — полный успех (порядок
  команд, повторный запуск приложения), `app-kept` (приложение не вышло — `open` не
  вызывается, подсказка), `not-connected` (приложение всё равно запускается снова), лимит 3
  за час, сброс ручным действием, нет параллельного возврата, нет приложения — ничего;
  win32 и linux — ни одной команды, нужные note и состояние действия.
- `provider.test.ts`: `createSession` при `remoteOwner: 'app'` вызывает `request` и
  возвращает тред не дожидаясь; статус во время возврата; передачи M7 больше нет.
- CI: macOS ARM64, Linux x64, Windows x64 и ARM64 для точного SHA на `ci/M43-codex-remote-owner`.
- Живая проверка (macOS — пользователь, iPad/телефон): ChatGPT держит управление (демон
  перезапущен при открытом приложении) → создать сессию ChatGPT в панели → ≤ 2 мин ChatGPT
  перезапускается, статус «демон подключён», чат открывается и пишется на iPad. Windows —
  проверяющий (подсказка). Linux — только CI.

## 6. Границы и риски

- Не входит: выключатель приложения ChatGPT «Allow this device to be discovered and
  controlled» для «Этот Mac» (Settings → Remote connections) — возможная профилактика, не
  проверено, не выключает ли он слот для общей установки вместе с демоном; запрет
  самообновления демона Codex; `pkill -9 … app-server.* --listen` в коде приложения при его
  перезапуске сервера (может задеть демон — разрыв, после которого сработает возврат).
- Риск: штатный выход прерывает ходы собственных (не Kit) чатов приложения; поэтому лимит
  попыток и подтверждение у ручного действия.

## 8. Уточнения реализации

- T001: шаг 1 — `osascript`; если служба не получила согласия «Автоматизация» на Apple Events,
  главному процессу ChatGPT (`isChatgptApp`) уходит `SIGTERM` — тот же штатный выход, не
  `KILL`. После `not-connected` автоматические попытки стоят, пока демон не будет замечен
  подключённым (новый pid приложения после повторного запуска не снимает остановку). Правило
  действия — чистая функция `reclaimAction(platform, remoteOwner, active)`.
- `open` не внесён в `programNames` platform-guard: слово совпадает с обычными строками кода
  (26 ложных находок); вызов есть только в ветке `darwin`, в allowlist описан `osascript`.
- Сквозной тест создания сессии при занятом приложением слоте — отдельный
  `test/provider-reclaim.test.ts` (лимит 400 строк у `provider.test.ts`); системные шаги в
  тестах подставные, настоящее приложение не трогается.
- Сценарий пользователя 18.11.2026 («сначала демон, потом ChatGPT» после перезагрузки) —
  целевое состояние: пока слот у демона, возврат ничего не делает; запуск ChatGPT после демона
  слот не забирает.
