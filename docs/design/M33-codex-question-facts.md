# M33: вопросы Codex — факты и проба T002

Дополнение к [спецификации M33](../planning/M33-agent-questions.md). Уровни доказательства:
**[код]** — прочитано в коде Kit; **[схема]** — типы протокола, сгенерированные локально
`codex app-server generate-ts --experimental` (codex-cli 0.169.0, 15.11.2026), поведение
сервера не испытано; **[проверено]** — наблюдалось вживую. Разделы 4 и 5 заполняет T002.

## 1. Схема протокола

- **[схема]** Запрос сервера `item/tool/requestUserInput`, параметры
  `{ threadId, turnId, itemId, questions, isBlocking, autoResolutionMs }`; помечен
  EXPERIMENTAL.
- **[схема]** Вопрос: `{ id, header, question, isOther, isSecret, options }`, `options` —
  массив `{ label, description }` или `null`.
- **[схема]** Ответ: `{ answers: { [id вопроса]: { answers: string[] } } }`.
- **[схема]** Уведомление `serverRequest/resolved { threadId, requestId }`.
- **[схема]** Статус треда: `active` с `activeFlags` из `waitingOnApproval`,
  `waitingOnUserInput`.
- **[схема]** Среди видов элемента истории (`ThreadItem`) вопроса пользователю нет: опросом
  `thread/items/list` его не прочитать.
- **[схема]** Другие запросы сервера: одобрения команд, правок и разрешений,
  `mcpServer/elicitation/request`, `item/tool/call` и служебные.

## 2. Проверено по коду Kit (0.13.7)

- **[код]** `createRpcSession` отвечает на любой запрос сервера ошибкой `-32601` «Workflow
  Kit does not handle server requests» и копит все уведомления в памяти соединения
  (`provider-codex/src/rpc.ts`).
- **[код]** Соединения короткие: каждая операция открывает своё (`withDaemon`, `readDaemon`).
  После служебного хода, прямого хода и смены параметров Kit делает `thread/unsubscribe`.
- **[код]** Лента не загружает тред и не подписывается: `thread/read`, `thread/turns/list`,
  `thread/items/list`; опрос раз в 3 с, пока карточка диалога видна.
- **[код]** Соединение с `experimentalApi` уже есть (`initializeSession`).
- **[код]** Windows ходит к демону через процесс `codex app-server proxy`.

## 3. Программа пробы T002

Стенд: демон Kit, одноразовый проект и тестовый тред в нём; пользовательские треды не
читаются и не возобновляются. Два соединения скрипта: A — слушатель, B — начинает ход.
Скрипт использует только публичный RPC, не импортирует код Kit и хранится в evidence в блоке
кода. Переписка в вывод не печатается: только методы, id, размеры и флаги.

| № | Что доказать |
| --- | --- |
| Q1 | Способ вызвать `request_user_input` в тестовом треде (режим плана или иной) и нужные параметры хода |
| Q2 | Соединение A, подписанное `thread/resume { excludeTurns: true }` до хода, получает `item/tool/requestUserInput` хода, начатого соединением B, в том числе после `thread/unsubscribe` соединения B; нужен ли `experimentalApi` |
| Q3 | Подписка A после появления вопроса (быстрый вопрос, панель открыта посреди хода): повторяет ли демон ожидающий запрос новому подписчику; что A видит без повтора |
| Q4 | Ответ A доходит до агента; B получает `serverRequest/resolved`; в ChatGPT карточка вопроса закрывается |
| Q5 | Гонка разных ответов A и B (или ChatGPT): признак, по которому A отличает свой принятый ответ от опоздавшего и от неподтверждённого (ответ сервера на поздний результат, порядок `serverRequest/resolved`, содержимое хода); нет признака — так и записать |
| Q6 | Ответ ошибкой `-32601` и молчание одного подписчика: влияет ли это на вопрос у остальных; то же для одного запроса одобрения команды |
| Q7 | Флаг `waitingOnUserInput` в `thread/read`, пока вопрос ждёт, и его снятие после ответа |
| Q8 | Трафик подписанного соединения за ход: виды уведомлений и байты |
| Q9 | Побочные эффекты подписки: `thread/loaded/list` до и после, состояние после `thread/unsubscribe` |
| Q10 | Прерывание хода при ожидающем вопросе: что получает слушатель |
| Q11 | Обрыв соединения A при ожидающем вопросе и новая подписка: повторяется ли запрос, остаётся ли вопрос у других клиентов |
| Q12 | `thread/unsubscribe` A посреди хода и повторная подписка до и после появления вопроса |

Что видно в приложении ChatGPT (Q4, Q5), подтверждает пользователь в одной совместной
проверке; без неё эти строки остаются «не проверено».

## 5. Выбор варианта (заполняет T002)

- **Момент подписки — L1** «по флагу»: демон повторяет ожидающий вопрос каждому новому
  подписчику (Q3, Q11, Q12). Для хода, который начинает сам Kit, подписка до `turn/start`
  остаётся (раздел 2.4 решения по провайдерам).
- **Признак исхода гонки — нет:** `serverRequest/resolved` не несёт ответа, поздний ответ
  игнорируется молча, в истории ответа нет (Q5). Исход ответа панели — только `unknown`:
  вопрос `answered` без `answers`. `question-stale` — только когда `serverRequest/resolved`
  получен до отправки.
- **Чужие запросы сервера на соединении слушателя — без ответа.** Ответ ошибкой отменяет
  вопрос и отклоняет одобрение для всех (Q6). Слушатель держит такие запросы до
  `serverRequest/resolved` и забывает их.
- **`experimentalApi`:** соединение слушателя открывается с `experimentalApi: true`, как в
  пробе.
- **Вывод для T006 вне выбора вариантов:** короткие соединения Kit, которые подписываются на
  тред (`thread/resume` прямого хода и параметров), сейчас отвечают `-32601` и могут
  отменить вопрос или отклонить одобрение. Критерий T006 «короткие соединения по-прежнему
  отвечают `-32601`» противоречит факту Q6 — решение пользователя (task:block перед T006 или
  `plan:extend`).

## 7. Живая проверка T008: инструмент вопроса и асинхронный вопрос

Проверка 15.11.2026, macOS, codex-cli 0.169.0, `gpt-5.6-luna` с низким усилием; ход —
[evidence](../evidence/M33-live-check-1.md). Два хода.

- **[проверено]** Тред, созданный Kit (`createSession`: служебный первый ход в обычном режиме),
  затем режим плана: параметром Kit (`thread/settings/update`) и прямо в `turn/start`
  (`collaborationMode: plan`). По журналу треда режим плана применён в обоих ходах, но модель
  ответила, что `request_user_input` недоступен. Набор инструментов хода плана — только
  `exec` и `functions`.
- **[проверено]** В треде T002 первый ход был в режиме плана, и `request_user_input` был в
  наборе инструментов каждого хода. Блокирующий вопрос возможен только в треде, начатом в
  режиме плана (например, в приложении ChatGPT). В сессиях, созданных Kit, его нет.
- **[проверено]** В обычном режиме у модели есть `request_user_input_async`. Его описание:
  «Ask the user one or more questions during ongoing work … The tool returns immediately
  without ending the turn or waiting for a reply; any reply arrives asynchronously as a new
  user message».
- **[схема]** Асинхронный вопрос — поле `questions: [{ title, options }]` элемента истории
  `agentMessage` (`options` — строки или `null`), а не запрос сервера. Ответ — обычное новое
  сообщение пользователя.
- Решение пользователя, 15.11.2026: асинхронные вопросы Codex входят в M33 (ответ из карточки
  уходит агенту обычным сообщением). Дополнительный бюджет живых проверок — до 2 ходов Haiku и
  до 4 ходов Codex.

## 8. Полная проверка T014

Проверка 15.11.2026, macOS, codex-cli 0.169.0; ход —
[evidence](../evidence/M33-acceptance.md).

- **[проверено]** Тред, начатый RPC (`thread/start`, затем `turn/start` с
  `collaborationMode: plan`) на `gpt-5.6-luna`: `request_user_input` есть, оба блокирующих
  вопроса пришли слушателю с содержимым сразу (L1). Ответ из панели — исход `unknown`, агент
  получил ответ; ответ из ChatGPT закрыл вопрос по `serverRequest/resolved`.
- **[проверено]** Обычный режим на `gpt-5.6-luna`: `request_user_input_async` недоступен (ответ
  модели). Обычный режим на `gpt-6.1-sol`: доступен; вызов возвращает `{"accepted":true}`, ход
  завершается; текст `agentMessage` повторяет вопрос и варианты строками «- <вариант>».
- **[проверено, пользователь, скриншот]** ChatGPT не показывает асинхронный вопрос: ни текста
  `agentMessage`, ни карточки. Ответ из ChatGPT — обычное сообщение; Kit закрывает карточку
  («Ответ дан сообщением»). Блокирующий вопрос ChatGPT показывает.
- **[проверено]** ChatGPT предлагает одобрить хуки проекта, у которых нет
  `hooks.state."<ключ>".trusted_hash` («Проверка хуков», «Разрешить все»). Хуки тестового
  проекта, созданного в обход панели, одобрены не были; хук SessionStart для его тредов не
  сработал. Связь этих фактов вероятна, но повторно не проверялась.
