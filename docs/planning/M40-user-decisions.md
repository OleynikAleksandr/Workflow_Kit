# M40: решения пользователя и барьеры записывает Kit, а не агент

## Цель и согласование

17.11.2026 пользователь проверял выпуск 0.15.1: включил «Полный автопилот» с ревью и дал
агенту задачу в новом проекте. Сразу появилась карточка «с ревью / без ревью». Причина:
служба записывает запуск только если агент сам передаст `wfk session plan --authorized
"<цитата>"`, а инструкции агенту этот флаг не называют. Пользователь указал на ошибку
устройства: «Карточку же показывает и формирует формат выполнения задачи не агент, а кит…
Зачем workflow киту нужно еще получать от агента какой-то авторизайт?» и поручил: «Проверь
внимательно все места, где мы поручаем агенту лишние ненужные задачи, тем более
дублирующие какие-то вещи. И это все надо исправить.»

Аудит ядра и службы нашёл три группы. Пользователь согласился разбить работу на два scope:
«Сделай так, как предложил - разбей на два скопе. И я включил автопилот полный.»

- **M40 (этот документ)** — решения пользователя и барьеры: всё, где Kit сейчас верит
  тексту агента о том, что решил пользователь, и правила, которые держатся только на
  тексте инструкции.
- **M41** — механика, которую Kit знает и может выполнить сам, и противоречия текстов;
  перечень — в [заготовке M41](M41-kit-mechanics.md).

M40 выполняется в режиме полного автопилота по прямой команде пользователя: подготовка,
ревью, выбор режима, выполнение, поставка, CI, автоматическая приёмка, закрытие и публикация
`main` в `origin/main` проходят без промежуточных нажатий, если все критерии проверены.

## 1. Принципы

- Агент может проигнорировать или неверно понять любую инструкцию; скрипт — нет. Всё, что
  Kit или служба знают сами (Settings, нажатая кнопка, текст сообщения пользователя,
  полученный хуком, состояние плана, разрешение запуска), они применяют сами.
- От агента остаётся смысловое суждение, которое скрипт сделать не может: «это задача на
  разработку», «в этом сообщении пользователь принимает результат». Агент сообщает только
  смысл, одной командой и без цитат: слова пользователя служба берёт у себя.
- Решение пользователя записывается в Kit только операцией хоста с одноразовым билетом
  (механизм `wfk-host/1` из M39). Свободный текст агента решением пользователя не является.
- Существующие проекты на Kit 2.3.x и проекты без приложения работают как раньше:
  новое правило включается ключом конфигурации, который ставит приложение (раздел 2.1).
- Ничего из M39 не ослабляется: ревью, CI, ручные критерии, пауза и стоп сохраняют силу.

## 2. Решения пользователя

Точный контракт — запрос решения, канал от ядра к службе, привязка к ходу и повторы —
в [контракте решений](M40-user-decisions-contract.md). Здесь — что меняется.

### 2.1. Режим решений в ядре

В `.harness/workflow/config.json` появляется ключ `"decisions": "host" | "agent"`.
Отсутствие ключа — `agent` (прежнее поведение, проекты без приложения и старый Kit).
Приложение ставит `host` при создании проекта и при «Обновить Kit» на Kit ≥ 2.4.0
(установщик получает `--decisions host`; ручная установка Kit без приложения ключ не ставит).

В режиме `host` команды ниже пишут решение только операцией хоста с билетом. Вызов без
билета не меняет план, отклоняется кодом `USER_DECISION_REQUIRED` и регистрирует в Kit
**запрос решения** — типизированную запись с идентификатором, параметрами и дайджестом
([контракт, раздел 1](M40-user-decisions-contract.md#1-запрос-решения)).

| Решение (`kind`) | Команда Kit | Что сейчас принимается от агента |
| --- | --- | --- |
| `choose` | `scope:choose` | `--note` без проверки, запись «выбрал пользователь» |
| `confirm-delivery` | `task:start <ID>` задачи delivery | `--confirmed "<любой непустой текст>"` |
| `accept` | `accept` | `--note`, длина ≥ 3 |
| `close` | `close` | `--note`, длина ≥ 10 |
| `unblock` | `task:unblock` | без проверки |
| `approve-install` | `quality:apply` с установкой инструментов | `approval`, длина ≥ 10 |
| `adopt-commits` | новая `commits:adopt` (раздел 3.2) | — |

Действующее разрешение запуска автопилота (`scope.authorization`) покрывает свои задачи
delivery само: `task:start <ID>` без флагов стартует задачу, которую покрывает живое
разрешение scope. `--autopilot-run <run>` остаётся допустимым для совместимости, но не
нужен и пропадает из инструкций. В режиме `agent` всё прежнее.

### 2.2. Источник решения в службе

Служба записывает решение, которое пользователь принимает сейчас, из двух источников
(решения по предварительному разрешению запуска автопилота — отдельный источник `grant`,
[контракт, раздел 5](M40-user-decisions-contract.md#5-решения-по-разрешению-запуска-автопилота)):

1. **Кнопка в панели.** Карточка построена по запросу решения из состояния Kit; кнопка
   передаёт идентификатор и дайджест запроса, которые видел пользователь. Маршруты, которые
   сейчас запускают ручные формы (`accept --note`, `scope:choose --note`, подтверждение
   поставки), для проекта `host` вызывают операции хоста; для Kit 2.3.x — прежние формы.
2. **Сообщение пользователя в чате.** Агент сообщает только смысл: `wfk decision <kind>`
   с параметрами выбора (`--task <ID>`, для `choose` — `--option`). Слова пользователя
   служба берёт из своего журнала и принимает только сообщение, доставленное в текущий ход
   ([контракт, раздел 3](M40-user-decisions-contract.md#3-сообщение-пользователя-как-источник)).
   Нет достоверной привязки — отказ `decision-source-missing` без записи решения.

Запрос решения от команды, которую агент вызвал в своём терминале, доходит до панели через
состояние Kit, а не через пересказ агента
([контракт, раздел 2](M40-user-decisions-contract.md#2-канал-от-ядра-к-службе)).

Подтверждение поставки: служба сама запускает `task:start <ID>` операцией хоста и только
потом пишет агенту «Задача T… начата по вашему подтверждению; выполните её». Сейчас служба
пишет «запусти `task:start T --confirmed "<слова>"`» (`texts.ts:93`), и агент может
переписать слова неточно или не выполнить команду.

Новые карточки: `unblock` («Снять блокировку», с причиной), `approve-install` (точный список
инструментов и команд установки) и `adopt-commits` (список коммитов). Для `accept`, `close`,
`choose` и `confirm-delivery` используются существующие карточки.

### 2.3. Вопрос о плане в полном автопилоте

`wfk session plan "<что делаем>"` остаётся единственным сигналом агента «это задача на
разработку». Решение принимает служба:

| Settings | Сообщение пользователя, доставленное в текущий ход | Результат |
| --- | --- | --- |
| `full`, Kit проекта поддерживает автопилот | есть | запуск записан (`source: user-command`, примечание — текст сообщения), ревью из Settings, агенту `action: prepare`; карточки нет |
| `full` | нет (сообщение от `Workflow Kit:`, ревьюера, напоминания; старый ход) | обычная карточка вопроса |
| `full`, Kit проекта старый | любое | `policy: kit-update-required`, как в M39 |
| `off`, `after-start` | любое | обычная карточка, как сейчас |

Источник проверяется тем же правилом, что решения в чате (контракт, раздел 3).
`--authorized` перестаёт быть нужным: значение принимается и игнорируется, поведение то же,
что без флага; флаг убирается из справки и инструкций. Повтор `wfk session plan` в том же
ходе возвращает тот же запуск. Другой активный запуск в проекте — как в M39, `run-active`.

### 2.4. «Стоп» и «пауза» распознаёт служба

Сейчас во время живого запуска служба отправляет продолжение после любого сообщения, а
агента просит самому выполнить `wfk session run pause|stop` (`run-turns.ts:32`).

Служба проверяет сообщение пользователя для сессии-владельца живого запуска **при
получении**, не дожидаясь доставки агенту: сообщение панели (`source=user`, проверенный
маршрут панели) — в момент приёма службой, даже если агент занят и сообщение встаёт в
очередь; текст, набранный в приложении провайдера, — в момент хука UserPromptSubmit
(раньше служба о нём не знает). Текст нормализуется: NFC, нижний регистр без учёта локали,
обрезка пробелов и конечной пунктуации. Если первое слово — `стоп`, `stop`, `останови`,
`остановись`, `остановить`, запуск останавливается; если `пауза`, `pause`, `приостанови` —
ставится на паузу.

Остановка действует сразу: следующие автоматические действия запуска — продолжение хода,
выбор режима, старт задачи, приёмка, закрытие, публикация — не начинаются. Уже начатые
коммит, сборка или push заканчиваются с записью результата, как в M39. Приоритет остановки
из M39 не ослабляется: ограничение «только доставленное сообщение» относится к выдаче
разрешений (контракт, раздел 3), а не к остановке. Агент при доставке сообщения получает
контекст «запуск остановлен (поставлен на паузу) вашим словом; ответьте и закончите ход».
Другие формулировки по-прежнему понимает агент и вызывает `wfk session run pause|stop` —
это смысловое суждение, без цитаты. Кнопки панели не меняются.

## 3. Барьеры ядра

Правила, которые сейчас обеспечивает только текст инструкции, получают проверку Kit.

### 3.1. Push

Хук `pre-push` читает строки `<local ref> <local sha> <remote ref> <remote sha>` из stdin
(сейчас stdin не читается, `kit-hooks.ts:195`), удаляя `\r`. Проверяется **целевой**
`remote ref` каждой строки, локальная ветка значения не имеет: `git push origin HEAD:main`
и push другой локальной ветки в `main` оцениваются как push в `main`. Один push с
несколькими refs отклоняется целиком, если отклонён хотя бы один ref.

- **Ветка публикации** — `automation.publication.branch` открытого scope, иначе ветка, на
  которой живут scope проекта. Push в неё отклоняется кодом `PUBLISH_SCOPE_OPEN`, пока scope
  открыт (ACTIVE, READY_FOR_ACCEPTANCE, ACCEPTED). После закрытия push проходит — это и
  путь кнопки «Опубликовать на GitHub», и публикация автопилотом.
- **Ветка CI** — `automation.ci.branch`, у плана без `automation` — `ci/<scope>`.
  В `automation.ci` появляется необязательное поле `task`: задача delivery, которая
  отправляет CI. Push отклоняется кодом `CI_PUSH_NOT_ALLOWED`, кроме случаев:
  - `task` объявлена — эта задача IN_PROGRESS или DONE (посторонняя начатая delivery,
    например установка приложения, push не разрешает);
  - `automation.ci` без `task` (CI отправляет служба на этапе проверки, как в M39) —
    все задачи scope DONE;
  - план без `automation` — есть задача delivery IN_PROGRESS или все задачи DONE
    (объявления, с которым можно сверить задачу, у такого плана нет).

  Push точного итогового SHA после завершения задач остаётся возможным: так работает
  проверка CI перед приёмкой в M39. Удаление ветки (нулевой SHA) проходит.
- Прочие ветки не затрагиваются. Существующие проверки хука сохраняются.

### 3.2. Коммиты в обход Kit

Коммит после базы scope без трейлера `Workflow-Transaction` (например, `git commit
--no-verify`) сейчас лишь помечается в истории как `external`. Теперь `task:start`,
`commit`, `accept` и `close` отклоняются кодом `EXTERNAL_COMMITS` со списком SHA.
Разрешение — решение пользователя `adopt-commits` (раздел 2.1): `commits:adopt` с билетом
записывает список в историю плана; в режиме `agent` команда принимает `--note`.
Коммиты интеграции и служебные коммиты Kit имеют трейлер и не считаются внешними.

### 3.3. Файлы задачи в main

`commit --task <ID>` в main сейчас добавляет в задачу всё изменённое. Теперь, если у задачи
есть список `files`, изменённые файлы вне него дают отказ `TASK_FILES_OUTSIDE` со списком
путей. Агент возвращает лишнее или явно расширяет задачу `task:update <ID>` (поле `files`
у задачи IN_PROGRESS); расширение видно в истории плана. Файлы, существовавшие до
`task:start` (preexisting), и управляемые Kit файлы обрабатываются как сейчас. Задача без
списка `files` не ограничивается.

### 3.4. Файлы `--input` и `--digest`

Файл внутри проекта, но вне `.harness/inputs/`, сейчас молча попадает в коммит (дайджест
DOCS). Теперь команда отклоняется кодом `INPUT_LOCATION` до чтения файла. Файл вне проекта
допускается. Сравнение путей — через `realpathSync.native` и платформенные помощники `path`.

## 4. Инструкции и тексты

- Управляемый раздел Kit (`installer-texts.ts`) в режиме `host` вместо `--confirmed`,
  `--autopilot-run`, `accept --note`, `close` и `task:unblock` содержит одно правило:
  «Решения пользователя (подготовка плана, режим, поставка, приёмка, закрытие, снятие
  блокировки, установка инструментов, внешние коммиты) записывает Workflow Kit по кнопке
  панели или по сообщению пользователя. Если пользователь решил в чате, выполните
  `wfk decision <kind>`; слова пользователя не передавайте». Режим `agent` получает
  прежний текст.
- Recovery (`next`, тексты автопилота) в режиме `host` не предлагает агенту ручные формы
  решений, а называет решение и где его принять.
- Раздел панели (`kit-structure/src/templates.ts`) не упоминает `--authorized`; для
  проектов `host` правило «понятная команда позволяет `scope:create` без вопроса» заменено
  на вызов `wfk session plan`.
- Тест сверяет сгенерированные тексты обоих режимов: в `host` нет снятых флагов и ручных
  форм, в `agent` текст прежний.

## 5. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Режим решений, билеты хоста | Node IPC родителя | То же | То же, x64 и ARM64; корень через `sameRoot` (8.3, регистр, `\` и `/`) |
| `pre-push`, целевые refs | stdin хука git | То же | Хук git через `sh` Git for Windows и `scripts\workflow.cmd`; stdin проходит через запускатель, `\r` удаляется |
| Внешние коммиты | вывод `git log` | То же | То же; CRLF в выводе не влияет на разбор |
| Файлы задачи, `--input` | `path.posix` | То же | `path.win32`, регистр без учёта, `realpathSync.native` |
| «Стоп»/«пауза» | NFC и нижний регистр | То же | То же |
| Карточки решений | Одинаково | Одинаково | Одинаково |

Новых вызовов программ ОС нет. Риски Windows разобраны заранее: короткие имена 8.3 и
регистр путей (сравнение только через нормализацию с внедрённой платформой), CRLF в stdin
хука и выводе git, занятые файлы при удалении временных папок тестов (`rm` с `maxRetries`),
запуск хука через `.cmd`. Тесты с внедрённой платформой `win32` используют пути, которых нет
ни на одной ОС. Kit ставит задачи delivery после DOCS, поэтому CI четырёх платформ возможен
только в конце раунда; это компенсируется тестами с внедрённой платформой в каждой задаче,
которая трогает пути, хуки и вывод git. Ранний CI силами Kit — предмет M41.

## 6. Версии и совместимость

Ядро — Kit 2.4.0 (T001), 2.4.1 (T002), 2.4.2 (T003), 2.4.3 (T004), 2.4.4 (T004A): каждый коммит ядра
повышает `KIT_VERSION` и пересобирает bundle, как в M39. Приложение — Workflow Kit 0.16.0.
Служба выбирает путь по возможностям Kit проекта: проект на Kit 2.3.x получает прежние
ручные формы и маршруты M39. Bundle Kit 2.3.3 сохраняется как тестовая фикстура для
регрессионной проверки. Сам Workflow_Kit в M40 остаётся на Kit 2.3.3 (без bootstrap нового
ядра посреди scope); переход на 2.4.x — штатным «Обновить Kit» после M40.

## 7. Проверка

Матрица и сквозные сценарии — [проверка M40](M40-user-decisions-validation.md).
Все критерии приёмки автоматические: тесты, typecheck, platform-guard, проверки документов
и CI четырёх платформ; живых ручных критериев нет. Доказательства — `docs/evidence/M40-acceptance.md`.

## 8. Границы

Не входит: Kit сам пушит CI-ветку и ждёт CI, условие зелёного CI для приёмки, Kit сам
стартует задачи под автопилотом, worktree для Codex/Kimi, автоматический `repair`,
`quality:apply --detected`, единый снимок recovery, пакет recovery для Kimi, задачи плана
для ревьюера из Kit, заголовок сессии без агента, устранение дублей вопроса о плане и
остальные противоречия текстов. Всё это — [M41](M41-kit-mechanics.md).
