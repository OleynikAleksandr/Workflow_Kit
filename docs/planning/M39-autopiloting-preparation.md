# M39: подготовка документов и порядок задач

Часть [спецификации M39](M39-autopiloting.md). Уточнение после ревью Claude, круги 1–2.

## 1. Документальные разделения до task:start

Это отдельные docs:commit между задачами, а не часть функционального коммита. Агент
выполняет их до указанной задачи; путь назначения и исходный раздел заданы заранее.
Текст переносится целыми разделами без сокращения фактов, на месте остаётся ссылка.
При смене каталога относительные ссылки корректируются только для сохранения адресата.
Старые anchors сохраняются короткими секциями-указателями. После переноса — чтение
через context, проверка ссылок, UTF-8 и размера, затем docs:commit. Если задачи уже
в работе, перенос откладывается до ближайшего безопасного промежутка, не смешивается.

добавляют host-ticket helper и тексты отдельными файлами; не расширяют предельные

T001–T004 меняют исходники и пересобирают vendor-бандл в том же work-коммите, как
предусмотрено контрактом kit-build и использовалось M31/M37/M38. Это генерация
отслеживаемой зависимости, обязательная для проверки коммита. Она не устанавливает
приложение и не публикует релиз. В рамках согласования M39 предлагается явно закрепить
эту узкую оговорку в источнике инструкций: правило delivery относится к сборке/упаковке/
установке выпуска приложения. Проверка свежести bundle остаётся обязательной на каждом
коммите ядра. До принятия плана оговорка не применяется для выполнения работ.

Каждая задача службы начиная с T005 проверяет свой публичный контракт на настоящем
новом бандле; fake-адаптеры служат только для управляемых отказов и гонок, не заменяют
интеграцию. DOCS идёт после готовых исходников ядра и всех изменений службы/панели.
Т010 добавляет интеграционные сценарии, но найденные дефекты DONE-задач исправляются
через plan:extend отдельными fixes-задачами, не скрыто в тестовой задаче.

## 3. Проверяемый bootstrap Kit для самого M39

**Отдельное решение пользователя до установки.** Для M39 предлагается исключение из
[границы M38](M38-kit-structure-update.md#5-границы): новый Kit устанавливается в сам
Workflow_Kit между T004 и T005, пока scope открыт. Причина — команды исправления
начатой delivery должны быть доступны до T012. В этот момент ядро проверено локально
и на временном проекте, но CI четырёх платформ ещё не пройден: это риск управления
собственным незавершённым планом. Выбор плана или одобрение ревью не считается отдельным
согласием на этот шаг. Сейчас такого подтверждения нет.

После T004 агент предъявляет конкретные исходную/целевую версии, SHA бандла, результаты
проверки миграции и следующую команду. До запуска получает прямое подтверждение
обновления Kit при открытом M39 и записывает дословный ответ с версиями/SHA в документ
согласования через отдельный docs:commit, например docs/evidence/M39-kit-update.md.
Это подготовка между задачами, на чистом дереве. Разрешение на последующие обновления
в рамках M39 действует только если пользователь явно включил их в тот же ответ;
иначе новая версия требует нового решения перед её установкой. При отказе или
отсутствии ответа T005 не запускается: требуется пересмотр плана, обход не применяется.

Условия установки: T004 закоммичена; нет текущей задачи, транзакций/назначений и обычных
незакоммиченных файлов. Старое приложение ещё поставляет 2.2.7, поэтому его кнопки
недостаточно. Через публичный #kit-bundle из исходников получают ensureKitBundle во
временном каталоге; затем запускают публичный CLI этого артефакта:
`node <bundle.file> install <project> --update --host harness`.
Это штатный установщик и его служебный commit, не ручное редактирование runtime/плана.
Управляемый раздел wfk обновляется штатно вместе с приложением/структурой; он не нужен
для команды defer-delivery. Статус согласования и результат установки записываются
раздельно: подтверждение не доказывает, что обновление выполнено.

T003/T004 заранее проверяют обновление временного проекта с открытым старым scope:
сохраняются задачи/DONE SHA/owner/revision, mode остаётся off; доступны schema и
`task:defer-delivery`. После обновления самого Workflow_Kit сверяются recover, validate,
version/capability, совпадение установленного бандла с выбранным и чистота дерева.

**Сбой до или после установки.** Отказ установщика или отказ/некорректный результат
команды Kit после успешной установки в T005 и далее останавливает выполнение M39.
Агент сообщает точную команду, ошибку, версии и последнее подтверждённое состояние и
ждёт решения пользователя о восстановлении. Сбой нельзя считать успешным переходом
или автоматически преодолевать ручной правкой runtime/плана, повторной установкой поверх
незавершённой транзакции либо понижением версии в обход штатного установщика. Даже если
recover/repair недоступен, состояние не восстанавливается догадками. После решения
пользователя используются только поддерживаемые команды восстановления/установки,
затем повторяются проверки; без их успеха задачи не продолжаются.

Весь M39 остаётся в режиме off с пользовательской приёмкой и публикацией. При красном
CI в T012 команда defer уже установлена; процедура — в
[контракте Kit](M39-autopiloting-kit.md) и [проверках](M39-autopiloting-validation.md).

## 4. Версии ядра и повторная поставка

Каждый коммит, изменяющий исходники kit-core, включая исправления после T010/T012,
повышает KIT_VERSION в workflow-installer/src/installer-payload.ts. В том же коммите
пересобираются vendor-файл с новым именем и метаданные/provenance в kit-bundle; его
контракт обновляется. Изменённое содержимое не выпускается под прежним номером.
Отдельный docs:commit с переносом текста без изменения исходников не пересобирает Kit.

При свободных номерах T001 — 2.3.0, T002 — 2.3.1, T003 — 2.3.2, T004 — 2.3.3;
каждое последующее исправление ядра — следующий свободный patch. Номера примерные:
перед коммитом проверяется текущая версия, снижение или повтор запрещены. T001–T004
каждая включает workflow-installer и kit-bundle в files. Функциональные fixes ядра
добавляют те же модули в свою новую задачу; DONE-задачи не расширяются и не меняются.
T011 фиксирует фактический итоговый номер Kit, source SHA и digest бандла в evidence
и CHANGELOG, а не обещает 2.3.0 для всего M39.

После любого изменения ядра позже первой установки проект до следующей задачи
обновляется той же процедурой §3: проверки, применимое явное согласие, чистая граница
между задачами, штатный install, сверка версии/digest/capability. До обновления агент
работает только с совместимыми публичными командами прежнего Kit; новые возможности
не используются. Отказ или сбой подчиняется правилу остановки §3. Временный проект
проверяет последовательные версии и видимость обновления: одинаковый номер не должен
маскировать различное содержимое.

Если исправления меняют уже установленный артефакт приложения 0.15.0, в том же
plan:extend создаётся новая delivery-задача с files поставки, installed-service и
следующей свободной patch-версией приложения (обычно 0.15.1). Для повторных исправлений
номер снова повышается. Завершённая T011 и опубликованный/установленный артефакт 0.15.0
не переписываются. Версия приложения независима от patch-версии ядра. Если артефакт не
изменился, новая поставка не нужна; CI всё равно проверяет новый точный SHA.
