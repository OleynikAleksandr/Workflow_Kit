## 2. Замечание 1: новая сессия Claude из мастера не открывается сама

Что видит пользователь: после создания проекта с первой сессией Claude мастер не переходит
на экран сессии — её приходится выбрать щелчком. С ChatGPT/Codex переход срабатывает.

Причина (проверено по коду):

- `createSession` Claude возвращает сессию с `localId` = `remoteId` (`session_…`): локальный
  id Claude ещё неизвестен (`provider-claude/src/sessions.ts`, `recordInfo`).
- Мастер запоминает ключ `claude:session_…` (`wizard-model.js`, `runView().sessionKey`) и
  ждёт, когда сессия с этим ключом появится в разделе `providers`
  (`project-wizard.js`, `sessionListed`: сравнивается только `localId`).
- Через секунды приходит хук `SessionStart` с локальным id Claude (UUID), и список уже
  показывает сессию с `localId` = UUID. Ключи больше не совпадают — переход не наступает
  никогда. У Codex id треда не меняется, поэтому там всё работает.

Исправление (`project-wizard`):

- Сессия запуска ищется в разделе `providers` проекта по провайдеру и по `localId` **или**
  `remoteId` запуска (`session_…` у Claude остаётся прежним).
- Переход идёт по ключу найденной сессии из списка (`sessionKey` панели), а не по ключу
  запуска: экран сессии и дерево проекта знают её уже под новым ключом.
- Поиск переносится в `wizard-model.js` (`listedSessionKey(state, projectId, session)`),
  чтобы его проверял тест без DOM.

Тесты (`project-wizard/test/wizard-model.test.ts`): сессия Claude, у которой в списке
`localId` сменился на UUID, находится по `remoteId` и даёт ключ `claude:<UUID>`; сессия Codex
находится по `localId`; отсутствующая сессия — `null`.

## 2a. Замечание 2: чат ChatGPT, открытый на Mac, не открывается на iPad

Что видит пользователь: сессия ChatGPT создана в панели на Mac и открыта в приложении ChatGPT
на Mac, агент выполняет задачу. На iPad щелчок по той же сессии в панели открывает ChatGPT,
и тот пишет «Эта задача используется в другом сеансе Codex. Завершите и закройте этот сеанс»,
затем «Не удалось открыть задачу».

Что известно (по коду, документам M3/M4 и состоянию службы 09.11):

- У треда Codex один писатель — один процесс app-server (M4: «thread-store conflict: … already
  has an active writer»).
- На Mac два процесса Codex: встроенный app-server приложения ChatGPT (он ведёт открытый
  на Mac чат и его ход) и демон Kit (`codex remote-control start`), который держит удалённое
  управление: служба показывает «демон подключён», pid 1033.
- iPad попадает на Mac через удалённое управление, то есть в демон. Демон не может открыть
  тред, который пишет приложение ChatGPT, — отсюда сообщение. Это ограничение Codex, а не
  ошибка панели: ссылка и тред верные.
- Удалённое управление держит тот, кто подключился первым: демон или приложение ChatGPT
  (M3-autostart, раздел 4, состояние `remoteOwner: 'app'`). Служба при старте запускает демон
  (0.3.7), поэтому обычно им оказывается демон.

Гипотеза (не проверена): если удалённое управление держит приложение ChatGPT, iPad попадает
в тот же процесс, который пишет тред, и чат открывается на обоих устройствах.

Проверка с пользователем (до решения):

1. Остановить удалённое управление демона, перезапустить приложение ChatGPT на Mac — панель
   показывает «через приложение ChatGPT».
2. Открыть сессию в ChatGPT на Mac и дать задачу.
3. Открыть тот же чат на iPad во время хода и после него.

Итог проверки (09.11, с пользователем): **подтверждено**. Демон остановлен
(`codex remote-control stop`), приложение ChatGPT перезапущено и взяло удалённое управление,
демон запущен снова (409, панель — «через приложение ChatGPT», создание сессий доступно).
Новый проект с сессией ChatGPT: чат идёт одновременно в ChatGPT на Mac и на iPad. На iPad
после «Открыть» в панели ещё раз мелькнуло «Не удалось открыть задачу», но чат открылся —
наблюдаем: возможно, след прежних попыток.

Открытый вопрос до реализации: берёт ли приложение ChatGPT удалённое управление само, когда
демон его отпускает, без перезапуска приложения. От ответа зависит, может ли служба передать
управление автоматически (проверка 2: закрыть ChatGPT — демон забирает управление; открыть
ChatGPT — управление у демона; остановить демон — смотрит ли приложение через минуту; снова
запустить демон — 409 означает, что приложение взяло управление).

Итог проверки 2 (09.11, 17:51–17:59): **положительный**. ChatGPT закрыт — демон сам
забрал управление (`connected`). ChatGPT открыт снова — управление осталось у демона (ход
агента продолжился в приложении). В демоне не было загруженных тредов (`thread/loaded/list`
пуст), демон остановлен в 17:57:26; через минуту запущен снова (17:58:31) — каждая попытка
подключения получает `409 Conflict … "Remote app server already online"`: приложение ChatGPT
взяло управление само, без перезапуска. Попутно: сразу после запуска демона, пока в журнале
Codex ещё нет строки 409, панель на несколько секунд показала «ошибка входа» вместо
«подключается» — исправляется вместе с замечанием.

Решение: служба уступает удалённое управление приложению ChatGPT,
когда оно запущено (демон остаётся локальным app-server для создания сессий), и забирает его
назад, когда приложение закрыто:

- признак приложения — его встроенный app-server (macOS: процесс
  `ChatGPT.app/…/codex … app-server`; Windows: процесс пакета `OpenAI.Codex`);
- передача — только когда в демоне нет идущих ходов (`thread/loaded/list` пуст): иначе
  остановка демона прервала бы работу, начатую с iPad;
- порядок: `codex remote-control stop` → ожидание соединения приложения (до 60 с) →
  `codex remote-control start` (демон получает 409 и остаётся локальным, `remoteOwner: 'app'`);
  если приложение не подключилось — демон запускается снова и держит управление, как раньше;
- забирать назад ничего не нужно: закрытое приложение отпускает управление, а демон
  переподключается сам (M3-autostart, раздел 4).

- соединение демона `errored` без строки 401 и без 409 в журнале в первые 60 с после его
  запуска — «подключается», а не «ошибка входа».

### Реализация замечания 2

- `provider-registry`: в контракте провайдера необязательный `maintain?(): Promise<string | null>`
  (обслуживание раз в минуту; строка — что сделано), у реестра `maintain()` →
  `{ done: string[], errors }`; служба (`cli`, `provider-lifecycle.ts`) вызывает его каждые
  60 с (`MAINTAIN_MS`, опция `maintainMs`, `0` — выключено) и пишет строки в журнал.
- `provider-codex`, новый `src/handover.ts` и `maintain()` провайдера:
  1. только macOS и Windows; демон работает и `remoteControl: 'connected'`;
  2. запущен встроенный app-server приложения ChatGPT: macOS — командная строка процесса
     содержит `/ChatGPT.app/` и `app-server` (`ps -axo command=`); Windows — процесс
     `codex.exe` пакета приложения (`OpenAI.Codex` или `ChatGPT` в пути, CIM; **П** — проверить
     на Windows);
  3. в демоне нет загруженных тредов (`thread/loaded/list` пуст), иначе — пропуск до
     следующей минуты;
  4. одна попытка на пару (pid демона, pid приложения): при неудаче не повторяется;
  5. `codex remote-control stop` → пауза `HANDOVER_WAIT_MS` = 60 с (проверка 2: ≤ 65 с) →
     `codex remote-control start --json`; итог по зонду: `remoteOwner: 'app'` — «передано
     приложению ChatGPT», `connected` — «приложение не подключилось, управление у демона»;
  6. пока идёт передача, создание сессии ChatGPT недоступно с причиной
     `HANDOVER_REASON` («удалённое управление передаётся приложению ChatGPT — около минуты»).
- Подпись: соединение `errored` без строки ошибки входа (`tokenError`) в первые 60 с после
  старта демона (`startMs` из `daemon.pid`) — «подключается», а не «ошибка входа».
- Тесты: подставные `runCommand` (список процессов, `remote-control stop/start`) и демон;
  передача при простое, пропуск при загруженных тредах, без приложения, на Linux, повторная
  попытка не делается; подпись в первые 60 с.

## 2b. Замечание 3: карточка «Выбор пользователя» без кнопок во время ожидания ревью

Что видит пользователь: на экране сессии, пока агент работает, периодически появляется
карточка «Выбор пользователя — Как составить и выполнить план этой сессии?» с причиной
рекомендации агента, строкой «Сначала ревью плана: оно начнётся, когда агент закончит ход» и
«или напишите ответ в чат своими словами» — без единой кнопки. Назначение непонятно;
пользователь просит её убрать.

Причина (по коду): `session-view/src/session-model.js`, `choiceView` — карточка выбора режима
строится, как только у Kit есть предложение плана (`scope:proposal`), и в состоянии
«ревью ещё будет» (`reviewComing`) показывается с полем `waiting` и без вариантов
(`session-view.js`, `choiceCard`). О том же уже говорит строка активности (этап ревью,
«Агент работает над ответом»), поэтому карточка лишь повторяет её и выглядит как вопрос без
ответа.

Исправление: пока ревью впереди (`reviewComing`), `choiceView` возвращает `null` — карточки нет.
Карточка с вариантами режима появляется, когда выбор действительно можно сделать (после ревью
или без него), как сейчас; карточка «Ревью не запустилось» с кнопкой «Повторить ревью» остаётся.
Поле `waiting` и его текст удаляются. Тест `session-model.test.ts` (строка с «Сначала ревью
плана») меняется: в этом состоянии `choiceView` — `null`.
