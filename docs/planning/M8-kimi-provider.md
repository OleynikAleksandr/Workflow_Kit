# M8: Kimi Code — третий провайдер

## Цель и согласование

Kimi Code становится третьим провайдером Workflow Kit: сессии из панели, имена, архив,
удаление, автопилот, ревью плана у ChatGPT, открытие чата на компьютере и удалённо.
Пользователь, 2026-11-09: «Как полноценного провайдера третьего», «речь идёт о Kimi
Code», «приступай к выполнению плана вплоть до сборки нового релиза и проверки».

Основания: [исследование](kimi-provider-research.md) и [проверенные факты
протокола](M8-kimi-protocol.md) — далее «Протокол». **П** — проверяется вживую (раздел 7).

## 1. Принципы

- Стык с Kit — контракт провайдера (`provider-registry/src/contract.ts`). Новые методы
  необязательны; поведение Claude и ChatGPT не меняется.
- Список провайдеров код берёт из реестра: вне адаптеров нет сравнений с `'claude'` и
  `'codex'`; различия выражены свойством или возможностью провайдера.
- С Kimi Kit говорит только через **свой** сервер `kimi web` на 127.0.0.1 и файлы каталога
  `KIMI_CODE_HOME` (иначе `~/.kimi-code`, далее `<home>`), названные в Протоколе.
- В каталог Kimi Kit пишет одно: блоки своего хука в `config.toml` — после предпросмотра и
  одобрения. Вход, модель, режим разрешений, рабочие области и чужие хуки не трогает.
- Токен сервера не попадает в журналы, URL, ответы API Kit и вывод процессов.
- Опрос `/api/state` программ не запускает: они только в `refresh()`.
- Проверенная версия Kimi — 2.5.2. Тесты работают на подставном сервере и временном
  каталоге; настоящий `~/.kimi-code` не открывают.

## 2. Провайдер Kimi: модуль `provider-kimi`

Новый модуль `provider-runtime/provider-adapters/provider-kimi`: id `kimi`, название
«Kimi», в `DEFAULT_PROVIDERS` после `codex`. Возможности: `trust`, `hooks`, `sessions`,
`createSession`; `orchestration` и `reviewer` — недоступны (раздел 5).

### 2.1. Программа, версия, сервер

- Программа: путь `kimi` из сохранённых `wfk install` программ, иначе `<home>/bin/kimi`.
  `refresh()` запускает `kimi --version`.
- Статус — первое совпавшее условие:

| Условие | `state` | Пометка |
| --- | --- | --- |
| программы нет | `not-installed` | «Kimi Code не найден» |
| версия ниже 2.5.2 | `unavailable` | «нужна версия Kimi Code не ниже 2.5.2» |
| сервер не поднялся, `meta.backend` не `v2` | `error` | причина |
| `40110` или `auth.models_ready: false` | `unavailable` | «нужен вход: `kimi login`» |
| `config.default_model` пуст | `unavailable` | «в Kimi не выбрана модель» |
| иначе | `ready` | версия не 2.5.x — «не проверялась с Workflow Kit» |

  Вне `ready` операции с сессиями отказывают `ProviderError` с этой пометкой.
- Сервер: `kimi web --no-open --port <свободный>` через `process-supervisor` **без
  сохранения вывода** (в нём токен; новый режим `logFile: null`). Запуск — по требованию и
  в `autostart()`, если есть записи сессий Kimi; `maintain()` поднимает упавший. Клиент,
  токен, проверка формы ответов и подхват сервера после перезапуска службы — Протокол, 10.

### 2.2. Рабочая область и доверие

- `ensureWorkspace(root)`: `GET /workspaces` → записи с той же папкой (`sameFolder`); при
  нескольких — с наибольшим `session_count`, затем с меньшим `id`. Нет ни одной →
  `POST /workspaces` с `idempotency_key: 'workflow-kit:' + sha256(realpath)`. Одновременные
  вызовы для одной папки объединяются.
- `trust(project)` читает только файлы `<home>/workspace-trust/*` и сравнивает `root`.
  `previewTrust` показывает запись доверия и, если рабочей области нет, её создание.
  `grantTrust` = `ensureWorkspace` + `POST …/trust` + чтение файла назад; требует `ready`.

### 2.3. Хук Kit в `config.toml`

Хуки Kimi только глобальные (Протокол, 5), поэтому хук Kit — пять блоков `[[hooks]]` в
`<home>/config.toml`, одни на все проекты; вне проектов Kit команда молча выходит с 0.

| Событие | Команда Kit | Таймаут, с |
| --- | --- | --- |
| `SessionStart` | `hook session-start --client kimi` | 30 |
| `UserPromptSubmit` | `hook prompt --client kimi` | 30 |
| `Stop`, `StopFailure`, `Interrupt` | `hook turn-end --client kimi` | 30 |

- Текст команды строит `kit-structure/hook-config` по `HookHost`: для `/bin/sh` на macOS и
  Linux и для `cmd.exe` на Windows (раздел 6; точные формы и кавычки TOML — Протокол, 8).
- `kitHook.status`: `approved` — все пять блоков точны; `pending` — блоков Kit нет;
  `modified` — часть блоков или иной текст; `unknown` — файл не разобран, Kit не пишет и
  показывает текст для ручной вставки. Новое необязательное `HookState.writes:
  TrustWrite[]` несёт файл и добавляемый текст для предпросмотра; `note` говорит, что хук
  общий для всех проектов и действует после перезапуска Kimi (**П**: подхват без него).
- `approveHooks(project, { command, hash })`, маршрут `hooks/approve` прежний. Разбор
  файла, отпечаток и порядок записи (замок, сверка отпечатка — иначе 409 `hooks-changed`,
  копия, атомарная запись, `kimi doctor config`, условный откат) — Протокол, 8.
- Действие провайдера `remove-kimi-hook` «Убрать хук Kit из Kimi» (с подтверждением)
  убирает блоки Kit тем же порядком.

### 2.4. Сессии

- Запись панели (`providerSessionsFile(dirs, 'kimi')`): `sessionId`, `projectId`,
  `projectPath`, `workspaceId`, `title`, `createdAt`.
- `createSession`: `ready` → `ensureWorkspace` → `POST /sessions { workspace_id, title,
  metadata: { cwd } }` → запись панели → `firstMessage` через `sendMessage` (2.5). Сбой
  отправки не отменяет сессию: она в списке с пометкой.
- Сессия принадлежит проекту, если её папка — папка проекта или внутри неё; правило одно
  для трёх источников `listSessions`, слитых по id с приоритетом: сервер
  (`GET /api/v2/sessions` по рабочим областям таких папок, с архивными, постранично; кэш
  5 с) > запись панели > журнал хука `SessionStart`. Сервер недоступен → записи и журнал
  с пометкой «Kimi недоступен: <причина>». Правила 2.4 и 2.5 полностью — Протокол, 9.
- `state`: `running`, пока жив замок сессии (2.5), иначе `stopped`. Имя — с сервера.
  `pending_interaction` у сессии → пометка «Kimi ждёт ответа пользователя».
- `renameSession` → `POST …/profile { title }`; при `40931` — `synced: false`, Kit ставит
  имя сам, когда сессия освободится (раздел 3).
- Архив панели — локальная отметка `session-titles`, как у других провайдеров;
  `archiveSessions` и `restoreSessions` повторяют её в Kimi (`:archive`, `:restore`).
  Сессии из локального архива Kit сообщений не шлёт; архивная только в Kimi — пометка
  «в архиве Kimi», доставка отказывает.
- `deleteSessions(project)` (папка проекта удаляется с диска) → `:delete` каждой сессии
  папки, включая созданные вне панели. Отказ или недоступный сервер → очередь
  `kimi-deletes.json` рядом с записями хранит намерение на папку (`root`, `since`,
  известные id); `retryDeletes()` (раз в минуту и при старте службы) перечисляет на сервере
  все сессии папки не новее `since` и удаляет их; запись уходит после полного перечисления
  без отказов. `forgetProjects` очередь не чистит. Рабочие области Kimi Kit не удаляет.
- `resumeSession`, `stopSession`, `wakeSession` нет: процесса на сессию нет.

### 2.5. Простой сессии и доставка сообщения

Три новых необязательных метода контракта; в M8 их реализует только Kimi.

- `sessionIdle(project, sessionId): Promise<boolean>` — нет живого замка
  `<home>/locks/sessions/<id>.lock` (Протокол, 4; нечитаемый файл — жив). Только чтение
  диска.
- `lastAnswer(project, sessionId): Promise<string | null>` — текст последнего сообщения
  `assistant` после последнего пользовательского с `origin.kind: "user"` (постранично).
  `null` — ход без текста; начало хода не найдено или сбой API → отказ, не `null`.
- `sendMessage(project, sessionId, text, delivery: { id }): Promise<boolean>` — `true`,
  когда Kimi принял промпт. `prompt_id = 'kit-' + id`: id даёт вызывающий и не меняет его
  при повторах, поэтому принятый промпт не выполняется дважды (`40927` → `true`). Вызовы
  по сессии идут по очереди; `40931` → три повтора, `40932` → `:reload`; архивной сессии
  Kit не шлёт, `:takeover` не вызывает.

### 2.6. Ссылки и Remote Control

- `links.desktop` = `kimi-code://open?root=<абсолютная папка>` — открывает проект в
  приложении Kimi Code (ссылки на сессию у Kimi нет). Есть ли приложение, проверяет
  `refresh()`; нет → ссылки нет, пометка «продолжить: `kimi -S <id>` в терминале проекта».
- `links.mobile` — адрес Remote Control, если он включён на сервере Kit
  (`GET /remote-control`): только вида `https://code-rc.kimi.com/devices/<id>/`, без
  учётных данных и параметров; иное отбрасывается. Действие провайдера `kimi-remote`
  «Включить Remote Control Kimi» и `kimi-remote-off` «Выключить…» (`POST /remote-control
  { enabled }`, с подтверждением); `40928` → «Remote Control уже ведёт другое приложение
  Kimi». `links.web` нет.
- `open-link` принимает `kimi-code://open` только с `root` зарегистрированного проекта и
  необязательным `new=1`.
- Панель: щелчок по сессии Kimi открывает её экран и на компьютере — проект в Kimi Code;
  на сенсорном устройстве `links.mobile` открывается только нажатием.

## 3. Конец хода без удержания `Stop`

У Claude и ChatGPT Kit отвечает следующим сообщением в удерживаемый хук `Stop`. У Kimi
так нельзя: `Stop` приходит и в конце хода подагента, продолжение одно за ход, текста
ответа в хуке нет (Протокол, 5). Хук Kimi отвечает сразу, а следующее сообщение Kit шлёт
промптом, когда сессия освободилась. Точные правила — Протокол, 11.

- Контракт: необязательное свойство `Provider.hookDialect: 'claude' | 'kimi'` (нет —
  `claude`). Диалект `kimi`: во входе `prompt` — массив частей (текст — их склейка); ответ
  `UserPromptSubmit` — `{ "message": text }`, пустой — без вывода. `parseHookInput` и
  ответы канала выбирают форму по диалекту; `AgentClient` — id из реестра.
- `wfk hook turn-end --client <id>` шлёт службе `POST /api/hooks/turn-end { client,
  sessionId, cwd, event }` (таймаут 3 с), ничего не печатает, выходит с 0. Маршрут
  принимает клиентов, у чьего провайдера есть `sessionIdle` и `sendMessage`.
- `agent-channel`: наблюдатель (один на сессию) раз в секунду спрашивает `sessionIdle`, до
  120 с; `Stop` подагента приходит при живом замке, и наблюдатель ждёт. Истёкшее ожидание
  подбирает `maintain()` раз в минуту.
- Сессия свободна → «отложенный Stop»: Kit ставит отложенное имя, читает `lastAnswer` и
  идёт тем же путём решения, что `stop()` (очередь, автопилот, ревью, удержание), но
  продолжение уходит через `sendMessage`. Сбой чтения ответа не становится ответом агента:
  слушатели конца хода и автопилот не вызываются, сессия несёт пометку.
- Доставка — «исходящее» слота (текст, происхождение хода, источники, id): создаётся до
  отправки и живёт до приёма. Отказ → слот «ждёт», следующая попытка шлёт то же исходящее
  с тем же id; пять неудач подряд → пометка «сообщение не доставлено: <причина>».
- Свой промпт: `UserPromptSubmit` с текстом исходящего (текст запомнен **до** запроса) —
  промпт Kit: происхождение и источники хода сохраняются, поэтому автопилот считает ход
  своим, а ревью узнаёт ответ на замечания. Другой текст — промпт пользователя: он
  отменяет ждущий отложенный Stop.
- Сообщение ждущему слоту (замечания ревью, «Сообщение агенту») уходит сразу —
  `channel.flush(key)`; его же зовут `wakeIdle` для провайдеров с `sendMessage` и
  `maintain()`.
- `StopFailure` и `Interrupt`: слот — «ждёт», автопилот сам не продолжает; очередь цела.
- Kimi без замков сессий (`KIMI_CODE_SESSION_LOCK=false`): `Stop` приходит без живого
  замка — Kit не обрабатывает конец хода и не шлёт сообщений этой сессии, пометка называет
  причину (**П**). Свой сервер Kit запускает без этой переменной.
- После перезапуска службы слоты пусты; `Stop`, пришедший без службы, теряется, как
  удерживаемый `Stop` у Claude и ChatGPT: работа продолжится после сообщения в сессию.

## 4. Список провайдеров из реестра

- **Сервер.** `cli`, `session-titles`, `plan-review`, `cross-review`, `autopilot`,
  `plan-view`, `project-setup`, `kit-structure` берут id и названия из реестра; `--client`
  проверяется по реестру. Различия — по `hookDialect`, наличию метода (`sendMessage`,
  `resumeSession`) и возможностям (`orchestration`, `reviewer`; нет ключа — доступна).
- **Мастер** (`project-setup`, `project-wizard`): кнопки провайдеров, шаги доверия и хука —
  по списку состояния. Провайдер первой сессии обязателен, шаги остальных пропускаются с
  пометкой. Отпечаток предпросмотра включает `hash` хука каждого
  провайдера; `writes` хука видны до одобрения, а `approveHooks` получает `command` и
  `hash` из показанного предпросмотра, а не перечитанные. Действия провайдера (`scope: 'provider'`)
  показаны у любого провайдера, в том числе готового и в существующем проекте.
- **Панель** (`panel-shell`, `session-view`): названия, метки, подписи кнопок, тексты
  подтверждений и «Программы» карточки «Система» — из состояния. Подъём сессии — только у
  провайдеров с `resumeSession`; открытие чата — по `links`.
- **Установка** (`service-installer`): `kimi` — необязательная программа в `PROGRAMS`,
  `wfk status` и `wfk doctor` её показывают.

## 5. Ревью, команды сессии, автопилот

- **Ревью плана.** Основная сторона Kimi → ревьюер ChatGPT; пары задаёт таблица в
  `cross-review` (`claude → codex`, `codex → claude`, `kimi → codex`). Замечания приходят в
  Kimi через очередь канала и `sendMessage`. Kimi ревьюером в M8 не бывает: возможность
  `reviewer` недоступна, панель его не предлагает.
- **`wfk session title|plan`.** У команд агента Kimi нет переменной с id сессии. Без
  `CODEX_THREAD_ID` и `CLAUDE_CODE_SESSION_ID` команда шлёт запрос без клиента, и служба
  берёт единственную сессию проекта с идущим ходом (по данным канала). Иначе → 409
  `session-ambiguous` с кандидатами и просьбой повторить с `--client <id> --session <id>`;
  по времени Kit не угадывает. `/api/sessions/plan` принимает клиента из реестра.
- **Автопилот.** Его сообщения идут по разделу 3. Провайдер с недоступной `orchestration`
  (Kimi) ведёт скоуп только последовательно: `choiceOptionsFor` не показывает
  `orchestrated` для сессии Kimi, тексты автопилота и шаблон `AGENTS.md`
  (`kit-structure/templates.ts`) говорят, что из Kimi оркестрация не запускается.
  **Изменено в M10** ([M10-kimi-orchestration.md](M10-kimi-orchestration.md)): сессия Kimi
  ведёт скоуп и с исполнителями (инструмент `Agent` в worktree оркестратора).

## 6. Поведение на ОС

| Что | macOS | Linux | Windows (x64, ARM64) |
| --- | --- | --- | --- |
| Каталог Kimi | `KIMI_CODE_HOME`, иначе `~/.kimi-code` | то же | `KIMI_CODE_HOME`, иначе `%USERPROFILE%\.kimi-code` |
| Программа | поиск `wfk install`, иначе `<home>/bin/kimi` | то же | поиск по `PATHEXT`, иначе `<home>\bin\kimi.exe` |
| Сервер `kimi web` | процесс supervisor без файла вывода | то же | то же, без окна консоли |
| Команда хука | `/bin/sh`: `[ -x … ] && … ; exit 0` | то же | `cmd.exe`: `"node.exe" "wfk.mjs" hook …` |
| Запись `config.toml` | временный файл и `rename`, права сохраняются | то же | временный файл и `rename` |
| Сравнение папок | `sameFolder` Kit | то же | то же: без регистра, `\` и `/` равны |
| Приложение Kimi Code | `Kimi Code.app` в `/Applications` или `~/Applications` | обработчик схемы: `xdg-mime query default x-scheme-handler/kimi-code` | ключ `HKCU\Software\Classes\kimi-code` (`reg query`) |
| Открытие `kimi-code://` | `open` | `xdg-open` | `rundll32 url.dll,FileProtocolHandler` |

Остальное (клиент, сессии, замок, доставка, конец хода, Remote Control, мастер, панель) —
одинаково. Нет обработчика схемы при открытии → 501 `no-handler` и пометка с
`kimi -S <id>`. На Linux и Windows Kimi вживую не проверялся: статус провайдера там несёт
пометку «на этой ОС не проверялся».
Вызовы `xdg-mime`, `xdg-open`, `reg`, `rundll32`, `open` — в `allowlist.json`.

## 7. Проверка

- Автоматические тесты `provider-kimi`: подставной HTTP-сервер отвечает реальными ответами
  Kimi 2.5.2 ([захваты](../evidence/M8-kimi-captures.md), копия в `test/fixtures`), каталог
  Kimi — временный. Ветки `win32` и `linux` — с подставленной платформой: хук, пути,
  проверка приложения, открытие ссылки. Команду хука тест ещё и исполняет оболочкой
  своей ОС (`spawn(…, { shell: true })`, в CI — `/bin/sh` и `cmd.exe`) с подставным
  `wfk`: stdin, пробел, кириллица и апостроф в путях.
- Сценарные тесты: два продолжения автопилота подряд; ревью Kimi → ChatGPT → Kimi; `Stop`
  подагента без доставки; `40931` с повторами; `40927`; удаление при недоступном сервере и
  повтор после перезапуска службы; `config.toml` изменён между предпросмотром и
  одобрением; отказ `kimi doctor config`; нет обработчика ссылки; несколько рабочих
  областей одной папки; двусмысленная `wfk session`.
- CI: macOS, Linux, Windows x64 и ARM64 — typecheck, тесты, `check:platforms`.
- Живая проверка — `docs/evidence/M8-acceptance.md` с результатом каждого пункта и
  списком непроверенного. macOS — пользователь: мастер с Kimi, хук, сессия из панели,
  автопилот, ревью, имя, архив, ссылка, Remote Control и **П**: `40932`, видит ли
  приложение ход сервера Kit, приложение 2.5.1 с CLI 2.5.2 на одном каталоге, подхват
  `config.toml` без перезапуска, `Stop` без замков. Windows — проверяющий на Windows
  (`kimi.exe`, `kimi-code://`, ARM64); приёмка M8 его не ждёт: пункты записаны как
  непроверенные. Linux — только CI. Несовместимость, найденная вживую, — пометка статуса
  и раунд исправлений.

## 8. Границы

Не входит: Kimi как ревьюер; оркестрация из сессии Kimi; проектные хуки Kimi (их нет);
ссылка на конкретную сессию; приложение Kimi (чат и Work); управление входом, моделью и
режимом разрешений Kimi; удаление рабочих областей Kimi; ACP; живая проверка на Linux.

## 9. План и уточнения реализации

Скоуп `m8-kimi-provider`, режим `sequential`; задачи T001–T012, их файлы и критерии — в
плане Kit. Уточнения, принятые при реализации (подробности — `module.md` модулей):

- Сервер Kimi запускается по требованию (`requireReady`), а не при старте службы; статус
  его не запускает; при неработающем сервере действие — «Запустить сервер Kimi».
- Контракт: `Provider.lockSwitch` — имя переменной замков для пометки из раздела 3.
- Удаление сессии при недоступном сервере — намерение на 7 дней; список — кэш 5 с.
- Remote Control: действия `kimi-remote` и `kimi-remote-off`; состояние читается только
  у работающего сервера. Windows: запасной ключ приложения — `HKCR\kimi-code`.
- Шаблон `AGENTS.md` получил пункт о Kimi (`STRUCTURE_VERSION` 3): раздел в проектах
  обновится; текст автопилота — `sequentialOnlyNote`.
- Сценарные тесты раздела 7 — `provider-kimi/test/scenarios.test.ts`.
