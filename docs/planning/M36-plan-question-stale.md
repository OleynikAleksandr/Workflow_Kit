# M36: вопрос о плане не остаётся висеть

## Цель и согласование

Вопрос о спецификации и плане (`wfk session plan`, раздел 12 [M4](M4-plan-review.md))
закрывается только ответом на карточке панели. Если пользователь ответил агенту в чате, вопрос
остаётся открытым навсегда. Пока он открыт, служба после каждого хода удерживает сессию и раз в
9 минут будит её напоминанием «пользователь ещё не ответил…»: агент тратит на него целый ход,
а выбор способа выполнения в панели ждёт ответа на этот вопрос (12.3 M4). Так было 15–16.11.2026
со scope M35: вопрос висел весь scope, сессия получила больше десятка пустых ходов, режим
пришлось выбирать в чате.

После M36 вопрос, на который уже ответили делом (агент предложил план или создан scope),
закрывается сам, а напоминание удержания приходит не чаще одного раза подряд в сессии, которую
служба может разбудить.

Пользователь, 16.11.2026: на предложение исправить это — «Исправь»; в панели выбраны
спецификация и план без ревью.

## 1. Факты

- **[проверено в коде]** Вопрос хранится в поле `question` файла
  `.workflow-kit/local/sessions/<client>.<id>.json` и закрывается только `answer()`
  (`plan-review/src/toggles.ts`), то есть маршрутом `POST …/plan-decision` с карточки.
- **[проверено в коде]** `decide()` (`cross-review/src/review.ts`) первым делом проверяет открытый
  вопрос сессии и возвращает `hold` `waiting-for-plan-decision` с напоминанием
  `QUESTION_REMINDER`, не глядя на план Kit. `choiceBlocked()` отказывает в выборе пути, пока
  в проекте открыт любой вопрос (`CHOICE_WAITS_QUESTION`).
- **[проверено в коде]** Удержание сессии, которую служба может разбудить (M29,
  `agent-channel/src/release.ts`), по истечении `STOP_HOLD_MS` (9 минут) ставит напоминание в
  очередь (источник `reminder`) и будит сессию. Хост Claude набирает
  «Workflow Kit: новое сообщение из панели.», хук отдаёт напоминание, агент отвечает и
  заканчивает ход, `decide()` снова удерживает — и так, пока вопрос открыт. Сессии без
  удерживаемого хука (M8, `detached.ts`) получают напоминание так же, исходящим сообщением.
- **[проверено в этой сессии]** M35: вопрос задан 15.11, пользователь ответил в чате, scope
  предложен, выбран (`scope:choose` по словам пользователя), выполнен, принят и закрыт — вопрос
  всё это время оставался открытым, напоминания приходили до конца.
- Ответ на вопрос будит сессию сам (слушатель `onAnswer`, `review-wiring.ts`); ответы и
  сообщения ревью тоже будят её. Сессии, которую можно разбудить, повторные напоминания не
  нужны.

## 2. Решение

### 2.1. Вопрос помнит scope (`plan-review`)

- `ask()` записывает в вопрос `scopeId` — id активного scope проекта в момент вопроса или
  `null`. Источник — новый необязательный параметр `scopeOf(projectId)` в
  `createReviewToggles`. Вопрос старого файла без `scopeId` читается как `scopeId: null`.
- Новый метод `dismiss(projectId, key)`: убирает вопрос из файла и памяти без решения о ревью и
  без слушателей `onAnswer` (агенту ничего не уходит). Возвращает закрытый вопрос или `null`.
- Новый метод `questions(projectId)`: открытые вопросы проекта, `[{ key, question }]`.

### 2.2. Устаревший вопрос (`cross-review`, новый `src/question-stale.ts`)

`staleReason(question, plan)` даёт причину или `null`; `plan` — открытое предложение проекта
(`createdAt`) и id активного scope:

| Вопрос | Устарел, когда | Причина в журнале |
| --- | --- | --- |
| `agent` (`wfk session plan`) | открыто предложение, созданное позже `askedAt` | `a newer proposal` |
| `agent` | активен scope, а при вопросе был другой или не было никакого | `another scope` |
| `proposal` (12.2 M4) | открытого предложения нет (путь выбран или предложение снято) | `no open proposal` |

- `decide()`: открытый вопрос сессии сначала проверяется; устаревший закрывается `dismiss` и
  `decide()` продолжает как без вопроса (в том числе 12.2 M4: предложение без решения о ревью
  задаёт вопрос `proposal`). Неустаревший — прежний `hold` `waiting-for-plan-decision`.
- `choiceBlocked()`: перед проверкой «открыт вопрос» закрывает устаревшие вопросы проекта.
- В журнал службы — `review: plan question of <key> closed: <причина>` без текста вопроса.
- Зависимости `CrossReviewDeps`: `question(projectId, key)` возвращает вопрос
  (`{ kind, askedAt, scopeId }`) или `null` вместо `boolean`; новые необязательные
  `questions(projectId)`, `dismissQuestion(projectId, key)` и `scope(projectId)` — id
  активного scope или `null`. Без них поведение прежнее.

### 2.3. Подключение (`cli`)

- `session-wiring.ts`: `scopeOf: (id) => workflow.get(id)?.scope?.id ?? null` для
  `createReviewToggles`.
- `review-wiring.ts`: новые зависимости `cross-review` — из `toggles` и `workflow`
  (`scope` — тот же источник, что `scopeOf`).

### 2.4. Одно напоминание подряд (`agent-channel`)

- Если ход, который только что закончился, начат только напоминанием (все доставленные
  сообщения хода — источник `reminder`, или ход начат исходящим напоминанием detached), а
  решатель снова удерживает сессию, то для сессии, которую служба может разбудить (освобождённое
  удержание M29 и detached M8), новое удержание идёт **без** напоминания: сессию разбудит то, чего
  она ждёт (ответ, сообщение ревью, сообщение панели). Без этого удержание ведёт себя, как
  сейчас удержание без `timeoutAnswer`: освобождённое снимается сроком, detached длится до
  пробуждения.
- Сессия с удерживаемым хуком `Stop` (служба не может её разбудить) получает напоминание, как
  раньше: оно — единственный способ закончить хук, не потеряв доставку.
- Правило общее для всех удержаний с `timeoutAnswer` (вопрос о плане, ожидание ревью). Тексты
  напоминаний не меняются.

## 4. Проверка

- `plan-review`: `ask` пишет `scopeId` из `scopeOf` (и `null` без него), старый файл без
  `scopeId` читается; `dismiss` убирает вопрос из файла и памяти без решения и без слушателей;
  `questions`.
- `cross-review`: таблица 2.2 построчно (вопрос `agent` и предложение до и после `askedAt`,
  тот же и другой scope, вопрос `proposal` с предложением и без); `decide` после закрытия
  `agent` задаёт вопрос `proposal` (12.2 M4) и не удерживает с устаревшим вопросом;
  `choiceBlocked` пропускает выбор после закрытия устаревших вопросов и по-прежнему ждёт
  неустаревший; без новых зависимостей — прежнее поведение.
- `agent-channel`: освобождённое удержание после хода-напоминания не ставит второго
  напоминания и снимается сроком; ответ будит сессию; удержание после обычного хода
  напоминает, как раньше; detached — так же; удерживаемый хук напоминает каждый раз.
- `cli`: подключение `scopeOf` и новых зависимостей.
- Все тесты с подставленными `darwin`, `linux` и `win32` там, где код зависит от платформы
  (здесь — нет); CI: macOS, Linux, Windows x64 и ARM64 для точного SHA поставки.
- Живая проверка на установленной 0.14.3 (macOS) с согласия пользователя, в тестовом проекте
  панели: агент задаёт `wfk session plan`, пользователь отвечает в чате «без ревью», агент
  предлагает маленький scope. Ожидается: после хода карточка вопроса агента исчезает, появляется
  «План предложен. Проверить его ревьюером…»; за 20 минут ожидания — не больше одного
  напоминания; после ответа на карточке выбор способа выполнения работает. Агент записывает
  хронологию через API службы. Бюджет — до 4 ходов Claude. Windows — проверяющий на Windows не
  нужен (общий код, CI); Linux — CI.

## 5. Границы

- Ответ в чате не становится решением о ревью: после предложения плана панель спрашивает
  «С ревью / Без ревью» (12.2 M4). Команда, которой агент записал бы ответ пользователя из
  чата, — отдельное решение.
- Текст пробуждения хоста Claude «Workflow Kit: новое сообщение из панели.» не меняется, хотя
  напоминание — не сообщение панели.
- Устаревший вопрос закрывается при следующем `Stop` сессии или при выборе пути, а не в момент
  изменения плана Kit.
- Тексты вопросов, ответов и напоминаний, срок удержания и правила ревью не меняются.
