# M33: интерактивные вопросы агента в диалоге

## Цель и согласование

Агент Claude (инструмент `AskUserQuestion`) и агент ChatGPT/Codex (`request_user_input`)
задают пользователю вопрос с вариантами ответа. В родных приложениях это карточка с выбором
и кнопкой «Submit». В диалоге Workflow Kit вопроса нет: видна только предыдущая реплика
агента, а ответить можно лишь текстом в поле ввода.

После M33 вопрос виден в ленте диалога панели карточкой: пользователь выбирает вариант или
пишет свой и нажимает «Отправить». Вопрос остаётся и в родном приложении: отвечает та
сторона, которая успела первой, вторая показывает итог.

Пользователь, 15.11.2026: «Что мы можем сделать, чтобы подобный интерактивный вопрос
возникал и в Workflow Kit диалоге? Ну или похожий хотя бы, чтобы не писать в поле ввода
пользователя «подтверждаю» или вариант, который предложен, а нажать, выбрать ответ и нажать
«Submit».» В панели выбраны спецификация и план с ревью.

## 1. Факты и принципы

Факты с уровнем доказательства — в [фактах Claude](../design/M33-claude-question-facts.md) и
[фактах Codex](../design/M33-codex-question-facts.md). Главное:

- Лента Claude читает транскрипт и берёт только текст; вызовы инструментов, в том числе
  `AskUserQuestion`, отбрасывает (код `provider-claude/src/chat.ts`).
- Клиент Codex отвечает `-32601` на любой запрос сервера и отписывается от треда после своего
  хода (код `provider-codex/src/rpc.ts`). Вопрос Codex — запрос сервера
  `item/tool/requestUserInput`; элемента истории для него нет, зато статус треда несёт флаг
  `waitingOnUserInput` (схема codex-cli 0.169.0).
- Claude Code документирует ответ на `AskUserQuestion` хуком (`PermissionRequest` или
  `PreToolUse`) через `updatedInput.answers`; вживую не испытано.

Принципы:

1. Kit не отвечает за пользователя. Ответ уходит только по явному нажатию в панели; автопилот,
   очередь сообщений и истечение времени ответом не являются. Одобрения команд и правок
   (approvals) Kit по-прежнему не принимает.
2. Родной вопрос не прячется. Вариант, при котором вопрос исчезает из приложения вендора, пока
   его держит Kit, без отдельного решения пользователя не выбирается.
3. Один вопрос — один ответ. Ответ с любой стороны закрывает вопрос на обеих; опоздавший ответ
   панели получает отказ `question-stale`.
4. Сначала пробы (T001, T002), потом код. Проба уточняет факты и выбирает только из вариантов,
   описанных здесь; противоречие факта критерию следующих задач — `task:block` и решение
   пользователя.
5. Текст вопросов и ответов — переписка: в журналы службы не пишется (только id, числа, коды).
6. Контракт общий для провайдеров. Kimi в M33 вопросов не отдаёт (раздел 5).

## 2. Решение

### 2.1. Общий контракт (`provider-registry`)

Новый файл `src/questions.ts`, типы и пределы экспортирует `src/index.ts`:

- `ChatQuestionOption { label, description }`.
- `ChatQuestionPart { id, header, question, options, multiSelect, allowOther }` — один вопрос
  карточки; `options` может быть пустым (тогда только свой текст, `allowOther: true`).
- `ChatQuestion { id, at, afterMessageId, state, parts, answerable, reason?, answers? }`:
  `state` — `pending | answered | cancelled`; `afterMessageId` — сообщение ленты, после
  которого стоит вопрос (`null` — в начале); `answerable` — Kit может доставить ответ сейчас
  (только у `pending`); `reason` — безопасный текст, почему нельзя; `answers` — у `answered`,
  по `part.id` список выбранных подписей или свой текст (нет — итог неизвестен).
- `ChatQuestionAnswer` — `{ [partId]: { selected: string[]; other?: string } }`.
- `ChatPage.questions?: ChatQuestion[]` — от старых к новым; нет поля — провайдер вопросов не
  отдаёт. `chatPageOut` нормализует: не больше `QUESTIONS_PAGE_MAX` (20) новейших.
- Пределы: частей 4, вариантов 8, заголовок 60, подпись 200, описание 1000, вопрос 2000, свой
  текст 2000 знаков. Вопрос сверх пределов показывается обрезанным с `answerable: false` и
  причиной `QUESTION_TOO_LARGE_REASON` («Вопрос больше, чем показывает Workflow Kit. Ответьте
  в приложении провайдера»).
- `checkQuestionAnswer(question, answer)` — общая проверка для провайдеров: ответ есть на
  каждую часть; без `multiSelect` — ровно один выбранный вариант или свой текст; с
  `multiSelect` — хотя бы один вариант или свой текст; подписи только из `options`; свой текст
  только при `allowOther`, очищен как `cleanDirectText` и не пуст.
- `Provider.answerQuestion?(project, sessionId, questionId, answer): Promise<void>` и
  возможность `answerQuestion` (явное включение, как `interruptTurn`).

Маршрут `POST /api/projects/:id/providers/:p/sessions/:sid/questions/:qid/answer`,
тело `{ answers }` → `{ answered: true }`. Маршрут проверяет форму тела, провайдер — ответ
против вопроса. Отказы (`ProviderError` → HTTP):

| Код | HTTP | Текст |
| --- | --- | --- |
| `question-invalid` | 400 | «Ответ не подходит к вопросу» |
| `question-stale` | 409 | «На вопрос уже ответили» |
| `question-unavailable` | 409 | причина из `reason` вопроса |
| `question-failed` | 502 | «<Провайдер> не принял ответ: <причина>» |
| `question-timeout` | 504 | «Ответ отправлен, подтверждение не пришло. Проверьте чат провайдера» |

Одновременные ответы на один вопрос выполняются по очереди: второй получает
`question-stale`. Нет метода у провайдера — 404 `unsupported`.

### 2.2. Claude: показ (`provider-claude`)

- `ChatReader` дополнительно извлекает из строк `assistant` (не `isSidechain`) части
  `tool_use` с `name: "AskUserQuestion"`: `id` вызова — id вопроса; `input.questions[]` —
  части (`id` — `q<номер>`, `allowOther: true`). Строка `user` с `tool_result` того же
  `tool_use_id` переводит вопрос в `answered` (ответы — по формату, который установит T001;
  нераспознанный формат — `answered` без `answers`) или в `cancelled` (ошибка, прерывание).
- Вопрос без результата, после которого в транскрипте есть более поздняя реплика пользователя
  или текст агента, — `cancelled`.
- Если T001 покажет, что строка `tool_use` появляется в транскрипте только после ответа,
  ожидающий вопрос берётся из регистрации хука (2.3), транскрипт даёт только итог.
- `sendDirect` при ожидающем вопросе возвращает `false`: текст не вставляется в открытый
  диалог терминала и уходит в очередь канала.

### 2.3. Claude: ответ

Варианты, по убыванию предпочтения:

**A1 — хук `PermissionRequest`.** Выбирается, если T001 доказала P1–P5 (факты Claude,
раздел 3): хук срабатывает в сессии с Remote Control; пока он ждёт, вопрос виден в терминале
и в Claude Desktop; ответ хука закрывает вопрос везде и доходит до агента; ответ в приложении
раньше хука ничего не ломает; хук живёт дольше 600 с.

- `kit-structure`: событие Kit `PermissionRequest` только для Claude, группа с
  `matcher: "AskUserQuestion"`, команда `wfk hook question --client claude`, `timeout`
  `QUESTION_HOOK_TIMEOUT_S` = 43 200 с (или наибольшее доказанное T001). `STRUCTURE_VERSION`
  растёт: существующие проекты получают статус «устарела» и обновляются прежней кнопкой.
  `.codex/hooks.json` и хуки Kimi не меняются.
- `cli`: `wfk hook question` читает stdin и держит длинный запрос `POST /api/hooks/question`
  (каждый не дольше 9 мин, повтор при ответе `{ wait: true }`). Ответ службы с решением —
  печать JSON решения. Службы нет, отказ, `{ release: true }` — выход 0 без вывода: родной
  диалог работает дальше. Обрыв во время ожидания — повторы до 2 мин, затем выход 0.
- `agent-channel`: маршрут `/api/hooks/question`; `cli` передаёт вызов в
  `Provider.questionHook`.
- `provider-claude`, `src/question-waiters.ts`: ожидающие хуки по сессии и ключу содержимого
  (sha256 нормализованных `questions`; `tool_use_id` в этот хук не приходит). Вопрос
  `answerable` только при живом ожидающем хуке; иначе причина «Ответьте в приложении Claude:
  эта сессия запущена до обновления хуков проекта» (или «…хук вопроса завершился»).
- `answerQuestion`: проверка, решение хуку (`behavior: "allow"`, `updatedInput` с исходными
  `questions` и `answers`: текст вопроса → подпись; несколько подписей и свой текст — в
  формате, доказанном T001), затем ожидание результата в транскрипте до 10 с. Итог с другими
  ответами — `question-stale`, нет итога — `question-timeout`.
- Закрытие соединения хука (вопрос закрыт в приложении) снимает ожидание. Хук никогда не
  отвечает за другие инструменты: служба проверяет `tool_name`.

**A2 — клавиши в терминале Kit.** Выбирается, если A1 не доказан, а T001 доказала K1–K4:
устойчивый кадр диалога вопроса и клавиши выбора, нескольких вариантов, своего текста и
отправки.

- `provider-claude/src/pty`: распознавание кадра (`question-screen.ts`) и движок
  (`question-engine.ts`) в общем контроллере expect/ConPTY; файлы запроса и результата рядом
  с `<debug>`, корреляция UUID/сессия/срок, как у параметров M27.
- Неизвестный кадр или версия ниже проверенной — `question-unavailable`; `answerable` только
  у сессии панели с новым хостом и распознанным диалогом этого вопроса. Подтверждение —
  результат в транскрипте.

**A3 — хук `PreToolUse`, удерживающий вопрос.** Документирован, но, по документации, прячет
вопрос от приложения, пока Kit его держит (принцип 2). В M33 не реализуется; если A1 и A2 не
доказаны — `task:block` T001 и решение пользователя.

### 2.4. Codex: показ и ответ (`provider-codex`)

- **C0 — флаг.** Опрос ленты уже читает `thread/read`. Статус `active` с флагом
  `waitingOnUserInput` без известного содержимого вопроса даёт вопрос-заглушку: `parts: []`,
  `answerable: false`, причина «Агент ждёт ответа. Ответьте в приложении ChatGPT». Карточка
  показывает причину и прежнюю ссылку на чат.
- **C1 — слушатель** (`src/question-listener.ts`): отдельное долгое соединение с демоном,
  подписка `thread/resume { excludeTurns: true }` на тред с идущим ходом. Момент подписки —
  по T002: L1 «по флагу» (если демон повторяет ожидающий запрос новому подписчику) или L2
  «с начала хода» (пока лента этого треда опрашивается и статус `active`). Подписка снимается
  через 30 с после конца хода или 60 с без опросов ленты; одновременно не больше 8 тредов.
- `rpc.ts`: обработчик запросов сервера и режим без накопления уведомлений только для
  соединения слушателя; обычные короткие соединения отвечают `-32601`, как сейчас.
- `item/tool/requestUserInput` → вопрос: id — `itemId`; части — `questions[]` (`id` Codex,
  `multiSelect: false`, `allowOther` = `isOther` или нет вариантов). Часть с `isSecret` делает
  вопрос `answerable: false` с причиной «Секретный ответ вводится только в приложении ChatGPT».
- Ответ — результат того же запроса: `{ answers: { [id]: { answers: [подпись или текст] } } }`;
  подтверждение — `serverRequest/resolved` или продолжение хода до 10 с.
- `serverRequest/resolved` без ответа Kit — вопрос `answered` без `answers` («Ответ дан в
  приложении»); конец или прерывание хода при ожидающем вопросе — `cancelled`.
- Чужие запросы сервера на соединении слушателя (одобрения и прочее) обрабатываются способом,
  который по T002 не влияет на диалоги ChatGPT (без ответа или `-32601`).
- Закрытые вопросы треда хранятся в памяти (последние 20) и после перезапуска службы не видны.
- Если T002 покажет, что запрос не доходит до второго подписчика, реализуется только C0, а
  C1 — `task:block` T002 и решение пользователя.

### 2.5. Панель: карточка вопроса (`session-chat`)

Новые `src/question-model.js` (чистая модель) и `src/question-card.js`; стили — в
`session-chat.css`. Эталон — карточка Claude Desktop (снимок пользователя 15.11.2026, тёмная
тема) в токенах панели.

- Ожидающий вопрос стоит в конце ленты над полем ввода; закрытый — в ленте после
  `afterMessageId`, компактно: вопрос и выбранный ответ, «Ответ дан в приложении» или
  «Вопрос отменён».
- Часть: заголовок-метка, текст вопроса, варианты (подпись и описание) — радиокнопки или
  флажки при `multiSelect`; при `allowOther` — строка «Свой вариант» с полем текста.
  Несколько частей идут одна под другой в одной карточке.
- «Отправить» активна, когда выбран ответ на каждую часть; с клавиатуры — Ctrl/⌘+Enter.
  Одно нажатие по варианту ответ не отправляет. Кнопка «Пропустить» есть, только если проба
  доказала родное действие пропуска у этого провайдера.
- `answerable: false`: варианты видны без выбора, под ними причина и ссылка на чат провайдера.
- Выбор хранится вместе с состоянием сессии и переживает опрос. Вопрос закрылся, пока
  пользователь выбирал, — карточка показывает итог; `question-stale` — то же и внеочередной
  опрос; другие отказы — текст ошибки под карточкой, выбор сохранён, повтор той же кнопкой.
- Сенсорные цели не меньше 44 px, без элементов, видимых только при наведении; тёмная и
  светлая темы; узкая раскладка iPad.
- Пока есть ожидающий вопрос, строка состояния диалога — «Агент ждёт вашего ответа».

### 2.6. Пробы и бюджет

Программы T001 и T002 — в документах фактов (раздел 3 каждого). Пробы идут в одноразовом
проекте Kit, пользовательские сессии не трогают, исполняемых файлов в репозиторий не
добавляют: скрипт — в evidence, в блоке кода. Живые ходы — только после прямого согласия
пользователя: Claude — не больше 10 коротких ходов Haiku (серия K — ещё до 4, только если A1
не доказан), Codex — не больше 6 коротких ходов. Что видно в Claude Desktop и ChatGPT,
подтверждает пользователь; без подтверждения факт остаётся «не проверено».

## 3. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Контракт, маршрут, карточка | общий код Node и панели | так же | так же; x64 и ARM64 |
| Claude: показ из транскрипта | путь из хука | так же | так же |
| Claude A1: хук вопроса | команда `wfk hook question` | так же | exec-форма `node.exe wfk.mjs`, как остальные хуки Claude |
| Claude A2: клавиши | expect-хост | expect-хост, нужен `expect` | ConPTY, те же клавиши |
| Codex C0: флаг | сокет демона | так же | `codex app-server proxy` |
| Codex C1: слушатель | долгое соединение с сокетом | так же | долгий процесс proxy |

Поведение одинаково на трёх ОС; отличается только транспорт. Вопрос Codex виден Kit только
там, где ход идёт в демоне, к которому Kit подключён (как Stop): без общего доступа к чатам
ходы приложения ChatGPT Kit не видит. Новых вызовов программ ОС нет.

## 4. Проверка

- Тесты: нормализация и `checkQuestionAnswer`; транскрипт Claude (ожидание, ответ, отмена,
  несколько частей, sidechain); ожидающие хуки и `wfk hook question` на подставной службе, или
  движок A2 на записанных кадрах; слушатель Codex на подставном демоне (подписка, запрос,
  ответ, `serverRequest/resolved`, секретный вопрос, чужой запрос, обрыв); маршрут и коды;
  модель карточки. Ветки `win32` и `linux` — с подставленной платформой.
- Браузер (изолированный Chromium): выбор, свой вариант, несколько частей, отправка, отказы,
  закрытие с другой стороны, обе темы, узкая раскладка.
- Живая проверка, macOS, пользователь и агент (T008): вопрос Claude и вопрос ChatGPT — ответ
  из панели и ответ из приложения. Windows — проверяющий на Windows. Linux — только CI.
- CI точного SHA поставки: macOS, Linux, Windows x64 и ARM64, ветка `ci/M33-agent-questions`.

## 7. Наблюдение вне M33

Пользователь, 15.11.2026: в Claude Desktop во время долгого хода появилась строка о ходе
работы («Сейчас разбираюсь с тем, как устроены лента и каналы…»), в диалоге Workflow Kit её
нет. Формулировка в Desktop не совпала с текстом реплики агента в том же месте. Причина не
установлена (транскрипт не читался). Это расхождение полноты ленты — отдельная веха.
