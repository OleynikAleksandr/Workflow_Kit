# M39: состояние, разрешения и переходы автопилота

Часть [спецификации M39](M39-autopiloting.md). Здесь описан новый контракт; названия
публичных API окончательно сверяются при ревью до реализации. Старый режим остаётся
совместимым. Прямого доступа службы к `.harness/workflow/runtime` нет.

## 1. Настройки и журнал запуска

Настройки службы: `autopiloting = { version: 1, revision, mode, review }`,
`mode: off | after-start | full`, `review: boolean`. Файл `autopiloting.json` в
`DataDirs.configDir`; отсутствие даёт `off`, `review=false`. Существующее решение о
ревью текущего задания имеет приоритет; нельзя мигрировать разные значения сессий
в одно случайно выбранное глобальное значение. Новая настройка — default будущих заданий.
Чтение и атомарная запись используют `#data-store`, остальные поля конфигурации сохраняются.
Невалидный/нечитаемый файл не включает автопилот: ошибка видна в Settings.

Маршруты через штатную авторизацию HTTP-сервера:

- `GET /api/settings/autopiloting` → настройки и доступность.
- `POST /api/settings/autopiloting { expectedRevision, mode, review }` → сохранённые
  настройки. Неизвестное значение — 400 `bad-request`; устаревшая ревизия — 409
  `settings-stale` с актуальными значениями. Сначала запись на диск, затем публикация
  нового состояния. Выбор `off` приостанавливает будущие действия с reason=settings-off, resumable=true.
- Раздел `/api/state.autopiloting`: настройки и краткие записи запусков по проектам;
  длинные цитаты пользовательских сообщений в состояние панели не попадают.
- `POST /api/projects/:id/autopiloting/pause|resume|stop { runId, expectedRevision }`:
  только соответствующий проект/запуск. `resume` действует в пределах прежних полномочий,
  после `stop` можно продолжать план вручную либо явно запустить новый разрешённый цикл.
  После off явный resume фиксирует новое пользовательское действие и новую ревизию
  разрешения того же runId в прежних границах. Одного изменения Settings для этого мало.

Записи запуска — `.workflow-kit/local/autopiloting/<runId>.json` в проекте (вне git),
пишет только служба. Версионированный JSON, атомарная запись и сериализация по проекту.
Данные содержат:

- `runId`, `projectId`, `owner` (provider/session), `mode`, `review`, `revision`;
- `request`: источник `panel-start | user-command | plan-decision | panel-resume`, id/номер исходного
  пользовательского хода, его точная цитата разрешения, время и краткая цель;
- `proposal`: scopeId, generation, digest окончательного предложения и связанных
  спецификаций; `scopeId` после выбора; один активный запуск проекта;
- `authority`: разрешённые delivery task ids/эффекты, приёмка/закрытие/publication,
  исходная ветка, remote/upstream, исходный HEAD, `revocation: { at, reason, resumable } | null`;
- `phase`, `pausedFrom`, `reason`, `nextAction`, время изменения;
- `pendingAction`: стабильный actionId, тип, входная ревизия/HEAD, стадия intent/sent;
- `receipts`: выполненные переходы и их доказательства (task id, commit SHA, id операции
  Kit, review digest, CI/check evidence, опубликованный SHA). Повтор не создаёт новую запись;
- счётчики повторов по действию, последний ключ прогресса и время следующего повтора.

Фазы: `preparing → reviewing → choosing → starting → executing → delivering →
verifying → accepting → closing → publishing → completed`; побочные состояния
`waiting`, `paused`, `blocked`, `stopped`. В `waiting/paused/blocked` хранится этап
возврата. Выключенный `review` пропускает `reviewing`, обычные work/delivery могут
чередоваться только согласно плану Kit. `completed` означает проверенную публикацию.
Scope NONE после закрытия не удаляет запись запуска: остаётся этап publication.

## 2. Прямое разрешение и подготовка

`wfk session plan "<summary>" --authorized "<точные слова пользователя>"` расширяет
существующую команду. Флаг применим только к прямому разрешению текущей задачи:

- `full` + подтверждённый пользовательский источник → регистрирует или возвращает тот
  же запуск и печатает `action: prepare`, `runId`, зафиксированное ревью и инструкцию
  создать спецификацию и `scope:propose`; агент продолжает этот ход без карточки вопроса;
- без `--authorized` сохраняется обычная карточка вопроса. В full её ответ `review|plan`
  может запустить подготовку, `talk` — нет; это сохраняет работу старых клиентов;
- `off/after-start`: прямое поручение может сразу разрешить подготовку без повторного
  вопроса, но не даёт автоматического выбора/старта или прав на публикацию. Они появятся
  только при ручном старте after-start. Ответ содержит фактическую политику;
- одинаковый авторизующий ход/проект/задание возвращает существующий runId, а не создаёт
  повторный запуск; другой активный запуск — 409 `run-active`;
- старый CLI без поддержки выдаёт обычную ошибку версии; новые инструкции при таком
  capability не предлагаются.

Агент понимает смысл просьбы; скрипт не ищет регулярным выражением слово «да». Служба
подтверждает происхождение: сохраняет доступный `HookInput.prompt` настоящего
UserPromptSubmit после определения own/delivery либо исходное сообщение панели
`source=user`. Цитата должна присутствовать в исходном пользовательском тексте.
Для `plan-decision` источником служит факт ответа пользователя на карточке. Нельзя
передать цитату из reviewer/decider/reminder и получить новое разрешение. Хранится
только связанный с запуском источник, без копирования полного транскрипта. Если хук
не передал текст/источник, возвращается `authorization-source-missing` с объяснением;
поддержку этого пути проверяют live для каждого провайдера, обхода через выдуманную
цитату нет. После регистрации источник и runId переживают перезапуск.

При старте after-start источником служит существующий маршрут кнопки start; запись
разрешения происходит до отправки первого рабочего сообщения. Идентичный повтор
кнопки/HTTP-запроса не меняет scope и не запускает первый task повторно.

План full обязан описывать автоматические критерии и действия поставки. Автор устраняет
пропуски при подготовке, до запуска. Если обязательны новые данные/ручная проверка,
он объясняет конкретное препятствие. Выбор full не переписывает требования пользователя.

## 3. Ревью и выбор способа выполнения

`plan-review` читает default Settings для нового задания, а затем snapshot запуска.
Старые session decisions остаются данными конкретного задания. Убирать старые вопросы
можно только штатным `dismiss`, не массовым удалением файлов.

`cross-review` хранит `reviewedProposal = { scopeId, generation, digest }`. Digest
считает публичный Kit: канонические поля плана и байты документов `spec`/`context`,
включая вынесенные части спецификации, упомянутые контекстом предложения. Времена,
служебная ревизия журнала и собственные поля ревью не влияют на digest. Перед выбором
повторно читаются предложение и документы. ScopeId сам по себе не является доказательством.

Существующий цикл `REVIEW: APPROVED` + `REVIEW: AGREED` используется с этой привязкой.
Каждое изменение автором даёт ревьюеру актуальный digest и список документов; ответ
для старого digest не разрешает старт нового. Итог `agreed` запускает событие reconciler,
а не прямую отправку бесконтрольного нового сообщения. Неуспех/отмена, поздние сообщения
после stop и ответы посторонней сессии не разрешают выбор.

Без review используется текущий digest, но стадия помечена `skipped-by-setting`, а не
«ревью пройдено». После successful review → public `scope:choose` с текущей generation
и записью «Автоматический выбор по поручению <runId>» → обновление состояния → привязка
scope-разрешения → общий метод start. Ручной и автоматический пути сериализуются одним
мьютексом проекта. Уже выбранный/начатый этим запуском план подтверждается и не создаётся
вторично; чужой scope/owner — `scope-changed`, без захвата проекта.

Рекомендация orchestrated применяется при доступной capability провайдера. Последовательный
fallback записывается явно и допустим только если все задачи можно выполнить последовательно.
Политика maxWorkers не превышает значение плана и доступные возможности приложения.

## 5. Продолжение, ожидания и восстановление

Единственный отправитель M39-продолжений — reconciler; старые маршруты и Stop передают
ему события. Полная таблица управления, after-start на старом плане и вопросы провайдера
вынесены в [M39-autopiloting-controls.md](M39-autopiloting-controls.md).

В `autopilot` выделяется reconciler: читает сохранённый запуск, свежий Kit status,
состояние канала, ревью и Git; выбирает не более одного следующего действия. Триггеры:
Stop/idle, изменение Kit, окончание ревью, результат checks/CI, startup службы и
истечение backoff. Всё под одним мьютексом проекта. Опрос не создаёт новые поручения.

Порядок приоритетов: revocation/stop → pause/пользовательская коррекция цели → сверка
owner/scope → незавершённое действие → обязательные барьеры → следующий этап. Перед
каждым изменением состояния/внешним действием после await повторно проверяется
актуальность run revision и stop; поздний callback не возобновляет остановленный запуск.
Включение/отзыв и действия сериализуются, чтобы публикация не началась после отзыва.

Перед действием пишется intent с actionId. После успеха — receipt. После падения между
ними проверяется реальность: task status/HEAD, история accept/close, generation выбора,
очередь сообщения, SHA remote. Повторяется только незавершённый эффект. Для отправки
агенту используется тот же message id и подтверждение доставки; отсутствие ответа
не означает, что сообщение не было доставлено. Новый owner не выбирается молча.
После перезапуска активная сессия сначала сверяется с провайдером, второй ход параллельно
не отправляется; если автоматическое пробуждение недоступно, видна конкретная причина.

Прогресс — переход task/assignment/integration, новая проверенная ревизия/HEAD,
завершённая операция или новое состояние обязательного CI. Просто текст агента,
обновление времени и повторный poll прогрессом не считаются. Долгое ожидание имеет
отдельный статус и не расходует попытки исправления. По одному ошибочному actionId
максимум 3 автоматических повтора с backoff 5/15/45 секунд; после них `blocked` с
ошибкой и следующим действием. Для agent-no-progress — 3 последовательных завершённых
хода без такого прогресса. Успешная новая стадия сбрасывает относящийся к ней счётчик.
Нет общего лимита 40 полезных задач. Стандартные ограничения доступа провайдера сохраняются.

Обычное пользовательское сообщение получает приоритет в очереди, после обработки
статус-вопроса/уточнения исполнитель продолжает. Прямой stop/pause регистрируется через
`wfk`/панель до следующего действия; пользовательское намерение трактует агент, не
грубый regexp. Новая несовместимая цель не смешивается с текущим разрешением.
Поддерживается live остановка кнопкой даже во время недоступного/зависшего агента.

Для CI источник обязательных проверок — только `automation.ci` окончательного плана,
включённый в review digest и grant. `progress` не может уменьшить requiredChecks,
сменить remote/branch или отключить exactSha. При plan:extend разрешённая политика
сохраняется; её ослабление требует нового пользовательского решения и ревью.

Новый `wfk session progress --input <json>` и loopback-маршрут принимают runId,
actionId, stage, targetSha, ciPolicyDigest и waitReason; только owner данного запуска.
Полный JSON описывается справкой CLI; чужой owner, устаревший actionId, неподходящий
SHA или неизвестный digest отвергаются. Это уведомление об ожидании, не результат CI.
`pending`, `failed`, `cancelled`, отсутствующий job и результат другого SHA не дают
успеха. Новый функциональный HEAD требует новых доказательств; повторный poll не прогресс.

`GitHubCi.read(target, sha, frozenPolicy)` независимо получает GitHub Actions status
через настроенный gh, сверяет repository, SHA и весь закреплённый перечень jobs.
Отсутствие gh/авторизации даёт capability blocker только если удалённый CI обязателен.
Исполнение через execFile с аргументами/таймаутом, без shell и вывода секретов.
`gh` — кроссплатформенная зависимость, не OS-specific программа: изменений allowlist
платформ не требуется. Адаптер/тесты — git-publish, wiring — cli. Программы не ставятся
автоматически. При ci=null остаются обязательные проверки Kit.

При failed CI начатой delivery применяется публичный defer-delivery и fixes round
по [контракту Kit](M39-autopiloting-kit.md), а не повтор заведомо запрещённого plan:extend.

## Поведение на ОС

| Область | macOS | Linux | Windows |
| --- | --- | --- | --- |
| JSON и блокировки | Atomic helpers, path | То же | То же, x64/ARM64 |
| Хуки и источник команды | Реестр провайдеров | То же | То же |
| Запуск Kit/Git | KitRunner/GitRunner | То же | Существующие Windows-адаптеры |
| Рестарт, пауза, повтор | Общая машина состояний | То же | То же |

Новые прямые вызовы программ ОС и сравнения `process.platform` не требуются.
