# Публикация на GitHub — после закрытия scope

## Цель и согласование

Сейчас push на GitHub выполняется задачей поставки внутри scope. Коммиты, которые появляются
после неё (запись о публикации, приёмка, закрытие scope), остаются неопубликованными. Так было
09.11 со scope `m4-claude-reviewer`: на GitHub не попали три служебных коммита.

Решение пользователя (09.11.2026): «Публикация должна быть тогда, когда полностью принят и закрыт
какой-то текущий скоп. И это правило нужно в Workflow Kit … интегрировать. … не всегда будет у
локального репозитория … GitHub версия. Но как только пользователь ее попросит сделать, этот
принцип должен появляться. Что GitHub публикация — это внеплановое действие после закрытия плана
и скоп»; «Да, пиши спецификацию».

## 1. Принцип

- Публикация на GitHub (`git push`) — действие вне плана. Её нет в задачах scope, в том числе в
  задачах поставки.
- Публиковать можно только при закрытом scope (активного scope нет): в удалённый репозиторий уходит
  законченный результат вместе с приёмкой и закрытием.
- Публикация происходит только по просьбе пользователя или по нажатию кнопки в панели. Агент не
  публикует по своей инициативе.
- Сборка, упаковка и установка релиза остаются задачами поставки внутри scope: пользователь
  проверяет релиз до приёмки. Наружу выносится только push.
- Без удалённого репозитория (нет upstream у текущей ветки) принцип не проявляется: нет кнопки,
  нет подсказок агенту о публикации.
- Публикация безопасна: только fast-forward, без `--force`, без удаления веток. Если удалённая ветка
  ушла вперёд или истории разошлись, публикация отказывает с причиной; объединение — отдельная
  работа по решению пользователя.

## 2. Слой Kit (Harness Workflow Kit, проект harness-ai)

Kit — отдельный проект; здесь лежит его бандл 2.2.2 (`kit-bundle`). Его управляемый раздел
`AGENTS.md` сейчас говорит «Build, packaging, publishing and push happen only in delivery tasks».
Для Kit это требования, которые выполняются в harness-ai, после чего бандл здесь обновляется
отдельным scope:

- команда `scripts/workflow publish`: при открытом scope — отказ `SCOPE_OPEN`; при грязном дереве —
  `WORKTREE_DIRTY`; без upstream — `NO_UPSTREAM`; без новых коммитов — `NOTHING_TO_PUBLISH`;
  удалённая ветка впереди или история разошлась — `REMOTE_AHEAD`; иначе `git push` текущей ветки
  в её upstream без `--force`, сверка SHA после push, запись события публикации в историю Kit;
- push-хук Kit (`git-hook pre-push`) отказывает в push, пока scope открыт;
- управляемый раздел `AGENTS.md`: вместо push в задачах поставки — «Publishing to the remote is not
  a plan task: after the scope is closed and only when the user asks, run `scripts/workflow publish`»;
- до обновления бандла продуктовый слой (раздел 3) действует сам и не зависит от этой команды.

## 3. Слой Workflow Kit (этот репозиторий)

### 3.1. Служба: состояние и действие публикации

- Новый модуль `git-publish` (кластер `projects` части `backend-core`).
- Состояние публикации проекта — раздел `publication` в `/api/state`, по проекту:
  `{ branch, upstream, ahead, behind, dirty, scopeOpen, state, reason, lastPublished }`, где
  `state` — `none` (нет upstream: раздел пуст, кнопки нет), `up-to-date`, `ready`, `blocked`
  (причина по-русски: «scope открыт — опубликовать можно после закрытия», «есть незакоммиченные
  изменения», «на GitHub есть коммиты, которых нет локально»).
- Состояние считается командами git в папке проекта (`rev-parse --abbrev-ref @{u}`,
  `rev-list --left-right --count @{u}...HEAD`, `status --porcelain`) не при каждом опросе панели,
  а при изменении плана Kit, после публикации и не чаще раза в 30 с по запросу состояния;
  удалённый репозиторий не опрашивается (`fetch` — только перед самой публикацией).
- `POST /api/projects/:id/publish {}`: заново проверяет условия (scope закрыт — по `workflow`
  проекта; дерево чистое; upstream есть), делает `git fetch` upstream, отказывает 409 с кодом
  (`scope-open`, `worktree-dirty`, `no-upstream`, `nothing-to-publish`, `remote-ahead`), иначе
  `git push` без `--force` (хуки репозитория, в том числе хук Kit, работают как обычно), затем
  сверяет SHA локальной ветки и upstream. Ответ — `{ published: true, from, to, sha }` или ошибка
  с выводом git. Один push на проект одновременно.
- Учётные данные git не трогаются: push идёт с настройками пользователя (helper ключей macOS);
  ошибка аутентификации показывается как есть, с подсказкой выполнить push один раз в терминале.

### 3.2. Панель

- На экране проекта и на экране сессии-владельца закрытого плана — строка «GitHub»:
  «Опубликовано» / «Неопубликованных коммитов: N · Опубликовать на GitHub» / причина блокировки.
  Без upstream строки нет.
- Кнопка подтверждения не требует (действие обратимо только новым коммитом, поэтому текст кнопки
  точный: «Опубликовать на GitHub (N коммитов)»); во время push — «Публикуем…», затем результат
  с коротким SHA или ошибка git.

### 3.3. Агент

- В разделе `AGENTS.md`, который Workflow Kit ставит в проекты (`kit-structure`, `AGENTS_SECTION`),
  — правило «GitHub publication»: push не входит в задачи scope, включая задачи поставки; если
  пользователь просит опубликовать при открытом scope — сначала довести scope до приёмки и
  закрытия (по командам пользователя), затем опубликовать кнопкой панели или командой
  `wfk project publish`; без просьбы пользователя не публиковать.
- `wfk project publish` — команда CLI для агента и терминала: вызывает
  `POST /api/projects/:id/publish` для проекта текущей папки и печатает результат.
- Правило действует и для этого репозитория: его релизные задачи больше не делают push.

### 3.4. Журнал изменений

- Задача поставки релиза переносит записи из `[Unreleased]` в раздел версии `CHANGELOG.md`
  (версия и дата). Пропущенные версии 0.4.6 и 0.4.7 добавляются в этом scope по документам
  приёмки M4.

## 4. Границы

- Изменения бандла Kit и его команды `publish` — в harness-ai, не в этом scope.
- Создание удалённого репозитория, настройка `origin`, объединение разошедшихся историй, теги и
  GitHub Releases — не входят.
- Живую проверку релиза выполняет пользователь (решение 09.11): агент ограничивается тестами,
  проверками Kit и `wfk doctor --installed`.
