# M32: соединение и состояния панели

Часть [спецификации](M32-codex-history-recovery.md).

### 2.5. Исчезновение сокета и восстановление

В runtime расширить существующий daemon()/inflight координатором соединения на
экземпляр провайдера/CODEX_HOME; отдельный второй цикл проб не создавать. Общий probe
проверяет доступность, но не подменяет собственные свежие RPC Stop.
В каждой попытке заново разрешается controlSocket через realpath; учитывается замена
символической ссылки, исчезновение цели и перезапуск сервера. Старые probe/cache состояния
не считаются подтверждением нового соединения. Подключение выполняет новый handshake
и initialize; успех означает именно прошедшую инициализацию и успешное чтение.

Для безопасных чтений (лента, параметры, metadata/status) разрешены повторные подключения
после ENOENT, ECONNREFUSED, ECONNRESET, EPIPE и преждевременного закрытия транспорта.
Задержки 250 мс, 1 с, 2 с, 4 с, затем максимум 10 с с небольшим jitter. Опрос ленты
ограничен 5 с ВМЕСТЕ с подключением, initialize, status и items, а не CHAT_TIMEOUT_MS=30с.
В cooldown HTTP отвечает сразу из снимка либо типизированным отказом, не ждёт нового
подключения. Только один due poll начинает очередную попытку; другие используют тот же
probe с собственным оставшимся deadline. Чтение параметров также ограничено 5 с; Stop
сохраняет собственный общий deadline 8 с и не ждёт общего inflight ленты.
Один общий recovery probe предотвращает шторм от вкладок, ленты и параметров; соединения
для пользовательских действий не разделяют RPC id и уведомления с чужим запросом.
При успешном чтении backoff сбрасывается. Нет фонового busy-loop и неограниченного
количества таймеров; dispose/остановка службы освобождают ресурсы.

Координатор может повторять соединение ДО отправки изменяющего RPC, но никогда не
переисполняет произвольный callback withDaemon: он может содержать turn/start, interrupt,
запись параметров или удаление. Повторное чтение после неопределённого исхода действия
не считается повтором самого действия. Deadline Stop имеет приоритет над backoff.
Ошибки авторизации, unsupported, invalid params, frame-too-large не являются причиной
перезапуска соединения по бесконечному сетевому retry.

Windows proxy должен сохранять причину раннего завершения: безопасный ограниченный stderr,
exit code и тип ошибки без токенов/текстов диалога. Повторяет только тот же connect/recovery
контракт. Не считать любое завершение proxy отсутствующим сокетом.

Recovery автоматически подключается к вернувшемуся демону, но не запускает/не убивает
демон, не меняет CODEX_HOME, вход и общий доступ. Если демон не возвращается, показать
«Нет подключения к Codex. Проверьте демон в настройках провайдера»; существующее действие
запуска демона остаётся отдельным. Отсутствующий сокет не объявляется потерей истории.

### 2.6. Панель и сообщения об ошибках

Сохранять ленту, черновик, очередь, фокус и позицию прокрутки. В области ошибки ленты
показывать одну краткую строку: «Восстанавливаем подключение к Codex…»; после 30 секунд
недоступности — текст о проверке демона из 2.5. Во время первичной/дополнительной загрузки
показывать «Загружаем диалог…» в области состояния ленты. Успешная синхронизация убирает
строку без сообщения об успехе. Не возвращать служебные строки под composer, удалённые M28.

Автоматическое чтение не создаёт повторных тостов. Ошибки пользовательского действия
остаются видимыми. Ошибка восстановления не очищает текст, не повторяет отправку,
не включает Stop по устаревшему снимку. После возвращения связи обновляются также параметры.


### 2.7. Детерминированный контракт sync и HTTP

`sync = { state: loading | ready | partial | reconnecting | unavailable,
reason?: string, retryAfterMs?: number, gaps?: { turnId: string, reason: string,
itemId?: string, beforeItemId?: string, afterItemId?: string }[],
gapCount?: number }`. Необязательные поля добавляются в ChatPage и whitelist chatPageOut.
Gaps ограничены последними 64 записями; gapCount сообщает общее число известных пробелов
текущего прохода. Их состояние живёт в том же ограниченном LRU, без отдельного безлимитного
кэша. itemId известен лишь при доказанной идентичности; иначе границы before/after
обозначают открытый непрочитанный диапазон, отсутствие границы — край хода. Не утверждать,
что внутри только один item. reason — безопасный русский текст, без stderr и внутренних путей.

Первый сбой и 30-секундный интервал считает серверный координатор по монотонным часам,
общим для всех вкладок. Success сбрасывает отсчёт; перезапуск службы начинает новый.
Серверная идентичность: наблюдаемые pid/start identity, realpath цели, initialize.userAgent.
Локальный reconnect epoch меняется только при доказанном транспортном сбое
(ENOENT/ECONNREFUSED/ECONNRESET/EPIPE/неожиданное закрытие незавершённого RPC).
Изменение серверной идентичности или такой сбой инвалидирует снимки управления
и кэш возможностей; неизвестность признака не доказывает совпадение.
withDaemon создаёт соединение на вызов: его нормальное закрытие, oversized, malformed JSON
и unsupported не меняют epoch и не запускают сетевой backoff. Ошибка status может
инвалидировать снимок независимо; oversized при чтении items не инвалидирует успешный status.
Gaps ключуются серверной идентичностью и статусом хода, а не epoch; при временно неизвестной
идентичности не стирать границы и не перечитывать gap до успешной проверки сервера.

| Ситуация | HTTP и данные | sync / интерфейс |
| --- | --- | --- |
| Первичная загрузка ещё идёт | 200, накопленный снимок | loading; «Загружаем диалог…» |
| Успешно загружен хвост | 200, полный хвост до 100 | ready; строка состояния скрыта |
| Один элемент/диапазон недоступен, остальные читаются | 200, доступный хвост | partial + gaps/reason; видимая пометка о пробеле, новые сообщения приходят |
| Сетевой сбой <30с, снимок есть | 200, ПОЛНЫЙ последний снимок | reconnecting, retryAfterMs |
| Сетевой сбой <30с, снимка нет | 503 codex-reconnecting, details.sync и retryAfterMs | reconnecting; сохранить браузерную ленту, не заменять пустотой |
| Сетевой сбой ≥30с, снимок есть | 200, полный последний снимок | unavailable + retryAfterMs; проверка демона, попытки продолжаются |
| Сетевой сбой ≥30с, снимка нет | 503 codex-unavailable, details.sync и retryAfterMs | unavailable; сохранить браузерную ленту |
| Неподдерживаемый протокол | 502 codex-history-unsupported, details.sync | unavailable; причина совместимости, сетевой retry не запускается |

Временный сбой никогда не возвращает 200 с пустым массивом вместо существующего снимка.
При серверной ошибке панель сохраняет собственный список; свежий пустой тред при ready
может очистить ленту. Поэтому catch сохраняет nodes, а apply заменяет только полным
снимком или накопленным initial loading при отсутствии ранее успешного снимка.
При повторной синхронизации со старым снимком держать его до готовности нового хвоста.
REGISTRY readError должен сохранять status 503 для двух новых временных кодов; прежние
ошибки других провайдеров сохраняют контракт 502. Пробелы не превращаются в ready без reason.

### 2.8. Параметры и промежуточные состояния

UX параметров остаётся как в M28/M29: ошибка фонового GET не создаёт строки/тоста,
последние подтверждённые значения сохраняются, следующий штатный poll после recovery
обновляет их. POST никогда не повторяется координатором; ошибка явного действия
показывается существующим report. FAILURE_SHOW_MS остаётся только механизмом прежних
pending failures (включая Claude), не таймером транспортного GET Codex.
T004 проверяет эти правила вместе с лентой и восстановление параметров без reload.

T002b1 вводит типы и обработку всех состояний sync/503 в registry, но существующие
провайдеры могут не отправлять sync. T002b2 выдаёт loading/ready/partial без retryAfterMs.
До T003 сетевой сбой возвращает прежнюю типизированную ошибку HTTP 502 (даже при наличии
кэша); успешный stale-снимок не выдаётся за свежий. Unsupported уже даёт 502
codex-history-unsupported с sync unavailable без retryAfterMs и без сетевого retry.
T003 добавляет серверный отсчёт 30 с, reconnecting/unavailable для транспортных сбоев,
200 со снимком или 503 без снимка; retryAfterMs — оставшееся время до следующей пробы,
неотрицательное, ограничено 10 с плюс заданным jitter (±10%, максимум 11 с).

До завершения T004 панель ещё не понимает sync; промежуточные исходники T002b2–T003
не устанавливаются пользователю. Поставка возможна только после T005 и DOCS.
