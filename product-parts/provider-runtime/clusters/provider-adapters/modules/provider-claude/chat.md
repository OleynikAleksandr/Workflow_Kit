# provider-claude: диалог сессии

Лента сообщений и прямая отправка реплики для сессий Claude (M18, раздел 2.2;
`docs/planning/M18-session-chat.md`; исправления — M19, разделы 2.1 и 2.4,
`docs/planning/M19-session-chat-fixes.md`). Контракт (`ChatMessage`, `ChatPage`,
`CHAT_PAGE_LIMIT`) — `provider-registry`, его `chat.md`. Ссылка — из `module.md`.

## Чтение: `readMessages(project, sid, { limit })` (`src/chat.ts`)

- Источник — транскрипт сессии: `transcript_path` журнала хука (`findSession` →
  `hook.hook.transcriptPath`). Каталог транскриптов не вычисляется. Маршрут передаёт
  `localId` сессии; поиск — как у остальных методов (`localId` или `session_<X>`).
- Сессия без транскрипта в журнале хука (в том числе сессия панели, которую хук ещё не
  записал), файла ещё нет или путь не абсолютный `.jsonl` — пустая страница
  `{ messages: [], truncated: false }`.
- Файл есть, но не читается (нет прав, не файл, ошибка чтения) —
  `ProviderError('chat-unavailable', 'Claude не отдал переписку: <причина>')` (502).
- `createChatReader({ keep?, maxFiles? }) → ChatReader { read(path, limit), clear() }` —
  в `runtime.chat`; `refresh` провайдера очищает его. Чтение инкрементное, как у
  `transcripts.ts`: состояние на файл (`ino`, смещение, остаток строки, `TextDecoder` в
  потоковом режиме), до 200 файлов (самый старый выбывает). Смена `ino` или уменьшение
  размера — чтение с начала. Одновременные чтения одного файла ждут одно.
- В памяти — последние `keep` (`CHAT_PAGE_LIMIT`, 100) сообщений файла; выброшенные старые
  ставят `truncated: true`. Ответ — последние `limit` из них, от старых к новым, полные
  тексты (обрезает маршрут); `truncated` и тогда, когда `limit` меньше хранимого.
- `chatMessageOfLine(line) → ChatMessage | null` — правила строки:
  - строка длиннее `CHAT_MAX_LINE` (8 МБ, в знаках), не JSON-объект или без
    `"type":"user"`/`"assistant"` — не сообщение (длинная строка пропускается целиком,
    даже разорванная между чтениями);
  - нужны `uuid` (это `id`) и объект `message`; `at` — `timestamp` или `null`;
  - запись с `isCompactSummary: true` (служебная сводка сжатия контекста, M19) — не сообщение;
  - `user`: не `isMeta`, не `isSidechain`; текст — `message.content` строкой или части
    `type: "text"` через `\n`; части и строки, начинающиеся (после пробелов) с
    `<local-command`, `<command-name>`, `<command-message>`, `<task-notification>`,
    `<system-reminder>`, отбрасываются; только `tool_result` — не сообщение. Ответ хука
    `Stop` («Stop hook feedback: …») остаётся: это то, что получил агент;
  - `assistant`: не `isSidechain`; только части `type: "text"` (без `thinking` и
    `tool_use`) через `\n`;
  - пустой (из пробелов) текст — не сообщение. Каждая строка транскрипта — своё
    сообщение (Claude пишет части одного ответа отдельными строками с разными `uuid`).

## Запись: `sendDirect(project, sid, text)` (`src/direct.ts`)

- Только сессия панели с живым процессом: `runningPanelRecord` (`src/sessions.ts`, общий с
  `wakeSession`) поднимает прерванную (`resumeSession`), остановленная намеренно, чужая или
  в архиве — `false`.
- `cleanDirectText(text)`: `\r\n` и `\r` → `\n`, управляющие символы (C0, DEL, C1) кроме
  `\n` и `\t` удаляются, в том числе `ESC` — текст не может закрыть вставку. Пустой (из
  пробелов) после очистки — `false`.
- Очередь на сессию (по `sid` и экземпляру провайдера): следующий вызов ждёт итога
  прежнего. Ожидание, пока прежний `<debug>.text` заберут, — до `directWaitMs` (5 с,
  проверка раз в `DIRECT_POLL_MS` 200 мс); не забрали — `false`, чужой файл не трогается.
  Ждущий `<debug>.message` (пробуждение) отправке не мешает.
- Запись: `<debug>.text.partial`, затем переименование в `directTextFile(debugFile)` =
  `<debug>.text`; содержимое — очищенный текст без префикса (UTF-8). Забрали за
  `directWaitMs` — `true`; нет — файл удаляется, `false`, служба кладёт сообщение в очередь
  («В очереди»). Так и со сценарием старой версии (0.9.0 и раньше): `<debug>.text` он не знает,
  сообщение не теряется. Любая ошибка — строка журнала и `false` (не бросает).
- Известное ограничение: если сценарий забрал файл ровно в момент тайм-аута, текст уже вставлен,
  но `sendDirect` вернул `false` и служба кладёт сообщение ещё и в очередь канала — агент изредка
  получает его дважды.
- `wakeSession` не пишет `<debug>.message`, пока ждёт `<debug>.text` (сообщение само начнёт
  ход), и пишет `wake\n` только если файла пробуждения нет (`wx`).

## Управляющие файлы `<debug>.text` и `<debug>.message`

| Файл | `session.exp` и `pty/host.ts` |
| --- | --- |
| `<debug>.text` (не пустой) | `ESC[200~` + текст + `ESC[201~`, пауза 700 мс (`PASTE_ENTER_MS`), `\r`, строка `MESSAGE_SENT` |
| `<debug>.message` (любое содержимое, префикс `text\n` не разбирается) | `WAKE_TEXT` «Workflow Kit: новое сообщение из панели.», 300 мс, `\r`, строка `WOKEN` |

Оба файла читаются раз в секунду после ссылки (сначала `.text`), затем удаляются.
Пробуждение, найденное в тот же опрос, что и вставленный текст, удаляется без ввода: ход
начинает сообщение. `session.exp` читает файлы в UTF-8, как `.rename`. Константы
(`MESSAGE_WAKE`, `TEXT_FILE_SUFFIX`, `WAKE_FILE_SUFFIX`, `PASTE_START`, `PASTE_END`,
`PANEL_SESSION_ENV`) — `src/pty/screen.ts`. Ввод во время хода Claude сам ставит в очередь и
отдаёт агенту в том же ходе (проба 2026-11-12).

## Поведение на ОС

| Что | macOS | Linux | Windows (x64, ARM64) |
| --- | --- | --- | --- |
| Лента | транскрипт по пути из хука | так же | так же |
| Вставка | `session.exp` (`expect`) | так же, нужен `expect` | `pty/host.ts` через ConPTY |
| `<debug>.text` / `<debug>.message` | `session.exp` | так же | `pty/host.ts` |
| Файлы | пути через `path`, запись UTF-8 | так же | так же |

Новых вызовов программ ОС нет. Вставка через ConPTY и в сессии с Remote Control вживую не
проверены (раздел 2.7 спецификации).
