# M25: правила надёжности параметров сессии

Приложение к [спецификации M25](../planning/M25-session-parameters.md): правила, добавленные
по двум кругам ревью плана (13.11.2026). Факты проб — [M25-session-parameters-facts.md](M25-session-parameters-facts.md).

## 1. Проба осуществимости идёт первой (T001)

Главный результат — управление ChatGPT из Kit — зависит от поведения приложения ChatGPT,
которое пробами без пользователя не проверить. Поэтому первая задача плана — живая проба
с пользователем при активном общем доступе, на чате проекта:

1. Kit (скрипт пробы, в репозиторий не входит) меняет усилие и модель через
   `thread/settings/update`.
2. Пользователь смотрит переключатели приложения ChatGPT на Mac и на iPad.
3. Пользователь отправляет следующий ход из приложения; из файла сессии читается
   `turn_context` этого хода: фактические модель и усилие.
4. Обратное направление: пользователь меняет параметр в приложении, Kit читает его из
   файла сессии.

Исходы:

| Исход | Признаки | Что дальше |
| --- | --- | --- |
| Положительный | Переключатели приложения на Mac и на iPad показывают значения, заданные из Kit; ход из приложения идёт с ними; обратное направление читается | T002 |
| Частичный | Ход из приложения идёт с новыми параметрами, но переключатели их не показывают, хотя бы на одном устройстве | блокировка |
| Отрицательный | Ход из приложения идёт со старыми параметрами, либо приложение заменяет их своими | блокировка |

Только положительный исход разрешает T002. При частичном и отрицательном T001 записывает
наблюдения в факты и доказательства и завершается, затем scope блокируется:
`scripts/workflow task:block --reason "<исход пробы T001>"`. Агент сам ограничение не
принимает.

Продолжение — только по решению пользователя. Если он принимает частичный исход как
ограничение приложения, до `task:unblock` согласованно меняются: требование «видна в
приложении ChatGPT» в разделе 4 спецификации, критерии T004, T007 и T008
(`task:update`), `docs/usage.md`; слова пользователя записываются в доказательства.
Критерий scope «действуют на следующий ход, в том числе отправленный из приложения» при
этом остаётся выполнимым. При отрицательном исходе он невыполним: план пересматривается
вместе с пользователем.

## 2. Принадлежность сессии и очередь изменений

- `GET` и `POST …/parameters` находят сессию в `provider.listSessions(project)` по `localId`,
  затем по `remoteId` — как маршрут ленты (`chat-routes.ts`). Нет — 404 `unknown-session`
  до любого обращения к `readParameters` или `updateParameters`. Провайдеру передаётся
  `localId` найденной сессии.
- `POST` одной сессии (ключ — провайдер и `localId`) выполняются строго по очереди в
  процессе службы. Провайдер внутри очереди читает текущие значения заново и строит
  изменение от них, а не от того, что видел клиент.
- Kit отправляет присланное поле и зависимые поправки, прочие настройки не передаёт.
  Демон значений не проверяет, поэтому несовместимая пара не должна попасть в тред: при
  смене модели в тот же `thread/settings/update` входят `effort`, если прежнее усилие
  модели не подходит, и `serviceTier: null`, если не подходит прежняя скорость
  (спецификация, 2.3, шаг 2). Усилие и скорость, которые модели подходят, не передаются.
- Унаследованное значение заменяется автоматически со строкой в `notes`. Значение,
  присланное в запросе и не подходящее модели, — отказ `parameter-invalid`: Kit не
  исправляет то, что пользователь выбрал явно.
- Проба: при `thread/settings/update { effort }` или `{ model }` демон сам согласует
  `collaborationMode.settings` и сохраняет `developer_instructions`. Поэтому смена модели,
  усилия, скорости или разрешений `collaborationMode` не передаёт.
- `collaborationMode` передаётся только при смене режима: `{ mode, settings: { model,
  reasoning_effort, developer_instructions: null } }` с моделью и усилием, прочитанными
  внутри очереди. Проба: `null` означает встроенные инструкции выбранного режима (демон
  подставил текст режима «План» и режима «Обычный»); свои инструкции при смене режима
  заменяются встроенными. Это смысл смены режима, а не побочный эффект смены усилия.

## 3. Чтение новейших записей JSONL (`provider-registry/src/jsonl-tail.ts`)

Файл сессии Codex и транскрипт Claude читаются одним средством.

- Холодное чтение (файл ещё не читался, стал короче или заменён): блоки по 1 МиБ с конца
  файла, пока не найдены все нужные виды записей или не достигнуто начало. Предел —
  256 МиБ; за ним ненайденный параметр отсутствует.
- Затем в памяти хранятся эффективные значения и смещение конца последней полной строки;
  следующее чтение разбирает только дописанное. Редкая запись, ушедшая из хвоста,
  остаётся в эффективных значениях.
- Строка длиннее блока собирается из нескольких блоков. Незавершённая последняя строка
  не разбирается и не пропускается: смещение остаётся перед ней. Строка с неверным JSON
  пропускается.
- Образцы тестов: редкая запись за пределами последнего мегабайта; строка длиннее блока;
  незавершённая последняя запись; укороченный файл.

## 4. Разрешения Codex: распознавание

Стандартный профиль распознаётся только по проверенной структуре `permission_profile`
новейшей записи `thread_settings_applied` (образцы сняты пробой):

| Профиль | Структура |
| --- | --- |
| `:danger-full-access` | `{ "type": "disabled" }` |
| `:read-only` | `managed`, сеть `restricted`, единственная запись: корень — `read` |
| `:workspace` | `managed`, сеть `restricted`; корень — `read`; `write` только у рабочих папок записи (`runtime_workspace_roots`) и у особых путей `slash_tmp`, `tmpdir`; остальные записи — `read` внутри рабочих папок |

Любая другая структура (запись в иной путь, сеть не `restricted`, незнакомый тип) —
«Особые разрешения»: `value: null`, в меню текущим не отмечен ни один вариант. `value`
распознанного профиля равен идентификатору из `permissionProfile/list`. Если новейшая
запись настроек — `turn_context`, используется его `sandbox_policy.type` только для
`read-only` и `danger-full-access`; `workspace-write` без записи `thread_settings_applied`
показывается как «Особые разрешения».

## 5. Соединения Codex, каталоги и доступность вариантов

- Проба: без `experimentalApi` работают `thread/read`, `account/rateLimits/read`,
  `model/list`, `permissionProfile/list`; `collaborationMode/list` и
  `thread/settings/update` отвечают `requires experimentalApi capability`.
- Соединения `parameters.ts` (чтение и изменение) открываются с `experimentalApi: true`.
  Демон отклонил такой `initialize` — повтор без флага: показ работает полностью, вариантов
  изменения нет. Остальные соединения Kit не меняются.
- Вариант изменения есть только у параметра, чей каталог получен: `model` и `effort` —
  `model/list`; `speed` — `serviceTiers` модели; `permissions` — `permissionProfile/list`;
  `mode` — `collaborationMode/list`. Каталог недоступен — параметр показывается (подпись
  по известным значениям или идентификатор), у него нет `options`, есть `reason`.
  `editable` — истина, если `options` есть хотя бы у одного параметра. В меню такой
  параметр остаётся: раздел с текущим значением и причиной, без выбора (спецификация,
  2.6). Пример частичной доступности: `model/list` получен, `collaborationMode/list`
  нет — модель и усилие меняются, «Режим» показан недоступным с причиной.
- Отказ `thread/settings/update` «метод недоступен» запоминается до `refresh()`: дальше
  `options` не отдаются, причина — «Эта версия Codex не поддерживает изменение параметров».
- Общий доступ: `GET` берёт последнее сохранённое состояние (`shared.cached()`, даже
  просроченное) и не вызывает `runCommand`; состояния ещё нет — вариантов нет, причина
  «Состояние общего доступа проверяется». Состояние обновляет действующее обслуживание
  (`maintain()`). `POST` перед изменением вызывает `sharedMode.refresh()`.

## 6. `wfk statusline`: оболочка и завершение

- Команда пользователя запускается той оболочкой, какой её запускал бы Claude: macOS и
  Linux — `/bin/sh -c`; Windows — Git Bash (`CLAUDE_CODE_GIT_BASH_PATH`, иначе `bash` из
  `PATH`), нет Git Bash — PowerShell (`powershell -NoProfile -Command`). `cmd` не
  используется.
- stdin передаётся байт в байт, stdout возвращается байт в байт; тесты — Unicode, кавычки,
  многострочный вывод.
- Ожидание 5 с. По истечении завершается всё дерево процессов команды: macOS и Linux —
  отдельная группа процессов и сигнал группе; Windows — `taskkill /T /F` через публичный
  вход `process-supervisor`. Обёртка выходит с кодом 0 и пустым выводом.
- Ошибка записи снимка, отсутствие службы, отсутствие оболочки не меняют вывод
  пользовательской команды (без оболочки вывод пустой) и код завершения.
- Пустой вывод скрывает строку состояния Claude (документация) — как и без Kit.

## 7. Файл настроек запуска Claude

Каждый запуск и возобновление получают свой файл `<logs>/claude/session-<ref>.settings.json`
(`ref` — тот же, что у журнала pty этого запуска). Файл пишется один раз до старта и не
переписывается; одновременные запуски разных проектов не пересекаются.

## 8. Поставка и CI

В `AGENTS.md` два правила. Раздел о трёх ОС: поставка не завершена без зелёной CI
четырёх платформ; до приёмки CI идёт на ветке `ci/<scope>`, `main` — после приёмки и
закрытия. Управляемый раздел Kit: `git push` не выполняет ни одна задача плана,
публикация — только по просьбе пользователя.

Коммит поставки (SHA) появляется лишь с завершением задачи поставки, а CI нужен уже
отправленный коммит. Поэтому поставка M25 — две delivery-задачи:

1. **T008** — локальный релиз 0.11.0 и живая приёмка. `git push` не выполняет. Её коммит
   — SHA поставки; в доказательствах запись «CI ожидает отправки ветки».
2. **Ветка `ci/m25-session-parameters`** на SHA поставки. Отправляет пользователь либо
   агент по его прямой команде в чате; команда и есть согласие на отправку до приёмки.
   Без команды никто ветку не отправляет: агент называет SHA и ждёт.
3. **T009** — delivery-задача «CI четырёх платформ». До `task:start` агент проверяет
   прогон CI для SHA поставки; задача начинается с подтверждением пользователя и только
   при зелёной CI на macOS, Linux, Windows x64 и Windows ARM64. Она записывает в
   доказательства SHA, ссылку на прогон и итог по каждой платформе. `git push` не
   выполняет, функциональных файлов не меняет.
4. **Красная или незапущенная CI**: T009 не начинается и остаётся TODO (новый раунд
   возможен, только пока задачи поставки не начаты). Дефект исправляет раунд исправлений
   (`plan:extend`) со своей локальной поставкой; ветка отправляется заново по команде
   пользователя, T009 проверяет новый SHA.
5. **Приёмка и публикация**: `accept` — после T009; `main` — после приёмки и закрытия.

Отступление от буквы раздела о трёх ОС одно: T008 завершается до CI, потому что без её
коммита проверять нечего. Его закрывает T009: поставка scope не завершена и scope не
принимается без зелёной CI. Решение принято 13.11.2026 по поручению пользователя
исправить план по итогам ревью («Я даю тебе полное разрешение»); прецедент M24 основанием
не служит.

## 9. Риски

- `thread/settings/update` и `collaborationMode/list` — экспериментальная часть протокола
  Codex. При отказе показ остаётся, варианты изменения отключаются с причиной.
- Формат файла сессии Codex и транскрипта Claude не публичен. Незнакомая запись
  пропускается, параметр не показывается; структура разрешений вне образцов — «Особые
  разрешения».
- Поведение приложения ChatGPT при внешнем изменении проверяет T001 до остальных задач;
  частичный и отрицательный исход блокируют scope (раздел 1).
- Строка состояния Claude: оболочка на Windows взята из документации, на устройстве
  проверяет проверяющий на Windows.
