# provider-kimi: серверы Kimi

Часть контракта модуля [provider-kimi](module.md), спецификации M8 (раздел 2.1)
и [M9](../../../../../../docs/planning/M9-kimi-start-fixes.md) (раздел 2.1).
Код — `src/server.ts`, решения провайдера — `src/provider.ts`.

## Чей сервер

Сессиями Kimi на машине может управлять несколько серверов: свой сервер
приложения Kimi Code (внутри процесса приложения), `kimi web` пользователя и
сервер Kit. Приложение видит вживую только ход своего сервера, а чужую
рабочую область папки не знает и заводит свою (живая проверка 0.6.0).
Поэтому Kit говорит с одним сервером:

- **Сервер приложения** (`server.app()`) — самая поздняя живая запись
  `server/instances`, которая не принадлежит Kit (`foreign()`: pid не из
  учёта процессов с `SERVER_OWNER`, процесс жив по `Liveness`), и чей
  `GET /api/v1/healthz` отвечает (ответ хранится `APP_SERVER_CACHE_MS`,
  5 с). Токен тот же — `server.token`.
- Пока он есть, `current()` и `ensure()` отдают его клиента: область,
  доверие, сессии, сообщения, список, имя, архив, удаление и ответ идут на
  него, свой сервер Kit не запускает. `owner()` — `app`.
- Нет его — сервер Kit (`own()`), как раньше; `owner()` — `kit`.
- Приложение запустилось при работающем сервере Kit: `maintain()` вызывает
  `retire()` — сервер Kit останавливается, когда ни один живой замок хода
  не принадлежит другому процессу, кроме приложения; иначе ждёт следующего
  обслуживания. Строка «server of Kit stopped: the Kimi Code app serves the
  Kimi sessions» идёт в журнал службы.
- Приложение закрылось: следующий `requireReady()` или `maintain()` (сервер
  уже использовался) запускает сервер Kit.
- При сервере приложения действия `restart-kimi-server`, `kimi-remote` и
  `kimi-remote-off` выключены с причиной `APP_SERVER_REASON` «сервер Kimi
  сейчас ведёт приложение Kimi Code», а их вызов — `ProviderError`
  `kimi-app-server` (409). `links.mobile` читается у сервера приложения
  (только чтение). Kit не меняет сервер, вход и Remote Control приложения.
- Статус: `details.server` — `app`, `kit` или `null`; при сервере приложения
  в `note` — `APP_SERVER_NOTE` «сессии Kimi ведёт сервер приложения Kimi Code».
- Хуки сервера приложения Kit не обновляет: при старом запуске приложения —
  `APP_RESTART_NOTE` (см. «Хук Kit» в [module.md](module.md)).

## Сервер Kit

- Запуск: `kimi web --no-open --port <свободный порт>` через
  `process-supervisor` с владельцем `{ provider: 'kimi', project: null,
  kind: 'server' }`, `logFile: null` (вывод отбрасывается: в нём ссылка с
  токеном), рабочий каталог — домашний, из окружения убран
  `KIMI_CODE_SESSION_LOCK`. Готовность: запись `server/instances` с pid
  процесса (или его портом) и ответ `GET /api/v1/healthz`, не дольше 15 с;
  иначе процесс завершается и операция отказывает `kimi-server`.
- Запуск по требованию (`requireReady()`); в `autostart()` — только при
  записях сессий Kimi; `maintain()` поднимает упавший сервер, если он уже
  использовался этой службой или есть записи сессий. Одновременные запросы
  делят один запуск.
- После перезапуска службы сервер находится по записи учёта процессов
  (`check` → `alive`) и записи `server/instances`; исчезнувший или чужой
  процесс из учёта убирается.
- Действие `restart-kimi-server` (область `provider`): при работающем
  сервере — «Перезапустить сервер Kimi» с подтверждением
  (`POST /api/v1/shutdown`, через 5 с — завершение процесса, затем новый
  запуск); при неработающем — «Запустить сервер Kimi».

## Поведение на ОС

Одинаково на macOS, Linux и Windows: записи читаются из
`<каталог Kimi>/server/instances` (`kimiPaths`), живость pid —
`process.kill(pid, 0)` (`defaultLiveness`). Приложения Kimi Code для Linux
нет: там «сервер приложения» — только `kimi web` пользователя.
