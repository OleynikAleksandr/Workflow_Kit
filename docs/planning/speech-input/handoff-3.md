## 10. Поток текста и защита черновика

Это центральная часть интеграции. Хорошее распознавание не компенсирует потерю пользовательского текста.

### 10.1. Владение полем

При старте зафиксировать:

- projectId и session key или идентификатор карточки вопроса;
- конкретный экземпляр поля;
- dictationId и поколение подключения;
- исходное значение;
- selectionStart/selectionEnd;
- актуальную ревизию черновика.

Одна диктовка принадлежит одному полю до завершения. Она не переезжает вслед за фокусом.

### 10.2. Алгоритм вставки

Простой проверяемый вариант:

1. Разделить исходный черновик на prefix, выделенный участок и suffix.
2. На первом непустом результате заменить выделение распознанным текстом.
3. Последующие transcript-события обновляют только выделенный для диктовки участок:
   prefix + transcriptSnapshot + suffix.
4. Финальный результат заменяет этот же участок.
5. При пустой/отменённой диктовке до первого текста исходное выделение сохраняется.

Вставлять у курсора, а не безусловно в конец. Пробелы на стыке определять локальным правилом один раз на основании prefix/suffix и проверять на пунктуации. Не применять trim ко всему черновику.

Нельзя делать input.value += committed + tentative при каждом событии: committed обычно содержит уже показанную часть, а tentative может изменяться.

В обычном textarea нельзя надёжно раскрасить часть значения. Первая версия может показывать единый текст и отдельный статус «Распознаю…». Не заменять textarea на сложный rich-text editor только ради серого tentative.

### 10.3. Ручные изменения во время диктовки

Предлагаемая простая политика:

- при пользовательском изменении поля немедленно отвязать автоматическую вставку;
- отменить поток и освободить микрофон;
- сохранить видимый текст и пользовательскую правку;
- поздние transcript/final игнорировать.

Отвязка должна произойти синхронно до применения запоздалого результата. Для ввода/вставки/удаления использовать beforeinput/input и поколение владельца, сохраняя IME-логику.

Это сознательный компромисс первой версии: пользователь может начать редактировать сразу, а приложение не пытается объединять параллельно изменяемые диапазоны сложным алгоритмом.

Перемещение каретки само по себе не должно незаметно менять место вставки. Либо сохранять исходный участок и не перехватывать каретку, либо при явной смене участка завершать диктовку. Выбрать один вариант в спецификации и проверить UX. Предпочтительно завершать диктовку при намерении редактировать другой участок.

### 10.4. Ревизии и отправка

Каждое фактическое изменение значения от диктовки должно проходить через общий путь обновления черновика:

- обновить draftRevision;
- пересчитать высоту;
- пересчитать действия;
- сохранить значение тем же способом, что ручной ввод.

Не генерировать искусственное событие input без различения происхождения: оно может сработать как ручная правка и отменить собственную диктовку.

Пока состояние preparing/listening/finalizing:

- send() и все альтернативные пути отправки должны проверять speech blocking state;
- Enter не отправляет незавершённый текст;
- отправка в очередь тоже заблокирована;
- существующая «Остановить ответ» агента остаётся отдельной доступной операцией по прежним правилам;
- начать диктовку во время уже выполняющейся отправки того же черновика нельзя.

Нажатие микрофона никогда не вызывает interruptUrl и не отменяет ответ агента.

При достижении лимита текста не продолжать невидимо накапливать результат. Остановить поток, сохранить допустимый текст и сообщить о лимите. Не разрезать surrogate pair; согласовать подсчёт с существующим canSend.

## 11. Состояния и жизненный цикл

| Состояние | Что видит пользователь | Допустимые действия |
|---|---|---|
| unavailable | Причина недоступности | Открыть настройки/справку |
| model-missing | «Скачать модель» | Выбрать и скачать |
| idle | Обычный микрофон | Начать диктовку |
| preparing | «Подготовка…» | Повторным нажатием отменить старт |
| listening | Активный микрофон, «Слушаю» | Нажать для остановки |
| finalizing | «Завершаю распознавание…» | Дождаться или отменить при явной проблеме |
| error | Короткое сообщение, текст сохранён | Повторить после устранения причины |

Download/load — состояния модели; listening/finalizing — состояния диктовки. Не смешивать их в один неуправляемый набор boolean.

### 11.1. Stop и Cancel

**Stop**: больше не принимать звук, передать оставшийся короткий буфер в правильном порядке, выполнить finalize, применить final, освободить владение.

**Cancel**: больше не менять поле, остановить звук, прервать/reset поток, сохранить уже видимый текст. Cancel не обязан ждать финальный текст.

Операции должны быть идемпотентными. Двойное нажатие, повторный сетевой close и dispose не должны создавать исключения или вторую финализацию.

### 11.2. Скрытие поля и переход между диалогами

При скрытии/удалении поля:

- синхронно закрыть право обновлять этот DOM/черновик;
- остановить запись;
- сохранить уже видимое;
- отменить старый поток.

Не вставлять запоздалый final в новую сессию. Для первой версии надёжнее потерять ещё не распознанный хвост при уходе из диалога с понятным завершением, чем перепутать адресата текста.

Обычная потеря фокуса окна не обязана останавливать диктовку. Закрытие/уход страницы, удаление поля и переключение целевой сессии — обязаны.

### 11.3. Конкуренция и восстановление

- Один активный поток на службу; второму полю/окну показать «Диктовка уже используется».
- Не перехватывать владение молча.
- При обрыве соединения остановить запись, закрыть поток; автоматический replay всей записи не нужен.
- При падении helper сохранить видимый текст, показать ошибку и разрешить новый запуск.
- CPU fallback может оказаться слишком медленным; сообщать о фактическом backend и не обещать прежнюю скорость.
- После sleep/wake или исчезновения устройства требовать нового явного запуска.
- Простой таймер выгрузки модели допустим как внутреннее значение, но не делать сложную настройку обязательной.

## 12. Каталог, загрузка и хранение моделей

### 12.1. Минимальная запись каталога

Нужны:

- стабильный modelId и отображаемое имя;
- семейство/архитектура;
- repository, revision, filename;
- sizeBytes и sha256;
- quantization;
- languages;
- декларативные capabilities;
- license и source URL;
- минимальная совместимая версия движка, если она предусмотрена донором.

В каталоге Handy capability определяется также GGUF-метаданными:

    general.architecture
    general.name
    stt.variant
    general.languages
    stt.capability.streaming

При загрузке проверять реальные capabilities runtime. Наличие тега в каталоге не заменяет успешную инициализацию. Неизвестный тег не превращать в true.

### 12.2. Первая поставка

Рекомендуется встроенный закреплённый каталог проверенных моделей. Обновления каталога приходят вместе с обновлением Kit.

Не нужен сервис удалённой конфигурации, который может незаметно поменять URL и доступные модели. Произвольный import GGUF можно оставить следующим этапом.

Сохранить выбранные modelId/quantization в существующем конфигурационном хранилище Kit через его публичный API. Не хранить состояние установки только в браузерном localStorage.

### 12.3. Загрузка

1. Проверить доступное место для модели и временного файла.
2. Скачать в файл с временным суффиксом в управляемом каталоге.
3. Показывать прогресс и разрешать отмену.
4. Проверить ожидаемый размер и SHA-256.
5. После проверки атомарно переименовать в окончательное имя.
6. Только после этого показывать модель установленной и разрешать загрузку в engine.

При ошибке checksum не пытаться запускать модель. При отмене/перезапуске корректно обработать partial-файл; resume реализовать только если это просто переносится из проверенного донора и надёжно валидируется.

URL берётся из закреплённого каталога, путь назначения определяется приложением. Поле modelId из запроса не является путём файла.

### 12.4. Пути и удаление

- Веса и состояние хранить в существующем пользовательском каталоге данных Kit, вне репозитория.
- Сначала изучить публичный контракт data-store, затем определить подкаталоги speech/models.
- Не коммитить GGUF, записи и runtime cache.
- Удалять только файл, которым управляет Kit.
- Нельзя автоматически удалять общий Hugging Face cache, файлы установленного Handy или чужие симлинки.
- Активную модель сначала выгрузить; удаление во время диктовки отклонить с понятной причиной.
- Если позже потребуется использовать уже скачанный файл Handy, это отдельный явный import/link с проверкой; не сканировать и не перемещать все его данные автоматически.

## 13. Производительность и ограничение очередей

Реальный критерий streaming — текст поступает во время речи, а очередь аудио не растёт бесконечно.

Измерять отдельно:

- холодную загрузку модели;
- повторный старт с уже загруженной моделью;
- время до первого текста;
- задержку обновлений в устойчивом потоке;
- время завершения после Stop;
- размер и длительность очереди аудио;
- память idle/loaded/listening;
- выбранный compute backend;
- скорость обработки относительно длительности звука.

Нужен bounded buffer на каждом переходе. При перегрузке нельзя произвольно выкидывать аудиоблоки и продолжать как будто всё нормально. Если очередь достигает лимита, остановить текущую диктовку, сохранить текст и сообщить, что компьютер не успевает.

Пример начальных, **не согласованных как SLA**, ориентиров для локального испытания:

- видимые обновления примерно в пределах 1–1.5 секунды в устойчивой речи;
- отсутствие растущего отставания на записи 5 минут;
- приемлемая пользователю финализация после Stop.

Значения уточняются по фактическому Mac, языку и квантизации. Не объявлять выполнение требования на основании одного короткого английского примера.

Память Mac пользователя велика, но это не устраняет необходимость проверки GPU/CPU-скорости и не определяет требования ко всем будущим пользователям.

## 14. macOS, сборка и поставка

### 14.1. Apple Silicon

В проверенном Handy для macOS aarch64 используется Metal. Это основной путь технической проверки.

Поставлять helper вместе с подходящими нативными библиотеками/ресурсами. Конечному пользователю не должны требоваться Rust, CMake, Xcode, Python или Docker для обычной работы модуля.

Проверить:

- запуск helper из фактической упаковки Kit;
- пути с пробелами и кириллицей;
- расположение ресурсов Metal и библиотек;
- ограничения подписи/quarantine/notarization выбранного способа распространения;
- корректное завершение дочернего процесса при остановке Kit.

Подпись, entitlements и microphone usage description зависят от того, какой процесс захватывает звук. При browser capture разрешение микрофона относится к браузеру/оболочке, а helper только вычисляет.

### 14.2. Intel Mac

В donor Cargo-конфигурации Intel macOS использует CPU-путь, в том числе из-за проблем инициализации Metal на AMD. Поэтому нельзя заявлять real-time Voxtral на любом Intel Mac без измерения.

Требование пользователя — macOS. Рекомендуемое начало с Apple Silicon не следует скрытно превращать в обещание поддержки только этой архитектуры. В спецификации явно указать результат:

- Apple Silicon — проверенная целевая конфигурация;
- Intel — либо отдельно протестированная поддержка, либо честная недоступность данной модели/скорости.

### 14.3. Другие платформы

Импорт модулей и запуск Kit на Windows/Linux не должны ломаться из-за отсутствия macOS helper. UI возвращает capability unavailable и не показывает работающую кнопку.

iOS/Android не подключаются к новому захвату. Не вмешиваться в их системную клавиатурную диктовку.
