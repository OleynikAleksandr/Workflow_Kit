# M40: контракт решений пользователя

Часть [спецификации M40](M40-user-decisions.md). Определяет запрос решения, канал от ядра
к службе, привязку решения к сообщению пользователя и поведение при повторах.

## 1. Запрос решения

Запрос решения — типизированная запись о том, что именно пользователь разрешает выполнить.

```
{ id: "dec-<12 hex>", kind, scopeId | null, proposal: { generation, digest } | null,
  taskId | null, params, inputDigest, revision, createdAt, state: "pending" | "applied" | "stale" }
```

`inputDigest` — sha256 канонического JSON `{ kind, scopeId, proposal, taskId, params }`.
`revision` — ревизия плана при создании записи; билет хоста привязан к ревизии на момент
исполнения, как в M39. Параметры по видам:

| `kind` | `params` | Запрос устарел, если |
| --- | --- | --- |
| `choose` | `option` (`sequential`, `orchestrated`, `refine`), `session`; `proposal` обязателен, `scopeId` — null: scope ещё нет | изменилось поколение или дайджест предложения (`scope:proposal --digest`: тело, спецификация, документы контекста) |
| `confirm-delivery` | `taskDigest` — дайджест определения задачи (название, файлы, проверки, критерии, зависимости) | задача изменена или уже не следующая |
| `accept` | `head` — SHA HEAD, `result` — состояние результата | появились коммиты или scope не READY_FOR_ACCEPTANCE |
| `close` | `head` | появились коммиты или scope не ACCEPTED |
| `unblock` | `reasonDigest` — дайджест причины блокировки | задача разблокирована или причина другая |
| `approve-install` | `profileDigest`, `install: [{ tool, command }]` — точные команды установки | агент повторно вызвал `quality:apply` с другим входом (новый запрос заменил прежний) или изменился профиль качества проекта |
| `adopt-commits` | `commits` — точный упорядоченный список SHA | список внешних коммитов другой |

Правила ядра:

- Запрос создаёт Kit: команда решения без билета в режиме `host` ничего не меняет в плане,
  возвращает `USER_DECISION_REQUIRED` и записывает запрос. Повтор той же команды с тем же
  `inputDigest` возвращает тот же `id`. Другой вход того же вида и цели заменяет запрос:
  прежний получает `state: stale`.
- Для `approve-install` Kit хранит вместе с запросом полный канонический вход
  `quality:apply`. Исполнение — `quality:apply --decision <id>` с билетом: Kit применяет
  сохранённый вход. Правка файла входа после регистрации запроса на запрос не влияет:
  пользователь разрешает ровно то, что показала карточка. Устаревает запрос только
  регистрацией нового: повторный `quality:apply` с другим входом заменяет запрос, и кнопка
  прежней карточки даёт `DECISION_STALE`.
- Исполнение любого решения: операция хоста получает `--decision <id>` и билет, привязанный
  к `id`, `inputDigest`, ревизии и корню. Kit заново вычисляет запрос из текущего состояния;
  если дайджест не совпал, отказ `DECISION_STALE`, запрос помечается `stale`, а при
  сохранившейся потребности создаётся новый. Так изменение данных после показа карточки
  не исполняется по старой кнопке.
- Применённое решение записывается в историю плана с `decisionId`, источником и
  примечанием. Источник — `button` или `message` (сессия, идентификатор сообщения, время)
  для решения, которое пользователь принял сейчас, либо `grant` для решения по
  предварительному разрешению запуска автопилота (раздел 5). Повторная операция с уже
  применённым `decisionId` ничего не меняет и возвращает `already: true`.
- Решения до появления scope: `choose` привязан к предложению; `prepare` (подготовка плана
  в полном автопилоте) — решение уровня службы, в Kit не записывается и живёт в журнале
  запуска автопилота, как в M39.
- Хранилище запросов — локальное состояние Kit (`.harness/workflow/local/`, не в git),
  запись под блокировкой Kit. `HostOperation` расширяется операциями решений;
  `HostRequest.runId` становится необязательным, решение вне запуска несёт `decisionId`.

## 2. Канал от ядра к службе

Агент вызывает `scripts/workflow` отдельным процессом; служба его вывод не видит. Канал —
состояние Kit, а не вывод команды и не пересказ агента:

- `scripts/workflow status` (JSON) получает поле `decisions` — список запросов `pending`.
  При выдаче Kit заново вычисляет каждый запрос; запись, которая не воспроизводится из
  текущего состояния (устарела или подложена в файл), в список не попадает.
- Служба читает `status` тем же вызовом `kit-runner`, которым получает план для панели:
  при опросе панели и после событий хуков сессий проекта (Stop, UserPromptSubmit).
  Запросы публикуются в состоянии панели проекта вместе с планом; карточка строится по
  ним. Сетевых обращений из Kit к службе нет.
- Подложенный файл запроса даёт не больше, чем карточку: решение исполняется только по
  кнопке или сообщению пользователя, билетом, привязанным к дайджесту, который Kit
  проверяет заново.
- `choose` запроса от агента не требует: карточку выбора служба строит по предложению,
  как сейчас, и добавляет в решение поколение и дайджест предложения.

Проверка: отдельный процесс «агента» вызывает `accept` без билета → в состоянии панели
появляется карточка приёмки, хотя агент об отказе ничего не сообщал.

## 3. Сообщение пользователя как источник

Служба ведёт журнал сообщений пользователя по сессиям. Привязка опирается на существующее
поколение хода канала агента (`generation` слота сессии в `agent-channel`) и происхождение
хода (`TurnOrigin`: `user`, `delivery`, `decider`, `reminder`, `unknown`), а не на
отдельный счётчик. Запись журнала: идентификатор сообщения, сессия, текст, время, способ
(`prompt` или `panel`) и поколение хода, который это сообщение начало.

- **Доставка.** В журнал попадает только доставленное сообщение: текст хука
  UserPromptSubmit (Claude, Codex) или сообщение панели `source=user`, которое служба сама
  передала сессии подтверждённым ответом хука. Сообщение панели, стоящее в очереди во время
  идущего хода, источником не является, пока не доставлено.
- **Поколение хода.** Источник годен, только если текущее поколение хода сессии равно
  поколению записи и происхождение этого хода — `user` либо `delivery`, составленная
  только из сообщений `source=user`. Любое новое поколение прекращает доступность прежнего
  источника: автоматическое продолжение автопилота (Stop с `block`, происхождение
  `decider`), напоминание (`reminder`), доставка замечаний ревью и других служебных
  сообщений, ход неизвестного происхождения. Поэтому сообщение пользователя не переживает
  автоматический ход, даже если Stop не был отпущен.
- **Не источники.** Тексты с префиксом `Workflow Kit:`, ответы ревьюера, напоминания и
  продолжения автопилота в журнал слов пользователя не записываются.
- **Одно сообщение — одно решение.** Сообщение служит источником одного решения (вид и
  цель). Приёмка и закрытие по-прежнему требуют отдельных команд пользователя.
- **Примечание.** Текст сообщения (до 500 символов) становится примечанием решения; агент
  цитату не передаёт.
- **Нет достоверной привязки** — провайдер без хука и сообщение не через панель; служба
  перезапущена посреди хода и поколение не восстановлено — отказ `decision-source-missing`,
  решение не записывается, остаётся кнопка в панели.

Это ограничение относится к выдаче разрешений. Слова «стоп» и «пауза» служба исполняет
раньше, при получении сообщения ([спецификация, раздел 2.4](M40-user-decisions.md#24-стоп-и-пауза-распознаёт-служба)).

## 4. Повторы и идемпотентность

Ключ решения — sha256 от проекта, вида, цели, `inputDigest` и источника (идентификатор
сообщения или идентификатор запроса кнопки). Служба ведёт журнал решений проекта
(`.workflow-kit/local/`, не в git): `{ key, decisionId, state: "issued" | "applied" | "failed", result }`.

- Запись `issued` создаётся до вызова Kit. Одному ключу соответствует один `decisionId`;
  второй билет на другое решение по тому же ключу не выдаётся.
- Повтор команды, двойное нажатие: запись `applied` → возвращается сохранённый результат
  (`already: true`), Kit не вызывается.
- Потерянный ответ или сбой между вызовом Kit и записью результата: запись осталась
  `issued` → служба сверяет состояние с Kit по `decisionId` (история плана). Применено —
  записывает результат; не применено — повторяет операцию с тем же `decisionId` (Kit
  применяет его не более одного раза).
- Перезапуск службы: журнал читается с диска, записи `issued` сверяются при первом
  обращении. Билеты восстанавливаются, как в M39.
- Отказ Kit `DECISION_STALE` переводит запись в `failed`; новая карточка даёт новый ключ.

## 5. Решения по разрешению запуска автопилота

Запуск автопилота M39 — предварительное поручение пользователя: одна команда (прямое
поручение подготовить план в `full` или кнопка старта в `after-start`) разрешает
согласованные действия до публикации. Эти действия служба выполняет сама после окончания
хода пользователя. Они не являются новыми ручными решениями и не потребляют сообщение.

- **Какие решения.** В `full` — автоматический выбор режима (`choose`); в обоих режимах —
  старт задач delivery запуска, автоматическая приёмка (`accept`) и закрытие (`close`).
  Публикация остаётся операцией службы после закрытия, как в M39.
- **Источник.** В истории плана такое решение имеет источник
  `{ kind: "grant", runId, authorization }`: номер запуска и дайджест разрешения scope
  (`scope.authorization`). Примечание — «автоматически, по предварительному поручению
  запуска <runId>», как автоматическая приёмка M39. Исходное сообщение пользователя
  используется один раз: оно записано в журнале запуска (`request`) и служит источником
  только регистрации запуска. Источник `button` или `message` у этих решений не появляется.
- **Выбор режима до появления scope.** Разрешения scope ещё нет. Решение `choose` несёт
  `runId` записи запуска службы, поколение и дайджест предложения и, при включённом ревью,
  дайджест согласованной версии. Разрешение scope создаётся сразу после выбора
  (`autopilot:authorize`), как в M39.
- **Проверки перед каждым решением.** Служба: запуск не остановлен и не на паузе, режим не
  выключен, фаза запуска соответствует действию. Kit: при исполнении операции с `runId`
  проверяет, что разрешение scope живое (не отозвано), принадлежит этому запуску и
  покрывает действие; иначе отказ M39 (`AUTOPILOT_UNAUTHORIZED`, `AUTOPILOT_REVOKED`).
  Отзыв или пауза между выдачей билета и исполнением останавливает решение на проверке Kit
  или службы; билет не погашается.
- **Билет.** `HostRequest` несёт и `runId`, и `decisionId`. Решение пользователя вне
  запуска несёт только `decisionId`.
- **Идемпотентность.** Ключ решения строится по разделу 4 с источником `grant:<runId>`.
  `decisionId` выдаёт Kit при регистрации запроса; служба хранит соответствие ключа и
  `decisionId` в журнале решений, поэтому одному ключу соответствует один `decisionId`. Квитанции журнала запуска M39
  (`receipts`) остаются: повтор шага после перезапуска находит квитанцию или применённый
  `decisionId` в истории Kit и не создаёт второго решения.
- **Старт delivery под запуском.** `task:start <ID>` агента без флагов: Kit сам находит
  живое разрешение, покрывающее задачу, и записывает подтверждение с источником `grant`.

## 6. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Запрос решения, реестр запросов, дайджесты | общий Node-код: JSON и sha256, запись под блокировкой Kit | то же | то же, x64 и ARM64 |
| Билет хоста и привязка к корню проекта | Node IPC родителя; корень сравнивает `sameRoot` службы | то же | то же; `sameRoot` не учитывает регистр, `\` и `/`, раскрывает имена 8.3 |
| Журнал сообщений и журнал решений службы | файлы в `.workflow-kit/local/`, атомарная запись | то же | то же |

Поведение одинаково на всех ОС, отличается только сравнение путей. Программы ОС не
вызываются. Подробно — [спецификация, раздел 5](M40-user-decisions.md#5-поведение-на-ос).
