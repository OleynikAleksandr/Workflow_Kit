# M39: единое управление и ожидающие вопросы

Часть [спецификации](M39-autopiloting.md) и [runtime](M39-autopiloting-runtime.md).

## 1. Один отправитель продолжений

Для активного запуска M39 единственный отправитель автоматических продолжений —
reconciler. Решатель Stop собирает факты и будит reconciler; сам не возвращает второй
continue и не вызывает enqueue. Старые start/resume/confirmDelivery/fixes передают
намерение этому же reconciler. При отсутствии M39-run сохраняется прежний решатель.
Смена владельца/переход к legacy атомарно выключает прежнего отправителя. Один actionId
охватывает и событие Stop, и HTTP-нажатие, и повтор после рестарта.

| Существующее действие | При активном M39-run | Без M39-run |
| --- | --- | --- |
| start | Повтор того же scope — текущий результат, без второго сообщения; другой scope — конфликт | Прежний старт; after-start сначала определяет effective policy |
| workflow/pause | Общая пауза run и pause:set; новая задача/эффект не начинается | Прежняя пауза Kit |
| workflow/resume | Тот же reconciler снимает паузу и сверяет grant; после off нужен явный новый resume-source | Прежнее продолжение |
| confirm-delivery | Если task уже разрешён/начат — вернуть факт без enqueue; если ждёт ручного решения — записать его только для этого task | Прежний ручной путь |
| fixes | Снять готовность к завершению; если delivery IN_PROGRESS — defer по условиям Kit, затем plan:extend; единственный отправитель — reconciler | Прежний путь с теми же guards Kit |
| accept | Только READY_FOR_ACCEPTANCE; записать реальный source=panel, если пользователь нажал; конкурирующее auto-accept завершается одной записью | Прежняя приёмка |
| close | Только ACCEPTED и чистое дерево; один commit; run продолжает publication, если это разрешено | Прежнее закрытие |
| publish | До close — scope-open; после close общий publish с run actionId/мьютексом; повтор возвращает факт | Прежняя публикация |
| Остановить ответ (M24) | Прервать провайдера, поставить паузу, закрыть барьер будущих действий до явного resume | Прежний M24 |
| autopiloting/pause, resume | Алиасы той же операции; отдельного enabled-флага с иной логикой нет | no-run |
| autopiloting/stop | Окончательное revoke, state=stopped; поздние события игнорируются | no-run |
| Settings off | suspend: paused, revoke reason=settings-off, resumable=true; on сам не будит run | Меняется default |

Поля отзыва: `{ at, reason: settings-off | user-stop, resumable }`. После user-stop
resumable=false: нужен новый запуск. После settings-off явный resume подтверждает
новую ревизию прежних полномочий, с user-source; revoked запись не стирается из истории.
Обычная пауза не отзывает разрешение, но блокирует действие в обоих слоях.

Все действия сериализуются по проекту; пауза/stop выставляют барьер до ожидания
завершения внешнего процесса. Перед следующей мутацией после await барьер перечитывается.
При уже совершённом внешнем эффекте записывается факт, обратное действие не выдумывается.
Старые маршруты не должны повторно включить автоматический режим после stop/off.

## 2. Вопросы и разрешения провайдера

Неразрешённый AskUserQuestion/request_user_input или PermissionRequest переводит run
в waiting с reason=question, questionId/providerRequestId, стадией возврата и deadline,
если его сообщил провайдер. Отсутствие deadline не заменяется догадкой. Это отдельное
состояние, не no-progress: попытки и счётчик ходов не расходуются, новый рабочий turn
не отправляется, пока прежний удерживается вопросом.

Ответ пользователя проходит только существующий answerQuestion/маршрут разрешений.
Подтверждение доставки и принятия ответа провайдером позволяет сверить сессию и
продолжить прежний run. Один клик не отправляет и ответ, и новое рабочее сообщение.
Поздний ответ после stop, ответ другому questionId и закрытый provider waiter не дают
автопродолжение. Автопилот не выбирает первый вариант ответа и не выдаёт blanket approve.

Если время хука/канала ответа истекло, статус — blocked с reason=question-expired и
надписью «Нужны данные: ожидание ответа у провайдера завершилось». Нельзя бесконечно
отвечать устаревшему waiter. Штатный маршрут ответа сообщает, можно ли восстановить
тот же вопрос; при недоступности агенту предлагается повторить вопрос после явного
resume пользователя. Новый вопрос имеет новый id, прежний остаётся в истории.

Наличие pending permission, не показанного как обычный вопрос, тоже блокирует отправку
новых ходов; причина и допустимый способ ответа берутся из capability провайдера.
Проверяются Claude, Codex и Kimi там, где их адаптер поддерживает соответствующий запрос.
Отсутствие поддержки видно как blocker, а не автоматический отказ или подтверждение.

## 3. after-start и неполный план

Политика определяется до нажатия start и показывается на карточке:

- План с automation, автоматическими критериями и доступными проверками: полный путь.
- Automation есть, но содержит обязательный ручной критерий: start не отклоняется;
  grant разрешает заявленные delivery, close и publication, но accept=false.
  До старта написано «Остановится на приёмке: требуется ручная проверка …». После
  настоящего ручного accept reconciler продолжает разрешённые close/publication.
- Automation отсутствует (старый план): start не отклоняется, но новые права M39 не
  создаются. Effective policy=legacy, до старта видно «Для этого плана: ручное
  подтверждение выпуска, приёмки, закрытия и публикации — нет описания автоматизации».
  Обычные work-задачи продолжаются прежним механизмом. Это явное ограничение, не
  скрытый переход на auto-accept. Возможность дополнить план обсуждается отдельно.
- Новый Kit/capability отсутствует: отображается требование обновления; ручной legacy
  запуск остаётся доступен с той же явной подписью, full-автозапуск недоступен.

Full с обязательными ручными критериями не начинает исполнение молча: автор должен
выявить препятствие при подготовке и назвать его. Автоматизировать критерий можно,
только сохранив исходное требование. Возможности gh/upstream проверяются лишь тогда,
когда их требует закреплённая политика этого плана.
