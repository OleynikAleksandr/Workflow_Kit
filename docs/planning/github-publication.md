# Подготовка и публикация Workflow Kit на GitHub

## Цель и согласование

Подготовить текущую версию 0.4.6 для нового пользователя и опубликовать
репозиторий на https://github.com/OleynikAleksandr/Workflow_Kit.

Поручение пользователя (09.11.2026): «сделай тогда, пожалуйста маленький короткий
scope для подготовки локального репозитория к публикации на GitHub»;
«всю необходимую информацию, как работает данное приложение, как его
проинсталлировать, добавь в нужные документы»; «лучше сделать стандартный
файл change log»; «подготовь и опубликуй этот репозиторий на GitHub».
Это согласие на подготовку и последующий push в указанный репозиторий.
Режим выполнения пользователь выбирает в карточке Kit.

## 1. Документы и состав репозитория

- README: назначение приложения, один процесс бэкенда и HTTP-панели,
  основные возможности и обычный сценарий работы, ссылки на подробности.
- Установка с нуля: локальное скачивание ZIP или git clone по точному URL,
  распаковка и переход в корень папки, Node.js 24+, отдельные требования
  к провайдерам, install, открытие панели и её адрес, диагностика,
  обновление, остановка и удаление; отдельно запуск из исходников.
- Подробности в docs/installation.md: пути, ярлыки и автозапуск macOS,
  Windows и Linux, запуск после входа пользователя, требования к PATH,
  отсутствие готовых установочных пакетов. Не выдавать платформенные
  тесты за проверки на устройствах: интеграции провайдеров на Windows
  отключены, Linux требует живой проверки. npm ci нужен для разработки
  и проверок, не описывать его как обязательную runtime-зависимость.
- CHANGELOG.md в корне: раздел Unreleased и история подтверждённых версий
  по документам приёмки и истории Kit, новые версии сверху, Added/Changed/Fixed
  по необходимости. Не выдумывать даты и изменения, дать ссылку из README.
- Согласовать относящиеся к установке сведения в архитектурном обзоре.
- Проверить .gitignore и фактически отслеживаемые файлы: CHANGELOG и
  необходимые для установки исходники включены; локальные стартовые материалы,
  окружение, зависимости, временные данные и секреты исключены. До T001
  docs/start исключался только через локальный .git/info/exclude.
- Проверить также предназначенную к отправке историю на случай ранее
  закоммиченных локальных данных; содержимое Kit runtime и бандла не читать.
  При обнаружении секрета остановить публикацию и сообщить причину;
  историю самостоятельно не переписывать. Права и лицензию не придумывать.

## 2. Публикация и проверка

- Перед отправкой повторно проверить удалённую main и её содержимое:
  репозиторий публичный, ветка существует; считать его пустым нельзя.
- Настроить origin на указанный URL, сохранить существующие удалённые
  изменения. Не использовать force push и не удалять удалённые ветки.
  При несовместимой истории подготовить безопасное объединение; если для
  этого нужны изменения вне разрешённых файлов, уточнить план через Kit.
- Выполнить настроенные проверки Kit и проверить инструкции в отдельной
  временной копии без установки или перезапуска пользовательской службы.
- Опубликовать main только в delivery-задаче. После последнего локального
  коммита этой задачи отправить его и сверить SHA main локально и на GitHub;
  проверить доступность README, CHANGELOG и инструкции установки.
- Записать результат проверок в docs/evidence/github-publication.md.
  Не объявлять успешной публикацию без подтверждения удалённого состояния.

## План

1. T001 — документация, CHANGELOG и правила включения файлов;
   parallelSafe: false, поскольку изменения взаимосвязаны.
2. T002 — delivery: проверка и публикация на GitHub, зависит от T001.

Kit добавляет согласование документов DOCS и при необходимости QUALITY.
Новый функционал, повышение версии, сборка установочных пакетов, установка
службы и реализация поддержки Windows/Linux в этот scope не входят.
Приёмка и закрытие scope остаются отдельными решениями пользователя.
