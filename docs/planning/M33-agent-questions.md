# M33: интерактивные вопросы агента в диалоге

## Цель и согласование

Агент Claude (инструмент `AskUserQuestion`) и агент ChatGPT/Codex (`request_user_input`)
задают пользователю вопрос с вариантами ответа. В родных приложениях это карточка с выбором
и кнопкой «Submit». В диалоге Workflow Kit вопроса нет: видна только предыдущая реплика
агента, а ответить можно лишь текстом в поле ввода.

После M33 вопрос виден в ленте диалога панели карточкой: пользователь выбирает вариант или
пишет свой и нажимает «Отправить». Вопрос остаётся и в родном приложении: отвечает та
сторона, которая успела первой, вторая показывает итог.

Пользователь, 15.11.2026: «Что мы можем сделать, чтобы подобный интерактивный вопрос
возникал и в Workflow Kit диалоге? Ну или похожий хотя бы, чтобы не писать в поле ввода
пользователя «подтверждаю» или вариант, который предложен, а нажать, выбрать ответ и нажать
«Submit».» В панели выбраны спецификация и план с ревью.

## 1. Факты и принципы

Факты с уровнем доказательства — в [фактах Claude](../design/M33-claude-question-facts.md) и
[фактах Codex](../design/M33-codex-question-facts.md). Главное:

- Лента Claude читает транскрипт и берёт только текст; вызовы инструментов, в том числе
  `AskUserQuestion`, отбрасывает (код `provider-claude/src/chat.ts`).
- Клиент Codex отвечает `-32601` на любой запрос сервера и отписывается от треда после своего
  хода (код `provider-codex/src/rpc.ts`). Вопрос Codex — запрос сервера
  `item/tool/requestUserInput`; элемента истории для него нет, зато статус треда несёт флаг
  `waitingOnUserInput` (схема codex-cli 0.169.0).
- Claude Code документирует ответ на `AskUserQuestion` хуком (`PermissionRequest` или
  `PreToolUse`) через `updatedInput.answers`; вживую не испытано.

Принципы:

1. Kit не отвечает за пользователя. Ответ уходит только по явному нажатию в панели; автопилот,
   очередь сообщений и истечение времени ответом не являются. Одобрения команд и правок
   (approvals) Kit по-прежнему не принимает.
2. Родной вопрос не прячется. Вариант, при котором вопрос исчезает из приложения вендора, пока
   его держит Kit, без отдельного решения пользователя не выбирается.
3. Один вопрос — один ответ. Ответ с любой стороны закрывает вопрос на обеих; опоздавший ответ
   панели получает отказ `question-stale`. Ответ панели передаётся провайдеру не больше одного
   раза, а чужой или неподтверждённый итог агенту не приписывается.
4. Сначала пробы (T001, T002), потом код. Проба уточняет факты и выбирает только из вариантов,
   описанных здесь; противоречие факта критерию следующих задач — `task:block` и решение
   пользователя.
5. Текст вопросов и ответов — переписка: в журналы службы не пишется (только id, числа, коды).
6. Контракт общий для провайдеров. Kimi в M33 вопросов не отдаёт (раздел 5).

## 2. Решение

### 2.1. Общий контракт (`provider-registry`)

Новый файл `src/questions.ts`, типы и пределы экспортирует `src/index.ts`:

- `ChatQuestionOption { label, description }`.
- `ChatQuestionPart { id, header, question, options, multiSelect, allowOther }` — один вопрос
  карточки; `options` может быть пустым (тогда только свой текст, `allowOther: true`).
- `ChatQuestion { id, at, afterMessageId, state, parts, answerable, reason?, delivery?, answers? }`:
  `state` — `pending | answered | cancelled`; `afterMessageId` — сообщение ленты, после
  которого стоит вопрос (`null` — в начале); `answerable` — Kit может доставить ответ сейчас
  (только у `pending` без `delivery`); `reason` — безопасный текст, почему нельзя;
  `delivery: 'sent'` — Kit уже передал ответ провайдеру, итог ещё не подтверждён; `answers` —
  только доказанный итог у `answered`: по `part.id` список выбранных подписей или свой текст.
  Итог неизвестен — поля нет: ответ панели без подтверждения агенту не приписывается.
- `ChatQuestionAnswer` — `{ [partId]: { selected: string[]; other?: string } }`.
- `ChatPage.questions?: ChatQuestion[]` — от старых к новым; нет поля — провайдер вопросов не
  отдаёт. `chatPageOut` нормализует: не больше `QUESTIONS_PAGE_MAX` (20) новейших.
- Пределы: частей 4, вариантов 8, заголовок 60, подпись 200, описание 1000, вопрос 2000, свой
  текст 2000 знаков. Вопрос сверх пределов показывается обрезанным с `answerable: false` и
  причиной `QUESTION_TOO_LARGE_REASON` («Вопрос больше, чем показывает Workflow Kit. Ответьте
  в приложении провайдера»).
- `checkQuestionAnswer(question, answer)` — общая проверка для провайдеров: вопрос `pending`,
  `answerable` и без `delivery`; ответ есть на каждую часть; без `multiSelect` — ровно один
  выбранный вариант или свой текст; с `multiSelect` — хотя бы один вариант или свой текст;
  подписи только из `options`; свой текст только при `allowOther`, очищен как
  `cleanDirectText` и не пуст.
- `Provider.answerQuestion?(project, sessionId, questionId, attempt): Promise<'accepted' | 'unknown'>`,
  `attempt` — `{ id, answers }`; возможность `answerQuestion` (явное включение, как
  `interruptTurn`).

Правила попытки ответа — серверные, общие для провайдеров; карточка их не заменяет, прямой
POST в обход карточки получает те же отказы:

- Непосредственно перед передачей ответа провайдер заново читает актуальное состояние
  вопроса и вызывает `checkQuestionAnswer`. Закрытый вопрос — `question-stale`;
  неотвечаемый (секретный, сверх пределов, без канала ответа) — `question-unavailable`.
  Наружу при отказе ничего не уходит.
- Тело запроса — `{ attemptId, answers }`, `attemptId` — UUID клиента. Передача наружу
  (решение хуку, результат RPC, нажатия клавиш) выполняется для вопроса не больше одного раза.
- Повтор с тем же `attemptId` (потерян HTTP-ответ) ничего не передаёт и возвращает исход
  первой попытки, дожидаясь его в пределах своего срока.
- Другой `attemptId` после передачи — `question-sent`, а если вопрос уже закрыт —
  `question-stale`; так же отвечает повтор с другого клиента.
- Новая попытка возможна только после отказа, при котором наружу доказуемо ничего не ушло:
  `question-invalid`, `question-unavailable`, `question-failed` до передачи.
- Исход: `accepted` — провайдер подтвердил именно ответ панели; `unknown` — ответ передан и
  вопрос закрыт, но чей ответ принят, провайдер не сообщает (вопрос `answered` без
  `answers`). Подтверждения нет за 10 с — `question-timeout`: вопрос остаётся `pending` с
  `delivery: 'sent'`, итог приходит позже обычным опросом ленты.
- Попытки хранятся в памяти службы. После перезапуска ожидающий хук или запрос прежнего
  соединения недоступен, поэтому повторно передать прежнюю попытку нельзя.

Маршрут `POST /api/projects/:id/providers/:p/sessions/:sid/questions/:qid/answer`,
тело `{ attemptId, answers }` → `{ answered: true, outcome }`. Маршрут проверяет форму тела,
провайдер — ответ против вопроса. Отказы (`ProviderError` → HTTP):

| Код | HTTP | Текст |
| --- | --- | --- |
| `question-invalid` | 400 | «Ответ не подходит к вопросу» |
| `question-stale` | 409 | «На вопрос уже ответили» |
| `question-sent` | 409 | «Ответ на этот вопрос уже отправлен» |
| `question-unavailable` | 409 | причина из `reason` вопроса |
| `question-failed` | 502 | «<Провайдер> не принял ответ: <причина>» |
| `question-timeout` | 504 | «Ответ отправлен, подтверждение не пришло. Проверьте чат провайдера» |

Нет метода у провайдера — 404 `unsupported`.

### 2.5. Панель: карточка вопроса (`session-chat`)

Новые `src/question-model.js` (чистая модель) и `src/question-card.js`; стили — в
`session-chat.css`. Эталон — карточка Claude Desktop (снимок пользователя 15.11.2026, тёмная
тема) в токенах панели.

- Ожидающий вопрос стоит в конце ленты над полем ввода; закрытый — в ленте после
  `afterMessageId`, компактно: вопрос и выбранный ответ, «Ответ дан в приложении» или
  «Вопрос отменён».
- Часть: заголовок-метка, текст вопроса, варианты (подпись и описание) — радиокнопки или
  флажки при `multiSelect`; при `allowOther` — строка «Свой вариант» с полем текста.
  Несколько частей идут одна под другой в одной карточке.
- «Отправить» активна, когда выбран ответ на каждую часть; с клавиатуры — Ctrl/⌘+Enter.
  Одно нажатие по варианту ответ не отправляет. Кнопки «Пропустить» в M33 нет (раздел 5).
- `answerable: false`: варианты видны без выбора, под ними причина и ссылка на чат провайдера.
- Выбор хранится вместе с состоянием сессии и переживает опрос. Вопрос закрылся, пока
  пользователь выбирал, — карточка показывает итог; `question-stale` — то же и внеочередной
  опрос.
- Попытка: карточка создаёт `attemptId` при нажатии «Отправить» и повторяет запрос с тем же
  `attemptId` при сетевой ошибке. Отказы, при которых ничего не передано (`question-invalid`,
  `question-unavailable`, `question-failed`), — текст ошибки под карточкой, выбор сохранён,
  новая попытка той же кнопкой. После `question-timeout`, `question-sent` и при
  `delivery: 'sent'` кнопки нет: «Ответ отправлен, ждём подтверждения», итог приходит опросом.
- Исход `unknown` и закрытие без `answers`: «Ответ отправлен. Какой ответ принят, провайдер
  не сообщил» или «Ответ дан в приложении» — без подстановки выбора панели.
- Сенсорные цели не меньше 44 px, без элементов, видимых только при наведении; тёмная и
  светлая темы; узкая раскладка iPad.
- Пока есть ожидающий вопрос, строка состояния диалога — «Агент ждёт вашего ответа».

### 2.6. Пробы и бюджет

Программы T001 и T002 — в документах фактов (раздел 3 каждого). Пробы идут в одноразовом
проекте Kit, пользовательские сессии не трогают, исполняемых файлов в репозиторий не
добавляют: скрипт — в evidence, в блоке кода. Живые ходы — только после прямого согласия
пользователя: T001 — не больше 12 коротких ходов Haiku (серия K — ещё до 4, только если A1
не доказан), T002 — не больше 8 коротких ходов Codex, T008 — до 3 ходов Haiku и 2 ходов
Codex, T009 — до 2 ходов Haiku и 2 ходов Codex. Что видно в Claude Desktop и ChatGPT,
подтверждает пользователь; без подтверждения факт остаётся «не проверено».

## 3. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Контракт, маршрут, карточка | общий код Node и панели | так же | так же; x64 и ARM64 |
| Claude: показ из транскрипта | путь из хука | так же | так же |
| Claude A1: хук вопроса | команда `wfk hook question` | так же | exec-форма `node.exe wfk.mjs`, как остальные хуки Claude |
| Claude A2: клавиши | expect-хост | expect-хост, нужен `expect` | ConPTY, те же клавиши |
| Codex C0: флаг | сокет демона | так же | `codex app-server proxy` |
| Codex C1: слушатель | долгое соединение с сокетом | так же | долгий процесс proxy |

Поведение одинаково на трёх ОС; отличается только транспорт. Вопрос Codex виден Kit только
там, где ход идёт в демоне, к которому Kit подключён (как Stop): без общего доступа к чатам
ходы приложения ChatGPT Kit не видит. Новых вызовов программ ОС нет.

## 4. Проверка

- Отрицательные тесты прямого POST: секретный, слишком большой, закрытый и уже отправленный
  вопрос — отказ и ни одной исходящей передачи; потерянный HTTP-ответ (тот же `attemptId`),
  задержанное подтверждение, повтор с другого клиента, гонка разных ответов панели и
  приложения.
- Claude A1: два одинаковых вопроса подряд, поздний ответ старого хука, переход между
  девятиминутными запросами. Codex: быстрый вопрос до подписки, открытие панели посреди хода,
  обрыв слушателя, снятие подписки через 60 с без опросов.
- Тесты: нормализация и `checkQuestionAnswer`; транскрипт Claude (ожидание, ответ, отмена,
  несколько частей, sidechain); ожидающие хуки и `wfk hook question` на подставной службе, или
  движок A2 на записанных кадрах; слушатель Codex на подставном демоне (подписка, запрос,
  ответ, `serverRequest/resolved`, секретный вопрос, чужой запрос, обрыв); маршрут и коды;
  модель карточки. Ветки `win32` и `linux` — с подставленной платформой.
- Браузер (изолированный Chromium): выбор, свой вариант, несколько частей, отправка, отказы,
  закрытие с другой стороны, обе темы, узкая раскладка.
- Живая проверка, macOS, пользователь и агент (T008, служба из исходников): вопрос Claude и
  вопрос ChatGPT — ответ из панели и ответ из приложения. После установки (T009) — короткая
  функциональная проверка установленной 0.14.0 у обоих провайдеров и обновление структуры
  существующего проекта при A1; это проверка поставки агентом, не пользовательская приёмка. Windows — проверяющий на Windows. Linux — только CI.
- CI точного SHA поставки: macOS, Linux, Windows x64 и ARM64, ветка `ci/M33-agent-questions`.

## 5. Границы

Не входит:

- одобрения команд, правок и разрешений (Claude и Codex), `ExitPlanMode`, MCP elicitation;
- вопросы Kimi; пометка ожидающего вопроса в дереве сессий и уведомления;
- кнопка «Пропустить»: у ответа нет контракта пропуска; отказаться от вопроса можно в
  приложении провайдера или кнопкой Stop;
- вариант A3 и сессии Claude, запущенные до обновления хуков (вопрос виден, ответ — в
  приложении);
- полнота текстовой ленты (раздел 7).
