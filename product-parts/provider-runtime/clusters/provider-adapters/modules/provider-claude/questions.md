# provider-claude: вопросы агента

Вопросы `AskUserQuestion` в ленте сессии Claude и запрет вставки текста в открытый диалог
вопроса (M33, раздел 2.2 [решения по провайдерам](../../../../../../docs/planning/M33-agent-questions-providers.md);
факты — [M33-claude-question-facts.md](../../../../../../docs/design/M33-claude-question-facts.md)).
Общий контракт (`ChatQuestion`, пределы, `questionsOut`, правила попытки ответа) —
`provider-registry`, его `questions.md`. Ссылка — из `module.md`; лента — [chat.md](chat.md).

## Показ: `src/questions.ts`

Транскрипт читает тот же `ChatReader` (`src/chat.ts`), что и ленту: строка разбирается один
раз, затем `noteQuestionRow(book, row, messageId, lastMessageId)` и сообщение ленты. Книга
вопросов (`QuestionBook`) живёт в состоянии файла рядом с сообщениями: дозапись, разорванная
строка, замена файла (смена `ino` или уменьшение — вопросы заново) и удаление файла — как у
сообщений.

- Строки `isSidechain` (субагенты) вопросов не дают и не закрывают.
- Строка `assistant`, часть `tool_use` с `name: "AskUserQuestion"` (`QUESTION_TOOL`) —
  вопрос: `id` — id вызова (`toolu_…`), `at` — `timestamp` строки, `afterMessageId` —
  сообщение этой же строки или последнее сообщение ленты до неё (`null` — в начале); части —
  `input.questions[]`: `id` — `q<номер>` с 1, `header`, `question`, `options`
  (`label`, `description`), `multiSelect`, `allowOther: true`. Вызов с уже известным id не
  создаёт второго вопроса. Другие инструменты вопросов не дают.
- Строка `user`, часть `tool_result` с `tool_use_id` ожидающего вопроса — закрытие. Действует
  первый результат вызова (T001: результат бывает записан двумя строками). `is_error: true`
  или `toolUseResult` строкой (Esc: «User rejected tool use») — `cancelled`. Иначе —
  `answered`, ответы из `toolUseResult.answers` (текст вопроса → ответ) по
  `partAnswerOf(part, raw)`:
  - массив — подписи вариантов, остальные строки через `, ` — свой текст (`other`);
  - строка, равная подписи, — эта подпись;
  - строка части с `multiSelect`, все куски которой по `, ` — подписи, — эти подписи
    (так пишет ответ хука, T001);
  - другая непустая строка — свой текст (`selected: []`, `other`).
  Нет ни одного распознанного ответа — `answered` без `answers` (итог неизвестен).
- Сообщение ленты (реплика пользователя или текст агента) после ожидающего вопроса без
  результата переводит его в `cancelled`; так закрывается и вопрос после
  «[Request interrupted by user for tool use]».
- В памяти — последние `QUESTIONS_KEEP` (20) вопросов файла; при переполнении первым выбывает
  самый старый закрытый, ожидающий — только если закрытых нет.
- Страница: поле `questions` (от старых к новым) есть, только когда в транскрипте есть
  вопросы; страница без вопросов — прежняя страница M18. Пределы и обрезку применяет
  маршрут (`chatPageOut` реестра).
- Ожидающий вопрос из транскрипта — `answerable: false` с причиной `CLAUDE_QUESTION_REASON`
  «Ответьте в приложении Claude»; отвечаемым его делает привязанное ожидание хука (ниже).

## Ответ: `src/question-waiters.ts` (вариант A1, T005)

Хук Kit `PermissionRequest` с `matcher: "AskUserQuestion"` (структура v4, `kit-structure`)
запускает `wfk hook question` (`cli`), тот держит `POST /api/hooks/question` (`agent-channel`),
служба вызывает `questionHook(project, request, signal)` провайдера.

- Ожидание — запись по `waiterId` в памяти службы (на экземпляр провайдера): транскрипт
  (`transcript_path` хука, иначе журнал хука), ключ содержимого `contentKey(parts)` (sha256
  заголовков, вопросов, `multiSelect` и вариантов), `tool_input` хука, время регистрации,
  состояние `waiting | decided | closed`, привязанный вопрос.
- `tool_name` не `AskUserQuestion` или `tool_input` не объект — `{ release: true }`: хук никогда
  не отвечает за другие инструменты.
- Новый `waiterId`: транскрипт перечитывается; кандидат — самый поздний ожидающий вопрос с тем
  же ключом и без привязки (вход хука id вызова не несёт, T001 P1, P7). Если у кандидата в
  журнале попыток (`readQuestionAttempts`) есть запись `sent` — `{ release: true }` без записи:
  ответ уже передан до перезапуска службы. Иначе — новая запись `waiting`; прежние ожидания
  того же транскрипта закрываются (вытеснение). Нечитаемый транскрипт или журнал — `release`.
- Известный `waiterId` продолжает ту же запись (смена девятиминутного запроса, возврат после
  обрыва): нового ожидания и вопроса нет. Запрос держится до `holdMs` (8 мин): решение —
  `{ decision }`, закрытие — `{ release: true }`, конец срока или закрытие HTTP-запроса —
  `{ wait: true }`. Раз в `tickMs` (500 мс) транскрипт перечитывается.
- Закрытие HTTP-запроса состояние не меняет. Ожидание закрывается только: вопрос закрыт в
  транскрипте; нет запроса дольше `recoveryMs` (2 мин); прошло `QUESTION_HOOK_TIMEOUT_S`
  (43 200 с) от регистрации; вытеснено новым `waiterId` того же транскрипта. Закрытое не
  оживает: его запросы получают `release` (закрытые хранятся, до `CLOSED_WAITERS_KEEP`, 200).
- Лента (`withWaiters`): ожидающий вопрос с привязанным ожиданием `waiting` —
  `answerable: true`; привязка была, но ожидание кончилось — `QUESTION_HOOK_ENDED_REASON`
  («…хук вопроса завершился»); привязки нет — `QUESTION_OLD_SESSION_REASON` («…эта сессия
  запущена до обновления хуков проекта»), а первые `graceMs` (5 с) после вызова —
  `CLAUDE_QUESTION_REASON` (хук приходит через ~0,1 с после строки вызова).
- `answerQuestion(project, sid, qid, attempt, commit)` — по правилам попытки реестра:
  транскрипт сессии перечитывается, вопрос с ожиданиями, `checkQuestionAnswer` (вопроса нет —
  `question-stale`; нет ожидания `waiting` — `question-unavailable`), `commit()`, затем без
  ожиданий между проверкой и записью — решение ожиданию один раз (`decided`). Решение:
  `{ hookSpecificOutput: { hookEventName: "PermissionRequest", decision: { behavior: "allow",
  updatedInput: { ...tool_input, answers } } } }`, `answers` — текст вопроса → подпись или свой
  текст строкой, несколько значений части с `multiSelect` — массивом (T001, D2). Повторный
  запрос ожидания `decided` получает то же решение. Подтверждение — результат в транскрипте за
  `confirmMs` (10 с): ответы равны ожидаемым (значение решения, разобранное `partAnswerOf` так,
  как его покажет транскрипт) — `accepted`; другие или отмена — `question-stale`; результат без
  распознанных ответов — `unknown`; нет результата — `question-timeout` (повторной передачи нет).
- Ответ в приложении раньше панели: результат в транскрипте закрывает ожидание, процесс хука
  получает `release` (сам он не завершается, T001 P4), попытка панели — `question-stale` без
  `commit`.
- Текст вопросов и ответов в журнал службы не пишется: только id сессии и причина ошибки.
- Возможность `answerQuestion` — `available` (`src/programs.ts`).

## Запрет вставки: `src/question-guard.ts`

Текст, вставленный в терминал при открытом вопросе, Claude принимает как ответ (T001, P6).

- `questionOpen(rt, project, sid)` — в транскрипте сессии (путь из журнала хука) есть
  ожидающий вопрос (`hasOpenQuestion(chat, path)` из `src/chat.ts`). Транскрипт не читается —
  считается открытым (строка журнала без текста), чтобы Kit не ответил за пользователя.
- `sendDirect` проверяет это непосредственно перед записью `<debug>.text` (внутри
  очереди сессии и аренды хоста): вопрос открыт — `false` без записи управляющих файлов,
  строка журнала без текста; служба кладёт сообщение в очередь канала («В очереди»).
- `wakeSession` провайдера при открытом вопросе возвращает `true` и не пишет
  `<debug>.message` (текст пробуждения тоже стал бы ответом); сообщение ждёт в очереди
  канала следующего хода.
- Известное ограничение: вопрос, записанный в транскрипт в ту же секунду, когда сценарий
  забирает уже записанный `<debug>.text`, может получить этот текст ответом; окно — между
  проверкой и вставкой (до секунды опроса сценария).

## Поведение на ОС

| Что | macOS | Linux | Windows (x64, ARM64) |
| --- | --- | --- | --- |
| Вопросы из транскрипта | путь из хука, общий Node-код | так же | так же |
| Запрет вставки и пробуждения | до записи файлов для `session.exp` | так же | до записи файлов для `pty/host.ts` |
| Хук вопроса | POSIX-команда `~/.local/bin/wfk hook question` | так же | exec-форма `node.exe wfk.mjs hook question` |
| Ожидания и ответ | общий Node-код службы | так же | так же |

Поведение одинаково на трёх ОС: проверка идёт в службе до записи управляющих файлов. Новых
вызовов программ ОС нет.

  и отмена после решения (`question-stale`); ответ в приложении раньше (`release`, без
  `commit`); `question-timeout` без второй передачи, закрытый и неотвечаемый вопрос без

  транскрипте вставка и пробуждение снова работают.
