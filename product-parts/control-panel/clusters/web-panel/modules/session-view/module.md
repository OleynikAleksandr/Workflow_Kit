# Модуль: session-view

Часть `control-panel`, кластер `web-panel`. Алиас импорта: `#session-view`.

## Назначение

Карточки процесса выбранной сессии и «Ревью плана» в боковой панели (спецификация вехи 2,
разделы 6, 8.3, 9.3, 10; шаги 5–10 исторического макета; раскладка M24): строка активности агента,
карточка выбора пути, карточка плана с кнопками, подтверждение выпуска.

## Публичный интерфейс для бэкенда (`src/index.ts`)

- `SESSION_VIEW_PREFIX` — `/session-view/`.
- `SESSION_VIEW_ASSETS_DIR` — абсолютный путь к `src/`.
- `sessionViewMount() → { prefix, dir }` — монтирование для `http-server`
  (подключает `cli`, `createApp`).

## Подключение к панели

`session-view.js` — расширение панели (`PANEL_EXTENSIONS` в
`panel-shell`): `install(shell)` заполняет слоты `sessionSidebar` и
`sessionReview` (`registerSlot`). Стили — `session-view.css`, подключены в
`index.html` панели.

## Карточки решений Kit (M40 T008)

Проект `decisions: host` (Kit 2.4.0+): решение пользователя записывает служба по кнопке. Слот
`sessionSidebar` (`sidebar-view.js`) получает `decisions` — карточки `decisionCardsView` идут
сразу после вопроса о плане и зажигают `data-needs-attention`; `host` и `requests` — запросы
`accept`, `close`, `choose`, `confirm-delivery` для кнопок существующих карточек. «Принять
план», «Закрыть план», «Выбрать» и «Подтвердить выпуск» добавляют к телу `decision: { id,
inputDigest }` и `requestId` запроса своего вида, если он есть: изменённые после показа данные
служба отклоняет (`DECISION_STALE`). «Подтвердить выпуск» в проекте `host` — одна кнопка без
поля слов: задачу выпуска начинает служба и сама сообщает агенту. Проект `agent` и Kit 2.3.x —
прежние карточки и тела запросов.

## Раскладка M24

`sidebar-view.js` регистрирует sessionSidebar, выбирает прежние модели без изменения правил
и сохраняет отдельные узлы карточек по проекту и сессии. Порядок: вопрос, ревью,
подтверждение выпуска, выбор, план, чужой план (`foreign`, M31), активность. Справа эти карточки больше не рисуются;
sessionBody остаётся совместимым слотом оболочки. Пустое состояние — компактная подпись.
Новый вопрос/действие отмечает кнопку скрытого сайдбара через data-needs-attention.

Таймер или прогресс не пересоздаёт остальные карточки. Черновики форм имеют составной
ключ проект+сессия; раскрытие записей журнала хранится по сессии и содержимому записи,
новая запись раскрывается по умолчанию. Оболочка сохраняет фокус полей при обновлении.
CSS карточек переносит длинные тексты и кнопки; размер колонок не зависит от ширины окна.
Существующие API, подтверждения и условия показа сохраняются.

## Поведение на ОС

Одинаково на macOS, Linux и Windows x64/ARM64: браузерные ES-модули, без веток ОС.
Карточки доступны и в desktop-сайдбаре, и в выдвижной панели iPad/телефона; таймеры
и правила выбора не зависят от вида устройства.
Пути вне коммитов (M37) приходят от службы через `/` на всех ОС и показываются как есть.

## Конец плана (M37)

Спецификация — [M37](../../../../../../docs/planning/M37-plan-close-flow.md), раздел 2.4.

- **Файлы вне коммитов.** `planView` отдаёт `dirty` — пути из `plan.dirty` службы (фазы
  `acceptance` и `accepted`; без поля — пустой список). При непустом списке карточка плана под
  списком задач показывает блок `.sv-dirty`: предупреждение `sv-warn` «В папке проекта есть
  файлы вне коммитов: `a`, `b` (и ещё N). Пока они есть, план не закроется.» (до пяти путей,
  каждый — `code`) и кнопку «Попросить агента убрать» → `POST …/workflow/tidy { session }`,
  ошибка — «Не удалось попросить агента» с текстом службы. Кнопки «Принять план» и «Закрыть
  план» остаются активными; отказ закрытия на грязном дереве приходит от службы по-русски.
- **Карточка «Ревью плана».** `crossReviewView` отдаёт `current`: `scopeId` ревью равен
  `scopeId` открытого предложения проекта (`workflow.projects[id].proposal`, сравнение как в
  службе — предложение без id равно ревью без id) или активного scope (`.plan.scopeId`,
  `.scope.id`). `showsReview(data)` (`sidebar-view.js`): идущее ревью и карточка в сессии
  ревьюера — всегда; законченное ревью основной сессии — только при `!plan && current`. После
  закрытия плана и после предложения другого scope карточка исчезает; пустое состояние
  считается по тому же правилу.
- **Тексты.** Решение о ревью при «да»: «Следующий план этой сессии проверит ревьюер — так
  решено ответом на вопрос о плане.» `REASON_LABELS`: `accepted` — «План принят», `closed` —
  «План закрыт» (те же тексты, что `STOP_LABELS` автопилота); строка активности показывает
  метку службы.
- Тесты — `test/plan-close.test.ts`.

## Автопилотирование (M39)

- Строка «Ревью плана: да/нет» убрана из сайдбара: слот `sessionReview` не регистрируется,
  настройка ревью — в «Настройки → Автопилотирование». Карточка «Ревью плана», замечания,
  повтор и журнал остаются. Под вопросом агента о плане сказано, что ответ — решение для
  этого задания.
- Часть `run` сайдбара (после выбора, перед планом) — `runCard`:
  - режим, этап и его признак;
  - причина ожидания (`wait.detail`: «Ждёт CI», «Ждёт ответа на вопрос агента») или
    остановки (`reason`; истёкший вопрос — «Нужны данные»), `nextAction`;
  - кнопки «Пауза», «Продолжить», «Остановить автопилот» (последняя — с `STOP_CONFIRM`) →
    `POST /api/projects/:id/autopiloting/pause|resume|stop { runId, expectedRevision }`
    ровно этого запуска;
  - после закрытия плана — «Публикует <sha> в <upstream>», затем «<sha> → <upstream> ·
    коммитов: N» (или «уже был на удалённой ветке, проверен»), либо «Публикация не
    выполнена: <причина>». Зелёным — только проверенная публикация.
  - M41: фаза `accepting` с `manualAcceptance` — «Ждёт вашей приёмки»
    (`USER_ACCEPTANCE_LABEL`), признак ожидания, причина и `nextAction` («нажмите «Принять
    план»…»), кнопки «Пауза» и «Остановить автопилот» (принимает карточка плана);
    `notice` запуска — строка-предупреждение (`RunView.notice`) без смены фазы, после
    `completed`/`stopped` не показывается.
  Остановленный или ждущий запуск зажигает `data-needs-attention`.
- `planView.autopilotingMode` — режим настроек, пока у плана есть кнопка старта.
  `policyLine` один раз на план и режим спрашивает `GET
  /api/projects/:id/autopiloting/policy` и показывает «Автопилот после старта: …»
  (legacy, ручная приёмка, «Обновите Kit проекта»), затем карточка перерисовывается.
- Тест — `test/run-model.test.ts`.

## Инварианты

- Чистая логика в `session-model.js` без DOM; покрыта `node --test`.
- Текст в DOM — только через `textContent`; ширина полосы — через CSSOM.
- Решения пользователя уходят только кнопками; ошибки показываются над
  экраном с подсказкой Kit.
