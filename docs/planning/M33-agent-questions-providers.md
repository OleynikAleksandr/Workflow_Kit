# M33: вопросы агента — решение по провайдерам

Продолжение раздела 2 [спецификации M33](M33-agent-questions.md): разделы 2.2–2.4 вынесены
сюда, чтобы спецификация оставалась в пределе 28 000 байт. Общий контракт и правила попытки
ответа — 2.1, карточка — 2.5, пробы и бюджет — 2.6 основной спецификации.

## 2. Решение (продолжение)

### 2.2. Claude: показ (`provider-claude`)

- `ChatReader` дополнительно извлекает из строк `assistant` (не `isSidechain`) части
  `tool_use` с `name: "AskUserQuestion"`: `id` вызова — id вопроса; `input.questions[]` —
  части (`id` — `q<номер>`, `allowOther: true`). Строка `user` с `tool_result` того же
  `tool_use_id` переводит вопрос в `answered` (ответы — по формату, который установит T001;
  нераспознанный формат — `answered` без `answers`) или в `cancelled` (ошибка, прерывание).
- Вопрос без результата, после которого в транскрипте есть более поздняя реплика пользователя
  или текст агента, — `cancelled`.
- Источник ожидающего вопроса и его id зависят от D1 (есть ли строка `tool_use` в
  транскрипте, пока вопрос ждёт) и от канала ответа. Допустимые сочетания:

| D1 | Канал | Источник ожидающего вопроса | id вопроса |
| --- | --- | --- | --- |
| да | A1 | транскрипт; `answerable` — при привязанном ожидающем хуке | id вызова `tool_use` |
| нет | A1 | регистрация хука вопроса (2.3) | `hook:<waiterId>`; когда результат записан в транскрипт, вопрос заменяется закрытым вопросом с id вызова |
| да | A2 | транскрипт; `answerable` — при распознанном кадре этого вопроса | id вызова `tool_use` |
| нет | A2 | не поддерживается: содержимое вопроса с экрана терминала источником не служит | `task:block` T001, решение пользователя |

- Поправка T008: D1 «да» даёт хук `PreToolUse` структуры Kit (2.3). В сессии без него
  (запущенной до обновления хуков) ожидающего вопроса в транскрипте нет: вопрос появляется в
  ленте только закрытым.
- Граница задач: T004 читает транскрипт — закрытые вопросы всегда, ожидающие при D1 «да».
  При D1 «нет» ожидающий вопрос появляется в T005 вместе с хуком.
- `sendDirect` при ожидающем вопросе возвращает `false`: текст не вставляется в открытый
  диалог терминала и уходит в очередь канала. Запрет реализует задача, которая даёт источник
  ожидающего вопроса: T004 при D1 «да», T005 при D1 «нет».

### 2.3. Claude: ответ

Варианты, по убыванию предпочтения:

**A1 — хук `PermissionRequest`.** Выбирается, если T001 доказала P1–P5 и P7 (факты Claude,
раздел 3): хук срабатывает в сессии с Remote Control; пока он ждёт, вопрос виден в терминале
и в Claude Desktop; ответ хука закрывает вопрос везде и доходит до агента; ответ в приложении
раньше хука ничего не ломает; хук живёт дольше 600 с; вызовы различимы.

- `kit-structure`: событие Kit `PermissionRequest` только для Claude, группа с
  `matcher: "AskUserQuestion"`, команда `wfk hook question --client claude`, `timeout`
  `QUESTION_HOOK_TIMEOUT_S` = 43 200 с (или наибольшее доказанное T001). `STRUCTURE_VERSION`
  растёт: существующие проекты получают статус «устарела» и обновляются прежней кнопкой.
  `.codex/hooks.json` и хуки Kimi не меняются.
- `kit-structure`, поправка T008: вторая группа Claude — событие `PreToolUse` с тем же
  `matcher: "AskUserQuestion"` и той же командой, `timeout` `QUESTION_PRETOOL_TIMEOUT_S` = 30 с.
  Claude пишет строку вызова в транскрипт перед хуками `PreToolUse` (факты Claude, раздел 7);
  без такого хука ожидающего вопроса в транскрипте нет. `wfk hook question` на входе
  `PreToolUse` читает stdin и сразу выходит с кодом 0 без вывода и без запроса к службе.
- `cli`: `wfk hook question` при старте создаёт `waiterId` (UUID) и передаёт его в каждом
  запросе. Он читает stdin и держит длинный запрос `POST /api/hooks/question` (каждый не
  дольше 9 мин, повтор при ответе `{ wait: true }`). Ответ службы с решением — печать JSON
  решения. Службы нет, отказ, `{ release: true }` — выход 0 без вывода: родной диалог
  работает дальше. Обрыв во время ожидания — повторы до 2 мин, затем выход 0.
- `agent-channel`: маршрут `/api/hooks/question`; `cli` передаёт вызов в
  `Provider.questionHook`.
- `provider-claude`, `src/question-waiters.ts`:
  - Ожидание — запись по `waiterId`: сессия, ключ содержимого (sha256 нормализованных
    `questions`), время регистрации, состояние `waiting | decided | closed`. Повторный запрос
    того же `waiterId` (переход между девятиминутными запросами) продолжает ту же запись и не
    создаёт ни нового ожидания, ни нового вопроса.
  - Привязка к вызову: ожидание привязывается ровно к одному вопросу. Если вход хука несёт
    идентификатор вызова (установит P1) — по нему. Иначе — к самому позднему ожидающему
    вопросу транскрипта той же сессии с тем же ключом содержимого, у которого ещё нет
    привязки. При D1 «нет» ожидание само задаёт вопрос `hook:<waiterId>`.
  - Закрытие отдельного HTTP-запроса хука (штатная смена девятиминутного запроса, сетевой
    обрыв, завершение процесса хука) состояние ожидания не меняет: запись и привязка к
    вопросу сохраняются. Само закрытие запроса не доказывает ответ в приложении.
  - Ожидание завершается (`closed`) только в одном из случаев: вопрос закрыт в транскрипте
    (подтверждённый итог); от этого `waiterId` нет запроса дольше 2 мин (срок
    восстановления); истёк срок хука `QUESTION_HOOK_TIMEOUT_S` от регистрации; ожидание
    вытеснено регистрацией нового `waiterId` той же сессии; ожидание без привязки — в
    транскрипте закрытый вопрос с тем же ключом содержимого, без привязанного ожидания и не
    раньше чем за `graceMs` (5 с) до регистрации (поправка T008: вопрос хука отвечен в
    приложении). Других условий нет.
  - Завершённое ожидание не оживает: любой более поздний запрос с его `waiterId` получает
    `{ release: true }`, новой записи и нового вопроса не создаётся.
  - Решение назначается только ожиданию, привязанному к `questionId` запроса, в состоянии
    `waiting`, и только один раз (`decided`); если открытого запроса хука в этот момент нет,
    решение получит следующий запрос того же `waiterId` в пределах срока восстановления.
    Повторный запрос ожидания `decided` в той же жизни службы получает то же решение (ответ
    мог не дойти), другого решения не бывает. Закрытое ожидание решения не получает: старый
    процесс хука не получит ответ на новый вопрос, даже одинаковый по тексту.
  - После перезапуска службы записи ожиданий нет. Хук, вернувшийся с `waiterId` вопроса, у
    которого в журнале попыток (2.1) есть запись `sent`, получает `{ release: true }`:
    решение повторно не передаётся, вопрос остаётся в родном диалоге. Хук без такой записи
    регистрируется заново как `waiting`: решения он не получал, иначе завершился бы.
  - Вопрос `answerable` только при привязанном ожидании `waiting`; иначе причина «Ответьте в
    приложении Claude: эта сессия запущена до обновления хуков проекта» (или «…хук вопроса
    завершился»).
- `answerQuestion` — по правилам попытки 2.1: транскрипт перечитывается, проверка, решение
  хуку (`behavior: "allow"`, `updatedInput` с исходными `questions` и `answers`: текст
  вопроса → подпись; несколько подписей и свой текст — в формате, доказанном T001), затем
  ожидание результата в транскрипте до 10 с. Те же ответы — исход `accepted`; другие —
  `question-stale`; результата нет — `question-timeout`, вопрос остаётся с `delivery: 'sent'`.
- Ответ в приложении раньше панели служба узнаёт по результату в транскрипте: ожидание
  завершается по правилу подтверждённого итога, а попытка панели до этого получает
  `question-stale` при перечитывании транскрипта перед передачей.
- Хук никогда не отвечает за другие инструменты: служба проверяет `tool_name`.

**A2 — клавиши в терминале Kit.** Выбирается, если A1 не доказан (не выполнено любое из
P1–P5, P7), D1 «да» и T001 доказала K1–K4: устойчивый кадр диалога вопроса и клавиши выбора,
нескольких вариантов, своего текста и отправки.

- `provider-claude/src/pty`: распознавание кадра (`question-screen.ts`) и движок
  (`question-engine.ts`) в общем контроллере expect/ConPTY; файлы запроса и результата рядом
  с `<debug>`, корреляция UUID/сессия/срок, как у параметров M27.
- Неизвестный кадр или версия ниже проверенной — `question-unavailable`; `answerable` только
  у сессии панели с новым хостом и распознанным диалогом этого вопроса. Подтверждение —
  результат в транскрипте.
- Нажатия одной попытки выполняются один раз. Попытка, прерванная после первого нажатия,
  заканчивается `question-timeout` без повторных нажатий; итог даёт транскрипт.
- Запись `sent` журнала попыток (2.1) сохраняется до файла запроса хосту. Хост живёт
  независимо от службы: после её перезапуска он доводит свою транзакцию до конца, служба
  нового запроса по этому вопросу не создаёт, а итог берёт из файла результата хоста и
  транскрипта. Запрос с уже встречавшимся id хост не выполняет.

**A3 — хук `PreToolUse`, удерживающий вопрос.** Документирован, но, по документации, прячет
вопрос от приложения, пока Kit его держит (принцип 2). В M33 не реализуется; если A1 и A2 не
доказаны — `task:block` T001 и решение пользователя.

### 2.4. Codex: показ и ответ (`provider-codex`)

- **C0 — флаг.** Опрос ленты уже читает `thread/read`. Статус `active` с флагом
  `waitingOnUserInput` без известного содержимого вопроса даёт вопрос-заглушку: `parts: []`,
  `answerable: false`, причина «Агент ждёт ответа. Ответьте в приложении ChatGPT». Карточка
  показывает причину и прежнюю ссылку на чат.
- **C1 — слушатель** (`src/question-listener.ts`): отдельное долгое соединение с демоном,
  подписка `thread/resume { excludeTurns: true }`. Одновременно не больше 8 тредов; подписка
  снимается через 30 с после конца хода или 60 с без опросов ленты.
- Момент подписки:
  - Ход начинает сам Kit (прямой ход, пробуждение): слушатель подписывается до `turn/start`;
    не успел за 2 с — ход начинается без него.
  - Ход начат в приложении: Kit узнаёт о нём только опросом ленты (раз в 3 с, пока карточка
    диалога открыта).
  - **L1** (демон повторяет ожидающий запрос новому подписчику, Q3): подписка по флагу
    `waitingOnUserInput`; вопрос доступен при любом порядке событий.
  - **L2** (повтора нет): подписка при первом опросе со статусом `active`. Вопрос, возникший
    до подписки, содержимого не имеет и остаётся заглушкой C0. Так бывает при быстром вопросе
    (раньше первого опроса), при открытии панели посреди хода, после снятия подписки по 60 с
    без опросов и после обрыва слушателя. Это ограничение L2 записывается в известные
    ограничения и в причину заглушки.
- Обрыв соединения слушателя: ожидающие вопросы этого соединения становятся
  `answerable: false` (ответ возможен только на соединении, получившем запрос). После
  восстановления при L1 повторённый запрос даёт вопрос заново, при L2 остаётся C0.
- `rpc.ts`: ни одно соединение Kit не отвечает на запросы сервера — ни результатом, ни
  ошибкой, кроме ответа слушателя на вопрос по нажатию в панели. Ответ ошибкой любого
  подписчика отменяет вопрос и отклоняет одобрение для всех клиентов (факты Codex, Q6);
  без ответа запрос остаётся у ChatGPT и после закрытия соединения (Q11). Режим без
  накопления уведомлений — только для соединения слушателя.
  Решение пользователя, 15.11.2026: «Мы сделали такое поведение кит, потому что вопрос
  никуда не приходил… Теперь, когда вопрос будет приходить, и приходить в любой из
  клиентов, это поведение, естественно, нужно изменить.»
- `item/tool/requestUserInput` → вопрос: id — `itemId`; части — `questions[]` (`id` Codex,
  `multiSelect: false`, `allowOther` = `isOther` или нет вариантов). Часть с `isSecret` делает
  вопрос `answerable: false` с причиной «Секретный ответ вводится только в приложении ChatGPT».
- Ответ — результат того же запроса: `{ answers: { [id]: { answers: [подпись или текст] } } }`,
  по правилам попытки 2.1. Если `serverRequest/resolved` этого запроса уже получен, ответ не
  отправляется (`question-stale`).
- Исход после отправки определяется признаком, который установит T002 (Q5): `accepted` —
  только если признак отличает принятый ответ Kit от ответа другого клиента; опоздавший
  ответ — `question-stale`. Если протокол такого признака не даёт, любое закрытие вопроса
  после отправки — исход `unknown`: вопрос `answered` без `answers`, ответ панели агенту не
  приписывается. Нет закрытия за 10 с — `question-timeout`, `delivery: 'sent'`.
- `serverRequest/resolved` без ответа Kit — вопрос `answered` без `answers` («Ответ дан в
  приложении»); конец или прерывание хода при ожидающем вопросе — `cancelled`.
- Чужие запросы сервера на соединении слушателя (одобрения и прочее) остаются без ответа и
  забываются по `serverRequest/resolved` (T002, Q6).
- Закрытые вопросы треда хранятся в памяти (последние 20) и после перезапуска службы не видны.
- После перезапуска службы запрос прежнего соединения недоступен. Если демон повторит вопрос
  новому подписчику (L1), а в журнале попыток (2.1) у этого `itemId` есть запись `sent`,
  вопрос не отвечаем (`delivery: 'sent'`): ответить можно в приложении ChatGPT.
- Если T002 покажет, что запрос не доходит до второго подписчика, реализуется только C0, а
  C1 — `task:block` T002 и решение пользователя.
