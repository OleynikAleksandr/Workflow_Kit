# M6: каждая доработка — для macOS, Linux и Windows

## Цель и согласование

С версии 0.5.0 Workflow Kit поддерживает macOS, Linux и Windows 11 (x64 и ARM64). Но
проверки по-прежнему идут только на Mac: CI в репозитории нет, `typecheck` и тесты
выполняются при коммите на этой машине. Ветки `win32` и `linux` видны только тем тестам,
которые подставляют платформу, а новые доработки легко снова сделать «только для Mac».

Решение пользователя (09.11.2026): «как сделать так, чтобы все последующие доработки
касались всех трех операционных систем?»; на предложение из трёх мер (CI на трёх ОС,
защитная проверка кода, правила в инструкциях) — «Да, готовь scope».

Scope не меняет поведение приложения: версия остаётся 0.5.0, служба не переустанавливается.

## 1. Принципы

- Самая надёжная мера — тесты на настоящих ОС (CI). Защитная проверка ловит то, что тесты
  не видят: новый код, который не даёт подставить платформу, и программы одной ОС без
  ответа для двух других. Правила в `AGENTS.md` объясняют агентам, как это соблюдать.
- Проверки не требуют ручной работы на каждой ОС: живая проверка остаётся в документе
  приёмки (macOS — пользователь, Windows — знакомый пользователя, Linux — пока только CI).
- Публикация в `main` — только после приёмки и закрытия scope (правило пользователя).
  Для запуска CI до приёмки используется отдельная ветка `ci/<scope>`, push — в задаче выпуска
  с подтверждением пользователя.

## 2. CI на трёх ОС

Файл `.github/workflows/ci.yml`:

- События: `push` в `main` и в ветки `ci/**`, `pull_request`, `workflow_dispatch`.
- `permissions: contents: read`; `concurrency` по ветке с отменой устаревших запусков.
- Матрица `fail-fast: false`: `macos-latest` (ARM64), `ubuntu-latest` (x64),
  `windows-latest` (x64), `windows-11-arm` (ARM64). Репозиторий публичный — запуски бесплатны.
- Шаги: `actions/checkout@v5`, `actions/setup-node@v5` с `node-version: 24` и кешем npm,
  `npm ci`, `npm run typecheck`, `npm test`, `npm run check:platforms`.
- Сессии, служба и провайдеры в CI не запускаются: тесты уже работают с подставными
  провайдерами и временным HOME.

Переводы строк. Без явного правила Git на Windows может выдать файлы с CRLF: ломаются
сравнения текста в тестах и сценарии для Git Bash у пользователей Windows. В `.gitattributes`
вне блока `workflow-kit` добавляются `* text=auto eol=lf` и `binary` для `*.node`, `*.dll`,
`*.exe`, `*.png`, `*.ico`, `*.icns`. Блок Kit не меняется: его правила (CRLF для
`workflow.cmd` и `workflow.ps1`) стоят ниже и имеют приоритет.

Первые запуски на Windows и Linux могут показать тесты, рассчитанные на POSIX. Такие
тесты исправляются раундом исправлений этого scope (`plan:extend`) до приёмки.

## 3. Защитная проверка `platform-guard`

Сценарий `tools/platform-guard/check.ts` (запускается Node 24 без сборки), список
исключений `tools/platform-guard/allowlist.json`, тесты `tools/platform-guard/test/`,
описание `tools/platform-guard/README.md`. Проверяется всё дерево, а не только изменённые
файлы, поэтому список исключений всегда точен.

Область: `product-parts/**/src/**/*.{ts,js,mjs}` и `bin/**/*.mjs`, кроме `vendor/**`
и кода браузера `product-parts/control-panel/**` (он работает в панели и не зависит от ОС
службы).

### 3.1. Правило A: платформа подставляется

`process.platform` допускается только как значение по умолчанию для подставляемой
платформы: `?? process.platform`, `= process.platform`, `platform: process.platform`.
Сравнение и `switch` по `process.platform` — ошибка, кроме файлов из
`allowlist.json → directPlatform` с причиной. Так любая ветка ОС проверяется тестом на Mac
с `platform: 'win32'` или `'linux'`.

Начальный список — пропуск `chmod` на Windows: `service-installer/src/fs.ts`,
`data-store/src/atomic.ts`, `data-store/src/events.ts`, `data-store/src/backup.ts`,
`provider-claude/src/config-writer.ts`.

### 3.2. Правило B: у программы одной ОС есть ответ для двух других

Строковый литерал, равный имени программы ОС или начинающийся с него и пробела, должен
быть описан в `allowlist.json → programs` для своего файла. Список имён — в том же файле
(`programNames`): `osascript`, `launchctl`, `expect`, `pbcopy`, `plutil`, `xdg-open`,
`systemctl`, `loginctl`, `rundll32`, `taskkill`, `tasklist`, `powershell`,
`powershell.exe`, `pwsh`, `cmd.exe`, `schtasks`, `wmic`, `reg`. Слово `open` в списке
нет: оно совпадает с именами маршрутов и действий; `open` macOS описывается в записи
файла, где оно вызывается.

Запись: `{ "file", "program", "darwin", "linux", "win32" }`, где каждое значение ОС —
что используется на этой ОС или `не нужно: <причина>`. Пустое значение или отсутствие ОС —
ошибка. Запись, программа которой больше не встречается в файле, — тоже ошибка
(устаревшая).

Начальный список составляется по текущему коду (около 15 пар файл — программа:
`launchctl`/`systemctl`/`reg` в установщике, `expect` в провайдере Claude,
`taskkill`/`wmic`/`powershell.exe` в `process-supervisor` и `pty-host`, `xdg-open`
в открытии ссылок).

### 3.3. Правило C: в новой спецификации есть поведение на ОС

Каждый `docs/planning/*.md`, кроме перечисленных в `allowlist.json → legacySpecs`
(все спецификации до M6, включая `M5-windows.md` и `M5-windows-vm.md`), содержит раздел
второго уровня, заголовок которого содержит «Поведение на ОС», и в этом разделе
упоминаются macOS, Linux и Windows. Эта спецификация — первая, к которой правило
применяется (раздел 6).

### 3.4. Вывод и подключение

- Ошибки печатаются по одной строке: `<файл>:<строка> <правило> <что исправить>`;
  код выхода 1 при ошибках, 0 — без них.
- Скрипт `npm run check:platforms` в `package.json`.
- Проверка `platform-guard` в профиле качества Kit через `quality:apply` (не руками):
  `role: custom`, `stage: commit`, `required: true`, `appliesTo` — область раздела 3,
  `docs/planning/**` и `tools/platform-guard/**`.
- Тесты `tools/**/test/*.test.ts` добавляются в скрипт `npm test` и в проверку `test`
  профиля; `tools/**/*.ts` — в `tsconfig.json`.

## 4. Правила для агентов

В `AGENTS.md`, вне управляемого блока Kit, — раздел «Три ОС» (на английском, как
остальной файл). `CLAUDE.md` ссылается на `AGENTS.md`, поэтому правило видят и Claude, и Codex.

- Каждая доработка рассчитана на macOS, Linux и Windows 11 (x64 и ARM64). Если поведение
  везде одинаковое, это сказано явно.
- В спецификации есть раздел «Поведение на ОС» с колонками macOS, Linux, Windows.
  Начать можно с шаблона `docs/planning/TEMPLATE.md`.
- Код с ветками ОС получает платформу параметром; у каждой ветки `win32` и `linux` есть тест
  с подставленной платформой.
- Вызов программы одной ОС добавляется в `tools/platform-guard/allowlist.json` вместе с тем,
  что делается на двух других.
- В том же коммите обновляются таблица ОС в `docs/architecture/OVERVIEW.md` и раздел ОС
  в `module.md` модуля.
- Документ приёмки содержит пункты живой проверки по каждой ОС с указанием, кто проверяет.
- Задача выпуска не завершается, пока CI не прошёл на всех ОС для отправленного коммита.

README (раздел «Запуск из исходников и разработка») коротко называет CI и
`npm run check:platforms`.

## 5. Выпуск: запуск CI до приёмки

Задача выпуска (с подтверждением пользователя):

1. `git push origin HEAD:refs/heads/ci/m6-cross-platform` — не `main`.
2. `gh run watch` по запуску этого коммита; итог по каждому из четырёх заданий
   записывается в `docs/evidence/M6-acceptance.md`.
3. Если хотя бы одно задание красное, задача фиксирует итог, а исправления идут раундом
   `plan:extend`; после них — повторный запуск CI.

После приёмки и закрытия scope `main` публикуется обычным `git push origin main`.
Ветка `ci/m6-cross-platform` удаляется только с согласия пользователя.

## 6. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| CI | `macos-latest`, ARM64 | `ubuntu-latest`, x64 | `windows-latest` x64 и `windows-11-arm` ARM64 |
| `platform-guard` | запускается при коммите и в CI | в CI | в CI; пути в выводе — с `/` |
| Переводы строк | LF | LF | LF при checkout, кроме CRLF-файлов Kit |
| Живая проверка приложения | не нужна: поведение не меняется | не нужна | не нужна |

Сценарий проверки читает файлы как UTF-8 и сравнивает пути в виде с `/`, поэтому
одинаково работает на всех трёх ОС; это подтверждает его запуск в CI.

## 7. Границы

- Поведение приложения, версия, установщик и служба не меняются.
- Управляемые проекты пользователей не затрагиваются: правило касается разработки
  самого Workflow Kit. Настройка «целевые ОС» для управляемых проектов — отдельная идея.
- Linux ARM64 в матрицу не входит; добавляется при необходимости одной строкой.
