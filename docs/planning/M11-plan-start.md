# M11: запуск плана с видимым ходом

## Цель и согласование

Сейчас кнопка «Начать выполнение плана» остаётся на карточке плана после нажатия, пока агент
сам не выполнит первую команду Kit (`task:start` или `assignment:create`). Сессии Kimi
перед этим восстанавливают контекст и читают документы, поэтому кнопка висит минуту и
больше, хотя агент уже работает. Повторное нажатие отправляет агенту второе стартовое
сообщение и заново начинает счёт продолжений автопилота.

Пользователь, 2026-11-10: «нужно сделать так, как предложил ты, но если вдруг по какой-то
причине нажатая кнопка не приведет к запуску плана, нужно, чтобы состояние этой кнопки
менялось с пауза на объяснение проблемы или на предложение повторно начать выполнение…
Может сделать какой-то спиннер. Пользователь нажал кнопку. Вместо нее появился спиннер.
Когда реально прошла команда по всем ступенькам и работа начата, появляется кнопка
«Пауза».»

Итог:

- после нажатия на месте кнопки сразу появляется спиннер «Запускаю план» с текущей
  ступенью;
- «Пауза» появляется только когда Kit записал начало работы;
- если запуск не удался, спиннер сменяется объяснением и кнопкой «Начать заново»;
- повторный старт во время запуска не шлёт агенту второе сообщение.

## 1. Принципы

- Фаза карточки плана по-прежнему считается только по состоянию Kit (`plan-view`,
  `phaseOf`): «План выполняется» и «Пауза» — только после записи Kit о начатой задаче или
  задании. Запуск — отдельное состояние автопилота поверх фазы `ready`.
- Канал доставки (`agent-channel`) не меняет порядок и гарантии доставки: сообщение
  доставляется один раз и уходит из очереди, только когда ответ хука или промпт принят.
- Состояние запуска живёт в памяти службы, как всё состояние автопилота. После перезапуска
  службы запуск забывается, и карточка снова показывает «Начать выполнение плана».
- Остальные кнопки карточки («Продолжить», «Нужны исправления», «Подтвердить выпуск») не
  меняются.

## 2. Решение

### 2.1. Состояние запуска в автопилоте

`SessionAutopilot` получает поле `start` (или `null`):

| Поле | Значение |
| --- | --- |
| `at` | время нажатия (ISO) |
| `messageId` | id стартового сообщения в очереди канала |
| `step` | `sending` — сообщение ещё в очереди или в неотправленном исходящем; `delivered` — агент его получил |
| `problem` | `null` или `{ code, text }` — почему запуск не удался |

Ступени считаются при чтении раздела `autopilot` (`section()`) и в решении на Stop, по
очереди канала (`channel.queued`) и состоянию сессии (`channel.get`). Отдельных таймеров нет.

Состояние сбрасывается (`start = null`), когда фаза плана перестала быть `ready` (Kit записал
начало работы, план на паузе, остановлен, принят или закрыт), при `accept` и `close`.

### 2.2. Когда запуск не удался

| `code` | Когда | Текст для пользователя |
| --- | --- | --- |
| `not-delivered` | сообщение остаётся в очереди дольше `START_DELIVERY_MS` (60 с), или канал записал у сессии «сообщение не доставлено» | «Агент не получил команду запуска[: причина из канала]. Проверьте, что сессия открыта, и начните заново.» |
| `turn-ended` | агент закончил ход, начатый стартовым сообщением, а фаза осталась `ready` | «Агент закончил ход, не начав первую задачу. Посмотрите его ответ в чате и начните заново.» |

При `turn-ended` автопилот не продолжает сам: Stop держится с причиной
`waiting-for-plan-start`, как до нажатия.

Если агент получил команду и работает, но Kit ещё не записал начало дольше
`START_SLOW_MS` (3 мин), это не ошибка: модель даёт признак `slow`, и панель добавляет
пояснение.

### 2.3. Повторный старт

`POST /api/projects/:id/workflow/start`:

- запуск идёт и `problem = null` — второе сообщение не ставится, ответ
  `{ owner, already: true }`;
- `problem` есть — новый запуск: если старое сообщение ещё в очереди, новое не добавляется,
  только заново начинается отсчёт; иначе ставится новое сообщение. `problem` сбрасывается.

### 2.4. Карточка плана в панели

Модель `planView` (`session-model.js`) в фазе `ready` берёт `start` автопилота
сессии-владельца и даёт `starting`:
`{ step, since, slow, problem }` или `null`. Пока `starting` есть и `problem = null`, кнопки
«Начать выполнение плана» нет.

| Состояние | Что видит пользователь |
| --- | --- |
| `step = sending` | спиннер «Запускаю план» · «команда ждёт отправки агенту» · таймер |
| `step = delivered` | спиннер «Запускаю план» · «агент получил команду и готовится к первой задаче» · таймер |
| `slow` | к строке добавляется «агент готовится дольше обычного — это не ошибка, можно подождать» |
| `problem` | предупреждение с текстом проблемы и кнопка «Начать заново» (тот же маршрут `start`) |
| фаза `running` | обычная карточка с «Пауза» |

Заголовок карточки на время запуска — «План запускается».

Спиннер появляется сразу по нажатию, ещё до ответа службы. Если запрос `start` вернул ошибку,
спиннер убирается, кнопка возвращается, ошибка показывается над экраном, как сейчас.

## 3. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Состояние запуска, ступени и проблемы | одинаково | одинаково | одинаково (x64 и ARM64) |
| Спиннер и «Начать заново» в панели | одинаково | одинаково | одинаково |

Поведение одинаково на всех ОС: кода с ветками по ОС и программ одной ОС нет, новых записей в
`tools/platform-guard/allowlist.json` не требуется. Доставка до Claude (Stop-хук) и до
Kimi (промпт через сервер Kimi) различается по провайдеру, а не по ОС.

## 4. Проверка

- Автоматические тесты (на всех ОС одинаковы):
  - `autopilot`: после `start` есть `start.step = sending`, после доставки — `delivered`;
    после записи Kit о начатой задаче `start = null`; `not-delivered` по времени и по
    заметке канала; `turn-ended` с удержанием Stop; повторный `start` во время запуска не
    ставит второе сообщение; `start` после проблемы — ставит;
  - `session-view`: `planView` в фазе `ready` со `starting` без кнопки старта, с
    проблемой — с «Начать заново», `slow`; заголовок «План запускается».
- CI: macOS, Linux, Windows x64 и ARM64.
- Живая проверка: macOS — пользователь (запуск плана в сессиях Claude и Kimi: спиннер со
  ступенями, затем «Пауза»; закрытая сессия Kimi — проблема и «Начать заново»); Windows —
  проверяющий на Windows; Linux — только CI.

## 5. Границы

Не входит:

- видимый ход для «Продолжить», «Нужны исправления» и «Подтвердить выпуск»;
- сохранение состояния запуска между перезапусками службы;
- отмена запуска из панели.
