# M8: протокол Kimi Code 2.5.2 — проверенные факты и правила работы с ним

Приложение к [спецификации M8](M8-kimi-provider.md). Всё здесь проверено 2026-11-09 на
`kimi` 2.5.2 (macOS, arm64) на стенде: отдельный `KIMI_CODE_HOME`, подставная модель,
два сервера `kimi web` на одном каталоге. Реальные ответы сервера и stdin хуков — в
[захватах](../evidence/M8-kimi-captures.md); тесты `provider-kimi` берут фикстуры оттуда
(`test/fixtures`). **П** — не проверено. Разделы 8–11 — не факты о Kimi, а правила Kit
(часть решения M8).

## 1. Сервер

- `kimi web --no-open --port N` — REST `/api/v1`, `/api/v2` и WebSocket на 127.0.0.1.
  В stdout печатает баннер **с токеном** (`Local: http://127.0.0.1:N/#token=…`).
- Токен — файл `<home>/server.token`, **общий на каталог**: второй сервер файл не меняет,
  оба принимают один токен. Заголовок `Authorization: Bearer <токен>`.
- Запись сервера: `<home>/server/instances/<server_id>.json` — `server_id`, `pid`, `host`,
  `port`, `started_at`, `heartbeat_at`, `host_version`; исчезает при остановке.
- `POST /api/v1/shutdown {}` останавливает сервер. `GET /api/v1/healthz` — без токена.
- `GET /api/v1/meta` → `server_version`, `server_id`, `backend: "v2"`, `capabilities`,
  `features`. `GET /api/v1/auth` → `models_ready`, `providers_count`, `managed_provider`.
  `GET /api/v1/config` → `default_model`, `default_permission_mode`, `providers`, `models`,
  `hooks[]`.
- Ответ — конверт `{ code, msg, data }`, HTTP 200 и при ошибке. Коды: `0` успех; `40001`
  неверный запрос; `40110` нет провайдера (нет входа); `40927` `prompt_id` уже использован;
  `40928` Remote Control уже работает; `40931` сессию ведёт другой процесс; `40932` сессия
  изменена другим клиентом, нужен `:reload` (**П**: на стенде не возник).

## 2. Рабочие области и доверие

- `POST /api/v1/workspaces { root, name?, idempotency_key? }` **без ключа создаёт новую
  запись при каждом вызове**. `GET /api/v1/workspaces` → `items[]`: `id`, `root`, `name`,
  `kind: "managed"`, `session_count`, `last_opened_at` (времени создания нет).
  `DELETE /api/v1/workspaces/{id}`.
- Доверие: `GET|POST /api/v1/workspaces/{id}/trust` → `{ trusted }`; на диске — файл
  `<home>/workspace-trust/wd_<имя>_<hash>` с `{ root, trustedAt }` (один на папку, сколько
  бы рабочих областей на неё ни указывало).

## 3. Сессии

- `POST /api/v1/sessions { workspace_id, title, metadata: { cwd } }` → `session_<uuid>`.
  У такой сессии `agent_config.model` пуст: ход падает `StopFailure` «Model not set».
  Поле `model: "<провайдер/модель>"` в теле `POST …/prompts` решает это, и сессия модель
  запоминает.
- `POST /api/v1/sessions/{id}/prompts { content: [{ type: "text", text }], prompt_id?,
  model? }` → `{ prompt_id, user_message_id, status }`; `status`: `running`, `queued` (идёт
  ход в этом же сервере; промпт выполнится после него), `blocked`. Повтор того же
  `prompt_id` → `40927`: промпт уже принят.
- `GET /api/v1/sessions/{id}/messages?page_size&after_id&before_id&role` — **от новых к
  старым**, `data { items[], has_more }`. Сообщение: `id`, `role` (`user`, `assistant`,
  `tool`), `content[]`. У пользовательских — `metadata.origin.kind`: `user` или
  `injection` (`variant`: `date_change`, `interruption`); **id пользовательского сообщения
  равен `prompt_id` запроса**. У ответа ассистента нет ни `prompt_id`, ни `metadata`.
- `GET /api/v1/sessions/{id}` → `busy`, `main_turn_active`, `pending_interaction`,
  `last_turn_reason`, `archived`, `agent_config`, `title`, `metadata.cwd`. **`busy` верен
  только для ходов этого же сервера**: во время хода в другом процессе он `false`.
- `GET /api/v2/sessions` (`workspace.id`, `meta.archived`, `page_size`, `page_token`) →
  `items[]`: `id`, `workspace { id, cwd }`, `meta { title, last_prompt, created_at,
  updated_at, archived }`, `activity { status, model }`; `has_more`, `next_page_token`.
- Действия `POST /api/v1/sessions/{id}:<действие>`: `reload`, `abort` (`{ aborted: true }`,
  хук `Interrupt`), `archive`, `restore`, `delete`, `takeover`. Имя —
  `POST …/profile { title }`. Пакетно: `POST /api/v2/sessions:archive|:restore { ids }`.

## 4. Замок сессии

- Файл `<home>/locks/sessions/<session_id>.lock`: `{ version, token, pid, hostname,
  startedAt, clientIdentity, clientDisplayName }`. Его берёт процесс, который ведёт ход,
  и отпускает через 3 с после конца хода (`SESSION_LOCK_RELEASE_DELAY_MS`). Так делают все
  клиенты Kimi (сервер, терминал, приложение): замок — общий слой движка.
- Замок считается живым, если `hostname` другой, или `pid` жив и `startedAt` не раньше
  загрузки системы.
- Пока замок чужой, запись в сессию из другого процесса отвечает `40931`; после простоя
  сессию ведёт любой процесс. `KIMI_CODE_SESSION_LOCK=false` отключает замки.
- Подагент (`Agent`) работает внутри основного хода: замок держится до конца основного хода.

## 5. Хуки

- Только пользовательский `<home>/config.toml`, массив `[[hooks]]`: `event`, `matcher?`,
  `command`, `timeout` (1–600 с, по умолчанию 30). Проектных хуков нет. `kimi doctor
  config` проверяет файл. Команда запускается через оболочку системы (`spawn(command, [],
  { shell: true })`): `/bin/sh -c` на macOS и Linux, `cmd.exe /d /s /c` на Windows.
- stdin — JSON (snake_case); всегда `hook_event_name`, `session_id`, `cwd`,
  `client_type`:

| Событие | Поля |
| --- | --- |
| `SessionStart` | `source` (`startup`, `resume`), `model`, `profile` |
| `UserPromptSubmit` | `session_title`, `prompt: [{ type, text }]` (**массив**), `is_steer`; срабатывает и для промптов из API |
| `TurnStarted` | `turn_id`, `origin_kind` (`user`, `system_trigger`), `origin_name?` (`subagent`), `prompt` |
| `Stop` | `session_title`, `stop_hook_active` |
| `StopFailure` | `error_type`, `error_message` |
| `Interrupt` | `session_title`, `turn_id`, `reason` |
| `SubagentStart`, `SubagentStop` | `agent_name`, `prompt` / `response` |

- **`Stop` срабатывает и в конце хода подагента** — с тем же `session_id` и без
  отличительных полей; порядок: `TurnStarted` → `TurnStarted(subagent)` → `SubagentStart` →
  `Stop` → `SubagentStop` → … → `Stop` основного хода. В `Stop` нет ни текста ответа, ни
  пути к журналу.
- Ответ хука: код 2 и stderr — блок; код 0 и JSON в stdout — `{ message? }` или
  `{ hookSpecificOutput: { permissionDecision: "deny", permissionDecisionReason } }`.
  `UserPromptSubmit` добавляет `message` (или сырой stdout) в контекст. Ответы формата
  Claude (`decision: "block"`, `additionalContext`) игнорируются. Продолжение по `Stop` —
  одно за ход. Ошибка и таймаут хука ход не останавливают.
- У команд агента нет переменной окружения с id сессии (`KIMI_SESSION_ID` — только
  подстановка в навыках).

## 6. Приложение и Remote Control

- Приложение Kimi Code (`com.kimi.code.desktop`, движок 2.5.1) делит каталог `~/.kimi-code`
  с CLI и держит свой сервер (своя запись в `instances`).
- Ссылка одна: `kimi-code://open?root=<абсолютная папка>[&new=1]` — открывает проект, не
  сессию.
- Remote Control: `GET /api/v1/remote-control`, `POST /api/v1/remote-control { enabled }`
  (включение и выключение одним запросом); один на машину (`<home>/server/rc.json`,
  `40928` у второго процесса); адрес для браузера —
  `https://code-rc.kimi.com/devices/<device_id>/`.

## 7. Поведение на ОС

Проверено только на macOS. На Linux и Windows те же пути внутри `KIMI_CODE_HOME` и тот же
API — **П**; отличие, известное из кода `kimi`: оболочка хука на Windows — `cmd.exe`, а
инструмент команд агента ищет Git Bash (`KIMI_SHELL_PATH`).

## 8. Запись хука Kit в `config.toml`

- Текст команды строит `kit-structure/hook-config` по `HookHost`. macOS и Linux:
  `[ -x "$HOME/.local/bin/wfk" ] && "$HOME/.local/bin/wfk" hook … --client kimi; exit 0`.
  Windows (оболочка `cmd.exe`): `"<node.exe>" "<wfk.mjs>" hook … --client kimi` с
  абсолютными путями. В TOML команда — строка в одинарных кавычках; есть `'` — в двойных с
  экранированием `\` и `"`. Путь с `"`, `%` или переводом строки → `status: 'unknown'` с
  причиной, запись не предлагается.
- Разбор файла — текстовый, без библиотеки TOML: блок `[[hooks]]` — от заголовка до
  следующего заголовка таблицы, с учётом многострочных строк. Блок Kit — тот, чья команда
  вызывает запускатель Kit (`callsLauncher`) с `--client kimi`. Файл не разбирается или
  хуки заданы массивом `hooks = [...]` → `unknown`: Kit не пишет и показывает текст для
  ручной вставки.
- `kitHook.status`: `approved` — все пять блоков с точными командами и таймаутами;
  `pending` — блоков Kit нет; `modified` — часть блоков или иной текст. Целевой файл =
  текущий без блоков Kit + пять свежих блоков в конце под комментарием `# Workflow Kit`.
  `kitHook.command` — добавляемый текст; `kitHook.hash` = sha256(текущий файл, `\0`,
  целевой файл). Новое необязательное `HookState.writes: TrustWrite[]` несёт файл и
  добавляемый текст для предпросмотра; `note` говорит, что хук общий для всех проектов и
  действует после перезапуска приложения Kimi Code и открытых в терминале `kimi`
  (**П**: подхват без перезапуска).
- `approveHooks(project, { command, hash })`, маршрут `hooks/approve` прежний; мастер
  передаёт `command` и `hash` из показанного пользователю предпросмотра:
  1. замок `config.toml.wfk-lock` (создание `wx`, содержимое `{ pid, startedAt }`).
     Чужой замок брошен, если его `pid` мёртв или `startedAt` раньше загрузки системы;
     нечитаемый — если файл старше 30 с. Живой замок → 409 `hooks-busy`;
  2. перечитать файл и пересчитать `hash`; не совпал → `ProviderError('hooks-changed')`
     (409), панель показывает новый предпросмотр;
  3. копия `config.toml.wfk-backup-<время>` (хранятся три последние);
  4. запись во временный файл рядом; **прямо перед `rename` файл читается ещё раз**: не
     равен прочитанному на шаге 2 → временный файл удаляется, 409 `hooks-changed`; иначе
     `rename`, права исходного файла сохраняются;
  5. `kimi doctor config`; отказ → вернуть копию, **только если файл всё ещё равен
     записанному**, иначе оставить и назвать путь копии;
  6. чтение назад → `approved`; замок снимается в любом исходе.
  Нет `config.toml` → файл создаётся из одних блоков Kit. Замок защищает от второй записи
  Kit; правку файла другой программой между сверкой шага 4 и `rename` (доли миллисекунды)
  Kit исключить не может: изменённый файл остаётся в копии шага 3.
- После записи: `GET /config` своего сервера не показывает хук → Kit перезапускает свой
  сервер, когда ни у одной сессии нет живого замка.

## 9. Сессии: список, ответ, доставка, удаление

- **Принадлежность.** Сессия принадлежит проекту, если её папка (`workspace.cwd`,
  `projectPath` записи, `cwd` журнала) — папка проекта или внутри неё (`sameFolder`,
  `isInside`); правило одно для всех источников. Рабочие области проекта — все из
  `GET /workspaces`, чей `root` — папка проекта или внутри неё. Вложенный
  зарегистрированный проект видит свои сессии и в родительском проекте, как у ChatGPT.
- **`listSessions`** сливает по id три источника с приоритетом: сервер > запись панели >
  журнал хука `SessionStart`. С сервера: `GET /api/v2/sessions` по `workspace.id` каждой
  рабочей области проекта, `page_size=100`, по `next_page_token` до 20 страниц, отдельно
  `meta.archived=false` и `true`; обрыв на пределе страниц → пометка «показаны не все
  сессии Kimi». Ответ кэшируется на 5 с. Сервер недоступен → записи и журнал с пометкой
  «Kimi недоступен: <причина>». Архивная в Kimi сессия, не архивная в панели, — пометка
  «в архиве Kimi».
- **`lastAnswer(project, sessionId)`.** `GET …/messages?page_size=50`, дальше по
  `before_id` до 10 страниц. Начало хода — новейшее сообщение `user` с
  `origin.kind: "user"`; ответ — текстовые части новейшего сообщения `assistant` после
  него. Нет такого сообщения ассистента → `null`. Начало хода не найдено за 10 страниц,
  ошибка API или неожиданная форма → отказ `ProviderError('answer-unavailable')`:
  отсутствие ответа и сбой чтения не смешиваются.
- **`sendMessage(project, sessionId, text, delivery: { id })`** — `true`, когда Kimi принял
  промпт:
  - вызовы по одной сессии идут строго по очереди; `prompt_id = 'kit-' + delivery.id`,
    id даёт вызывающий и повторяет его при каждой новой попытке той же доставки;
  - тело: `content: [{ type: 'text', text }]`, `prompt_id` и `model` =
    `config.default_model`, если у сессии `agent_config.model` пуст;
  - `running`, `queued` → `true`; `blocked` → `true` и пометка о ждущем вопросе; `40927` →
    `true` (промпт уже принят прошлой попыткой);
  - `40931` → повторы через 4, 8 и 16 с, затем `false`; `40932` → `:reload` и один повтор
    (**П**); сетевой сбой → один повтор после проверки сервера; остальное → `false`,
    причина — в журнале событий и в пометке сессии;
  - архивная в Kimi сессия → `false` с причиной «в архиве Kimi»; `:takeover` Kit не
    вызывает никогда.
- **Архив.** Истина панели — локальная отметка `session-titles`; сессии из локального
  архива канал сообщений не шлёт (проверка в `cli` до `sendMessage`).
  `archiveSessions`/`restoreSessions` повторяют отметку в Kimi; отказ или недоступный
  сервер отметку панели не отменяют, сессия несёт пометку «архив Kimi не обновлён».
- **Удаление.** `deleteSessions(project)`: при доступном сервере — полное перечисление
  сессий рабочих областей проекта (архивные тоже, без предела страниц) и `:delete` каждой
  плюс id из записей и журнала. Любой отказ, обрыв перечисления или недоступный сервер →
  в `kimi-deletes.json` остаётся намерение `{ root, since, sessionIds }` (`since` — время
  запроса удаления). `retryDeletes()` повторяет то же перечисление по `root` и удаляет
  сессии с `created_at ≤ since` и известные id; запись уходит только после полного
  перечисления без отказов. Так удаляются и сессии, созданные вне панели, а сессии новой
  папки с тем же путём, созданные позже `since`, не трогаются.

## 10. Свой сервер Kit и HTTP-клиент

- Сервер: `kimi web --no-open --port <свободный>` через `process-supervisor`, окружение
  `cleanEnv`. **Вывод процесса не сохраняется**: в нём токен; у `process-supervisor`
  появляется режим без файла вывода (`logFile: null` → `stdio: 'ignore'`). Готовность:
  запись `<home>/server/instances/*.json` с pid процесса (до 15 с), затем `healthz` и
  `meta`. Процесс переживает службу; после её перезапуска Kit находит свой сервер по записи
  supervisor и записи `instances` с тем же pid. Запуск — по первому требованию и в
  `autostart()`, если есть записи сессий Kimi; `maintain()` поднимает упавший. Действие
  провайдера `restart-kimi-server`: `POST /shutdown`, через 5 с — завершение процесса.
- HTTP-клиент: только `http://127.0.0.1:<порт>`, `redirect: 'error'`, таймаут 10 с (30 с у
  `prompts`). Токен читается из `<home>/server.token` на каждый запрос и идёт только в
  заголовке; отказ авторизации → перечитать и повторить один раз. `code ≠ 0` →
  `KimiError { code, msg }`; прочие поля ошибки (`stack`, `data`) отбрасываются.
- Проверка формы: у `meta`, `auth`, `config`, `workspaces`, `sessions`, `messages` клиент
  проверяет наличие и тип полей, которыми пользуется. Иная форма → `KimiError` «неизвестный
  ответ Kimi <версия>»: статус провайдера `error` с этой пометкой, операции отказывают.
  Версия не 2.5.x при верной форме — `ready` с пометкой «не проверялась с Workflow Kit».

## 11. Конец хода и доставка: правила канала

Для клиентов, чей провайдер даёт `sessionIdle` и `sendMessage` (в M8 — Kimi). Канал
получает эти методы зависимостью от `cli`; у слота появляются поколение хода, исходящее
и счётчик неудач.

- **Уведомление.** `POST /api/hooks/turn-end { client, sessionId, cwd, event }`. Событие
  `Stop`: поколение хода растёт; если в этот миг замка сессии нет — сессия работает без
  замков (ход ещё не кончен, хук выполняется внутри него, а замок держится ещё 3 с):
  пометка «Kimi запущен без замков сессий (`KIMI_CODE_SESSION_LOCK`): автопилот, ревью и
  сообщения панели для этой сессии выключены», конец хода не обрабатывается, `flush`
  ничего не шлёт, пока не придёт `Stop` при живом замке (**П**). Иначе запускается
  наблюдатель. `StopFailure`, `Interrupt`: наблюдатель отменяется, слот «ждёт», слушатели
  конца хода и решатель не вызываются; очередь и исходящее сохраняются.
- **Наблюдатель** — один на сессию, новое уведомление его перезапускает: раз в секунду
  `sessionIdle`, до 120 с. Истёк — слот остаётся «работает» с отметкой ждущего конца хода;
  `maintain()` раз в минуту проверяет такие слоты и запускает отложенный Stop, когда
  сессия свободна. Слоты без пришедшего `Stop` `maintain()` не трогает.
- **Отложенный Stop.** 1) запомнить поколение; 2) слушатели простоя (`onIdle`: отложенное
  имя сессии); 3) `lastAnswer`, при отказе — ещё две попытки через 2 с; 4) поколение
  изменилось или сессия снова занята → отмена (придёт новый `Stop`); 5) слот «ждёт»;
  ответ прочитан → слушатели конца хода (`StopEvent` с текстом, происхождением и
  источниками хода); не прочитан → пометка «ответ Kimi не прочитан: <причина>», слушатели
  и решатель не вызываются; 6) решение: есть исходящее → оно; иначе очередь не пуста →
  исходящее из всей очереди (`delivery`); иначе, если ответ прочитан, решатель:
  `continue` → исходящее (`decider` или `reminder`), `hold` → слот «удерживается» до
  `wake` или нового сообщения, `release` → ничего.
- **Исходящее** `{ id, text, origin, sources }` создаётся до отправки. Отправка: запомнить
  ожидаемый текст → `sendMessage(…, { id })`. `true` → исходящее снято, слот «работает» с
  его происхождением и источниками. `false` → слот «ждёт», исходящее остаётся: следующая
  попытка (`flush` из `enqueue`, `wake`, `maintain()`) шлёт его же с тем же id. Пять
  неудач подряд → пометка «сообщение не доставлено: <причина>», `maintain()` больше не
  повторяет; новое сообщение или `wake` обнуляют счётчик. Сообщения, пришедшие при живом
  исходящем, ждут в очереди следующей доставки.
- **`UserPromptSubmit`.** Текст равен ожидаемому → промпт Kit: исходящее снимается (это
  подтверждение приёма, даже если `sendMessage` ответил отказом), слот «работает» с
  происхождением и источниками исходящего, ответ хука пуст, `HookReply.own = true`
  (проводка зовёт `autopilot.onPrompt(key, true)`). Хук может прийти раньше ответа API —
  поэтому текст запоминается до запроса. Иной текст → промпт пользователя: поколение
  растёт, отложенный Stop отменяется; непринятое исходящее `delivery` возвращается в
  голову очереди и уходит ответом хука `{ message }`, исходящее решателя отбрасывается;
  происхождение — `user`.
- **Нет подтверждения.** `sendMessage` ответил `true`, а `UserPromptSubmit` не пришёл за
  60 с → пометка «хук Kit не работает в Kimi (перезапустите Kimi Code)»; повторной
  отправки нет: промпт принят.
- **`flush(key)`**: слот «ждёт» или «удерживается», не помечен «без замков», отправка не
  идёт и сессия свободна → шаг 6 отложенного Stop (решатель — только после `wake`).
  Сессия занята → ничего: доставит конец хода.
- **Перезапуск службы.** Слоты и очередь живут в памяти: после перезапуска повторять
  нечего. `Stop`, пришедший, пока службы нет, теряется, как удерживаемый `Stop` у Claude
  и ChatGPT; работа продолжится после следующего сообщения в сессию.
