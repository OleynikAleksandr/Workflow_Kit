# M39: подготовка документов и порядок задач

Часть [спецификации M39](M39-autopiloting.md). Уточнение после ревью Claude, круг 1.

## 1. Документальные разделения до task:start

Это отдельные docs:commit между задачами, а не часть функционального коммита. Агент
выполняет их до указанной задачи; путь назначения и исходный раздел заданы заранее.
Текст переносится целыми разделами без сокращения фактов, на месте остаётся ссылка.
При смене каталога относительные ссылки корректируются только для сохранения адресата.
Старые anchors сохраняются короткими секциями-указателями. После переноса — чтение
через context, проверка ссылок, UTF-8 и размера, затем docs:commit. Если задачи уже
в работе, перенос откладывается до ближайшего безопасного промежутка, не смешивается.

| До | Исходник и разделы | Назначение |
| --- | --- | --- |
| T001 | workflow-kit/module.md: Operations | тот же модуль, operations.md |
| T004 | WorkflowKitExecutionModes.md: 10. Harness; 11. Мелкие исправления того же релиза | docs/architecture/workflow-kit/WorkflowKitHost.md |
| T004 | WorkflowKitInstallation.md: 5. Интеграция с Harness; 7. Перевод репозитория Harness AI на Kit | docs/architecture/workflow-kit/WorkflowKitHostInstallation.md |

Прочие разделы не урезаются ради лимита. До каждого изменения дополнительно проверяется
размер его contract/module.md; если нужен ещё перенос, он выполняется тем же отдельным
docs:commit до task:start. Все новые части остаются не больше 28 000 байт.

Функциональное разделение autopilot.ts (400 строк) и decide.ts (399 строк) — первый
шаг T005: выделить storage/settings и orchestration decision в отдельные исходники
того же модуля, сохранив public API и проверив прежние тесты до добавления поведения.
Это код, поэтому входит в T005, а не в подготовительный docs:commit. Ранние T002/T004
добавляют host-ticket helper и тексты отдельными файлами; не расширяют предельные
autopilot.ts/decide.ts до этого разделения.

T001–T004 меняют исходники и пересобирают vendor-бандл в том же work-коммите, как
предусмотрено контрактом kit-build и использовалось M31/M37/M38. Это генерация
отслеживаемой зависимости, обязательная для проверки коммита. Она не устанавливает
приложение и не публикует релиз. В рамках согласования M39 предлагается явно закрепить
эту узкую оговорку в источнике инструкций: правило delivery относится к сборке/упаковке/
установке выпуска приложения. Проверка свежести bundle остаётся обязательной на каждом
коммите ядра. До принятия плана оговорка не применяется для выполнения работ.

Каждая задача службы начиная с T005 проверяет свой публичный контракт на настоящем
новом бандле; fake-адаптеры служат только для управляемых отказов и гонок, не заменяют
интеграцию. DOCS идёт после готовых исходников ядра и всех изменений службы/панели.
Т010 добавляет интеграционные сценарии, но найденные дефекты DONE-задач исправляются
через plan:extend отдельными fixes-задачами, не скрыто в тестовой задаче.

## 3. Проверяемый bootstrap Kit для самого M39

До T005, после коммита T004 и на чистом дереве без транзакций/назначений, выполняется
штатное обновление Kit проекта до нового проверенного бандла. Старое приложение ещё
поставляет 2.2.7, поэтому использовать его кнопку для этого недостаточно. Через
публичный #kit-bundle из исходников получают ensureKitBundle во временном каталоге;
затем запускают публичный CLI этого артефакта: `node <bundle.file> install <project>
--update --host harness`. Это штатный установщик и его служебный commit, не ручное
редактирование runtime/плана. Управляемый раздел wfk обновляется штатно вместе с
приложением/структурой; он не нужен для команды defer-delivery.

T003/T004 заранее проверяют обновление временного проекта с открытым старым scope:
сохраняются задачи/DONE SHA/owner/revision, mode остаётся off; доступны schema и
`task:defer-delivery`. После обновления самого Workflow_Kit сверяются recover, validate,
version/capability и чистота дерева. Отказ обновления означает остановку подготовки
T005, без обхода и без установки поверх незавершённой транзакции. Весь M39 остаётся
в обычном режиме с пользовательской приёмкой и публикацией.

Таким образом, при красном CI в T012 команда defer уже установлена. Фактическая
процедура исправлений описана в [контракте Kit](M39-autopiloting-kit.md) и
[проверках](M39-autopiloting-validation.md).
