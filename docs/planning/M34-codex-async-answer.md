# M34: ответ на асинхронный вопрос ChatGPT в идущий ход

## Цель и согласование

В M33 асинхронный вопрос ChatGPT/Codex (`request_user_input_async`, раздел 2.7
[спецификации M33](M33-codex-async-questions.md)) показывается карточкой в диалоге панели, а
ответ из карточки уходит маршрутом сообщения панели, как текст из поля ввода. Пока агент
работает, этот маршрут кладёт текст в очередь канала, и очередь отдаётся агенту только в конце
хода. Агент же ждёт ответа внутри хода, поэтому ход не кончается, ответ из очереди не
приходит, и диалог стоит. В ChatGPT тот же вопрос отвечается сразу: ответ входит в идущий ход.
Ответ из ChatGPT виден в ленте панели сырой служебной обёрткой.

После M34 ответ из карточки панели входит в идущий ход так же, как ответ из ChatGPT, и агент
продолжает работу. Ответы в ленте читаются как обычный текст, а закрытая карточка показывает
выбранный ответ.

Пользователь, 15.11.2026, о проекте 002: «карточка с вопросом возникла в Workflow Kit
диалоге, и я на нее ответил. На этот первый вопрос. Кит выставил его ответ в очередь, и эта
очередь никуда не пришла». И дальше: «если мы рассчитываем, что ответ выбранный доходит до
агента только когда он находится в этапе пассивном, то он никогда не придет. Он же ждет».
После проверки на проекте 003: «результаты ответов появились, хоть и в плохо читаемом виде, с
ненужной служебной информацией и в диалоге Workflow Kit». В панели выбраны спецификация и
план без ревью.

## 1. Факты

Живая проверка 15.11.2026 на проектах 002 и 003 — раздел 9
[фактов Codex](../design/M33-codex-question-facts.md). Главное:

- **[проверено]** Агент, которому велено «дожидаться ответа», не заканчивает ход после
  асинхронного вопроса: весь опрос из трёх вопросов прошёл одним ходом. В T014 агент после
  вопроса ход закончил. Бывает и то и другое.
- **[проверено]** ChatGPT показывает асинхронный вопрос своей карточкой и отправляет ответ
  сообщением пользователя внутри того же хода (хука `Stop` между ними нет). Текст сообщения —
  служебная обёртка (раздел 2.2).
- **[проверено]** Ответ из карточки панели при идущем ходе ложится в очередь канала (`pending
  1`) и до конца хода агенту не уходит.
- **[проверено, вывод по хронологии]** Сообщение, влитое в ход, вызывает хук
  `UserPromptSubmit`: очередь канала опустела через 2 с после ответа из ChatGPT, то есть
  канал отдал её контекстом этого хука.
- **[схема codex-cli 0.169.0]** `turn/steer { threadId, input, expectedTurnId }`, где
  `expectedTurnId` обязателен: запрос отклоняется, если он не совпадает с идущим ходом. Ответ —
  `{ turnId }`. Проба M18: текст входит в идущий ход; без хода — ошибка «no active turn to
  steer».
- У асинхронного вопроса нет множественного выбора: `AsyncUserInputQuestion { title,
  options: string[] | null }`.
- T014 этого не поймал: хуки тестового проекта не были одобрены, канал не знал состояния
  сессии и отправлял ответ сразу; к тому же агент в T014 закончил ход.

## 2. Решение

Ответ на асинхронный вопрос идёт маршрутом ответа (раздел 2.1 M33) со всеми его правилами
попытки. Codex передаёт его в идущий ход (`turn/steer`) той же обёрткой, что ChatGPT, а без
хода начинает ход этим текстом. Лента разбирает обёртку: показывает ответ текстом и даёт
вопросу `answers`.

### 2.1. Контракт (`provider-registry`)

- `ChatQuestion.reply: 'message'` теперь значит: ответ уходит агенту сообщением пользователя
  (обёртка раздела 2.2), но через маршрут ответа `POST …/questions/:qid/answer` с
  `attemptId`, журналом попыток и кодами раздела 2.1 M33. У такого вопроса могут быть
  `delivery: 'sent'` и `answers` (разобранные из ответного сообщения, кто бы его ни прислал).
  Место карточки после своего сообщения и неизменная строка состояния остаются (2.7 M33).
- Нормализация страницы (`questionsOut`) сохраняет `answers` и `delivery` у вопроса с
  `reply: 'message'`. Маршрут и журнал попыток не меняются.
- `QUESTION_BY_MESSAGE_REASON` больше не нужен для отказа и удаляется, если не используется.

### 2.2. Обёртка ответа (`provider-codex`, новый `src/question-reply.ts`)

Формат, как в ответе ChatGPT (проект 003):

```text
<send_user_message_question_reply>
[{"questionItemId":"[\"request_user_input_async\",\"<id элемента>\",0]","question":"<вопрос>","answer":"<ответ>"}]
</send_user_message_question_reply>
```

- `replyText(itemId, parts, answers)` — открывающий тег, перевод строки, JSON-массив одной
  строкой (`JSON.stringify`, кириллица без `\u`-экранирования), перевод строки, закрывающий
  тег и перевод строки. Элемент на каждую часть вопроса по порядку: `questionItemId` —
  `JSON.stringify(['request_user_input_async', <id элемента>, <номер части с 0>])`,
  `question` — текст части, `answer` — свой текст, если он не пуст, иначе выбранная подпись.
  Порядок ключей — `questionItemId`, `question`, `answer`.
- `parseReply(text)` — элементы `{ itemId, index, question, answer }` или `null`. Разбирается
  только текст, который без пробелов по краям целиком равен одной обёртке с JSON-массивом
  объектов со строковыми полями; `questionItemId` — JSON-массив из `'request_user_input_async'`,
  строки и целого числа не меньше 0. Иначе — `null`, текст остаётся как есть.

### 2.3. Ответ (`provider-codex`, `answerQuestion` для `async:…`)

1. Без общего демона (`shared()` ложно) — `question-unavailable` с
   `QUESTION_UNAVAILABLE_REASON`; ничего не передаётся.
2. Свежее чтение ленты треда (не кэш). Вопроса нет — `question-unavailable`; не `pending` —
   `question-stale`; `answerable: false` — `question-unavailable` с его причиной.
3. `checkQuestionAnswer` (`question-invalid`), затем `replyText`.
4. В одном соединении с демоном — состояние треда и идущий ход, как у прерывания
   (`thread/read`, затем `thread/turns/list` по убыванию, `interrupt.ts`). Состояние не `active`,
   не `idle` и не `notLoaded` (или чтение не удалось) — `question-unavailable` «Ответьте в
   приложении ChatGPT» без передачи.
5. `commit()` (запись `sent` журнала), затем одна передача:
   - `active` с идущим ходом — `turn/steer { threadId, input: [{ type: 'text', text }],
     expectedTurnId }`;
   - `idle` или `notLoaded` — подписка слушателя вопросов (`prepareTurn`) и `wakeThread`
     с текстом обёртки (`thread/resume` без ходов при `notLoaded`, `turn/start`);
   - демон отклонил `turn/steer` (ход кончился или сменился) — ничего не передано: ещё одно
     чтение состояния и одна передача по тем же правилам (`turn/steer` в новый ход или
     `turn/start`). Больше попыток нет.
6. Демон вернул `turnId` — исход `accepted`: сообщение с ответом панели принято в тред.
   Какой ответ агент получил первым, показывает лента (2.4).
7. Ответа демона нет за срок запроса или соединение оборвалось после отправки —
   `question-timeout` с `delivery: 'sent'`, без повтора. Демон отклонил и вторую передачу —
   `question-failed` «ChatGPT не принял ответ: <причина>»; запись журнала остаётся `sent`, как
   после любой передачи.
8. Хук `UserPromptSubmit` влитого сообщения канал обрабатывает как сообщение пользователя из
   ChatGPT (факт раздела 1): очередь канала отдаётся контекстом, ход продолжается.
   `agent-channel` не меняется.
9. В журнал службы — строки без текста вопроса и ответа: `codex: question answer steered into
   turn <turnId> of thread <id>` или `codex: question answer started a turn of thread <id>`.

`turn/steer` используется только здесь; поле ввода панели по-прежнему не вливает текст в
ход (M18, раздел 5).

### 2.4. Лента (`provider-codex`, `history-*.ts`)

- Сообщение пользователя, текст которого `parseReply` разбирает, показывается читаемым
  текстом: один элемент — ответ; несколько — строки «<вопрос> — <ответ>». `id`, роль и время
  сообщения прежние. Преобразование идемпотентно (контракт синхронизации ленты M32). Так же —
  в истории `legacy`.
- Асинхронный вопрос по-прежнему `answered`, когда после него в ленте есть сообщение
  пользователя. Если первое такое сообщение — обёртка с элементами этого вопроса (`itemId`
  равен id элемента), вопрос получает `answers`: часть `q<index+1>` — `{ selected: [<подпись>] }`,
  если ответ совпал с подписью варианта, иначе `{ selected: [], other: <ответ> }`. Иначе
  вопрос закрыт без `answers`, как раньше.
- Байты разобранных ответов входят в предел кэша истории; текст ответов в журнал не пишется.

### 2.5. Карточка (`session-chat`)

- Карточка вопроса с `reply: 'message'` отправляет ответ маршрутом ответа, как блокирующая:
  `attemptId`, фазы попытки, повтор при сетевой ошибке и запрет второй передачи — по разделу
  2.5 M33. Отправка маршрутом сообщения, фаза `messaged` и текст «Ответ отправлен
  сообщением» удаляются.
- Выбор — один вариант или свой текст (`multiSelect: false`, `allowOther: true`), как в M33.
- Закрытый вопрос с `answers` показывается, как закрытый блокирующий: вопрос и выбранный
  ответ. Без `answers` — «Ответ дан сообщением» (ответили обычным сообщением из поля ввода
  или из ChatGPT не обёрткой).
- Место карточки после своего сообщения и строка состояния — как в M33.

## 3. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| `turn/steer`, `turn/start` ответа | сокет управления демона | так же | `codex app-server proxy`; x64 и ARM64 |
| Обёртка, разбор ленты, карточка | общий Node-код и код панели | так же | так же; x64 и ARM64 |

Поведение одинаково на трёх ОС; отличается только транспорт к демону, он уже есть. Новых
вызовов программ ОС нет, `tools/platform-guard/allowlist.json` не меняется.

## 4. Проверка

- Автоматические тесты `provider-codex` на подставном демоне с подставленными `darwin`,
  `linux` и `win32`: обёртка байт в байт по образцу раздела 2.2, разбор (несколько элементов,
  кириллица, чужой тег, лишний текст, неверный `questionItemId`); ответ: `active` —
  `turn/steer` с `expectedTurnId`, `idle` — `turn/start` с обёрткой, `notLoaded` —
  `thread/resume` и `turn/start`, отклонённый `turn/steer` — одна повторная передача,
  закрытый вопрос и вопрос без общего демона — отказ без единого RPC, потерянный ответ
  демона — `question-timeout` без повтора; лента: читаемый текст, `answers` из обёртки
  (вариант и свой текст), обёртка другого вопроса, история `legacy`.
- `provider-registry`: нормализация вопроса `reply: 'message'` с `answers` и `delivery`;
  повтор с тем же `attemptId` не передаёт ответ второй раз.
- `session-chat`: модельные тесты и браузерный прогон в изолированном Chromium — отправка
  маршрутом ответа, закрытая карточка с ответом, обе темы, ширина 390 px.
- CI: macOS, Linux, Windows x64 и ARM64 для точного SHA поставки.
- Живая проверка на установленной 0.14.1 (macOS; пользователь в панели и ChatGPT, агент
  записывает хронологию состояний через API службы): новый проект панели, задача из раздела
  «Цель»; вопрос 1 — панель (вариант), вопрос 2 — ChatGPT, вопрос 3 — панель (свой текст).
  Ожидается: агент продолжает ход после ответов панели без `Stop`; карточка ChatGPT
  закрывается после ответа панели (подтверждает пользователь); лента читаема, карточки
  показывают ответы; очередь канала пуста. Бюджет — до 2 ходов `gpt-6.1-sol` (весь опрос —
  один ход) с согласия пользователя. Windows — проверяющий на Windows; Linux — только CI.

## 5. Границы

- Текст из поля ввода панели во время хода по-прежнему ждёт конца хода в очереди (M18). Если
  агент ждёт асинхронного ответа, отвечать нужно карточкой: в ней есть свой вариант.
  Вливание текста поля ввода в ход — отдельное решение.
- Кнопка ChatGPT «Пропустить» и формат её сообщения не разбираются: такое сообщение
  закрывает карточку, как любое сообщение пользователя.
- Блокирующие вопросы Codex, вопросы Claude и Kimi не меняются.
- Вторая сессия Codex в канале, которая с начала числится «работает» и не получает `Stop`
  (видна в проектах 002 и 003), — отдельный вопрос.
- Ответ, застрявший в очереди проекта 002, не вычищается.
