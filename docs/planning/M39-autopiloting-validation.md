# M39: проверки и поставка

Часть [спецификации M39](M39-autopiloting.md). Тесты не заменяют пользовательскую
приёмку и факт публикации. Новый режим этого релиза автоматически не включает сам себя.

## 1. Обязательные автоматические сценарии

### 1.1. Настройки и источник разрешения — T001

- Чистая установка и старый config: off, прежние session review decisions сохраняются.
- Запись режима/review переживает рестарт и видна двум клиентам панели. Ошибки записи,
  повреждённый файл и устаревшая expectedRevision дают отказ и фактическое значение.
- Переключатель сам не запускает обсуждение, старый план или другой проект.
- Прямое поручение из user prompt и ответ plan-decision принимаются; review/reminder/
  автоматический prompt, отсутствующая исходная цитата и чужая сессия отвергаются.
- Повтор одной команды/кнопки даёт один runId; два конкурирующих старта дают один запуск.
- Новые API соблюдают существующую авторизацию; loopback-only CLI не открывается удалённо.
- off отзывает будущие действия; быстрое off/on не возобновляет старый запуск.

### 1.2. Полный автопилот и ревью — T002

- После прямого поручения без review: prepare → proposal → choose → start без карточек
  дополнительного согласования; рекомендованный способ выполнения записан.
- С review: реальное задание ревьюеру, замечания автору, изменённый план снова ревьюеру,
  согласие обеих сторон именно по окончательному digest, затем choose/start.
- Изменение текста спецификации без новой generation отменяет допуск. Проверяется
  race изменения между чтением одобрения и вызовом scope:choose/start.
- Отказ/таймаут/отмена/пять кругов/недоступный ревьюер не запускают план автоматически.
- Late callback после stop, второй владелец и предложение другого scope не запускают работу.
- Настройка review=false записывает skipped, не successful review.
- После рестарта ревью не создаёт дубликат reviewer и не теряет уже полученное согласие.
- after-start никогда сам не выбирает режим и не нажимает start.

### 1.3. Выполнение и восстановление — T003

- Sequential: work → docs → delivery с предварительным разрешением. Orchestrated:
  выдача независимых назначений, ожидание, интеграция и cleanup без ручного продолжения.
- Более 40 успешных переходов не останавливают запуск. Три хода без фактического
  прогресса дают понятный blocker. Повторный poll/изменение timestamp не считается прогрессом.
- Pending CI и работающий исполнитель не считаются зацикливанием. Failed/cancelled CI,
  чужой SHA и отсутствующий обязательный job запрещают продолжение к приёмке.
- Восстановление при каждом intent/receipt: до и после доставки сообщения, task:start,
  commit, окончания review, выбора режима и старта. Второе сообщение/ход не дублируется.
- Рестарт во время собственной переустановки службы восстанавливает проект/owner/этап.
  Работающая у провайдера сессия не получает параллельный turn.
- «Как идёт?» получает ответ, работа продолжается. Явная пауза/stop, off и барьер M24
  отменяют последующие автоматические действия, включая callback после await.
- Неподдерживаемая wake capability, архивированная сессия и потерянный owner не обходятся
  созданием произвольной новой сессии; панель объясняет препятствие.
- Исправление собственного дефекта проходит в task либо fixes round; новая цель,
  неизвестный секрет и новый внешний эффект требуют решения пользователя.

### 1.4. Завершение и публикация — T004 и T006

На временном git-репозитории и отдельном bare upstream, с настоящим новым Kit:

- Проверенный результат проходит accept/close/publish; в истории source=autopilot,
  runId и исходное поручение, отсутствует выдуманная личная проверка пользователя.
- Нет grant, grant другого scope/task, revoke, manual criterion, старый evidence SHA,
  неподтверждённые checks и pending integration дают типизированный отказ.
- После close сохраняется publishing. Crash после accept и после close не повторяет
  соответствующий коммит. Другой scope/ветка/upstream блокируют старый запуск.
- Crash/timeout после успешного push восстанавливается через fetch и SHA; повторного
  push не требуется. Неполученное подтверждение не превращается в ложный failed/success.
- Remote-ahead, no-upstream, грязное дерево и отказ credentials отображаются отдельно.
  Чужие файлы не удаляются и не попадают в коммит.
- Nothing-to-publish считается успехом только после сверки ожидаемого SHA на remote.
- CI проверяет финальный SHA с accept/close на ci-ветке; запись доказательства вне git
  не создаёт новый непроверенный коммит. main получает именно проверенный SHA.
- Конкурирующие кнопка publish/автопилот/stop дают один согласованный результат.
- Матрица старого режима и разрешённого M39 одинакова в решателе службы и Kit-core.

### 1.5. Панель — T005

- Точные три названия режима, включая «После ручного запуска Плана»; radio/keyboard
  selection, review toggle, статус сохранения и возврат значения после отказа.
- Настройки отображаются одинаково на двух клиентах; гонка revision не теряет изменение.
- Review toggle отсутствует в sidebar; фактическое ревью/замечания/повтор остаются.
- Обе служебные карточки закрыты при загрузке, раскрываются отдельно мышью/клавиатурой;
  заголовки целиком доступны на узком экране. Скрытые контролы исключены из Tab.
- State polling и переход между экранами не сбрасывают раскрытие. Полная reload закрывает.
- Скругления совпадают с `.panel`; светлая/тёмная темы, desktop и iPad portrait.
- Этапы preparing/reviewing/executing/waiting/publishing/completed/blocked/paused
  показывают фактические причины, не устаревший last.reason другого scope.
- После закрытия scope карточка публикации остаётся до проверенного завершения.

## 2. Поставка и проверки коммитов

Профиль уже CONFIGURED: typecheck, test, platform-guard, kit:doc-size, kit:md-links,
kit:file-lines, kit:docs-contracts, kit:conflict-markers. Дополнительная проверка
поставки — installed-service. Новые инструменты не устанавливаются без отдельного
поручения; существующий набор достаточен для тестов. Код каждой задачи проходит
`workflow commit --task`; хуки и проверка свежести vendor-бандла сохраняются.

T001–T005: сервис/панель развиваются против явных интерфейсов нового ядра, fake Kit в
unit/integration boundary тестах. Они не меняют `kit-core` и не требуют пересборки Kit;
старый Kit сообщает unsupported, поэтому новые действия на нём не запускаются.

T006 — задача **delivery**: реализация и поставка нового контракта Kit 2.3.0 одним
коммитом. В ней меняются исходники ядра, генерируемые agent-facing инструкции, версия,
собирается `npm run build:kit`, обновляются vendor/PROVENANCE/bundle-meta и выполняются
сквозные тесты службы с этим настоящим бандлом. Это необходимая атомарная граница:
проверка свежести не позволяет коммитить новые исходники и старый бандл раздельно.
Установленный runtime проекта руками не меняется. Версии и размер module.md проверяются
до правок; документы, которым не хватает места, заранее делятся отдельным docs:commit
между задачами, с переносом целых разделов без сокращений.

T007 — delivery приложения 0.15.0: версии, CHANGELOG, сборка, установка штатным способом,
`wfk doctor --installed`, smoke маршрутов и новой сессии. Проверка installed-service
должна относиться к установленному релизу. В evidence фиксируются версия, SHA, результаты
и отдельно непроведённые live-сценарии. Обновление Kit самого Workflow_Kit выполняется
штатно после закрытия его scope, а проверки нового Kit до этого идут в одноразовых
проектах, чтобы не менять процесс посередине M39.

T008 — delivery проверки: CI четырёх платформ на точном pushed SHA в `ci/M39-autopiloting`;
при ошибке — исправления штатным раундом, повтор CI на новом SHA. Это техническая
CI-ветка до приёмки, не публикация main. Если evidence обновлён коммитом задачи,
проверить и этот SHA, а последний факт успеха оставить в отчёте/внешнем журнале без
нового коммита. Сам scope M39 принимает и закрывает пользователь; main публикуется
по отдельной команде после закрытия. Нельзя применять ещё не принятую функцию для
самостоятельного принятия и публикации её реализации.

## 3. Живые сценарии и доказательства

macOS — пользователь выполняет итоговый live-прогон в установленной панели; агент
может подготовить одноразовые проекты и собрать факты автоматических проверок.
Windows — проверяющий на Windows x64/ARM64; Linux — только CI на текущем этапе.

Для каждого доступного провайдера Claude, Codex и Kimi подготовить отдельные проекты
с короткой проверяемой задачей и настроенным одноразовым upstream. Реальный GitHub
remote для live-публикации согласуется заранее; локальный bare достаточен для
автоматического теста, но не называется live-публикацией на GitHub. Отсутствие провайдера
или нужного доступа записывается как «не проверено» и не подменяется fake-тестом.

Минимальные пользовательские прогоны:

1. after-start: подготовить план, убедиться, что сам он не стартует; один раз нажать
   «Начать выполнение плана». Проверить выполнение, поставку, приёмку, закрытие и remote SHA.
2. full без review: обсудить задачу — ничего не началось; дать прямую команду подготовить
   план. До публикации больше ничего не нажимать. Проверить источник разрешения.
3. full с review: ревьюер получает окончательные документы, находит замечание, автор
   исправляет, итоговая версия согласована; автоматический выбор/старт и путь до SHA.
4. В одном из проходов перезапустить службу при исполнении и после close перед publish;
   после восстановления нет повторных коммитов/первой задачи/публикаций.
5. Во время работы задать вопрос о статусе; затем отдельно проверить pause/resume и
   stop. После stop позднее окончание ревью/CI ничего не запускает.
6. Проверить Settings на Mac и iPad: точные подписи, перенос review, изначально закрытые
   System/shared cards, клавиатуру, обе темы, сохранение раскрытия при обновлении состояния.

Для каждого прогона evidence хранит начальную команду/нажатие, provider/version,
runId/scopeId, review digest и согласие, список task commits, результаты проверок и SHA,
источники accept/close, фактический remote SHA, число дополнительных действий пользователя,
рестарт/ошибку и итог. Счётчик промежуточных подтверждений успешного прохода равен нулю.
Видимая карточка и статус READY_FOR_ACCEPTANCE не доказывают последующие стадии.

## Поведение на ОС

| Проверка | macOS | Linux | Windows |

| Автоматические unit/integration | CI | CI | CI x64 и ARM64 |

## 4. Definition of done

- Все согласованные режимы/Settings реализованы; инструкция, recovery и backend не
  противоречат друг другу и не обходят неуспешное ревью или проверки.
- Обязательные проверки коммитов и CI четырёх платформ успешны на указанных SHA.
- Установленная версия соответствует исходникам и новому бандлу; новый фактический
  hook/context проверен на новой сессии, а не по старой открытой сессии.
- Матрица live заполнена фактами; непроведённые проверки названы. Приёмка M39 — отдельное
  пользовательское решение по этому отчёту; требуемый им live не закрывается тестами.
- В успешных сквозных прогонах один разрешающий старт приводит к фактической публикации
  всех коммитов, включая закрытие, без промежуточных нажатий.
