## 6. Завершение и публикация

Оркестратор/служба получает финальную матрицу criterion → evidence. Автоприёмка возможна
только после завершения обязательных работ/поставок и checks. Если подготовительный
план M39 сам требует пользовательских live-проверок, они остаются ручными; новый режим
не используется для фиктивной самоприёмки этого релиза.

Accept и close выполняются общим сервисом завершения с явным source; ручные методы
сохраняются. На auto-path стандартные acceptedMessage/closedMessage не отправляют
инструкции ждать пользователя/новую задачу. В журнале видны отдельные доказанные стадии.
Dirty tree: агент может убрать собственные временные файлы и закоммитить нужные документы
штатно; чужие файлы и функциональные изменения вне задания дают блокер, не `git add -A`.

Перед публикацией перечитываются scope NONE, текущая ветка/upstream, HEAD, чистота дерева
и grant запуска. Смена любого адресата — `publication-target-changed`, без push в новый
remote. Начальный scope закрыт, но появился другой — `scope-changed`; старый запуск не
публикует новый незаконченный результат. Используется публичный сервис `git-publish`,
один на кнопку и автопилот, под мьютексом проекта. Fetch → проверки → push → fetch →
сравнение SHA; force/удаление веток не добавляются.

После timeout push или падения службы сначала fetch и проверка результата: нужный SHA
уже там → receipt без повторного push; SHA не опубликован и fast-forward допустим →
ограниченный повтор; remote ушёл иначе → blocker. `nothing-to-publish` — успех только
если подтверждено, что текущий ожидаемый финальный SHA уже на нужной удалённой ветке.
Одного локального ahead=0 для успеха недостаточно.

CI-политика — `automation.ci` из согласованного плана и grant. Сервис git-publish
предоставляет `stageCi(runId, sha, frozenPolicy)`: сам отправляет точный разрешённый SHA
на закреплённые remote/branch без force, сверяет удалённый SHA и записывает receipt.
Операция сериализуется с main publish/stop; после close выполняется службой без хода
агента. Никакой progress-аргумент не заменяет адресата или набор requiredChecks.

Финальная проверка CI идёт на закреплённой CI-ветке до main: готовится кандидат, затем
после accept/close новый финальный SHA также проверяется на CI-ветке если в grant exactSha=true (для Workflow_Kit обязательно). До main push не пишется новый коммит с доказательством этого же SHA:
результат фиксируется в журнале запуска вне git, чтобы не создавать бесконечную цепочку
SHA → evidence commit → новый SHA. Сборки/тесты по иному коммиту явно различаются.
Публикация final main разрешена только после обязательного CI выбранного кандидата.
При failed после close ремонт не изображается как редактирование DONE-scope: запуск
блокируется, исправление требует отдельного согласованного scope.
