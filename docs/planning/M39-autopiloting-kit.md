# M39: контракт Kit 2.3.x

Часть [спецификации M39](M39-autopiloting.md) и [контракта runtime](M39-autopiloting-runtime.md).

## 4. Контракт Kit 2.3.x

Изменяются исходники `workflow-plan`, `workflow-kit`, `workflow-recovery`,
`workflow-autopilot`, `workflow-installer`, а при необходимости публичные типы
`workflow-execution-mode` и `workflow-git`. Старые планы без новых полей валидны.
2.3.0 — первая версия серии; каждый коммит изменения исходников ядра повышает
KIT_VERSION по [правилу версий](M39-autopiloting-preparation.md#4-версии-ядра-и-повторная-поставка).
Полный capability появляется только после завершения T004, не по сравнению номера.

В схеме scope появляется необязательный `automation`:

- `acceptance`: записи для каждого индекса критерия scope: `{ criterion, kind:
  automatic | manual, checks: string[], evidence: string[] }`. `checks` — существующие
  id обязательных/выбранных проверок, `evidence` — канонические пути результатов с
  проверяемым форматом, указанным в спецификации. Одной строки «готово» недостаточно.
- `delivery`: `{ taskId, effects: string[] }[]` — конкретные сборка/установка и внешние
  действия, уже предусмотренные задачами. Публикация upstream остаётся после scope.
- `ci`: `null` если обязательного удалённого CI нет, иначе `{ remote, branch,
  requiredChecks: string[], exactSha: boolean }`. Для Workflow_Kit requiredChecks
  охватывает четыре job матрицы ОС и exactSha=true. Список проверяется относительно
  CI-конфигурации проекта, входит в digest ревью и snapshot разрешения. Он не берётся
  из текущего сообщения progress. Отсутствующий обязательный job не считается успехом.
- `publication`: настроенные branch/upstream, либо отсутствие публикации, несовместимое
  с конечной целью автоматического прохода до GitHub (видимый блокер до старта).

`schema scope:propose/create`, validation и recovery показывают эти поля. Неизвестные
checks, отсутствующие/повторные критерии, чужой taskId — ошибка до старта. Ручные критерии
не исчезают при миграции. До старта проверяется digest документов ревью. После старта он хранится как доказательство
согласования; плановые изменения module.md и task status не инвалидируют запуск.
Отдельный execution digest охватывает цель, критерии, files/эффекты задач и адресата
публикации, исключая DONE/status/служебные записи. Его изменения валидируются явно.
Snapshot разрешения добавляется службой только после выбора
scope отдельной командой, не самими полями предложенного агентом плана.

Новые команды:

- `scope:proposal --digest`: публичный read-only ответ до появления scope с generation,
  scopeId, proposalDigest и documentDigests. Нет предложения — `NO_PROPOSAL`. Канонизация
  исключает сам digest/времена; task/criteria/automation/CI и байты всех spec/context
  документов входят. `scope:choose --expected-digest <digest>` сверяет его под блокировкой
  перед выбором; несовпадение — `PROPOSAL_CHANGED`. После выбора digest доступен в status.

- `autopilot:authorize --input <json>`: `{ runId, scopeId, ownerSession, mode,
  source, note, proposalDigest, deliveryTaskIds, accept: boolean, close: boolean,
  ci, publication: { branch, upstream }, acceptancePolicy }`. Только активный scope и
  ожидаемый owner/digest. Для полного прохода все критерии automatic; для after-start
  с manual-acceptance допустим grant accept=false, close/publication=true после настоящего
  ручного accept. Старый план без automation нового grant не получает. Note — реальная команда пользователя и
  указание, какие действия заранее поручены. Запись делает штатный коммит Kit.
- `autopilot:revoke --run <id> --reason settings-off|user-stop --note "..."`:
  хранит reason и resumable (true только settings-off), повтор идемпотентен.
  Возобновление после off — новая authorize revision со source=panel-resume и прежними
  границами. После окончательного stop старый запуск не возобновляется.
- `autopilot:status` дополняется capability, scope authorization, digest и состоянием
  автоматических критериев. Нужные сведения читает служба только через публичный CLI.
- `task:start <id> --autopilot-run <id>` для delivery: подтверждение берётся из записи
  полномочий, taskId/эффекты сверяются. Произвольная строка runId ничего не разрешает.
- `accept --autopilot-run <id> --input <evidence.json>`: проверяет DONE всех задач,
  обязательные checks/evidence на соответствующем HEAD, отсутствие manual blockers;
  записывает source=autopilot, runId, исходное разрешение и доказательства.
- `close --scope <id> --autopilot-run <id>`: проверяет действующее разрешение и auto/manual
  acceptance, чистое дерево и отсутствие транзакций; сохраняет runId и финальный SHA
  в доступной истории закрытия. Сама запись close не объявляет публикацию завершённой.

Ручные варианты `--confirmed` и `--note` остаются совместимыми. Нельзя передавать оба
взаимоисключающих источника. Отказы: `AUTOPILOT_UNAUTHORIZED`, `AUTOPILOT_REVOKED`,
`AUTOPILOT_SCOPE_MISMATCH`, `AUTOPILOT_PLAN_CHANGED`, `AUTOPILOT_EVIDENCE_REQUIRED`,
`AUTOPILOT_MANUAL_REQUIRED`; каждый содержит понятные message и nextAction.

### Host-only операции

`authorize/revoke` и автоматические варианты accept/close выполняются только через
`KitRunner.runHost`. Это отдельный метод, не общий run с произвольной env-переменной.
Служба после проверки реального source выдаёт одноразовый короткоживущий host ticket,
связанный с корнем проекта, runId, scopeId, owner, operation, expectedRevision и digest
входа. Ticket передаётся только прямому дочернему процессу Kit по приватному каналу;
его нельзя брать из текста команды, recovery, файла входа или генерируемого сообщения.

Механизм — Node IPC родителя: `kit-runner` в `runHost` запускает CLI бандла через
`child_process.fork` с каналом `ipc` в stdio и отдельными pipe для stdout/stderr.
Проверяющая сторона — обработчик этого child в службе, созданный вместе с запуском;
реестра хостов, адреса, socket-файла или env-настройки verifier нет. До мутации ядро
через `process.send` запрашивает проверку ticket с requestId и payload digest.
Родитель сверяет source и привязку ticket к этому child/операции, атомарно погашает его
в журнале и возвращает ответ на том же канале. Ядро принимает только ответ текущему
requestId в пределах срока ticket. На macOS, Linux и Windows x64/ARM64 используется
один Node IPC-протокол; shell, пути сокета и программы ОС не требуются.

Обычный запуск агентом через scripts/workflow не имеет IPC-канала и получает
`HOST_AUTH_REQUIRED` до мутации. Истёкший, повторный, чужой или неподтверждённый ticket
даёт `HOST_AUTH_INVALID`; timeout, disconnect или завершение родителя — отказ без
записи. Внешний адрес/флаг/env не заменяет IPC и не включает fallback verifier.
Повтор результата уже выполненной операции возвращается по actionId/receipt без новой
мутации. Отметка погашения восстанавливается вместе с журналом запуска после рестарта.
Простой флаг `WFK_HOST=1` не является доказательством. Среда процессов агентов ticket
не наследует; секрет не печатается в stdout, диагностике или `/api/state`.

Agent-facing инструкции не предлагают authorize/revoke или auto-accept/close:
агент завершает текущую задачу, служба сама выполняет разрешённый переход. Обычный
`task:start --autopilot-run` лишь использует уже выданное разрешение для разрешённого
владельца/task; не создаёт новых прав. Тест запуска из обычного окружения агента
обязательно получает отказ при попытке выдачи grant/auto-accept/close.
Это защита workflow от самоподтверждения через публичную команду, не обещание изоляции
от злонамеренного процесса с полным доступом к аккаунту ОС.

Все новые JSON имеют schema, служебные input идут в `.harness/inputs/`, plan/grant
руками не меняются. Для resume после settings-off verifier требует новое явное событие
пользователя; user-stop окончателен для старого runId.

`plan:extend` для исправления исходного результата сохраняет связь runId, но новый
delivery-эффект или изменение критериев требует повторной валидации полномочий.
Автоматически допустимы только исправления прежних критериев без новых внешних эффектов;
новый taskId не получает разрешение на delivery простым совпадением заголовка.
Проверенное расширение обновляет список taskId отдельной штатной командой authorize с
тем же runId, ссылкой на прежнее поручение и текущим digest. Новые эффекты дают блокер.

### Возврат начатой поставки к исправлениям

`task:defer-delivery <ID> --reason "<сбой и ссылка на проверку>" --expected-revision N`
возвращает текущую delivery из IN_PROGRESS в TODO и очищает currentTaskId. Условия:
ACTIVE scope; задача именно текущая delivery; у её текущей попытки нет завершённого
коммита; нет транзакции/integration/активных assignments; нет незакоммиченных обычных
файлов (штатные изменения проекции Kit исключаются). Служба до вызова убеждается,
что связанные сборка/установка/push остановлены или завершены, не отменяет их задним числом.

Операция оставляет DONE-задачи и их SHA неизменными, сохраняет причину/номер попытки и
результат внешней операции в истории, снимает старое подтверждение delivery. Дальше
`plan:extend round=new` переносит TODO-delivery за новые fixes и DOCS. Повторный старт
требует действующего grant либо ранее данного пользовательского поручения на ту же
поставку, записанного честно; расширенные эффекты требуют нового разрешения.

Неверный вид/статус, dirty tree, чужая ревизия или незавершённая транзакция дают
`DELIVERY_DEFER_NOT_ALLOWED`, `DIRTY_TREE`, `STALE_REVISION` или штатный отказ без записи.
При неполном коммите сначала штатный repair, при собственных незакоммиченных evidence
сначала сохранение вне git/уборка собственных временных файлов; чужие файлы не трогаются.
Команда не является универсальным reset задачи и не переводит DONE в TODO.
Тест: started delivery → failed CI → defer → new fixes round → исправление → DOCS →
повторная delivery → зелёный CI; то же для ручного и M39-пути, со свежими SHA.

### Инструкции и recovery

Recovery всегда сообщает: mode, runId, stage, полномочия, review, следующий шаг,
причину блокировки. Исполнитель получает только свою задачу, без прав приёмки/публикации.
При `off` тексты сохраняют ручные барьеры. В full/after-start «заверши ход» значит
передать управление Kit, а не спросить пользователя. Close не говорит «ждём новой
задачи», пока остаётся publication. Правило push во всех шаблонах едино: после закрытия
по прямой просьбе либо действующему предварительному поручению конкретного запуска.
