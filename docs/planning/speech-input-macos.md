## 1. Принципы

Пользователь нажимает микрофон, видит текст во время речи, повторным нажатием
завершает диктовку, редактирует черновик и отдельно отправляет сообщение.
Основной движок — Voxtral Mini 4B Realtime через совместимый с Handy transcribe-cpp.
Начальная экспериментальная конфигурация — Apple Silicon, Metal, Q8_0.
Задержка, память, доступность Intel и второй модели подтверждаются измерениями.

Результат распознавания — снимок committed/tentative, обновляющий свой диапазон
черновика. Ручная правка синхронно отвязывает поток; поздние события игнорируются.
Смена диалога и удаление поля отменяют поток. Все пути отправки блокируются во
время preparing/listening/finalizing. Остановка ответа агента независима от микрофона.
Диктовка не вызывает отправку, прерывание провайдера или действие над его очередью.

Модули общаются через публичные входы; каждый новый и изменённый модуль обновляет
свой module.md в том же коммите. Записи и веса не попадают в git.

## 2. Архитектура и контракты

Новые части размещаются в `product-parts/speech-input/` с документом product-part.md:

- `clusters/local-recognition/modules/speech-helper`: отдельный Rust executable,
  pinned transcribe-cpp, Metal/CPU, handshake, load/begin/feed/finalize/reset/shutdown;
- `clusters/local-recognition/modules/speech-service`: Node-каталог, хранилище моделей,
  супервизор helper, один активный поток, приватные события владельцу соединения;
- `clusters/browser-input/modules/speech-input`: захват, resampling, адаптер поля,
  состояния, владение и блокировка отправки без знания провайдера.

Новые part/cluster/module документы берутся из `.workflow-kit/templates/`.
CLI подключает публичные фасады. Новые библиотеки и сборочные команды обосновываются
проверкой; инструменты не устанавливаются без отдельного разрешения пользователя.

### 2.1. Нативный процесс

Первой проверкой фиксируются Cargo.lock, bindings и native library, совместимые
между собой; наличие промежуточных результатов доказывается русским аудио,
подаваемым в реальном времени. Проверяются backend, очередь, первый текст и finalize.
Нет рабочего потока — дальнейшая UI-интеграция не считается подтверждением движка.

Протокол версионированный, stdout только для framed JSON/PCM, stderr для диагностики.
Frame читается инкрементально; запросы сериализуются. Node запускает executable
через spawn с массивом аргументов без shell. EOF и shutdown завершают worker.

### 2.2. Каталог и модели

Встроенный каталог фиксирует repository/revision/filename/sizeBytes/sha256,
языки, streaming, quantization и лицензию. Начальный набор — проверенные варианты
Voxtral. Выбор сохраняется через data-store. Скачивание: временный файл, прогресс,
отмена, размер/checksum и атомарное переименование. Удаляются только управляемые
файлы Kit. Данные Handy автоматически не сканируются и не удаляются.

### 2.3. Поток аудио

getUserMedia и AudioWorklet захватывают звук в локальной панели. Непрерывный
resampling реальной sampleRate даёт mono float32 LE 16 kHz. Модель готовится до
показа «Слушаю». Поздно выданное разрешение после отмены освобождает tracks.

Same-origin WebSocket использует существующий HTTP-сервер Kit через публичный
upgrade-интерфейс. Проверяются путь, Host/порт, Origin, loopback адреса, версия,
размеры и частота frames. Отсутствующий/null Origin отклоняется. JSON API не ослабляется.
Нужная WebSocket-библиотека выбирается при реализации; собственный RFC 6455 не пишется.

Очереди на каждом переходе ограничены. Перегрузка останавливает поток с сохранением
видимого текста. Скрытого batch fallback, записи аудио на диск и общего broadcast текста нет.

### 2.4. Поля и интерфейс

Composer сохраняет project/session/field/dictation/generation и исходное выделение.
Снимок меняет только диапазон диктовки через общий путь draftRevision/fit/refresh.
Проверяются ручная правка, IME, лимит 20 000 символов, старый send-ответ и late final.
Кнопка вложений остаётся независимой. Перед отправкой проверяется состояние speech
внутри send(), очереди, Enter и Ctrl/Cmd+Enter, а не только disabled на кнопке.

Settings показывает модель, размер, доступность потока, состояние загрузки и действия
скачать/отменить/выбрать/удалить. Свободный ответ question-card подключается через
существующий writeOther; ответ не превращается в сообщение чата.

### 2.5. Изоляция от работающего приложения

Экспериментальная служба использует собственный WFK_DATA_DIR и свободный WFK_PORT.
Нет общей установки, перезапуска действующей службы, редактирования общих git config
и запуска автопилота основного проекта. Node-зависимости у дерева собственные.
По прямой команде 17.11.2026 этот scope реализует только код и проверки.
Релизная сборка, упаковка, установка, публикация и merge не выполняются.
Тестовая компиляция helper разрешена для проверки кода. Задачи выполняются подряд
автономно по прямому поручению пользователя; host-разрешение M40 не переносится.

При будущем объединении сначала сверяется актуальный main и согласуются затронутые
общие файлы. Новый план не заменяет план основного проекта при merge. Перенос результата
и судьба истории планов оформляются отдельно после завершения чужой работы.

## 3. Поведение на ОС

| Что | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Распознавание первой версии | Локальная панель, Apple Silicon после измерений; Intel только после отдельной проверки | unavailable; импорт и запуск Kit работают | unavailable; запуск Kit работает на x64 и ARM64 |
| Браузерный ввод | Разрешение браузера, AudioWorklet, loopback | Микрофон нового модуля недоступен | То же |
| Каталог и протокол | Общая Node-логика, helper только поддерживаемой архитектуры | Общая логика тестируется; helper не запускается | То же; пути через path и внедрённую platform |
| Проверки | Unit/integration и живая речь пользователя | CI без inference | CI x64/ARM64 без inference |

На iOS/Android новый захват не включается; системная диктовка остаётся доступной.
Платформа внедряется параметром, ветки win32/linux тестируются. Новые OS-команды
заносится в platform-guard allowlist с объяснением поведения других ОС.
В коммитах кода обновляются module.md и OS-MATRIX.md; матрица при необходимости
разделяется отдельным docs:commit до задачи, без сокращения существующих разделов.

## 4. Проверка

Детерминированные тесты покрывают framing/EOF, порядок feed/finalize/cancel,
владение полем, snapshots, ручные правки, все пути отправки, проверки upgrade,
checksum/partial/remove, падение helper и ограничение очереди.

Перед первым функциональным изменением сверяется существующий профиль качества,
добавляются необходимые Rust/helper проверки штатными quality-командами.
Проверки проекта: typecheck, test:app, test:kit и check:platforms согласно профилю.
Наличие mock helper не доказывает реальное распознавание.

Доказательства в `docs/evidence/speech-input-acceptance.md`: SHA, upstream pins,
модель/revision/hash, macOS/архитектура/browser/backend, команды и результаты,
холодный/тёплый start, задержка текста, finalize, память и длина очереди.
Живые проверки: macOS — пользователь (русский, смешанная лексика, 10–20 с,
1 мин и 5 мин, Safari и используемый браузер); Windows — проверяющий на Windows
подтверждает отсутствие регрессий; Linux — CI. Непройденные проверки отмечаются явно.
CI четырёх платформ и интеграционная проверка на актуальном main нужны до итогового
слияния; они не выдаются за выполненные локальными тестами или наличием пакета.

## 5. Границы

Не входят: чужой M40/M41, глобальные hotkeys/paste, Tauri/React целиком,
TTS, перевод, cloud STT, API-ключи, удалённый микрофон, бесконечная запись,
автоматическая отправка, установка поверх действующего приложения и push main.
Лицензии и происхождение донорского кода сохраняются; актуальность pins проверяется
в первой задаче по первичным источникам, без обещаний качества до эксперимента.
